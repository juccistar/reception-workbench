# 0.4.2 开发方案：按新版界面收敛功能与优化后端

日期：2026-11-16。面向开发实施、产品评审与验收人员。

**状态：0.4.2 实施与定向验证中，尚未完成打包及公开发布。** 实施基线为 `f8339ad`，保留此前 0.4.1 按需人工建议、侧栏及后续已确认修复。源码、窗口、候选和公开状态分别记录在[本版验证记录](verification/0.4.2.json)，不以原型截图或局部用例通过推定版本已交付。历史 0.4.1 状态继续以其版本记录为准。

## 1. 交付原则与依据

0.4.2 的目标是把已确认的新前端落实为真实工作台，同时收敛旧功能和重复后台工作。**功能范围由前端界面及用户最终修订确定；消息类型、消息内容、发送能力与回执，以现有真实平台接口为准；不新增附件接口，不因后台已有代码而增加产品功能。**

按以下顺序判断实施范围：

1. 用户最后明确的修订，包括完整消息时间、直接接管/恢复、无 AI 预检、取消发送核查入口等。
2. [本轮设计要求](design/reception-redesign/LATEST_REQUIREMENTS.md)与[状态及弹窗方案](design/reception-redesign/FEEDBACK.md)。
3. [全套设计入口](design/reception-redesign/README.md)、[接待页](design/reception-redesign/index.html)、[其他页面](design/reception-redesign/pages.html)、[场景目录](design/reception-redesign/feedback.html)。
4. 真实接口能力及当前生产实现，用来限定数据来源、参数、平台操作和可用状态。

设计稿中的合成客户、SVG 商品图、PDF 文件气泡、模型名称、价格、时间和回执均不是接口证据。不能为了还原样例而补造字段、消息、平台返回、公司资料、头像或发送成功。

本方案明确改变旧文档中与本版目标冲突的日常行为；旧版说明和验证记录保留当时事实。实施完成后同步更新现行规则、实施契约和用户说明，不能把本稿提前写成“已实现”。

## 3. 接待页必须保留的显示与数据语义

### 3.1 原来的时间格式

消息标题沿用当前正式程序 [ui.tsx](../apps/desktop/src/renderer/components/ui.tsx) 中的 `messageDateTime()`，格式为 **`YYYY-MM-DD HH:mm:ss`**，例如 `2026-11-16 13:28:15`。保留秒数，继续使用现有时间格式化及本地时区规则，不采用原型中的 `10:48`、“刚刚”或仅“今天”替代完整消息时间。

**客户列表按设计稿实施**，包括布局、筛选、消息预览、状态和紧凑时间呈现；列表时间按真实最近消息计算。保留原完整时间格式的要求只针对聊天消息标题，不要求客户列表照搬旧界面。消息时间取真实平台消息时间，后台补全、受理确认或界面重绘的时间不得覆盖它。没有可靠时间时沿用 `messageDateTime()` 的“时间未知”处理，不编造平台时间。

### 3.2 消息与编辑器

- 买家/商家角色、正文、消息 ID、真实时间、实际返回的媒体元信息继续来自对应平台适配器。
- 客户数、筛选数量、未读和最近消息来自真实数据；不沿用设计稿固定人数、红点或样例业务状态。
- 人工只有一份正文，普通人工发送不依赖 AI 检查、已有采购事项、采购条件齐全或最后一条来自买家。
- 查看及生成建议不接管；手写、采用建议和人工发送接管当前客户。接管只影响当前会话。
- 一次发送冻结确切正文与版本；在途回执只完成原发送，不清除之后输入的新正文。
- 自动回复沿用已有自然 1—3 条逐条发送，不为匹配界面改成固定条数或多条人工编辑器。
- 当前生成/发送状态与人工输入分开；完成状态短暂显示，取消独立发送历史入口。
- 需求仍为中文 ai-v1，摘要独立按会话保存；浏览旧事项不改变后台当前事项，不自动重开已停止事项。

### 3.3 建议、润色与中文译文

建议和润色结果均在同一待处理区域显示外语正文及中文译文，保留“替换正文 / 重新生成 / 弃用”。**结果译文独立于聊天消息的中文显示开关**，关闭聊天译文不应把建议和润色译文一起隐藏。译文仅供阅读，采用和发送只使用外语正文；不把中文译文拼进客户回复。

复用现有翻译队列、路由、缓存与结果状态，不新建“建议翻译管理”功能。结果先到时可先显示外语；译文失败只显示“译文暂不可用”，不阻止采用或普通人工发送。翻译结果按商家/账号、会话、建议或润色结果身份及正文版本匹配，旧结果不得覆盖新正文或串到另一客户。

润色只处理冻结正文和适用的现有补充，不因补译文而写需求、摘要或采购结果。任意新输入不得用设计样例中的固定中文代替真实翻译。

### 3.4 直接操作与简短状态

人工接管、恢复自动接待直接执行，不弹确认。手工发送不再增加“接管并发送”的确认。恢复当前客户只解除该客户的人工接待状态，仍受全局开关、已保存范围、平台状态及未决发送保护约束，不暗中开启全局接待或扩大范围。

发送结果未知只显示“发送结果待确认”；请求尚未确认只显示对应状态。移除手动核查按钮、核查详情弹窗、逐条人工确认及以确认代替平台回执的操作。后台继续处理原操作，不把 unknown 变为失败、已受理或可重发。

译文、图片及历史补全等状态只写必要短句。删除“原文不受影响”“需求内容不受影响”“不会触发回复”等第二行解释。退出未保存内容、数据恢复等真正涉及内容丢失或数据变更的确认仍按对应设计及宿主边界处理。

## 4. 自动接待及 AI 调用调整

### 4.1 两种范围与一次开启动作

设置仅有 `all` / `selected` 两种新选择。选择 selected 立即展开可搜索的客户多选列表；设置持久化到当前真实业务归属下，而不是照搬原型 sessionStorage。

现有引擎的 all 会冻结开启时已同步的客户，incoming 另有授权起点含义，不能只删下拉选项或改标签。本版把“客户范围”和“消息触发起点”分开：all 表示当前归属下全部已同步及随后新增的有效单聊，selected 只覆盖明确选择的稳定 ID；两者都排除人工接待客户。历史回填不成为新实时入站，授权起点及旧消息保护继续内部保存。该调整覆盖提供此范围设置的工作台及相关测试。独立 WhatsApp 按设计中已有的账号自动开关、允许商家、当前绑定和人工接管状态运行；不为统一后台而额外给它增加另一套选客户功能，也不把国际站的 selected ID 直接套到 WhatsApp 单聊。

范围至少绑定当前商家、渠道及账号；被选对象保存稳定会话/聊天 ID，名称只用于显示。跨商家、跨 WhatsApp 账号或同名客户不能互相继承选择。前端换页与重启后读回设置；自动发送授权仍不随程序重启恢复。

顶部只有状态和“开启自动接待 / 关闭自动接待”。点击开启是本次有效范围的明确授权动作；后台一次完成必要的本地身份、范围和运行状态核验，不再要求另点 AI 检查、生成授权、发送授权或重复确认。

未配置范围的新用户按既有默认初始化；已有 all/selected 原样保留。旧 incoming 等不再提供的新范围不能静默扩大成 all：保留原记录解释历史操作，升级后授权关闭，转为 selected 空集合并让用户在设置中明确选择。selected 为空不能启动，不增加第三种范围。

保存范围或影响接待依据的设置后，按现有语义撤销相关接待资格；用户可直接重新开启，不需要通过 AI 检查。普通翻译显示偏好不应撤销无关接待授权。

### 4.2 取消 AI 预检前置

启动程序、开启自动接待、生成建议及润色均不先发 AI 检查请求，也不把历史模型能力检查的“通过”记录当作前置。平台连接页的“检查模型”保留为用户主动诊断，与接待启停及建议可用性独立。

这需要修改后台真实门控，不只是隐藏检查按钮：现有人工建议/润色的直接尝试基础继续复用，自动生成也改为在本次有效授权下直接使用当前配置。不得伪造 `ai_checked=true` 或把未检查能力写为检查通过。

模型配置、凭据修订、当前身份、商家/账号/客户归属、来源版本、图片范围、当前授权及实际输出结构仍在对应执行阶段校验。保留受限宿主桥，不向 renderer 暴露可绕过授权的通用参数。

### 4.3 失败时才提醒

实际生成失败后显示一次“AI 不可用”及短因，可关闭或查看模型设置。按任务及客户归属去重；关闭后可再次主动生成。保留输入和补充，普通人工发送独立可用。

取消、排队、业务忙碌、来源已变化、模型配置已切换、客户已切换、旧服务代次的迟到失败，不当作 AI 不可用。失败不能触发跨端点自动回退、无限重试、恢复历史授权或扩大客户范围。

## 5. 真实消息接口与附件边界

### 5.1 两层约束

界面决定本版要提供哪些动作，平台接口决定这些动作能真实取得或提交什么。Electron/Python 现有 RPC 是应用内部契约，不能把它的字段想当然地当成平台支持的字段。实施要同时核对应用调用、原生适配器/锁定 SDK、真实返回结构和已有回执证据。

| 内容 | 本版处理 |
| --- | --- |
| 普通文字发送 | 沿用真实平台已经实现的文字提交及确切回执路径，不增加新通道 |
| 聊天正文、角色、时间 | 原值及真实来源优先，不从商品卡样例或 UI 文案反推事实 |
| 收到的图片 | 仅按现有实际消息/媒体接口支持的引用受控读取、缓存、展示 |
| 收到的文件/PDF/其他类型 | 实际接口明确返回的元信息才展示；没有真实内容读取能力时不提供虚构预览或下载按钮 |
| 未识别或不支持消息 | 保留现有原始记录及可读字段，显示简短不支持状态，不伪装成文字、图片或文件 |
| 业务补充附件 | 只复用已经存在并经过宿主约束的本地选择、粘贴、上传、移除和预览能力；不新增接口、类型或额度 |
| 模型同轮受控原图 | 复用已有原图准备和请求编码，不等同于向客户发送附件 |
| 平台不提供头像、公司等信息 | 不采集、不猜测、不填假资料；头像占位全部移除 |

### 5.2 本版明确不新增

不新增聊天附件上传/发送接口、附件中转服务、公开下载接口、任意文件/URL 读取接口、跨平台转发、语音/视频处理、PDF OCR 或文件内容采集器。也不为把示意文件气泡做成可点而增加后台能力。

设计中的“添加附件”只对应已有会话业务补充。若某一实际环境不能使用该既有能力，就收敛相应控件与状态；不能绕到平台消息接口新增附件功能。现有附件和原图数据随原业务库保全，不因禁止新增接口而删掉。

### 5.3 补全历史与定位来源

补全按钮只作用于当前客户，复用现有历史读取；记录真实覆盖范围、去重及消息版本，不制造新消息。历史补全不得作为“新实时入站”触发自动回复、重复生成需求、创建新采购事项或补发旧内容。

来源链接直接定位现有 evidence_id 对应的确切消息。消息未在当前页时使用已有本地分页/历史读取路径加载目标附近数据，再滚动高亮；窄窗口同时关闭资料抽屉。不增加来源查询弹窗或新的附件接口，不以同文、相似商品或显示名匹配来源。

## 6. 多余功能删除清单

删除范围同时覆盖组件、导航、事件、桥、DTO 投影、后台触发器、样式和相应旧测试。下表的“保全”部分不是保留日常入口，而是保留真实数据、内部恢复或其他界面确实需要的基础能力。

| 编号 | 删除/退役项 | 实施范围 | 必须保全或替代 |
| --- | --- | --- | --- |
| D01 | 接待页与其他页面重复导航、聚焦时切换另一套导航 | 合并路由/导航配置、删除重复组件和专属位置样式 | 全部页面共用一个导航源，保留当前页与布局偏好 |
| D02 | 客户照片、人物图、字母头像、伪头像字段展示 | 列表、聊天头、客户资料、关联选择、Chrome 侧栏 | 名称、真实标识与状态；商家品牌标识不冒充客户头像 |
| D03 | 发送记录弹窗、历史批次列表和所有入口 | 接待、侧栏、账号卡片、运行记录中的替代入口；只移除纯历史展示投影 | 当前进度及围栏仍需最小批次状态；不能直接删 `reply_batches` / `Snapshot.outbox` 令 `conversationFence` 等失效 |
| D04 | 手动核查发送按钮、核查明细弹窗、请求核查向导 | renderer/preload/main 常规公开调用及日常 DTO | 自动沿原 operation 处理；无人工放行、无重发 |
| D05 | 人工接管/恢复确认及“接管并发送”确认 | 页面、hook 和宿主中仅服务这些日常动作的确认分支 | 直接执行对应会话操作及既有版本/归属复核 |
| D06 | 启动 AI 检查前置、检查后才能建议/润色/自动接待 | UI 禁用逻辑、后台能力检查前置、重复授权步骤 | 当前配置执行校验、真实发送授权和失败提醒 |

## 7. 数据保全与升级边界

界面退役不等于数据库清理。消息、需求、摘要、客户草稿、业务补充及现有附件、资料版本、供货方案、任务、operation/outbox、原生账本、确切回执、有效 WAL、unknown 和幂等关联全部保留。

本版优先通过停止生成、停止投影、移除调用和入口收敛功能，不执行大范围实体清洗、数据库重建、目录搬迁或清空登录环境。必要索引/设置升级必须可重入，保留旧数据与版本；不降低 SQLite WAL/FULL 持久化保证。

范围设置与开启授权分开：设置可以持久保存，重启后自动接待仍关闭。旧 sending/unknown 继续挡住相关会话的新发送；恢复旧备份不得让已经发生过的发送重新变成未发送。保留商家、账号、连接代次和数据根的真实隔离。

前端布局偏好采用既有布局存储；不能把设计稿使用的临时浏览器存储直接当作正式业务权威数据。完整备份与空目标恢复沿用现有宿主维护流程，真实业务迁移不由本次方案编写自动执行。

## 8. 后端功能调整与优化方案

### 8.1 已有基础继续使用

当前已实现以下基础，不列成 0.4.2 的新增成果：

- JSON Lines 自有子进程、受限 IPC、当前商家/账号隔离及 SQLite WAL/FULL。
- FAST 立即分派，SLOW 通常返回 job_id 并入一个有界业务队列；这不是两套独立快慢 worker。模型执行已从业务协调中分离，消息监测独立，发送和回执具备优先级及公平调度。
- 跨进程共享接待 1 槽、翻译 1 槽、HTTP 合计 2 槽、带图 1 槽；取消后实际结束才归还资源。
- SQLite 内按归属过滤、已有会话/事项索引、有限消息分页、活动优先监测、翻译缓存与批量处理、HTTP 连接复用、前端刷新合并。

优化先减少重复工作，不提高并发上限，不按账号数倍增模型额度，也不重写为 HTTP 服务、微服务或另一套数据库。

### 8.2 历史补全与实时入站分离：优先级最高

**现状：** `service.py._task_fill_history()` 仍调用普通 `_ingest()`，头部读取存在 `history=False`；单独传 history 标志也不足以隔离后续业务影响。入库可能推进 `last_buyer_at`、修改事项版本/状态、失效生成，并在完成后进入普通正文同步，进而影响接待调度。

**改造：** 明确区分实时监测、历史补全、本地分页及原回执确认的入库意图。历史补全只更新消息、覆盖范围、真实来源和必要版本；不产生新的回复资格、续答触发、新需求分析或采购任务。其完成后排队的同步仍携带同一意图，不能在后续普通同步中重新当作新入站。

原消息确实被更正时，相关证据和旧建议仍须失效；不能为“不触发回复”而保留错误依据。未读、水位、角色与消息时间保持真实，历史导入不伪造买家新活动。不新增用于解释这些细节的产品页面或确认步骤。

**完成条件：** 全局接待已开启时补入旧买家消息，允许聊天增加旧记录，但生成/发送计数不增加、不新建事项；真实后续新入站仍能正常接待。来源修订会撤销旧结果，不自动开启另一轮。

### 8.3 自动接待门控与权威投影一起调整

**现状：** 人工 `generate_manual_suggestion` 的建议/润色已通过 `_freeze_reception_model(allow_unchecked=True)` 尝试当前配置；自动路径仍在 `set_reception`、自动执行、补充调度、`ReceptionProjection.status` 及独立 WhatsApp 开启/生成中依赖已通过 AI 检查。

**改造：** 删除这些路径的远端检查前置和“检查通过”资格，执行时才解析并冻结当前模型配置。发送复核使用本轮真实配置/来源快照，不再绕回检查能力记录。私有直接尝试参数仅在明确的任务用途和当前授权下设置，不成为 renderer 可任意传入的绕过开关。

设置范围落库并读回；运行授权保留进程内语义。调整前端 `aiReceptionReady`、自动授权确认链和后台投影，避免按钮已可点但真实服务仍拒绝，或后台已开启而前端继续显示需检查。

已有 `check_ai` 排队会暂停接待的行为必须拆开：用户独立检查不改变接待授权；只有真实配置、来源、身份或显式启停变化改变相应资格。不得靠填充假的 passed 状态兼容旧门槛。

### 8.4 回执自动处理与发送状态收敛

国际站已有 `_schedule_continuity()` 按原 operation 退避处理 unknown，且不依赖接待开关；继续复用。核实并补齐 reconciliation job 的 operation_id 等去重归属，保证一个原操作不会反复排出并行核查任务。

WhatsApp 已在连接时核对 pending，并处理 ACK 事件；当前没有等价的持续回执轮询。移除人工核查入口前，补齐必要的**内部有界到期处理**：只处理已有未决操作、沿原账号/连接归属及确切 ID 查询，单操作单在途，退避可取消，断连时等待原账号恢复。没有确切 ID 时继续待确认，不按同文搜索猜测受理，更不重发。

编辑器继续依据确切操作结果结算。先从 `Snapshot.outbox` / `reply_batches` 的现有消费者中分离出当前发送、围栏、登记和纯历史展示；只有调用迁移完成后才删除后者的响应载荷。任务成功、RPC 返回和平台受理分开，不能用 job 完成清空新输入。

重试按钮只在权威证据明确 `submission_started=False` 等确切未提交条件下出现。RPC 超时、后台断开或未知异常均不能直接进入可重试状态；保留冻结正文、client_request_id、版本和原 operation 的对应。

### 8.5 快照与详情减少重复全量计算

**现状：** `get_snapshot` / `ReceptionProjection` 在客户投影时重复读取消息、计算待回复与自动来源，并可能逐客户读取模型权威配置。`get_conversation` 又构造全局投影、重建建议上下文，并读取补充附件。

**改造：**

1. 一次快照中的身份、配置修订、全局接待/范围等公共信息只计算一次；执行和发送边界仍重新核对权威来源。
2. 客户行用最近消息、未读、人工接管、待回复及当前任务的有界摘要；不为每行解码整段历史。
3. 当前详情只计算当前客户所需资料。普通列表刷新不重新组装全部模型上下文；建议新鲜度先比对权威修订，相关修订改变时才做必要重建。
4. 产品、供应商、报价事项和运行记录按页面需求读取。列表不给原图/base64、完整任务请求、冻结 prompt 或纯历史发送明细。
5. 不新建通用事件流/全量增量同步平台；优先改造现有方法内部查询与已有事件归属。

**完成条件：** 一个客户的无关更新不重算其他客户详情；接待人数增大时，单客户详情的解码消息量不随全部客户聊天量增长。快照仍是本地查询，不触发网络、模型或所有商家服务启动。

### 8.6 SQLite 查询、索引与 WhatsApp 账号读取

国际站消息已有分页与归属索引，补充与实际游标顺序一致的组合索引候选，覆盖商家/会话、原消息时间及稳定 ID。以 `EXPLAIN QUERY PLAN`、实际解码行数和前后结果一致性决定是否采用，不把“新增索引”本身当成优化完成。

独立 WhatsApp 的 `AccountRepository` 当前部分调用按 kind 取全部记录后解码；增加内部按账号、chat 和 segment 过滤的受限读取，减少跨聊天扫描。它只是当前侧栏、聊天、摘要与任务读取的实现优化，不开放任意查询接口。

新增索引先在合成副本核对建立时间、锁占用和写入成本，保持原始记录、来源、事务和完整备份语义，不通过重建业务库获得性能数据。实施时发现0.4.1严格schema不接受新增索引，因此本版只在新建库建立；现有库打开时不加索引，尚未实现旧库离线索引升级。索引测量只适用于新库，旧库schema兼容证据和限制见[性能记录](verification/0.4.2-performance.json)。

### 8.7 事件刷新、长列表与编辑器保存

已有刷新合并继续使用，进一步利用事件中的会话/任务归属：无关客户的任务不触发当前客户全量详情重读；身份、范围、配置等全局变化仍及时刷新。读取确认完成后避免显式刷新和事件刷新重复执行同一轮查询。

前端按页/稳定标识组织长列表，待报价列表与详情独立滚动；选择事项与“打开聊天”分开，避免复用 `selectConversation()` 导致选择即跳页。按会话保存补充和人工草稿，保存合并只作用于未提交编辑；发送前仍持久冻结确切版本。

客户搜索只覆盖界面需要的已保存信息。产品“关联客户”等列只从现有真实绑定计算，缺少可证关系时显示缺值；不新增跨商家客户资料采集来填满设计列。

### 8.8 原图与既有补充附件的读取优化

`attachment_rows` 等现有路径会在使用时重复解码、校验原件。把摘要/预览投影与原件验证分开：投影可按可靠 revision、附件 ID、SHA 和归属缓存，原图按需走原有宿主读取；读取和真正模型使用时仍核对真实字节与来源。

列表只取缩略图或安全引用，不把五张全尺寸图同时塞进快照。保留透明 PNG、原图复制、媒体预算、Blob URL 释放及局部失败状态。此项不新增附件类型、上传/下载接口、任意路径或来源 URL 能力。

### 8.9 建议翻译、取消与迟到结果

现有建议和润色都保存为 `manual_suggestion`，模式由 mode 区分；`get_translations` / `request_translations` 已支持该来源。复用它完成双语展示，拆开聊天译文开关和建议译文的请求/展示条件，不新增另一套翻译协议。

设计有“取消生成”，但当前公开 API 没有对应取消方法。补齐**仅面向当前客户人工建议/润色的定向取消入口**，规划名可用 `cancel_manual_suggestion`，绑定当前归属、conversation_id 和 job_id；这是界面已有动作的必要契约，不扩展任意任务控制台。只允许取消当前归属的人工生成，已结束任务幂等返回，不接受此入口取消发送或其他账号任务。再生成时取消被替代的旧任务，先撤发布/采用资格，等待真实清理后才释放模型槽。

现有 `manual_latest` 和请求序号继续防止旧建议覆盖新结果；取消、切换客户和旧代次结果不得弹错客户。自动 AI 失败补齐与人工任务同等的归属及去重投影，不把一个全局 boolean 当作多个客户的故障队列。

`ModelRequestBudget._remove` 当前存在同步竞争重试；若迁至异步/工作线程清理，必须一直持有原租约直至删除完成。不能为避免阻塞而提前归还额度。

### 8.10 性能验证边界

| 当前客户操作 | `takeover`、`begin_manual_edit`；WhatsApp `takeover_whatsapp` 及受限侧栏动作 | 明确目标，点击即执行，保留来源/版本与未决保护 |

| 产品与供货 | `list_products/get_product`、`get_product_main_image`、`list_suppliers/get_supplier/save_supplier`、现有供货选择/默认方法 | 只服务设计中的清单与详情，不新增销售定价或交易能力 |
| 找货及登记 | 原有采购任务方法、`reconcile_procurement`、有独立用途的 outbox/登记方法 | 找货核对与发送核查入口分开；飞书按现有独立授权，不扩为新工作流 |

结构化原生 content 或 quote 可能以原 JSON/既有附件记录保留；当前前端的非图片附件只是已有名称/记录展示，并没有规范化任意文件的读取与下载契约。设计里的 `Brand logo.pdf` 不能成为新增此契约的理由。

Chrome 客户侧栏当前受限动作是 search/save/takeover，View 尚未提供当前发送进度和 pending 投影。如展示设计所需的当前异常，只补充已有 job/operation 的最小状态，并继续核对 workspace、账号、连接代次、chat 和 view_revision；不新增自由发送、发送历史或任意 RPC 通道。

设计侧栏中的“业务补充”是需要落地的文本编辑功能，不能把原型内存值当作已保存。优先复用适用的既有本地补充存储；当前受限桥尚未覆盖的，仅补面向当前已核验单聊的文本保存与版本校验动作。正文按 workspace/账号/chat/当前商家分段隔离，切换客户保留各自编辑、更换商家不带入旧商家内部补充；不反写国际站、不开放通用实体写入，也不为侧栏新增附件接口。

## 12. 定向验证与验收标准

只按本版修改范围运行相关后端、桌面/宿主和工具文件；本方案不要求 `npm test` 或依次跑完整分组。类型检查、正式构建、受影响窗口和候选核验按阶段执行。测试用临时目录、合成数据和替身，生产包不带演示服务。

| 验收项 | 必须验证的结果 |
| --- | --- |
| 导航及页面 | 全部设计页面可达，聚焦/收起资料不改变导航图标、位置或顺序；无原型工具条 |
| 客户列表 | 按设计稿展示、搜索筛选、滚动及切换，不显示头像；列表时间采用紧凑呈现 |
| 消息时间 | 买卖双方消息均保留 `2026-11-16 13:28:15` 这类完整到秒的格式；缺值仍为真实缺值状态 |
| 建议/润色 | 两者都有正确匹配的中文译文；聊天译文关闭时结果译文仍可见；替换及发送只有外语正文 |
| 失败与取消 | 无启动 AI 预检；实际失败只弹当前归属的一次短提醒；取消和迟到结果不误报，不抢新结果 |
| 直接接管/恢复 | 点击即生效，无确认弹窗；不改变其他客户、不清未知发送、不自动扩大范围 |
| all/selected | 设置持久读回，跨商家/账号隔离；all 覆盖本归属有效客户，selected 只处理选中客户；两者排除人工 |
| 原范围升级 | 旧 incoming 不静默转 all；升级后权限关闭，原记录和未知操作保留 |
| 补全历史 | 接待开启时补入旧消息也不新增 AI/发送/事项/采购；真实更正仍使旧依据失效 |
| 来源定位 | evidence_id 对应的消息可直接定位和高亮；不弹来源窗口，窄侧栏关闭；不改当前事项 |
| 人工发送 | 无事项/无 AI 检查也可发送；在途后新增正文不被旧回执清空；RPC 超时不误判可重试 |
| 未决发送 | UI 只有状态；新发送被围栏阻止；无手动核查/重发；自动处理仅沿原操作 |
| 多条自动 | 原 1—3 条自然回复逐条受理，人工输入独立，停止/新买家消息使未提交尾部停止 |

| 真实消息类型 | 两渠道分别按已接入字段显示；没有 filename/MIME/内容时不造可下载文件气泡 |
