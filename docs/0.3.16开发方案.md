## 2. 已核实的问题与现有基础

### 2.1 需求反复变化的原因

当前自动接待和人工建议提示词要求每轮返回 requirements。后台 `_save_ai_conversation_state` 用本轮返回字段覆盖已有字段，未先比较新旧内容；通过校验的 null 和空图片数组也能覆盖旧值。普通人工建议生成完成后立即保存需求，无须先采用建议。

因此，没有新增采购信息的一轮回复，也可能重新表述需求，或将遗漏的信息输出为空。表单只展示有内容的字段，清空字段还会使对应行消失。当前完全省略 requirements 本身不会清空需求；需要修正的是固定输出要求、变更表达和应用流程，不能误写成“缺字段自动清空”。

另有独立来源：消息同步以整条记录比较判定消息变化，并使依赖该消息的需求字段失效。需要区分正文／有效图片来源变化和无关元数据变化。

### 2.2 多事项管理的基础与缺口

现有数据结构允许一个 conversation 下保存多个 case，每个 case 有独立需求、状态、来源和修订。会话以 conversation.case_id 保存默认当前事项，界面可通过下拉选择查看其他事项。

目前自动接待主要处理默认当前事项，由 new_case=true 触发另建事项；普通人工建议主要更新所选事项，没有相同的新建流程。模型没有完整的同会话事项目录，难以在客户重新提到旧产品时可靠切回原事项。界面选择某个事项也不会直接修改后台默认事项。

初次同步新会话可能先建立空 case。这个空壳记录不等同于已采集到真实采购需求，本版首次整理真实需求时应优先复用合适的空壳，避免额外制造一条无内容事项。

### 2.3 保留的业务基础

正式需求继续为 ai-v1 的 13 个固定字段：product、product_id、product_url、product_images、quantity、specifications、customization、destination、delivery、budget、packaging、certifications、contact。值结构和真实依据继续保留；product_url 继续由程序派生。

会话摘要、业务补充和人工正文仍按 conversation 保存，需求、供货选择及采购关联仍按 case 保存。润色只处理冻结正文，不修改需求、摘要或事项归属。

## 3. 需求改为按需输出与字段增量更新

### 3.1 何时输出

AI 在同一次自动接待或普通人工建议任务中判断是否需要改变需求，不增加专门判定变化的 AI 调用。

- 新的真实采购：建立需求。
- 原采购增加、明确更正、撤回条件，或需要纠正此前错误归纳：更新对应需求。
- 信息没有变化、只是正常答复或重生成回复：省略整个需求变更块，不重复输出已有字段。
- 无真实采购的问候、目录咨询、致谢等，不为完成结构而创建需求。
- 会话摘要按独立规则更新，不以需求是否变化为前提。

### 3.2 建议的模型输出契约

用可选的 `requirement_changes` 数组表达实际变更，替代每轮固定输出整份 requirements 和独立 new_case 布尔值。数据库中仍保存完整 requirements，前端展示完整表单。

每项包括：

| 字段 | 用途 |
| --- | --- |
| action | create 或 update |
| case_ref | 更新时引用宿主提供的已有事项别名；创建时使用本轮唯一的 new:1 等临时别名 |
| trigger_evidence_ids | 本次创建、更正或撤回对应的真实消息依据 |
| set_fields | 新增或更新的字段，沿用 value、evidence_ids、source_excerpts 结构 |
| clear_fields | 明确撤回或纠错后须清除的字段及对应依据；通常省略 |

同时允许可选 `reply_case_refs` 表达本次回复涉及哪些事项，值为本轮目录的已有别名或创建操作的临时别名。它只表示回复归属：可以引用旧事项而没有任何需求变更。普通会话回复可以省略，不强行绑定某个产品。

同一事项每轮最多一项 update；同一字段不能同时出现在 set_fields 和 clear_fields。创建项不接受 clear_fields。模型不负责生成数据库 case_id、版本号、来源哈希、产品链接或幂等键。

示例一：回复内容变化，需求不变，省略 requirement_changes：

```json
{
  "reply": "客户沟通语言的正常回复",
  "reply_sources": ["m8"],
  "conversation_summary": "当前会话的中文摘要",
  "reply_case_refs": ["c1"]
}
```

示例二：客户将旧眼镜事项的数量改成 800 副，只返回数量更新：

```json
{
  "reply": "客户沟通语言的正常回复",
  "reply_sources": ["m9"],
  "reply_case_refs": ["c1"],
  "requirement_changes": [
    {
      "action": "update",
      "case_ref": "c1",
      "trigger_evidence_ids": ["m9"],
      "set_fields": {
        "quantity": {
          "value": "800副",
          "evidence_ids": ["m9"],
          "source_excerpts": {"m9": "Change the glasses quantity to 800 pairs."}
        }
      }
    }
  ]
}
```

示例三：客户明确说包装另议，撤回此前礼盒要求：

```json
{
  "action": "update",
  "case_ref": "c1",
  "trigger_evidence_ids": ["m10"],
  "clear_fields": {
    "packaging": {
      "evidence_ids": ["m10"],
      "source_excerpts": {"m10": "Cancel the gift box requirement; packaging is undecided."}
    }
  }
}
```

示例二的原文必须实际存在于 m9，示例三同理；示例消息只供说明契约。自动接待继续保留原有 action 等任务字段；这些示例不是删除其他任务字段的完整白名单。

### 3.3 省略、空值与清空

- 省略变更块、返回空变更数组：保持已有需求。
- update 只修改明确列出的字段，其他字段及其依据保持原样。
- update 中的 null、空字符串、空数组不能隐式删除旧值；需要删除时使用 clear_fields 并提供明确依据。
- create 至少有真实产品描述及可归属的买家依据；未提供的其他字段，由程序按完整 13 键结构补 null 或空图片数组。不能仅因模型给出 create 标签就建立空采购。
- 缺少证据、事项归属不明确或字段无效，不将这些问题转换为对已有内容的清空。
- product_url 不接受 AI 设置或清除；根据有效 product_id 统一派生或移除。
- 普通格式归一后与已有值及有效依据完全一致的补丁按无变化处理，不刷新需求修订、不触发产品同步。
- 只换同义中文表述而没有业务信息变化时，提示词要求省略补丁；程序不为比较语义再调用一次 AI，也不承诺通过普通字符串比较识别所有同义改写。

### 3.4 保存时机

保持现有“普通人工建议生成完成后，可保存有依据需求”的时机，但只应用明确的有效变更。采用／弃用建议只处理建议正文，不回滚或重复应用已经保存的事实变更。

生成建议、建立／更新需求仍不等于接管客户或发送消息。润色的返回契约禁止 requirement_changes、reply_case_refs 和摘要修改。

## 4. 同一客户多轮、多笔采购的归属

### 4.1 给模型提供当前会话事项目录

同一轮输入提供当前会话已有事项的简明目录：事项别名、已有需求值、业务阶段，以及程序保存的实际当前事项和界面选中事项。沿用已有需求作为参考，不要求它们再次出现在输出中。

- 目录只来自当前商家、买家和 conversation。
- 按别名关联各事项的需求、适用资料和有效供货条件，避免把 A 产品的供货条件应用到 B。
- 最近 50 条消息和窗口外必要依据的机制继续保留；补齐目录中相关事项的必要旧依据，不能只携带当前默认 case 的证据。
- 产品链接、程序展示图及其他已由程序排除的数据继续不进入接待模型；不为这些排除项增加解释段。
- 目录、依据和图片继续受上下文预算约束。无法安全容纳时明确返回上下文准备失败并保留现状，不静默删掉旧事项后让 AI 重建。

### 4.2 归属规则

1. 同一采购中的数量、规格、交期等补充，更新原事项。
2. 客户明确提回旧事项，使用其已有 case_ref，不因为它不是默认当前事项而另建。
3. 产品 ID 相同不能单独证明同一笔采购；客户明确提出另一笔订单时，允许相同产品建立不同事项。
4. 产品名称相似也不能直接合并。样品与大货、备选与确定、不同配送条件按真实语义保留。
5. 一轮同时修改旧需求并新增另一款产品，允许返回多项明确变更；不能把两款产品拼进一套 product、quantity 字段。
6. “再加 200”归属不明确时，通过正常回复澄清，或在独立会话摘要保留未决问题；不猜目标、不把整句归到默认事项，不新建独立质量提醒或逐项协助表单。
7. 不因重生成建议、重新启动、改变 job_id 或重复处理同一来源而重复创建事项。

例子：眼镜 A → 新增帽子 B → 客户“眼镜改为 800 副”，应更新 A，B 保持原样；随后“帽子照旧，眼镜还有其他颜色吗”，可回复 A 的问题而不返回需求变更。

### 4.3 查看事项与当前处理事项

界面查看选择与后台默认当前事项继续分开，不能因为浏览旧记录而改变自动接待对象。

- 多事项下拉继续存在，显示产品名称及必要的区分信息；同产品两笔采购可用数量／日期／简短编号区分，不把内部长 ID 铺在界面上。
- 用户手动查看 A 时，后台更新 B 不强制把视图切走；下拉中的状态按保存结果更新。
- 未固定浏览旧事项、处于跟随当前事项的视图时，后台明确切换到新事项后可跟随显示。
- 单一、明确的回复事项可更新后台默认当前事项；同轮涉及多个事项时，保持已有指针，按 reply_case_refs 保存完整回复归属。
- 普通人工建议使用相同的归属与新建能力，但不能改变接待授权、接管状态或自动发送开关。

### 4.4 事务、版本与防重

新增共用的需求变更应用模块，供自动接待、普通人工建议及现有手工创建入口复用。

- 每轮冻结目录别名到真实 case_id、各事项版本、会话来源版本和相关供货选择版本。提交前在锁内逐一复核，过期结果不能基于新版本自动重放。
- 同轮多项变更先整体校验再在一次事务中应用；结构、归属或版本不合法时，不应用其中一半。
- 保存本轮创建别名、真实 case_id 和应用结果的映射。恢复或重读已完成结果时复用原记录，不重新创建。
- 创建前在事务内核对现存事项的建立来源、原文范围和产品身份；同一来源重生成应复用已有事项。不能仅按 job_id 或 product_id 去重。原文不能区分两笔采购时先澄清。
- 在已有 case 中增加独立 requirements_revision：仅正式需求或有效依据变化时递增。旧记录缺失时，有有效 ai-v1 需求按初值 1、空壳按 0 读取，实际更新时再落盘并递增，不批量重写所有旧数据。
- case.revision 仍承担整个事项的并发与发送保护；任务状态、统计和会话摘要变化不冒充需求修订。
- 没有实际需求变更时，不调用产品绑定同步、不重复建立采购任务，不清除所选供货方案。
- 产品身份确实变化时，按现有规则处理原绑定和所选方案；仅数量、交期变化不重新抓取商品元数据。
- 草稿、来源复核和发送指纹纳入全部 reply_case_refs 对应的需求与有效供货版本，不能用 A 的旧上下文校验改为 B 的回复。
- 自动生成调度及排队去重按会话及实际来源继续约束，不因当前 case 指针变化重答同一消息。

### 4.5 来源失效与界面稳定

- 文本需求按实际依据正文版本核对；图片需求还核对真实图片内容及对应来源版本。
- 消息显示时间、无关附件元数据等变化，不应直接清空无关的文本需求。
- 真正的正文更正、图片来源变化或撤回，仍使对应旧依据失效，并阻止依赖它的旧草稿发送；不能为了表面稳定继续把失效内容当有效事实。
- 只处理受影响字段，旧内容在修订历史保留；不在每次启动任务时重新清空整份表单。
- 前端需求和图片读取依赖需求／媒体版本，不依赖每次 job 事件或通用 case 修订反复清掉本地已显示图片。

## 5. 图片原图预览、复制和产品链接

### 5.1 原图与显示预览分开

现有 image_asset.original_b64 保存聊天、需求及商品图的原始内容，业务补充使用 supplement_attachment.original_b64。当前大图组件仍显示缩略预览：补充图最多 256×256、48 KiB，商品五图使用单独受限预览，因此仅扩大弹窗尺寸不能变清楚。

- 列表、普通快照及事件继续传小预览，沿用 0.3.15 的五图传输预算。
- 打开大图或明确复制时，按图片引用读取已缓存原图；查看和复制不会启动平台查询或 AI。
- 延续单张 6 MiB、单边 8192 像素、总像素 2000 万及有效格式限制。原图缺失、损坏或版本已变化时明确反馈，不把放大的缩略图称作原图。
- 商品五图增加稳定的单图引用，绑定对应资产及来源版本；失败项被过滤后不能靠显示序号反推资产，避免复制错图。
- 聊天图、需求图和补充图同样校验消息／事项／附件关联与实际商家归属，不能只凭裸资产哈希取图。

### 5.2 有界的原图读取链路

6 MiB 原图转 Base64 已有 8,388,608 字符，再加 JSON 包装会超过现有响应行预算。本版不提高全局限额、不新增本地 HTTP 业务端口。

新增仅供宿主使用的本地原图描述和分块读取方法。宿主通过现有 JSON Lines 子进程链路获取内容，每块最多 256 KiB 原始字节，并限制总量、并发和读取存活时间。每次读取绑定原图标识、版本、总长度及 SHA-256，拼接后核对完整性；来源在读取中变化则停止，不能混拼前后两版。

宿主经专用 IPC 向 renderer 返回有界的 Uint8Array，renderer 用 Blob URL 展示；CSP 仅对 img-src 增加 blob:，connect-src 继续关闭。关闭预览、切图、切换客户和组件卸载时取消或丢弃迟到结果，释放 Object URL。

原图读取方法不加入普通业务 API_METHODS 的任意调用面；renderer 只提交受约束的业务图片引用，不提交文件路径、任意 URL 或完整原图 Base64。main 继续验证调用窗口及主 frame，后台复核真实归属。

### 5.3 共用居中图片预览

业务补充图片取消右侧抽屉，商品图、聊天图、需求图及补充图使用共用居中图片卡片：

- 背景遮罩、按比例完整显示、加载及失败状态，避免背景页面布局改变。
- 默认适配窗口，提供原始尺寸查看及必要的平移／滚动；不把适配窗口等同于压缩原图。
- 点击卡片外部、关闭按钮或 Esc 关闭，焦点回到原触发入口。
- 图片组保留上一张／下一张、左右键和张数显示；单张图片不显示无效切换控件。
- 限制焦点在打开的模态卡片内，预览卡片尺寸和内容滚动受窗口约束。
- PDF／文本继续使用实际提取文字的预览语义，本版不增加完整 PDF 阅读器或 OCR。

### 5.4 缩略卡与大图右键复制

在商品五图、聊天／需求图、补充图的缩略入口和放大图片上右键，打开固定原生菜单“复制图片”。宿主从绑定的图片引用获取对应原图，仅在用户选择复制后写入系统剪贴板。

- 缩略卡可直接复制，无须先放大；大图复制当前选中的同一资产。
- 复制原图的全尺寸像素内容，不复制 URL、路径、组件截图或缩略预览。
- 系统剪贴板允许以全尺寸 PNG 等兼容格式承载；不承诺保留原始文件编码、压缩方式或 EXIF 字节。源文件及缓存不改写，方向和透明度按有效原图正确处理。
- PNG、JPEG、WebP 分别核验。转换受独立内存／输出预算约束，无法支持时明确提示，不能静默改用低清缩略图。
- 成功后简短反馈；加载失败、菜单取消、剪贴板拒绝分别处理，不能在异步写入完成前提示成功。
- Electron 45.2.3 本地类型定义使用异步 clipboard.write(ClipboardItem[])；实现必须按实际安装版本核对和验证，不直接套用旧 writeImage，也不使用按页面坐标复制预览图的方式替代原图。
- 菜单入口只接收固定图片引用，不接受 renderer 自定义菜单、待写剪贴板内容、任意路径或外部资源。

### 5.5 完整产品链接及独立打开入口

采购需求中完整展示由数字 product_id 派生的规范链接，允许自然换行，文字可选择。点击链接文字复制完整地址，并给出短暂“已复制”反馈。

链接旁放置独立的小箭头，title 和可访问名称明确为“在浏览器打开产品链接”。箭头通过专用宿主入口提交 case／产品引用，由宿主取得并核对程序派生的规范 HTTPS 地址，再调用系统默认浏览器；不开放任意 URL 或协议。点击箭头不触发文字复制，点击文字不打开浏览器。

打开失败就近提示；保留 Electron 内页面导航和新窗口拦截，不将页面跳转替代系统浏览器。无平台 ID 的定制产品不生成虚构链接。产品库的相同链接入口沿用同一行为。

## 6. 接待界面与弹层

### 6.1 历史入口直接执行

顶部历史图标的可访问名称改为“补全当前客户历史”。点击直接执行现有 fill_history，不展示解释卡片或原生二次确认。

任务提交后立即显示忙碌状态；提交中和排队／执行中禁用该按钮，避免连续点击产生重复任务。后台也按会话合并重复活动任务。进度和成功／失败进入现有任务状态区或简短反馈，结束后恢复按钮。执行期间切换客户，任务和结果仍归原会话。

### 6.2 当前客户接待按钮移到顶部

历史、翻译、状态工具旁放置当前客户的接待切换按钮。人工接管时显示“恢复自动接待”，否则显示“暂停此客户自动接待”；执行中显示处理中，以服务返回的实际状态更新。

复用现有 takeover 接口和禁用条件，保留服务连接、退出、未保存输入、发送中和结果未知等保护。恢复当前客户仍受全局启停、授权范围和能力检查约束，按钮不能伪装成已经启动全局接待。状态弹层保留详细状态与原因，移除重复操作入口。

窄窗口优先压缩装饰和客户名占用，保留可直接触达的切换按钮，不再把它藏回长说明卡片。

### 6.3 信息弹层统一关闭

会话状态、附件格式说明等临时信息弹层统一使用受控打开状态：再次点击关闭、点击外部关闭、Esc 关闭、同级弹层互斥；切换客户或页面时关闭。通过浮层定位覆盖内容，不参与输入框高度分配；边缘位置自动限制在可视窗口内。

该规则不包括待处理建议／润色框。建议在处理前持续保留，替换或弃用后关闭，同一条已处理结果重开不再弹出；不能把点击空白视为弃用。

### 6.4 固定业务补充底部工具

业务补充面板采用标题、可滚动内容、固定底部工具的布局。附件和文字占中间可用高度；文字过长或附件增多时在内容区滚动。

“＋”“？”和保存状态固定在面板底部；拖动需求／补充分割线、展开附件说明、增删附件或调整窗口时，不因文字框自身高度提前结束而上移。说明卡片浮在“？”上方，不占布局高度。聊天回复区也核对发送按钮和保存状态的稳定位置。

### 6.5 图标与已确认布局

仅删除客户名称前的字母头像。摘要书本图标、摘要文字及展开箭头继续保留。保持紧凑三栏、删除重复日期／翻译行、无“回复客户”标题、无常驻建议条的现有结果。

## 7. 提示词、契约与已有数据

同步修改审核稿、生成脚本、静态运行模块、实际请求装配、Demo 和返回解析；运行时仍不读 docs。

- 自动接待和普通人工建议使用相同的需求变更与事项别名契约。
- 润色明确不输出需求变更、摘要或事项路由。
- 新提示词与新解析器随同版本发布，不把旧 requirements/new_case 与新操作静默混合应用。
- 对升级前未完成的旧生成任务沿现有中断／过期恢复处理，不能把历史旧结果重新解释成新的创建操作；发送 operation 的恢复规则保持原样。
- 保留事实与意图、希望／能力／同意／执行的区分，禁止编造及擅自承诺，保留来源、工具权限、图片真实读取证据、提问上限和输出限制。
- 不恢复 display_value、质量／待核实／协助提醒实体，或旧卡片、SKU、历史链接猜测解析。
- 旧 case、原消息、修订、产品绑定、所选供货、原图、operation、outbox 和原生回执继续保全。方案不包含历史事项的自动合并／拆分或真实商家数据迁移。

## 9. 实施顺序与定向验收

### 9.1 顺序

1. 固化需求变更、事项别名、清空、版本和幂等契约，建立能复现当前反复覆盖问题的定向用例。
2. 实现共用变更应用、多事项上下文、自动／普通建议统一处理及指纹；保留润色隔离。
3. 实现按需原图读取、共用居中预览、原生复制和受限链接打开。
4. 完成历史直接执行、顶部接待切换、临时弹层关闭、补充底栏和图标修正。
5. 执行相关定向测试、类型检查、提示词生成同步和构建；用隔离 Demo 实际操作 Electron，查看截图并保存报告。
6. 后续进入打包交付时，检查最终 EXE、来源一致性、固定更新签名和公开下载结果，按实际执行范围分别记录。

### 9.2 需求与多事项验收

- 相同输入连续生成回复建议：需求内容、需求修订、图片、产品绑定及采购任务数量不变。
- 省略变更块、空数组或无效空值不会清空旧内容。
- 只改数量时，产品、规格、交期、图片和各自依据保持原样。
- 客户明确撤回字段时能按证据清除；模型漏填不能清除。
- A 眼镜、B 帽子交替沟通时，各自更新正确；同轮更新 A 并新增 C 可原子应用。
- 同产品明确的第二笔采购可以新建；重复 job、重复生成和重启恢复不能重复新建同一来源需求。
- 新会话的空 case 可被真实首笔需求复用，不产生额外空事项。
- 归属不明时不改错事项；跨客户别名、旧目录、过期结果或同轮冲突被拒绝。
- 自动接待、普通人工建议一致；查看／采用／弃用建议与需求保存、接管和发送各自独立；润色不改变任何需求。
- 手动查看旧事项不改变后台默认指针；后台更新其他事项不把当前视图强行切走。
- 多事项回复绑定全部相关需求与供货版本，旧条件不能经换事项绕过校验。
- 仅时间或无关元数据变化不清空无关需求；真实证据更正仍阻止旧依据发送。

### 9.3 窗口与宿主验收

- 历史按钮一次点击即可启动，连续点击只产生一个活动补全任务，切换客户后结果不串会话。
- 顶部可直接恢复／暂停当前客户，保留实际禁用条件和独立的全局状态。
- 临时信息弹层点外、Esc、互斥及客户切换关闭；未处理建议框仍保留。
- 补充图片以原始分辨率来源居中预览，商品五图和其他图片交互一致；点击遮罩可关闭。
- 缩略卡和大图右键复制正确图片，可在原生应用粘贴；不得复制成 URL、路径或缩略图。
- 完整产品链接可换行、点击复制；箭头打开确切地址，复制操作不同时打开浏览器。
- 窗口宽度 1920、1440、1100，低高度及拖动分割线时，底部工具可见且不漂移；长文件名、五附件及大图有界滚动。
- 客户字母头像消失，摘要书本图标保留；现有未决发送核查、保存失败及断连反馈继续可用。
- 原生菜单、系统剪贴板、浏览器打开与图片来源替身分别记录，替身结果不冒充真实 Windows 行为。

### 9.4 验证与交付约定

按改动范围执行相关文件或用例，不因新版本、构建或打包运行全量测试。实际截图必须逐张查看；合成模型和数据不替代真实模型语义、平台、图搜或供应商验收。

新版本构建完成后立即创建中文本地 commit，包含版本号、主要变更及可纳入仓库的源码、测试、文档和验证记录，提交前检查范围、敏感文件与 git diff --check。构建产物、业务数据、凭据和私钥不入库。

用户已明确要求开始开发，开发完成后直接打包上传。安装、默认入口晋级、真实业务数据迁移和私有源码推送仍分别处理；自动定向询价与报价回收的 blocked 状态不在本版交互调整中宣称解除。
