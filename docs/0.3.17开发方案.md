# 0.3.17开发方案：商品图与复制修复、完整消息时间及WhatsApp原生界面接入

日期：2026-11-13。面向接待人员、开发及验收人员。

状态：已按要求先修复并提交，再完成WhatsApp并打包公开发布。源码和公开latest均为0.3.17；最终C构建提交a150253，实际EXE、六张截图、SDK原始公共扫码页、ZIP与固定更新签名检查通过，见[发布说明](0.3.17发布说明.md)与[验证记录](verification/0.3.17.json)。WhatsApp原始页面、独立单聊状态、可选背景与发送账本已实施；未登录真实账号或执行真实收发。本方案为本版主入口，[WhatsApp技术方案](WhatsApp接入与跨渠道接待开发方案.md)及[界面约定](WhatsApp接待界面设计稿.md)随之更新；原自绘聊天原型不再作为实施目标。

## 1. 本版目标

1. 商品图片能区分尚未读取、明确无图、平台读取失败、图片下载失败及缓存异常；手动重新采集时直接覆盖旧图组，不保留旧图或失败回退。
2. 修复产品ID、产品链接等文字复制，核对缩略图和原图的图片复制链路；提示准确归属到发生操作的位置。
3. 国际站聊天每条消息直接显示“发送方 YYYY-MM-DD HH:mm:ss”，例如“Kayla ca 2026-11-12 14:05:05”，不加日期分隔线。
4. 左侧新增独立WhatsApp模块，使用WhatsApp Web原始界面；本版自动接待覆盖当前账号所有单聊客户，包括未绑定国际站及后续新增联系人。国际站对话绑定为可选背景增强，绑定后才单向带入该客户的国际站上下文。

维持0.3.16的需求增量、多事项归属、固定补充底栏和原图交互。补图及日期显示不重写正式需求、不增加接待AI任务。WhatsApp后台采用独立会话、授权与发送回执，首版不把其消息、摘要或需求反向同步到国际站。

## 2. 已确认事实与尚不能确认的部分

### 2.1 文字复制失败的原因：宿主拒绝剪贴板写权限

[SharedRequirementCard.tsx:30](../apps/desktop/src/renderer/components/SharedRequirementCard.tsx#L30)直接调用navigator.clipboard.writeText；[main/index.ts:644](../apps/desktop/src/main/index.ts#L644)对页面权限请求一律callback(false)，剪贴板写请求也被拒绝。根因是复制路径依赖浏览器写权限，而宿主禁止这项权限，修复不能只调整提示文案或位置。

已在同版本Electron45.2.3的隔离file页面、相同sandbox/contextIsolation设置和相同拒绝处理器下核实权限链路：

- 页面是安全上下文，已聚焦，navigator.clipboard和writeText均存在，排除这些前置条件缺失。
- 仅查询navigator.permissions时clipboard-write显示granted，因此只查权限状态不能证明实际写入可用。
- 发起text/plain写权限探测后，实际触发clipboard-sanitized-write；宿主拒绝后返回NotAllowedError，具体信息为Write permission denied。
- 探测使用永不提供Blob内容的ClipboardItem，验证实际写权限拒绝而不向系统提交剪贴板内容；没有读取或改动用户原剪贴板，也没有启动业务后台。

证据见[剪贴板权限核对记录](verification/clipboard-permission-0317.json)。该结果确认拒绝路径，实际产品按钮改走main剪贴板入口后的真实文本读回仍是实施验收项。需求卡底部共享错误提示的归属问题一并修复，但不是复制失败的根因。

### 2.2 “暂无商品图片”不是确切采集结论

[ProductMainImage.tsx:16](../apps/desktop/src/renderer/components/ProductMainImage.tsx#L16)只按local_product_id读取本地预览，不会发起远端采集。该组件对loading、failed、unknown有单独文案，但not_loaded、unavailable、缺失本地关联等多条路径会落到同一个空态；未完整显示后台原因。

[product_presentation.py:115](../services/reception/src/reception_service/product_presentation.py#L115)只自动调度not_loaded和特定旧单图补齐；已有failed、unknown、旧loading不会自动重试，这也被现有定向用例明确保持。该设计原意是避免反复查商品，目前缺少用户可控的恢复入口。

后台逐项下载失败会被转成无资产项；若全部失败，最终也可能显示“商品查询未提供可用主图”，不能清楚地区分“接口没有图片”和“接口返回图片但下载失败”。旧商品关联缺失、缓存损坏、响应结构不匹配也需要分别核查。

因此，不能只凭截图认定该商品无图、商品ID错误、网络故障或平台无权限。新版先补齐可定位状态，再通过隔离回归及明确目标的只读验收确认实际链路。

### 2.3 日期只在悬停中

[Reception.tsx:274](../apps/desktop/src/renderer/components/Reception.tsx#L274)的消息可见时间调用time，仅显示HH:mm；dateTime只放进title。后者目前也没有年份。截图的“02:11”和“12:32”无法直接判断是否同一天，属于显示缺口，不能据此推断原始时间戳丢失。

## 3. 商品图采集与恢复

### 3.1 以本轮重新采集结果为准

补充当前采集阶段、可展示数量、简短原因和最近尝试/成功时间。手动重新采集是覆盖操作：任务受理后清除当前商品旧图组的有效引用、递增媒体代次，页面显示本轮读取状态；新结果整组写入，不保留旧图备用，也不因失败恢复旧图。

| 实际状态 | 页面表现 | 可用操作 |
| --- | --- | --- |
| 首次尚未采集 | 尚未读取商品图片 | 读取图片；正常后台首次调度仍保留 |
| 任务排队/读取元数据/下载中 | 正在重新采集，旧图组已清除 | 当前商品按钮忙碌，重复点击复用原任务 |
| 成功或部分成功 | 展示最多五张有效图；部分失败时简短说明 | 重新采集；失败详情进入运行记录 |
| 平台明确返回空图片组 | 当前商品未提供图片 | 允许用户明确重新采集，不在轮询中反复查询 |
| 平台查询、授权或响应结构失败 | 商品图片读取失败或暂不可用 | 重试；身份问题引导按现有授权方式处理 |
| 有图片地址但下载/解码失败 | 图片下载失败 | 重试失败项；定位失效时重新读取元数据 |
| 本地原图/预览异常 | 本地图片缓存不可用 | 从有效本地原件修复预览，或重新采集 |
| 本地定制编号 | 无平台商品图片 | 不发平台请求 |
| 缺少有效产品/事项关联 | 商品图片尚未准备 | 先核对并修复本地关联，不伪装成平台无图 |

常态不增加来源解释卡；失败时仅一行原因和相关按钮。详细错误码、阶段和次数留在运行记录，界面不显示原始异常、私有路径、授权信息或带签名资源URL。

### 3.2 手动重新采集

增加拟定RPC request_product_images，接受受控的当前case或local_product_id引用、请求编号及必要预期版本，不接收renderer传来的任意产品URL或下载地址。具体字段同时核对shared DTO、preload、main和Python白名单。

- 根据当前商家及真实需求/产品记录解析数字商品ID，使用现有list-information、queryType=trunk、componentList=[images]接口。
- 单商品同一时刻最多一个活动任务；连续点击、客户端重试和多个页面复用已有job_id。页面轮询、切换客户、查看商品及普通AI任务不重置采集状态。
- 点击一次只开始一轮有界读取；读完失败、无图或unknown不自动排无限重试。此处是只读采集，可以在明确请求下重试，不能把该语义套到发送unknown。
- 已中断任务在确认旧worker不存在后才能被新请求接替；以任务编号/代次复核，防止迟到旧结果覆盖新结果。
- 使用现有独立媒体池和资源限制，不占Accio AI槽，不影响自动回复、人工发送或本地保存的队列优先级。
- 检查退出、数据维护、商家身份及当前来源；宿主拒绝授权时按既有方式处理，不换账号或身份重试。

### 3.3 下载、解析与缓存

保留数字产品ID、确切请求绑定、AliCDN安全校验、单图预算和最多五张限制，不改为扫描历史链接、解析假定SKU或从任意网页抓图。

1. 元数据阶段分别记录平台失败、结构无法识别、明确空组及可用图片候选。data为空或未知结构不能无条件等同“商品没有图片”。
2. 对已识别图片组逐项校验；单项非法URL/下载失败不吞掉其他可信有效项。显式商品ID不匹配仍整批拒绝，重复索引等歧义不猜选。
3. 下载/解码失败保留受限的项级原因和重试定位证据，不只保存asset=None；敏感资源定位不进入普通DTO和用户日志。
4. 受理手动重采集时使旧图组失效，随后用本轮校验结果整组覆盖；本轮全失败或明确无图就显示失败/空态，不恢复旧图。部分成功只展示本轮成功项，不与旧图拼接。
5. 新图只保留最多五张有效资产；不能用过滤后的序号重建图片引用，也不拿其他产品图片补位。旧展示资产在无其他有效引用时清理，不另留本商品旧图历史缓存；共享的聊天/补充原图、其他商品资产以及既有备份和业务证据不在该清理范围内。
6. 重采集受理即递增媒体代次，使该商品旧缩略图、已开原图及复制引用失效；新资产绑定本轮代次。旧worker或迟到复制请求不能把已清除旧图重新展示、复制或写回。
7. 原图仍通过0.3.16宿主私有分块读取，普通快照保持缩略图预算；缓存完成与本轮AI实际读取继续分开。

### 3.4 本地关联与旧记录

检查已有ai-v1有效product_id能否稳定取得产品、需求绑定及展示记录。0.3.16无需求变化时不会重复同步产品，不能依靠再生成一轮AI来修复旧记录缺口。

必要时提供独立的本地一致性修复流程：按真实需求产品ID复用现有产品、绑定与媒体元数据；必须补齐的对象遵守现有产品/采购原子与防重契约，不因补图重复创建采购任务，不额外发起找货或询价。修复不增加requirements_revision，不改客户条件、供货选择或原始消息。涉及真实数据调整时另保存完整备份及验证记录；本方案不视为迁移授权。

## 4. 文字和图片复制

### 4.1 统一通过受限宿主执行

产品ID和产品链接不再直接依赖renderer的navigator.clipboard.writeText。新增专用文本复制桥，由main根据真实case/product引用取得可复制字段，再按当前Electron API完成并等待写入结果。

字段限定为本版确需复制的产品ID、规范产品链接等，校验IPC来源和业务归属；不放开通用页面权限，也不开放任意文件/URL/脚本接口。核对产品库同类入口及现有启动指令复制，确保错误处理和返回时机一致，避免只修接待页的一处。

产品链接文字仍完整显示并可选择，点击复制；独立箭头打开浏览器，互不触发。受限复制失败时保留可选文字供人工复制，但不以“成功提示”替代实际写入结果。

### 4.2 反馈必须贴近操作

- 产品ID反馈显示在ID操作附近，链接反馈显示在链接附近；图片反馈位于对应图片组或原图卡片。
- 删除需求卡底部共用且长期滞留的copyStatus展示，避免文字复制失败看起来像图片采集失败。
- 换客户、换事项、换产品时清理旧反馈；迟到结果用操作来源/请求序号核对，不能把上一个客户的成功或失败写到新客户。
- 用户取消图片菜单不显示失败；未读到原图不开放成功复制状态。

### 4.3 图片复制专项核对

沿用固定原生菜单、图片引用、全尺寸PNG、EXIF方向及透明度处理。核查原图读取、资产版本、PNG转换和系统写入四个阶段，返回可区分的简短错误，不统一吞成“复制失败”。

缩略图与大图复制必须对应同一真实资产，不能退回复制缩略图冒充原图。手动重采集开始后旧图引用失效，已开的旧原图和排队复制不得继续使用；新图就绪后只复制新图。切换商品的迟到请求不串图，原图不可用明确失败。

## 5. 完整消息时间，不加日期分隔

按照用户指定格式，将国际站聊天中每条消息气泡上方的元信息显示为“发送方 YYYY-MM-DD HH:mm:ss”，直接可见，不依赖悬停。示例：

```text
Kayla ca 2026-11-12 14:05:05
这条是客户消息。

商家 2026-11-12 14:06:18
这条是商家回复。
```

- 不添加每天一条的日期分隔线，也不显示“今天/昨天”分组标题；不恢复顶部重复日期/翻译说明行。
- 年份四位，其余月份、日、时、分、秒均补齐两位，固定24小时制；姓名和时间保持在同一条元信息中，商家消息沿用“商家”标识。
- 使用系统本地时区格式化同一原始timestamp_ms，跨日、跨年自然显示实际年月日；悬停可补充时区，但不代替可见时间。
- 原timestamp_ms继续保存和传输毫秒，不重写、截断或把本地显示字符串存回消息，不改变来源指纹和发送版本。
- 无效/缺失时间显示“发送方 时间未知”，不强行归今天或显示1970年。
- 加载历史和新消息时保持原排序及滚动锚点；该改动不需要日期分组算法，不因分页增加额外标题。
- 窄窗优先保留完整时间，可让姓名合理截断或元信息在同一块内换行，不能只剩时分。聊天正文、原图、建议与底栏布局继续可达。
- 本项修改工作台自己渲染的国际站聊天消息头；WhatsApp Web原始界面里的日期和时间由其自身呈现，首版不注入CSS/DOM去改原生聊天布局。

## 6. WhatsApp原始界面与单向上下文接入

### 6.1 本版收敛范围

左侧导航新增“WhatsApp”，与“客户接待”并列。国际站接待页继续专门展示国际站聊天；WhatsApp模块使用WhatsApp Web原始界面，自动接待范围为当前账号全部一对一单聊，包括存量未绑定客户和后续新入站联系人。国际站对话绑定是可选背景增强，不是生成或发送前置条件。

不再实现旧设计稿中的自绘WhatsApp客户列表、气泡、发送输入框、建议/润色框、采购需求编辑页或跨渠道聊天合并。手工聊天、搜索和附件交互由WhatsApp Web自身提供；这不等于本程序已经验收这些原生功能的全部能力。

“原生UI”在本文指真实WhatsApp Web页面，而不是嵌入Windows版WhatsApp安装程序。外层只增加本程序需要的账号状态、当前控制对象、绑定客户、背景同步状态及自动接待开关。绑定/上下文详情按需打开小弹窗或抽屉，关闭后仍回到原页面。

### 6.2 原始页面与自动化必须共用会话

推荐Electron独立WebContentsView承载WhatsApp Web，使用按商家/账号隔离的持久session partition；页面保持原始布局。WhatsApp页面不加载工作台业务preload，不获得window.reception、Node、SQLite或任意文件能力，与工作台renderer分开。

whatsapp-web.js由受控Node工作进程/宿主适配层负责消息事件及自动发送。关键门槛是“用户可见页面”和自动化连接同一账号、同一会话、同一页面。不能单独开一个可见网页，再在后台另启一个独立浏览器，假称二者已经互通。

2026-11-13读取[官方Client.js](https://github.com/wwebjs/whatsapp-web.js/blob/main/src/Client.js)：设置browserWSEndpoint或browserURL时，库会puppeteer.connect后调用browser.newPage；直接配置已有浏览器并不等于复用已经嵌入的页面。故实施第一步须验证Electron45、固定Puppeteer/whatsapp-web.js版本的现有Page适配，必要时增加最小、可审查的初始化适配并保留上游来源与许可，不全局劫持newPage。

优先由Electron持久partition唯一管理嵌入页面的登录态；LocalAuth是另一种浏览器profile管理方式，不能假定两者天然共享，更不能并发写同一认证目录。最终实现必须通过关闭/重开、扫码、退出登录、页面刷新及SDK重连验证。不为整个工作台开启通用调试入口，不向renderer暴露CDP或浏览器控制能力。同页面适配未通过，则此项标记阻塞，不以另一份后台会话替代验收。

### 6.3 接入与绑定

- 首版每个商家连接一个WhatsApp账号；开启该账号自动接待后范围为全部单聊，新入站联系人自动纳入，不必逐个绑定国际站或逐个授权。登录持久化与自动发送授权分开，重启仍暂停自动接待；单客户人工接管/暂停和unknown保护继续适用。
- 用户在WhatsApp模块选中联系人后，点击外层“绑定国际站对话”。外层必须取得真实chat_id并显示确切控制对象；若原生页面的当前选中状态无法可靠识别，改由绑定弹窗明确选择后台已核实的WhatsApp联系人，不能按页面姓名猜测目标。
- 搜索范围限当前商家的国际站会话，展示客户名、关键原文和相关需求以核对；确认同一客户后保存绑定与版本。
- 外部ID按不透明值处理，兼容API明确给出的PN/LID别名，不把LID截成手机号，不靠同名/头像自动合并。
- 同一商家+WhatsApp账号+联系人仅有一个有效绑定，首版关联一个明确的国际站对话；支持解绑和改绑，冲突不静默覆盖。
- 原生页面切换聊天时同步显示当前绑定信息；AI路由始终由后台冻结账号/chat_id决定，不随用户切页或当前输入焦点漂移。
- 绑定、改绑、解绑或修改带入范围只改变背景来源：递增绑定状态版本，取消旧生成及未提交草稿；若该客户正在自动接待且仍有有效待回复消息，按新背景重新生成，不改变账号全部单聊范围，也不擅自恢复已人工接管/暂停客户。旧在途/unknown操作保留原目标和原核查记录。

### 6.4 严格单向同步

```text
所有单聊：WhatsApp对话 + 本渠道摘要 + 商家适用资料
                              ↓
                      WhatsApp自动接待上下文
                              ↑ 可选追加
已绑定时：对应国际站聊天、摘要、只读需求和业务补充
                              ↓
                      回复对应WhatsApp会话
```

这里“同步”是将国际站背景提供给AI，不是把国际站历史逐条发到WhatsApp聊天里。

- 国际站消息、摘要、需求和补充继续保存在原对象中；WhatsApp通过只读绑定读取最新本地版本，不复制成新的国际站对象或已发送WhatsApp消息。
- 切换到WhatsApp模块后，国际站原有消息监测仍在后台运行。正常同步完成后记录关联背景版本，下一次WhatsApp生成使用最新适用背景；不依赖国际站页面可见，也不每轮重新全量抓取平台历史。
- 国际站来源更新只使旧WhatsApp未提交结果失效，不因背景变化主动给客户发送新消息。
- WhatsApp消息只保存到独立wa_message/wa_summary/wa_draft/wa_operation等对象，不进入国际站conversation消息列表，不更新国际站摘要、case、采购需求、回复状态、未读或平台发送。
- 本版WhatsApp任务不调用国际站需求增量应用、产品绑定、采购/询价或飞书登记副作用。客户在WhatsApp新增或更正的条件可用于该渠道后续回复和独立摘要，但不反向改写国际站正式需求。
- 例如国际站“500个”，WhatsApp明确“改为800个”：本渠道按确切关联理解更正，国际站仍保留原500个及原始记录；若采购归属不明则澄清，不能跨事项猜测。
- 不将WhatsApp正文、摘要或平台回执混入国际站AI上下文。绑定关系只能开启国际站→WhatsApp的背景读取，不能隐含反向共享。

### 6.5 自动接待上下文与AI

保留当前商家Accio授权环境作为生成提供方；把现有国际站target数字ID校验与AI运行身份拆开，WhatsApp不伪造国际站客户ID。新建独立WhatsApp任务模式，首版输出该渠道回复、来源引用及独立摘要，不调用现有会自动改需求/产品/登记的国际站生成保存流程。

所有单聊每轮都使用当前WhatsApp近期消息、独立摘要和商家适用通用资料，未绑定国际站也正常生成及发送。仅当存在有效绑定时，再追加对应国际站会话的近期消息与必要旧依据、只读采购背景、业务补充和已提取附件文字；未绑定不借用其他客户背景。各来源保留渠道、角色、时间、版本及本轮短引用，商家补充不当作买家确认。

本版先形成文字自动回复闭环。国际站补充附件已提取的文字可带入；图片原件只有复用现有受控缓存并取得本轮真实读取证据后才参与理解，不承诺所有WhatsApp附件自动解析，也不把商品展示图自动加入上下文。无需为了理解绑定背景额外增加一次AI请求。

总上下文继续受预算限制，以WhatsApp当前对话为优先；国际站摘要只作导航，必要事实仍附原文来源。生成后及提交前复核商家/账号、WhatsApp来源、人工接管、授权及绑定状态版本：未绑定是合法状态，也保留版本标记以识别生成期间新增绑定；有绑定才额外复核国际站来源。国际站同步时间可在外层详情中查看，不能把本地背景称为实时完整平台历史。

两渠道共用当前商家的AI槽并公平调度；消息监听、绑定保存和暂停不排在长AI等待之后。只增加必要的渠道与来源规则，沿用现有事实、承诺和资料用途限制，不重写无关接待规则。

### 6.6 人工操作、发送与状态

原生UI手工发送、手机端人工发送及后台自动发送共同进入该WhatsApp渠道的接待状态。fromMe消息先按确切消息ID匹配本程序操作；非历史回放、非本程序发送的人工回复接管当前WhatsApp客户，取消过期AI，不影响国际站接待授权。

自动回复只提交冻结的WhatsApp账号、chat_id及正文，不依赖当前可见聊天窗口。保留业务operation与实际提交端持久账本，拿到确切消息ID后立即保存；ACK_SERVER、送达和已读分别记录。超时/崩溃后证据不足为unknown，只核查原操作，不换请求键或渠道重发，也不承诺远端严格exactly-once。

原生输入框由用户直接操作，本程序可拦截的是自有自动发送。若存在unknown，后台继续阻止新增自动发送并提示核查；不能声称同时禁止用户在原生页面或手机中自行发送。观察到新的人工操作仍独立记账，不能用其清除旧unknown或猜测旧操作已成功。

连接、可选国际站绑定、AI检查、账号全部单聊接待、单客户接管及消息ACK分开显示。未绑定联系人正常参加自动接待，也保留原生人工聊天；全部单聊不包含群聊、广播、状态和频道。处理有效新入站/待回复消息，不对所有历史联系人批量主动补发。账号/连接会话失效时撤销相关自动授权，重连不自动恢复；单纯切换模块或隐藏仍在线的原生视图不停止后台接待。
