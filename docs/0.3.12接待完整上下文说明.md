## 这个示例发生了什么

客户A先收到一张与用户实际格式相同的纯文本询盘：商品ID、询盘ID、商品标题和买家留言在同一条消息中。商品标题带Custom Logo，买家实际只问运费。程序认领一次商品首查；替身接口返回参考标题和目录价格，但没有URL，商品查询状态因此保存为no_link。

第二条消息明确100件、蓝色、发往法国并要求单独报价运费。正常接待再次运行，复用原商品档案和no_link记录，没有再查商品。当前业务补充说明运费尚未核实，不能承诺送达日期或寄送样品。示例另启用合成的公开资料、内部接待规则及简短聊天风格，使导出内容覆盖真实资料选择路径。

随后客户B询问同一商品，服务关联到同一个商品档案。三个生成任务合计只查一次商品；B仍使用自己的消息和补充，不会拿到A的100件、法国地址或业务补充。该过程在临时Demo服务中通过，查询次数由替身计数，不能称为真实平台三轮接待验收。

## 模型实际看见哪些层

固定指令定义接待、事实与承诺边界；适用资料分公开事实、内部指引及聊天风格，当前客户补充单独列出。消息使用最近50条及窗口外必要依据，并保留来源消息编号；本例只有两条合成消息。现有需求、逐问题跟进状态及本轮回复目标随任务进入。

商品部分包含当前来源、商品ID、查询状态、有限参考结果及当前客户适用性。product_context明确`allow_product_lookup=false`、`reference_only=true`、`listing_details_verified=false`。程序已处理首查；模型看到链接为空或no_link，也没有再查工具的许可。页面价格、材料、交期和标题不能直接当成本商家的核实事实，标题里的Custom Logo也不能当成买家定制要求。

模型同轮返回回复、摘要、采购事实、逐问题进度和product_ref，服务再核验来源、商品ID、URL、图片归属及当前版本。普通润色使用冻结正文，不增加商品查询或需求写入副作用。每次请求独立组装，不建立长期客户记忆。

## 一次真实AI检查的结果

实际调用返回正确的合成商品ID，product_url保持null；没有报价目录中的USD 0.01，也没有把Custom Logo写成客户已要求的定制。回复确认100件、蓝色和法国，说明运费尚需核实，并询问是否需要Logo。

原验收脚本错误地期待`action=reply`，而现有分析契约允许ask/wait_quote/skip，保存的合法结果为ask。首次失败记录完整保留；对同一份已保存响应进行离线核对后通过，没有再次调用模型。同时修复了一条旧的Logo重复提问误报，使其只看买家留言而不把平台标题作为要求。

本次CLI没有直接输出结果，现有机制从该请求自己的completed record恢复了响应；记录中保留exit code 1及恢复成功，不能据此称传输没有异常。响应仍有质量提醒，单一合成场景不证明长期语义质量或真实发送可靠性。完整证据见[离线核对记录](../artifacts/verification/reception-0.3.12/synthetic-ai-reviewed.json)及[本版验证记录](verification/0.3.12.json)。
