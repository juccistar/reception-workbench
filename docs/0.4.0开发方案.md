## 1. 版本目标与实施建议

本版优先解决启动等待、本地查询/图片查看延迟，以及不同 AI 任务互相排队的问题。建议采用以下顺序：

1. 补齐身份失效的统一撤权和错误分类，建立可比较的分阶段计时。
2. 优化按需加载、首屏就绪、重复查询、事件刷新和图片传输。
3. 将平台连接与模型推理解耦，支持保存多个 API，接待生成与中文翻译分别选择；接待 API 承载同轮文字和图片。
4. 完成文字、多图、来源绑定和实际模型质量/延迟验收，多模态作为本版必需能力交付。

接入前提已按用户补充确定：**启动台统一管理全部商家的模型配置，支持添加多个 API，全局分别选择接待与翻译使用的 API，可选不同服务商或同一服务商的不同模型，也可明确选用同一配置。** 接待生成使用具有视觉能力的 API，覆盖自动接待、人工建议、润色、需求整理、摘要和 WhatsApp 回复；有相关图片时同轮提交正文与图片，无图时使用所选接待 API 的文字输入。中文翻译单独选择 API，仅要求文字及翻译结构化输出能力。两类用途复用调用基础设施，配置、能力和数据范围分别管理。Accio 继续负责商家身份、平台读取、发送与真实采购工具；详见 [第三方多模态 API 调用设计](0.4.0第三方多模态API调用设计.md)。

0.4.0 必须交付：身份异常处理、分阶段观测、已确认重复工作的消除、正式 Demo 取消及轻量启动台、启动命令精简输出、启动台全商家统一模型配置、第三方多模态 provider、独立调度、WhatsApp 图片接入、请求级图片证据、配置/结果版本保护及定向验证。视觉 API 路径为主路径，不设“图片任务自动回到 Accio”的分支。现有翻译连接和凭据机制可复用其设计，业务调用启用仍绑定具体商家、数据根和允许发送的内容。

**最终复核判断：方向合理，但不能把换 API、增加并发或增加缓存本身视为性能收益。** 优先实施请求内复用、图片传输复用、非必要启动等待拆分及退役热路径删除；跨请求大缓存、双生成并发、schema v3、前端额外拆包和登录配置统一均以测量或必要依赖为准，不作为无条件交付项。历史兼容允许删除，但不为清理低频分支额外强制改写整库和登录配置。内存、失效、调度和验收约束分别见第 6、8、9、10 节。

用户已单独授权开发、定向验证、构建后立即本地提交，以及完成后的候选打包和公开发行。真实数据迁移、自动安装、私有源码推送、真实客户发送和付费模型调用不在本次执行范围内。package、锁文件及 Python 运行版本已在实施阶段统一为 0.4.0。

## 3. 身份校验与授权优化

### 3.1 先补齐失效行为

引入专门的身份失效处理入口，区别于用户对某一渠道的普通暂停。它负责：

- 在确认身份不匹配或无法继续核验时，将当前身份状态置为待重新核验，并发布受限、无原始敏感内容的原因。
- 撤销国际站、WhatsApp 自动接待及采购的运行授权，递增各自需要的 epoch / generation。
- 取消排队及在途的未提交生成，停止尚未提交的自动批次尾部；拒绝旧 provider 结果应用。
- 原生撤权为本地立即动作，不能排在远程身份查询或模型返回之后。
- 在途发送继续保留原 operation、账本及核查路径，不能把其改成“肯定未提交”，不能清除 unknown。

适配器必须提供可区分的身份错误码、stage 及是否属于主动取消；避免泛化 adapter_error 导致身份故障被当成普通模型故障重试。通用任务、LiveIntegration 内部再次核验、监测和采购边界要共用失效处理，不能只修复连接检查按钮。

身份不可用时可显示已加载的本地历史并注明状态，不能借此恢复发送或扩大第三方数据调用范围。正常暂停一个渠道仍保持该渠道原有语义，不把所有日常暂停都改成全局关闭。

### 3.2 安全减少重复工作

先统计每条链路身份解析次数和耗时，再做以下优化：

- 连接检查中使用带 seller、数据根、运行环境修订和 epoch 的短流程身份结果，减少没有跨外部等待的重复解析。
- 公司资料读取从首轮消息检查中拆开；保留该独立后台读取自己的身份和来源检查。
- 同一次提交的不可变上下文计算可共用，提交检查点读取最新授权、接管和来源版本。
- 跨 token 获取、外部等待以及实际提交时，继续按原通道约定核验新鲜身份。

不设计持久化发送许可或无条件 TTL 身份缓存；身份未核验前不打开卖家业务库。主 frame 来源校验、同商家排他、WhatsApp 账号/连接代次和临时 grant 继续保留。

## 4. 启动提速方案

### 4.1 把启动分成可独立观察的阶段

记录进程开始、窗口可见、renderer 桥就绪、离线预检完成、服务首次响应、身份核验完成、首轮消息可用，以及翻译/WhatsApp 模块就绪。分别显示“工作台已打开”“正在核验连接”等真实状态，不以窗口提前显示替代后台完成。

当前已经在 `ready-to-show` 显示窗口，并有独立消息监测；本版在此基础上去掉关键路径上的非必要工作。

### 4.2 具体改动

1. **WhatsApp SDK 按需加载。** 宿主入口不触发 puppeteer、whatsapp-web.js 顶层执行，首次连接 WhatsApp 时共用一个加载 promise。保持 SDK 版本锁定、单页面 CDP、固定 whatsapp-runtime.asar 导入路由和逐文件校验。加载期间页面状态、取消、退出及失败恢复都须可处理。
2. **轻量 Python 维护入口。** 将 ReceptionService 的导入移到正常业务分支，`--maintenance` 与 `--inspect-launch-owner` 只导入所需模块。保留维护后再启动服务的进程与恢复边界；没有测量证据前不合并为单进程。
3. **公司资料后台化。** 首次核验卖家后，优先完成必需的消息能力检查；公司名走可取消的低优先级只读任务，显示已有有效本地值或加载状态。
4. **翻译和核心服务分别就绪。** 首次业务快照成功即可发布核心 backend_ready；共享翻译设置和凭据单独初始化。凭据、端点、数据根确认均完成前不能调用第三方。KnownFolder 获取结果可在宿主进程内复用，不用环境变量替代真实 Windows 用户目录。
5. **首轮查询合并。** 宿主探活使用轻量状态接口或复用首次业务快照，避免宿主与 renderer 无意义地各建一份昂贵快照。保持启动未就绪时保存和发送的阻断行为。
6. **首屏外模块按需加载。** 在测量 Vite 产物与模块执行后，对采购/设置等非首屏页面采用适当的代码分割；不为拆包引入第二个后台或弱化桥隔离。

打包目前使用 PyInstaller `--onedir`，本版不把 onefile 解压当作现有问题。源码与最终 EXE 分别计时，防止源码启动快但包内归档加载仍慢。

**存储预检单独作为启动大项测量。** `validate_database` 复制数据库及 WAL 后执行 quick_check/schema 校验；正常 prepare 在同一持锁阶段存在再次调用的路径。记录每库复制字节数、次数和校验耗时。只在同一锁所有者、同一文件集合、无恢复/写入的连续只读阶段复用本次验证结果；recover_wal、清理、迁移、释放再取锁及跨进程启动均使结果失效。不增加“上次启动检查过”的持久跳过标记，不因轻量导入收益小就放宽预检。

维护增加宿主消费的固定阶段进度与协作取消，例如 stdin 控制取消、受限 stderr 阶段记录、stdout 保留最终结果 JSON，均不转发启动终端。超时首先结束普通等待并显示明确维护状态；只读复制/校验可在安全点取消，已进入写入阶段须完成提交或回滚。宿主只有确认该子进程退出和锁释放后才能启动业务服务、切换目录或重试；超时 reject 不能假装维护已结束。异常无法退出时保留原有明确强退/恢复边界，不为达成“有界启动”自动强杀写入或释放锁。

### 4.3 启动命令默认精简输出，减少 Accio 上下文消耗

用户明确指出，启动后的命令行内容会被 Accio 读取并进入上下文。因此本版直接缩小对外输出，不依赖用户手动清上下文或重复添加静默参数。

**默认输出契约：**

- 成功只向 stdout 写一行紧凑 JSON，保留准确的“已拉起、连接检查待完成”状态，例如 `{"status":"launched_read_check_pending"}`；总计不超过 128 个 UTF-8 字节，stderr 为空。
- 失败 stdout 为空，只向 stderr 写一行固定 status/code、必要简短提示和可选诊断记录编号；总计不超过 512 个 UTF-8 字节，保留非零退出码。
- 不再打印 PID、完整卖家 ID、路径清单、重复英文说明、阶段刷屏、进度条或原始子进程输出。详细连接/AI/自动接待说明在应用页面和使用文档显示。
- 拉起进程不等于身份或读取已经通过；精简状态不能改称“已连接”或“自动接待已开启”。

修改授权启动包装、connect-live.mjs、通用 launch.cmd 和开发 start.mjs；connect-live 当前已对桌面子进程使用 ignore，应保留。开发入口的自动补构建和 Electron 不再把 stdout/stderr 直接继承给 Accio；使用持续消费的有界管道或适用的输出隔离，不能让满管道阻塞启动，也不能把全部输出先堆进内存。

默认机器启动路径不执行 pause/等待按键，避免授权命令失败后一直挂起。确需双击交互保留时使用明确的本地交互入口，不通过无限等待增加 Accio 命令超时输出。授权入口成功拉起后及时退出，不等待整个桌面生命周期。

本地启动记录只保存允许字段、固定错误码、阶段耗时及经过处理的必要代码位置，按大小/份数轮转；不因“改成写文件”而保存令牌、Key、完整环境变量、原始客户聊天或模型响应。诊断写入失败不覆盖原错误，不返回虚构记录编号；显式诊断模式也不向命令行倾倒日志。

机器读取边界保持完整：宿主 dispatch 的 blocked/code 解析、维护结果 JSON 和 Python 业务 JSONL 继续按各自契约消费，只禁止转发到外部启动终端，不能把内部协议过滤成一行或直接丢弃。安装包 extraFiles 复制的启动脚本与源码一起更新，防止源码静默而交付包继续输出旧说明。

新增定向验证捕获完整命令生命周期的 stdout/stderr，覆盖正常、缺授权、身份不符、构建失败、诊断不可写、子进程大量输出和授权命令退出。断言行数、UTF-8 字节数、固定结构、退出码、无按键等待、无敏感信息，以及私有 JSONL/宿主错误解析不受影响；分别对源码入口和最终包内入口验收。预算覆盖本项目默认机器启动入口及其拥有的子进程输出；外层 Accio、shell 或 npm 自己打印的包装内容另计，不承诺控制第三方终端自身输出。成功状态仍仅表示拉起，之后的连接失败在窗口显示。

### 4.4 桌面启动器与已登记授权环境复用

用户希望首次从 Accio 授权环境启动后登记，以后直接从桌面选择商家打开。**轻量启动器可以实施；Accio 完全退出或系统重启后能否继续复用授权，当前尚未证明。** 保存环境变量只保存一次凭据快照，不延长令牌期限、不代替网关服务，也不自动产生刷新能力。本项目当前只有环境继承和原生核验，没有 Accio 令牌签发/续期实现。

**正式版取消 Demo 模式，默认双击只打开轻量启动器。** 不再提供演示入口、样例商家/聊天或可进入合成业务的生产启动参数；未登记商家显示添加入口，授权失效保留在启动器，不转入 Demo。主界面仅显示商家名称、账号尾号及“待核验/需重新授权/已打开”等必要状态；完整数据位置和核验记录放入商家详情。选择商家只改变选择，点击“打开工作台”才启动对应流程；已有运行窗口时激活原窗口，继续遵守跨目录单商家排他。

启动台提供统一的“模型配置”页面，所有商家共用同一 API 列表、接待 API 和翻译 API 选择。没有登记商家也可先配置模型；商家窗口只显示当前配置摘要和跳转入口，不保留另一份可编辑选择。模型管理不依赖 Accio 授权环境。启动器只读取宿主索引和全局模型配置，不创建业务 Python 服务、不加载 WhatsApp SDK、不提前打开商家业务 SQLite；主动能力检查另用有限生命周期的隔离检查进程。布局与交互见 [桌面启动器界面设计稿](0.4.0桌面启动器界面设计稿.md) 和 [本地交互预览](design/0.4.0-launcher/index.html)。

开发测试继续使用独立的合成夹具和专用 harness，迁出正式运行分派与发行闭包；现有 smoke-demo 检查改接测试入口，不把删除 Demo 理解为删除离线回归。旧 demo 目录不自动删除、不迁入 live，不粗暴删除存量 mode/namespace 字段；正式业务只允许 live，测试数据继续使用隔离临时根，旧备份和回执保全。取消正式模式的源码、构建闭包和测试入口改造属于后续实施，本轮只修改方案与静态设计稿。

登记分为两层：

| 层次 | 保存内容 | 实施边界 |
| --- | --- | --- |
| 商家启动索引 | 稳定记录 ID、显示名称、预期 seller、原 registry/state/data-root 引用、已提供的 Accio 账号路径归属、工具位置/版本及上次核验时间 | 置于真实 Windows KnownFolder；只登记已授权启动确认的来源，不扫描其他账号。元数据不构成当前授权 |
| 受控授权资料 | 仅当前授权会话明确提供、经接口契约核实允许重用的最小凭据和必要运行参数；保存可获知的有效期/修订 | 仅在确认可复用及生命周期后启用，Windows 用户 DPAPI 单独密封，绑定商家/账号/来源；不导出整份 process.env |

现有 merchant registry 默认取启动环境 LOCALAPPDATA，可能与桌面启动环境不同。新全局索引只指向已登记的原 registry 和 profile，不搬迁或合并原 merchants.json，不因新 KnownFolder 路径改变业务 namespace；目录缺失/不匹配时明确停止，不另建空库替代。索引可列出缓存显示信息，但未核验前不因选择某商家而预读其业务库。

如授权复用条件通过，流程为：从目标商家 Accio 首次启动并核验 → 用户登记当前环境 → 宿主密封最小资料 → 桌面启动器按所选记录解密并重建子进程所需环境 → 原生核验预期 seller → 按原工作区启动后台并完成只读连接检查。只从合法继承的本次环境取值，不读取其他进程内存或账号凭据库，不修改系统全局环境。凭据不进入 renderer、命令行参数、普通日志或业务备份，沿用第 4.3 节精简输出。

`ACCIO_GATEWAY_TOKEN`、Node/MCP 路径和 workctl 是现有已知依赖，但不能仅凭这几个变量存在认定整个环境完整。实施须核对原生工具实际依赖的网关地址、运行组件、账号绑定及撤销/过期规则；没有正式过期信息时记未知，每次启动走当前有效核验。当前聊天发送另按目标客户取得 chatToken，仅在本次提交内使用，不能把它存作长期启动凭据。

授权过期、退出登录、账号变化、运行组件变更或所需网关不可用时，停止新外部操作并提示重新从 Accio 登记。只有受支持的刷新接口经过核实时才实现续期，不能用旧凭据反复尝试模拟刷新。更换授权继续先正常关闭原商家实例，再以新进程启动，不向已运行窗口注入不同授权；原 operation/unknown 保全，平台登录资料复用不恢复自动接待或采购的本轮运行授权。

验收要分别记录：仅关闭 Accio 窗口但后台仍在、Accio 完全退出、桌面新进程重开、Windows 重启、自然过期/退出登录和账号切换。先在明确允许的目标商家范围做最小只读身份及远端读取核验，不以本地环境存在或一次 resolve-id 代替平台能力，也不把只读通过称为发送通过。关闭 Accio 或登录退出会影响现有会话，实际执行须另有相应操作授权；本轮没有执行这些操作或读取凭据。

现行启动规则“不保存令牌”是当前实现约定，不能当作上述设计的技术不可行证明。后续若正式采用受控授权持久化，必须同步更新该规则及凭据存储契约。若验证发现授权必须依赖 Accio 后台，则交付说明应明确该依赖；“完全不运行 Accio 也能长期使用”只有在支持的独立授权/刷新机制通过验证后才能承诺。启动器本身不依赖这一结论，可先完成界面与商家索引。

## 5. 数据存储与本地延迟方案

### 5.1 先做不改变 schema 的优化

- 详情中的事项读取改用已有 conversation_id 过滤。
- 一次快照内共用 ReceptionProjection、消息摘要、未决操作和任务集合，避免同一数据重复解析。
- 同一次生成内复用已冻结上下文和语义投影，按需校验版本，不多次重新 JSON 化同一份大对象。
- 使用有界、可重建的会话摘要/投影缓存；缓存只负责展示和纯计算，发送准入仍读取权威业务状态。
- job 列表、历史批次和发件记录拆成有界的当前状态与按需历史查询；未决 operation 必须完整保留在发送围栏中，不能随列表分页丢失。
- 将非关键性能/缓存命中计数批量写入。发送意图、受理回执、CAS 业务编辑和授权相关写入仍立即持久化。
- 消息分页下推到 SQL，使用现行 `(空时间映射为 -1 的时间, message_id)` 排序与复合游标，限定商家/会话，按当前已存在的回退/删除语义验收。先取最后 N 条再恢复显示顺序，避免深页 OFFSET；仅减少 Python 返回/解析量不等于 SQLite 免去全会话扫描与临时排序。没有排序索引时如仍慢，再进入 v3 评估。
- 锁内只取得有限、不可变的来源与版本快照；排序、重型 JSON 编码、Pillow 校验/转换和 HTTP 等待移出业务锁，并在发布时复核版本。图片 RPC 必要时改为短请求返回传输任务/准备状态，再走现有私有分块读取；仅释放业务锁却仍在同步 JSONL 分派线程长时间处理，仍会阻塞暂停/保存，不能算完成。

### 5.2 有测量收益才引入 schema v3

长会话分页和跨会话统计如经测量确需新索引或投影表，作为显式 v3 子阶段实施：

- 按 kind、conversation_id、规范化时间和 message_id 设计排序查询；排序必须等价于现有空时间处理及相同时间按 ID 排序规则。
- 上下文先读取最近 50 条有效文字及时间窗口内附件，再按明确证据 ID 补齐窗口外消息和相关图片。
- 如需单独消息索引/投影表，定义为可重建派生数据，和原 entities 在同一事务内维护；不能出现查询返回已更新而原始业务尚未提交的状态。
- 使用 EXPLAIN QUERY PLAN、查询/解析行数及合成数据对比选择索引，不凭“加一个索引应该更快”升级库。

严格 schema 签名、版本号、离线 prepare、完整备份和迁移验证必须同步修改。现有库不能静默新增对象。迁移只在正常关闭、完整备份验证及源文件 hash 匹配后执行；旧库/旧备份保留。v3 启用后旧版本不能直接打开新库，回退通过原版本和迁移前完整备份完成，并继续检查较新发送账本，不能覆盖已发生的发送。

保持 SQLite WAL/FULL 和现有商家、模式隔离。本版优先优化图片传输，暂不把原图从业务 SQLite 整体迁出，也不引入 Redis、向量库或长期客户模型会话。

## 6. 缓存与内存管理

### 6.1 缓存内容与正确失效

先使用请求内复用。跨请求缓存只有在命中率及内存测量证明有收益后启用；缓存失效不能只依赖计时器。

| 缓存 | 范围与键 | 失效与边界 |
| --- | --- | --- |
| 身份短流程结果 | 当前进程、seller、模式/数据根、运行环境修订、epoch、流程编号 | 身份异常/设置/运行环境改变即失效；不替代提交前检查 |
| 展示基础投影 | 商家+模式+数据根+会话/事项+已提交数据版本 | 只缓存不可变事实，不缓存整份 ReceptionProjection 的运行状态 |
| 上下文纯计算 | 上述范围+消息/需求/资料/补充/供货版本+prompt/payload/投影版本 | 任一依据改变失效；缓存不含图片字节，不复用模型答案 |
| 原图与复制传输 | 不可猜 token、完整来源引用、资产版本、SHA、运行代次 | 30 秒绝对期限、最多两会话，另受总字节额度约束；完成/取消/超时/来源失效后释放 |
| 译文 | 商家/数据根、来源 hash、语言、上下文、profile_id 及模型/端点/提示词语义版本 | 切换翻译 API 不命中旧配置译文；旧记录可保留，切回匹配配置可复用，不把整库加载进内存 |
| 模型图片输入 | 商家/模式/数据根+原图 SHA+输入格式/变换版本+能力修订 | 只复用受控内容或验证元数据；来源、角色及本轮输入证据仍独立核验 |
| HTTP/SDK 连接池 | profile+凭据修订+所属事件循环 | 改端点/Key 取消旧任务并关闭旧池；空闲连接有界，不保存长期客户会话 |
| 服务商前缀缓存 | 实际协议支持的稳定规则及允许资料 | 验证 usage 才统计命中，不把本地缓存或模型答案算作服务商命中 |

`ReceptionProjection.status` 依赖当前时间、合并窗口、任务状态、授权开关/范围、消息同步及 AI 能力。实现优先在每次输出时叠加这些轻量运行状态；如缓存派生状态，必须另绑定运行状态代次及最早失效时间。合并窗口/重试到期要由调度唤醒或到期刷新推进，不能因为没有数据库提交一直显示旧状态。健康失效和撤权立即生效，不能等 TTL。

所有依赖写入、删除和恢复均走仓库统一失效入口；只在事务成功后递增版本，回滚不发布版本，事务内局部计算不写入全局缓存。先允许使用粗粒度仓库提交代次保证正确，只有命中率需要时才拆分领域版本，不先建设复杂依赖图。来源读取、版本读取须属于同一快照，不能把旧数据盖上新版本。返回不可变值或防御性副本，调用者修改不能污染缓存。关闭/换根/身份失效清除相应缓存与会话；缺失/损坏时回读权威数据，发送准入从不读取展示缓存。

### 6.2 原图与界面生命周期

一次传输至多执行一次原始 Base64 解码和原图 SHA 校验；像素合法性检查、必要 PNG 转换及宿主最终 SHA 各有自己的计数，不能统称成“一次解码”。同图 PNG 转换复用已验证字节，默认不常驻解码后的像素。逐块只查轻量引用/资产版本，避免重新加载含 original_b64 的整条 JSON；所有资产写入点的失效机制验收通过后才移除现有逐块完整校验。

先短锁核验并取得资产引用，在受限媒体执行单元做校验/转换，发布会话前再复核。传输中的字节被引用计数固定，LRU 不能淘汰仍在使用的内存。取消先撤销访问资格，实际执行结束才返还额度；防止旧任务还占内存时新任务重复获得同一额度。超时和失败释放 token、缓冲及定时器，重开不会复用旧权限。

前端按变化域刷新并合并在途请求：同一键至多一条在途请求，期间变化置 dirty；完成后如仍 dirty 再读一次，后续变化继续循环，不能把“最多补一次”做成丢事件。健康/断线立即处理，未知事件回退全量刷新；序号保护保留。原图弹窗已有 Object URL 清理，应继续保留；切图/关闭同时取消尚未完成的传输，晚到响应丢弃并释放。列表只保存缩略图和引用，不随会话历史常驻原图。宿主 Buffer、IPC 副本和 renderer Blob/像素一起计入观测，不把 Python 内存代表整机应用。

### 6.3 资源预算与准入

以下为实施初始值，须在 M1/M2 的边界用例中校准，**不是已测出的进程峰值**。上限按一个商家业务进程/对应宿主实例计算；同机多个实例会相加，不能宣称已有跨进程全局限额。资源准入不持有业务锁。

| 资源 | 初始约束 | 耗尽时动作 |
| --- | --- | --- |
| 展示/上下文可选内存缓存 | 合计 16 MiB、最多 128 项；LRU，闲置 60 秒；单项超过 512 KiB 不缓存 | 回读/重算，不拒绝合法业务；计费采用含对象开销的保守尺寸 |
| 闲置图片内容缓存 | 合计 32 MiB、最多 8 项、闲置 60 秒；默认只留压缩原图，Base64/转换结果不长期双存 | LRU 淘汰；验证元数据单独限 256 项/1 MiB；跨请求命中低则关闭 |
| Python 原图/复制传输 | 最多 2 个会话，保留的载荷总计 96 MiB；单个复制 PNG 仍不超过 80 MiB；固定 30 秒 | 等待或明确繁忙，不丢弃正在传输的数据；转换工作区另预留 |
| Python 图片/模型重载荷 | 总预留初始上限 512 MiB，包含在用/闲置图片、传输、像素工作区、编码和 HTTP 请求副本 | 先淘汰闲置缓存，再延后新任务；单任务本身超上限直接报预算错误，不能无限等繁忙 |
| 媒体并发 | 下载至多 2；重型像素校验/转换同进程至多 1，AI 图片、原图复制、预览生成共用此限制 | 轻量排队，不同时展开多张最大像素图 |
| 宿主与 renderer 媒体 | 宿主最多 2 条传输、同时最多 1 次全尺寸复制；宿主媒体缓冲/转换预留初始 384 MiB；renderer 原图仅保留当前查看项 | 复用可安全复用的 Buffer，按实际副本准入，关闭即释放，不缓存整段全尺寸历史 |

512 MiB 是自有重载荷的预留上限，不包含解释器、SQLite、对象管理和 SDK 隐藏分配，不能称为 Python RSS 硬上限；宿主预算同样不约束 WhatsApp 网页内部资源。不得先分配后检查。基于已验证图片头、压缩长度、实际适配器编码方式估计下个阶段的峰值，计入已固定缓冲和安全余量后再准入；估计不足、分配失败或进程/系统内存压力时受控结束未提交任务，不降低图片质量、不终止未知发送、不靠循环重试顶住内存不足。

数量依据：20,000,000 像素的一份 RGBA 约 **76.3 MiB**，EXIF 转置/转换会有更多副本；重型像素工作区初始按至少 `16 × 像素数` 字节预留，PNG 输出及其副本另计。64 MiB 压缩图变为 Base64 约 **85.3 MiB**；若同时持有原字节、Base64、JSON 字符串和 UTF-8 请求体，常规单字节字符串就约 **320 MiB**。若含非 BMP 字符使整段 Python JSON 字符串使用四字节表示，该组合可约 **576 MiB**，尚未计像素和 SDK 副本。这是表示层的静态估算，非本机峰值测量。不能把 64 MiB 文件预算或“一个带图任务”当作内存上限。

逐张验证后释放像素，再进入请求编码；支持时直接构造受限编码体/流，避免先拼一份含 Base64 的巨大诊断 JSON。实际 SDK 必须整包编码时，按该实现的副本数预留并相应减小单次有效输入容量；本地 64 MiB 只表示最高准备额度，不保证所选 provider 可一次接收。所有必需图片无法同时满足预算时明确失败，不取前几张，也不自动压缩小字图来凑数。

持久图片、译文缓存及 revisions 的磁盘占用另行统计；本版只回收可重建的临时缓冲/会话，不因内存 LRU 规则删除业务原图、消息或发送历史。持久缓存清理如另行实施，必须定义引用集合、备份和清理边界，不能称此方案已经解决长期磁盘增长。

## 7. 可以使用第三方大模型的调用清单

“可替换”指替换推理部分。第三方输出不能确认平台身份、执行发送或创造受理证据。

| 调用/业务任务 | 当前状态 | 第三方可行性 | 建议纳入 0.4.0 的方式 |
| --- | --- | --- | --- |
| 聊天消息中文翻译 | 已独立第三方 HTTP | 高 | 使用单独选择的翻译 API，可为纯文字模型；优化连接池和批次 |
| 有效人工建议中文翻译 | 已独立第三方 HTTP | 高 | 使用翻译 API；保留来源 hash、配置隔离及替换失效保护 |
| 整段人工正文润色 | Accio generate_manual / POLISH | 高 | 首批开放；只改冻结正文，不改需求或摘要 |
| 普通人工回复建议 | Accio generate_manual / MANUAL | 高 | 首批开放；严格一个建议正文，仍按同轮更新有依据的需求/摘要 |
| 独立需求整理/补录 | Accio generate_requirements | 高 | 首批开放；保留中文 ai-v1、13 字段、增量与证据校验 |
| 国际站自动回复 | Accio generate / AUTOMATIC | 本版主路径 | 文字及相关图片同轮提交视觉 API；返回自然 1 至 3 条，逐条原生发送 |
| final / 业务补充续答 | 自动生成链路的任务模式 | 本版主路径 | 与普通回复共用多模态 provider，不另加一次固定调用 |
| 会话摘要 | 正常接待/人工建议同轮返回 | 本版主路径 | 随当前生成结果返回，避免单独增加模型往返 |
| 多事项归属、requirement_changes | 正常生成输出的一部分 | 本版主路径，严格校验 | 只输出候选增量，程序应用，不给模型直接数据库工具 |
| WhatsApp 自动回复及 wa_summary | 当前 generate_whatsapp 仅有文字上下文 | 本版主路径 | 增加 WhatsApp 图片入口后使用同一视觉 API；保留账号/连接代次和独立账本 |
| 客户图片/商家附件参与接待 | Accio 同任务 read_compat | 本版必需 | 由 Python 向视觉 API 提交受控图片字节和来源清单，使用请求级输入证据 |
| 商家 PDF/文本附件的语义理解 | 本地提取后随上下文生成 | 高 | 仅发送已解析且用户允许的文本；PDF 解析本身继续本地完成 |
| 产品/供应商候选资料的文字归纳 | 当前嵌于采购流程 | 可作后续拆分 | 可归纳已有真实结果，不能补造价格、库存或供应商事实；不列为首批必需交付 |

以下不属于可被通用大模型直接替换的调用：卖家身份与 Accio 授权、平台消息读取、公司名称/商品展示图读取、图片下载与 SHA 校验、平台发送/ACK/回执、飞书写入、供应商实际搜索/联系、数据库备份恢复。产品/供应商搜索当前依赖真实工具及原请求记录；自动询价和报价回收继续 blocked。

不把现存但非当前主路径的旧 translate / observe_photo 方法当作必定发生的额外请求，也不把自然三条回复拆成三轮需求分析。

## 8. 第三方大模型接入方案

### 8.1 已确定的接入前提

按用户选择，由启动台保存多个全局 provider profile，并统一为所有商家选择“接待 API”和“翻译 API”。每条配置包含独立的端点、模型、协议和凭据引用；可以来自不同服务商，也可以使用同一服务商的不同模型。接待仍以视觉 API 为本版主路径，不把图片安排到以后；翻译允许选择纯文字 API。

接待最低能力契约为文字、多图原生输入和完整结构化业务输出；翻译只需文字输入及符合翻译 schema 的完整输出，不要求图像能力。两者都要求本地可取消、有截止时间及可核验的完成状态；取消不要求服务商承诺远端立即停止。JSON Schema、缓存统计按各自协议启用，没有原生 schema 约束时仍严格本地验证。

能力按 profile/model/config_revision 分别记录文字、结构化、单图、多图及图文结构化组合的通过/失败/未验证。任务按实际必需输入准入，同步替换自动接待、人工入口、WhatsApp 和状态投影中的单一 `checks['ai'].status` 门控。文字与结构化已通过但视觉失败时，可处理真正不需图片的任务；不能删除必需图片来满足文字准入。配置变化使相应能力失效。能力小样本通过只证明该配置可工作，不能替代业务质量验收。

按两类用途所选 API 的实际协议实现适配器；协议相同复用实现，协议不同使用对应适配器，不为每条配置复制一套代码。接待使用 Chat Completions 兼容端点时必须支持真实图片内容块，仅接受图片 URL 文本或模型名含 vision 不算通过；翻译适配器不强制携带图像参数。实际协议为 Anthropic 时使用 Python 官方 SDK，不能向其他协议套用其专有参数。

配置保存不自动联网查模型或发起付费试用。用户主动检查时，接待检查文字、单图、多图和业务结构化输出，翻译检查文字/翻译结构化输出；仅用于翻译的配置不自动发视觉探针。具体模型、价格和参数按各自 API 资料核验，本轮不推断尚未指定服务商的限制。

### 8.2 平台集成与模型服务分层

在 Python 服务内增加模型层，建议模块边界为：

- `model_providers/base.py`：统一多模态请求、结果、能力与错误对象。
- `model_providers/chat_completions.py`：所选 API 使用兼容协议时，编码文字/图片内容块、管理受限连接池并解析完整响应。
- 对应服务商适配器：仅为实际协议需要增加；使用 Anthropic 时采用 Python 官方 SDK。
- `model_inputs.py` / `model_media.py`：组装时间线、受控图片字节、来源清单和请求级图片证据；不向 Accio 工作区落临时图片。
- `model_router.py`：按启动台全局接待或翻译绑定解析 profile，冻结用途路由及配置修订，并另行校验当前商家/数据根权限及所需能力；不执行平台操作，不互借另一用途的配置或自动回到 Accio。
- 共用生成校验模块：从 LiveIntegration 中提取/复用 schema、reply_messages、checked_metadata、validate_changes 和 validate_reply 等规则，同时把“本轮 read 工具读取”规则改为当前视觉输入证据契约。

这些路径是计划新增模块。原生消息和发送适配器保持原职责。自动与人工入口都调用相同模型路由和结果校验，防止第三方路径少做一层验证。

请求在本地冻结：task_kind、purpose、route_revision、profile_id 及其配置/凭据/能力修订、payload/prompt 版本、输出 schema、截止时间、取消标记和来源快照。接待使用现有 model_payload 任务投影，翻译使用其受限文字投影；商家身份 token、数据库路径、凭据和发送接口不作为模型工具提供。

结果至少包含：解析后的业务输出、provider/model 的请求值与返回声明、请求 ID、usage、耗时、停止原因、图片输入证据和原配置修订。第三方报告的 model/usage 只作受限诊断，不作为平台事实或身份凭据。

第三方正常结果必须通过和 Accio 等价的本地业务校验后才能写需求、发布建议或生成发送批次。格式不完整、截断、拒绝、工具调用、未知来源、越界需求或图片证据不齐都不能进入发送。

### 8.3 多 API 管理、用途选择与授权

**模型配置统一放在桌面启动台，作用域为本机同一 Windows 用户下的全部商家。** 页面提供“API 配置列表”，可添加、编辑、主动检查和删除多条配置；商家工作台只有当前配置摘要和“在启动台管理”入口，不再保存商家级 API 覆盖或另一组用途选择器。未登记商家时也能配置。每条有稳定 profile_id、显示名称、协议、Base URL、模型 ID、credential_ref、请求参数、能力状态和独立 config_revision。同名配置仍以 ID 区分，改名称不改变执行修订。列表下提供两个全局选择器：

| 用途 | 配置绑定 | 覆盖任务 | 能力及数据范围 |
| --- | --- | --- | --- |
| 接待 API | reception_profile_id | 国际站/WhatsApp 自动回复、人工建议/润色、需求整理及同轮摘要 | 视觉 API；仅外发当前任务允许的文字、需求、资料与相关图片 |
| 翻译 API | translation_profile_id | 聊天文字、有效人工建议的中文翻译 | 文字及翻译结构化输出；只发待翻译文字与受限翻译上下文，不发图片或完整接待上下文 |

两个用途可选同一配置，也可选不同配置。本版不为每个子任务增加独立模型选择器；接待各子任务保留独立启用/授权，图片和回复仍用同一接待请求完成。某用途未选择、配置缺失或能力未通过时只标记该用途未就绪，不自动借用另一个用途的 API。新增未选配置不影响现有任务，也不会自动连接、预热或建新工作线程。

profile 列表、reception_profile_id、translation_profile_id 及两个用途各自的 route_revision 统一保存到真实 Windows KnownFolder 下的宿主配置，独立于商家 registry 和业务数据根；切换商家、从 Accio 启动或更换数据根不产生新副本。配置全局共享，身份、业务内容、能力在当前进程中的可用状态、用途启用及数据外发/自动接待/采购授权仍按商家和实际数据根隔离。新增商家使用当前全局模型选择，不因有 Key 自动开启任何业务。

现有有效共享翻译连接规范为一条 profile 并只承接翻译用途；接待用途由用户明确选择。若发现多个不同的旧有效选择，列为待选择配置，不按最后打开的商家或第一条记录覆盖全局值。旧启用范围只对原商家/数据根有效，不升级为全商家接待授权；正式写入全局路由后停用旧商家级模型选择，保留必要迁移记录，不双向同步两套设置。

Key 沿用真实 KnownFolder 和 Windows 用户 DPAPI，不写业务库。renderer 只处理当次输入/清除，不回读明文；宿主按当前所选 profile/修订经专用受限入口注入 Python 内存，不在 argv、普通事件、诊断或备份包含密钥，也不把列表中所有未使用凭据一并注入。

每个 profile 独立执行端点校验：公网 HTTPS 或明确配置的回环 HTTP，禁止凭据 URL、重定向和环境代理隐式转发，受限响应及错误正文。现有 URL 检查仅覆盖 IP 字面量，扩大数据范围前须补实际连接地址校验，不能仅预解析一次留下重绑定窗口。首次向某端点外发对应用途资料时，按商家/数据根确认范围；已授权范围内正常调用不逐条重复询问。

**变更只影响实际依赖方：**

- 切换全局翻译绑定，递增翻译 route_revision，使全部运行商家的旧翻译失效并切换各自译文缓存命名空间，不撤销使用另一配置的接待授权。切换全局接待绑定则使全部运行商家的旧接待生成失效、撤销有关自动授权，需各商家重新开启；不影响独立翻译。界面在保存前明确显示影响全部商家及需要重新开启接待的情况，不添加逐商家重复配置步骤。
- 修改 profile 的端点/协议/模型/Key/执行参数使该配置修订递增，仅使引用它的用途和商家任务失效。两个用途共用该 profile 时，两者都受影响；修改共享 credential_ref 也影响实际引用该凭据的配置。仅编辑名称或新增无关配置不使任何在途结果过期。
- 请求冻结全局 purpose、route_revision、profile_id、config_revision、credential_revision 和 capability_revision，同时冻结独立的 seller/data-root/grant 来源；提交/应用时核对对应修订。目录列表修订只刷新 UI，不作为全部任务失效键。全局配置使用宿主跨进程锁、预期修订比较与完整快照原子替换，引用和凭据修订协调提交，冲突时拒绝覆盖并刷新编辑页。
- 运行中的商家宿主接收变更通知并有界刷新；通知是加速途径，调用、结果应用及未提交自动批次推进前仍核对最新依赖修订。无法确认最新配置时暂停相关外发，不沿用旧缓存继续调用。已进入不可撤销平台提交的操作保全原回执，不能因全局改配置当作未发送。关闭启动器不影响商家读取已保存配置，不要求启动器常驻或代理全部模型流量。
- 删除已被选用的配置前先解除绑定或在同次保存明确替换，不自动选列表第一项；后续打开商家发现所引用配置不存在时显示未配置，禁止静默回退。只停用一个用途不会关闭另一个用途仍在使用的连接池。

主动能力检查不构造商家业务服务或读取业务库，使用合成文字/图片和有限生命周期的 provider 检查进程；界面先说明可能产生 API 费用，用户点击才调用。全局记录按配置修订保存协议/模型能力证据，各业务进程仍校验自身网络/凭据可用性与商家权限；检查通过不代表所有商家已获接待授权。所有启动器窗口共用一次同 profile/修订/检查类型的在途检查，结束、取消及超时均释放进程和资源，不为仅打开设置页预建客户端。

译文缓存增加 profile_id 和端点/模型/提示词等语义修订，来源 hash、语言、上下文继续保留；切换后旧译文可保留历史，但不算当前命中。切回原配置且全部语义键仍相同时可复用，路由变更仍拒绝旧在途响应。费用/耗时按用途、profile 和实际模型分别统计。接待模型切换始终保全原发送操作、accepted 前缀及 unknown，不接续旧批次。

### 8.4 资源调度与连接复用

保留原 Accio 商家槽用于真实采购工具任务。第三方生成与其独立调度，**初始默认 1 个生成请求**；通过质量、配额及内存实测后最多 2 个，其中带图最多 1 个。同会话会更新正文/需求/摘要的生成互斥。翻译独立队列及最多 1 个请求，可与另一 API 的接待并行；全部 profile 的活跃 HTTP 在同一业务进程内默认合计最多 2 个，增加配置数量不扩大总并发或图片内存额度。

限流按 profile 及已知共享配额组分别记录，不让独立翻译 API 的 429 暂停接待 API。两个用途共用 profile，或同端点配置引用同一 credential_ref 时共用对应限流组；不同 Key 是否共用厂商账户配额不能仅凭配置推断，仍按实际 429/Retry-After 收紧。每个 profile 默认活跃请求上限也为 2，准入取用途、profile/配额组、进程总量及内存额度的共同约束。

队列只保留 job、来源 ID/版本、优先级和截止时间等轻量数据，不保存大上下文、Base64 或解码图。保留现有业务/翻译队列容量及公平调度，同任务范围合并重复生成；内存/限流未准入时延后就绪，不阻塞业务消费者，不无限追加线程。媒体先在有界媒体池准备，完成前不占模型 HTTP 槽；核验原始消息/附件的业务版本未变后，再冻结包含已就绪媒体摘要的最终输入。媒体下载状态变化本身不算新客户事件或新的自动重试预算；真正来源变化才取消旧输入。

人工发送、原操作核查和已就绪自动发送继续使用现有高优先级业务队列；人工建议优先于后台生成，同时保留公平配额避免其他客户长期饥饿。现有 `AI_JOBS` / `_generation_active` 改为明确的资源归属，任务完成、异常和取消只结算自己那次出队。重型媒体准入按第 6.3 节执行，在用缓冲未释放前不能仅因任务标为 cancelled 就提前返还槽位和字节额度。

当前翻译每批 `asyncio.run` 并新建 AsyncClient，不能把客户端直接缓存到多个事件循环间。一个业务进程的 provider runtime 拥有持续事件循环，按 profile/凭据修订管理隔离的客户端和有界连接池；同 profile 两用途复用，停用单一用途只减少其引用。只为当前绑定或主动检查的配置按需建客户端，未选配置不预建连接；检查结束或不再引用时关闭，旧版本清理期间的连接也计入总预算，不能切换一次留下一个池。不同 profile 不复用带授权状态的客户端，也不新建一组无限工作线程。多商家进程共享 Key 时，本地上限不代表服务商账户总限流；本版不另建跨进程网关。

**取消与健康分层。** 取消立即撤销结果发布资格，并主动取消异步请求、关闭其响应体；服务商可能仍在计算/计费。按请求登记单调时钟截止时间、资源归属和取消清理期限。provider 正常超时属于单任务失败；协调线程失活或执行单元越过已声明清理期限才触发执行器故障及原有撤权。不能沿用固定 420 秒 AI 阶段阈值来解释任意新 provider 超时，也不能为绕过 watchdog 无限制放大阈值。

关闭先停止准入、撤权并取消，再在受限期限内等待资源所有者完成；改造现有生成/翻译无期限 join。不可取消的底层工作仍登记在册，不复用其额度，迟到结果不得访问已关闭仓库；未确认退出时报告关闭故障并保留既有显式强退/恢复流程，不伪造 clean 标记或声称远端已停止。实际 SDK 若不能满足此所有权和关闭契约，须更换其可控调用实现后才启用并发。

### 8.5 输出、图片与失败处理

- 支持 JSON Schema 的模型优先请求结构化输出；仅支持 JSON Object 时仍做完整的本地 schema 和语义校验。不能只看到合法 JSON 就视为业务有效。
- 自动回复一轮返回 1 至 3 条，整体预算和来源约束沿用 0.3.21；人工建议严格一份正文；润色只修改冻结正文。
- 摘要、需求变化和回复尽量保持同一轮结果，防止额外请求增大延迟、费用和来源不一致。
- 协议需要时允许流式接收，但默认只在完整校验后展示有效结果，不把流式 UI 作为本版必需优化。若另做人工建议预览，预览不可采用或发送；自动发送始终等待整轮校验和冻结。限制响应总字节数、流累计内容和 JSON 深度/字段长度，超限主动取消，不因 stream=true 就无限累积。
- 相关原图与文字按时间线同轮提交，默认使用受控缓存中的完整原图字节，绑定 SHA、别名、角色和来源版本。不增加“先识图转文字、再生成回复”的固定两轮请求；不发送本地路径或需要第三方自行下载的平台私有 URL。
- 请求级图片证据由本地构建器和传输结果生成，记录实际编码清单、规范输入摘要和完成状态；只有适配器能在发送边界计算实际编码体摘要时才记录该字段，不把另一份 JSON 的 hash 冒充实际请求。模型自行声明“已看图”不能构成证据，输入可追溯不代表识别必然正确，不把视觉推断升级为买家确认或经营承诺。
- 图片能力未验证、来源失效、下载失败或预算不足时停止该图文任务并保留输入，不能丢图继续自动回复，也不自动回到 Accio。纯文字任务仍可按自己的能力状态使用。
- WhatsApp 补齐同页面 SDK 的受控媒体读取和私有分块传输，纯图片新消息也建立待回复来源；历史导入、联系人更新和媒体准备完成不额外创造一轮新消息。商家、WA 账号、连接代次、chat 和 message 全链路绑定。
- provider/SDK 内部隐式重试关闭。现有国际站生成、WhatsApp、人工任务和翻译不是一个通用尝试预算，实施时分别接入明确的 attempt_chain：自动任务绑定渠道/会话及真实输入来源，人工任务绑定显式操作及冻结正文，翻译绑定原文/上下文/目标语言。新 job、profile、进程或媒体 ready 状态不自动重置同一链；新客户输入或用户明确再试可创建新链，后台刷新不能模拟人工再试。
- 新模型调用默认每链最多 2 次 HTTP 尝试（首次加 1 次符合条件的重试），所有失败都记入同一链。仅发出前确定未提交的短暂网络失败、明确 429 或可重试服务端错误进入重试；后者仍记录可能计费。Retry-After 加退避必须装进原总期限，超期直接结束。401/403、参数/格式/大小错误、拒绝、截断和无效业务 JSON 不自动重试，不再发一轮“修复 JSON”。
- 已上传后断连/超时且无完整结果，默认标为生成结果未取得、可能已计费，停止该链自动重放；有可用查询协议时只查询原请求。来源/身份取消不重试。自动调度必须识别该来源已有失败/不确定链，不能再创建新 job 绕过策略。模型记录与客户发送 operation 的 unknown 分开，不能因为模型不确定就改写平台回执。
- 一条链使用准备、推理及含退避的总截止时间，另限排队年龄。生成链从开始准备起初始总期限 180 秒、媒体准备最多 60 秒；翻译沿用 30 秒总期限。实际配置按所选 API 校准并与健康/关闭期限对齐，重试不重新获得整段时间。响应初始总字节上限 1 MiB（含流累计），输出 token 上限按任务/schema 和实际协议确定，不能照抄翻译的 4096 为所有任务通用预算。
- 默认不做跨服务商或跨用途静默回退。接待切换到已配置、能力通过且允许处理相同内容的视觉 profile；翻译可切换到满足文字/翻译 schema 的 profile，不要求视觉。切换不重放旧发送批次。身份失效与单一模型限流分别处理，客户发送的最多三次尝试、5/15 秒退避和 unknown 原操作核查规则保持独立。

### 8.6 提示词缓存、上下文与费用

稳定系统规则与允许资料放在前缀，客户当轮消息、请求 ID 和变化内容放在后部。固定提示词仍由审核稿生成运行时模块，必要规则、证据与报价限制不以“提速”为由删除。

按模型实际能力开启前缀缓存，用 usage 中的缓存写入/读取字段验证。服务商缓存不能替代本地来源版本检查，也不意味着复用旧答案；不默认开启付费保活、预热或对每条聊天并行请求多家模型。

保持每次请求独立组装本地上下文，不引入服务商长期客户会话、Managed Agent 或向量检索作为本版前置条件。统一生成不新增自动分组归纳或摘要压缩请求，必要文字/图片超预算明确失败；原翻译已有文本分块继续按其独立契约使用。现行 Accio 图片也是同任务读取，不能把改用视觉 API 的收益描述成“原来固定两轮、现在一轮”。可验证收益来自移除桌面代理/临时工作区步骤、连接复用、本地准备和排队改善，模型本身是否更快另测。

接待与翻译可选不同 API，输出 token、推理强度和 prompt 按各自任务配置；翻译可选费用更低、延迟更小的文字模型，但实际收益必须通过测量。即使两用途选同一 profile，也保留各自任务参数和输出校验，仅在协议支持且质量通过时使用专有参数。前缀缓存按实际 profile/model 统计，没有命中证据不计收益，不为未命中再发一轮预热。

成本按完整任务及实际服务商计费口径计算。明确未缓存输入、缓存读写、输出和图片是否已包含在 token 中，避免对图像 token 或缓存输入重复收费统计；缺失 usage/价格的调用记录未知，不能按零费用。记录全部尝试、取消/不确定调用及成功发布数量，比较每个有效结果成本、失败率和耗时。实际模型试验在明确服务商、数据范围与费用预算后开展。

## 9. 性能指标和验收方法

### 9.1 建立能解释用户等待的记录

复用现有任务阶段数据，增加启动和请求链路指标：

- 本地：storage_prepare_ms、python_start_ms、first_snapshot_ms、snapshot_ms、detail_ms、context_ms、业务锁等待/持有时间、查询次数、解析行数、图片解码次数与峰值内存。
- 消息：活动检测、正文同步、合并窗口、入队等待分别计时。默认 2 秒检测/1 秒合并不等于已经有 3 秒固定总耗时，也不以无限提高轮询频率追求低延迟。
- 模型：队列等待、图片缓存/准备/编码、原始及实际请求字节数、图片数量/像素、连接/上传、首次可见输出、完整返回、解析校验及 provider 使用量；纯文字和带图任务分别统计。
- 发送：最后一次买家输入到第一条受理，以及整批全部受理；平台提交与回执分别计时。

使用单调时钟计算耗时，毫秒业务时间用于关联事件。诊断只保存受限标识、计数、版本和耗时，不采集客户正文、Key 或原始平台输出。日志轮转和写入失败不能阻止业务回执落盘。启动终端另记录输出行数、stdout/stderr UTF-8 总字节数和退出状态，不能用 Token 单价或主观估计代替实际输出量。

### 9.2 验收门槛与性能目标

原方案中的启动下降 30%、查询下降 50%、重复请求下降 60% 和模型下降 30% 没有当前基线支撑，不作为发行承诺；200 ms 本地交互也不作为所有硬件/历史大小通用阈值。M1 先记录基线、波动和目标场景，再确定该场景的数值目标；不得测完后降低门槛来宣称通过。

| 指标 | 可直接验收的条件 | 性能判断 |
| --- | --- | --- |
| 启动 | 窗口、核心本地服务、身份/读取、翻译/WA 分别就绪；非必需资料不挡首轮读取 | 同机同库交错比较各阶段；报告移到首次打开 WA 的成本，不只比较更早显示空窗口 |
| 查询与上下文 | 输出等价，必要窗口外证据和所有未决围栏保全；查询/解析次数减少 | 缓存冷/热各报中位/p95、SQL 扫描/返回行数、锁占用；无收益的缓存不启用 |
| 本地交互 | 生成、图片准备及超时并发时，保存/接管/暂停仍能处理 | 分别量测空闲与重负载尾延迟；不因后台任务占锁而显著退化 |
| 图片传输 | 一次传输原始 Base64 解码和原图 SHA 各至多 1 次，逐块版本与最终 SHA 通过 | 另报像素解码、PNG 转换、跨进程复制及峰值内存；缓存命中可为 0 次原图解码 |
| 事件刷新 | 每键最多 1 个在途读，dirty 变化最终收敛；健康/断线及时生效 | 固定突发序列比较请求数及最后一次变化到可见延迟，不只追求请求越少越好 |
| 模型任务 | 文字、单图、多图及业务质量通过；输出/费用/来源记录完整 | 分层比较完整任务、首条/整批受理、失败率及有效结果成本；不把 TTFT 当总时延 |
| 内存与退出 | 配额不超用，成功/失败/取消均释放归属，无持续新增线程/句柄/引用 | 热身后重复负载进入稳定区间；进程峰值及整组进程内存另报，不要求分配器立即把内存归还 OS |

性能型改动应在目标场景中产生超出基线波动的可重复收益，并且不显著恶化未改场景；只因正确性或第三方能力需要保留的改动，应按功能说明，不伪称提速。恢复、备份、首次升级和异常 WAL 单列，不能跳过校验或隐藏这些耗时。

### 9.3 测量与质量检查

已有本地 [0.3.21 启动诊断记录](../artifacts/verification/startup-0321-1115/findings.json) 提供参考：该记录一次主进程启动到完整连接检查约 29.4 秒，8 次成功连接检查约 14.5 至 22.8 秒，样本中的队列等待为 33 ms；启动器自身的前置身份探测未计时。这些是既有记录，本轮只读其摘要，未重启应用或复验真实平台，不能等同于完整冷启动基线或未来提速结果。该记录也提示维护子进程无总超时的等待边界，实施时补充可说明阶段的有界等待/取消，不能通过跳过备份/校验或强行终止数据维护来提速。

合成工作区至少覆盖小库、100 会话/5 万条消息、500 会话/20 万条消息，以及多事项、图片、长任务历史和 unknown。夹具在临时目录生成，不复制真实商家数据库。大工作区同时记录库大小、消息/任务/图片数量及硬件环境，避免只用版本号比较。

源码与最终 EXE 各测首次运行及正常再启动。关闭进程后重开仅称“进程重启”，不能称磁盘/OS 缓存冷启动；未控制 OS 缓存时明确记录，首次升级单列。正常再启动建议各 20 次，报告中位数、离散程度及最慢样本；本地 RPC 每场景至少 200 次后报告 p95，避免只报平均值。模型按获批预算小样本起步，质量不通过的请求仍计入失败率和成本，不从耗时报告静默删掉；样本不足不宣称尾部改善。新旧配置在同一时间段交错，固定输入/历史/网络条件并报告 provider 差异，不把服务商时段波动当代码收益。

内存分别采集 Python、Electron main、renderer、WhatsApp 页面及可归属子进程的 Windows Private Bytes、工作集、线程/句柄和自有缓存/在用预留计数。进程树合计 Private Bytes 用于分析提交内存；工作集简单求和可能重复计算共享页，不能标成精确物理占用。tracemalloc/JS heap 只作定位，不能替代 Pillow、Buffer、SQLite、Chromium 的进程级观测。

至少覆盖：20MP 高压缩合法图、6 MiB 单图、64 MiB 批量候选、大 PNG 复制与 AI 同时准备、带图请求取消、失败重试、快速切图/会话、旧响应迟到、缓存容量溢出和替换。热身后重复相同负载并穿插闲置/关闭，检查引用、预留、连接、线程是否归零或稳定，峰值是否符合估算；增加不同图片轮换以触发 LRU，不能只重复一张图。未做这些测量前，不宣称“512 MiB 以内运行”或“没有泄漏”。

语义样例必须覆盖单图、多图顺序、图文冲突、买卖双方同图、图片小字/规格/不确定性、纯图片消息、WhatsApp 媒体，以及自然回复、报价/交期限制、否定与更正、闲聊携带旧需求、窗口外依据、多事项归属、人工润色、补充续答和停止联系。保持现有质量底线：不编造、不丢证据、不扩大承诺、不误改需求、不串客户；测试替身只能验证协议和并发，真实模型语义需要实际模型样例。

## 10. 历史兼容清理与升级边界

本节纳入用户“此次版本可以删除为历史兼容设计的内容”的许可，优先删除已退役入口、无引用转换及热路径兼容扫描。它不要求为了减少分支而强制改写所有历史数据。新调用统一当前协议；仍在使用的历史账本和登录配置读取有实际用途，只有存在必要收益且转换经过验证时才移出运行时。持久数据确需转换时集中在离线升级阶段，不在普通快照或每次生成重复猜测。

### 10.2 确需转换的项目与可延后项

0.4.0 支持当前 0.3.21 工作区，包括其中仍然合法的旧发送历史。先用夹具证明无数据改写也能删除的分支，再评估必要转换。下列是条件清单，不要求全部在本版改写；WhatsApp v1/v2 配置统一、低频旧状态规范和更早凭据导入移除若无必要依赖/实测收益可延后，保留最小只读适配，不能既不转换又删掉仍在使用的 reader。

确需升级时，正常关闭、完整备份、验证来源和事务提交，记录独立业务格式标记；它与 SQL schema v3 分开。宿主配置与业务 SQLite 不在同一事务时，须有明确分阶段恢复/完成标记，不能声称跨文件原子升级。更早且不受支持格式通过相应旧版本/独立离线工具升级或导出；先验证可行入口，再给出限制。

- **旧人工分条草稿。** 确定没有 operation/发送历史的未发送正文，按现有正文语义规范成单正文；含 accepted 前缀的旧批次归入只读发送历史，不把整批或尾部自动填为新草稿。prepared/sending/unknown 保留原编号并进入原核查围栏；停止尚未提交尾部。完成后删除 message_parts 编辑、续发调度及前端专用旧编辑器分支，核查只更新对应历史记录。
- **旧接管/需求状态。** 把可确定的旧 case 状态转为现行状态，并保留会话人工归属；将缺失的稳定来源/尝试关联规范为明确记录。无法确定时保持阻断/待核查，不猜出“已发送”或重置失败预算。
- **旧资料 public/kind 推导。** 转换为显式 category、usage、enabled 和现行内容字段；旧私有、未确认或关闭资料不能因此自动对模型开放。运行时不再按旧 public 推断权限。
- **0.2.7 等旧空历史任务。** 将可确定的已有空读证据转换为现行等待活动状态，移除监测热路径的旧版本迁移分支；不重新遍历历史档案。
- **旧翻译凭据导入。** 当前有效共享连接转入规范 provider profile；删除每次启动/轮询查找更早私有凭据的回退。更早私有配置不自动启用，可保留旧文件供独立维护，不能输出密钥或继承更大数据授权。
- **WhatsApp 登录配置。** 用单一规范配置显式保存当前实际 partition 名、代次及归属；一次转换可保存原长分区名，不要求改目录或重新扫码。删除运行时反复读取 v1/v2 并按老公式推导的分支。新建短分区仍使用现有原生确认；配置统一不等于重建登录环境。

已完成并验证的转换才允许删对应 reader；未进入本版的转换保留必要现行读取。遇到不支持版本时明确拒绝并给出已验证的升级入口，不尝试多套猜测格式。离线升级器有明确输入版本及完成标记，不在正常业务热点反复执行。

### 10.3 从日常路径移出的历史能力

已存 accepted/unknown、原 operation、发送账本、采购确切请求 prompt/hash、有效 WAL、原图、客户消息和完整备份仍然是有效业务记录。将必要的旧回执解析或原请求核查收敛为只读模块，不能提供换键提交能力。

旧采购 prompt 形式只在原任务核查时解析；日常新任务只生成当前格式。更早工作区的 legacy-export 工具已有离线脚本调用，可从默认启动导入/默认发行闭包移出，当前备份恢复及历史备份原样保全仍保留。

当前 Accio 图片的 read_compat 解决的是原有接口没有原生附件参数的问题。按本次视觉 API 统一接待的设计，本版在多模态请求/证据路径通过验收后，删除接待专用工作区发现、临时图片落地、read_compat 运行分支和对应 read 工具提示词，不把它们保留为隐式回退。采购真实工具所需的 Accio 组件独立核对用途。宿主主 frame、商家/模式/数据根隔离、来源版本、unknown 防重与严格 schema 检查继续保留。

清理验收增加：旧规范升级幂等、升级中断可恢复、旧人工部分受理/unknown 保全、原分区名一致、旧私有资料不开放、无旧 DTO 回退仍可正常运行，以及无历史数据的新工作区正常启动。具体清理代码和迁移只在后续实施中执行，本轮未触碰真实数据。
