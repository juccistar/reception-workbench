# 0.4.0 代码检查报告

日期：2026-11-15。面向项目负责人、开发维护与验收人员。

检查基线：0.3.21，分支 `feat/natural-auto-replies-0.3.21`，提交 `c6be2c575a4d235ac2f1b42fa1ad035064c16740`。本报告配套 [0.4.0 开发方案](0.4.0开发方案.md)。

本次完成静态调用链检查及一个隔离的身份异常行为探针；没有实例化真实业务服务、读取商家业务目录、调用真实模型或平台、修改运行源码、构建或发布。未运行项目测试套件。以下“重复成本”是代码能够证明的工作量，不代表已测得其占据实际用户等待的比例。

## 1. 主要结论

1. 身份和存储隔离已有较完整基础：宿主主 frame / 页面来源校验、核验身份后打开卖家库、同商家跨目录排他、临时发送授权、来源版本保护及独立发送账本均应保留。
2. 确认一处身份失效处理缺口：`_ensure_identity` 遇到原生身份解析异常时直接抛出，未走正常返回不匹配时的暂停路径。隔离替身复现了该行为。现有原生发送还有独立身份和提交门控，本报告没有证明存在跨账号发送。
3. 数据层已使用 SQLite WAL、FULL 同步及 conversation/case JSON 表达式索引；主要问题是调用层重复加载、解析和投影。没有确认需要更换数据库或降低持久性才能优化的依据。
4. 启动有可测量的重复初始化：WhatsApp 两个 SDK 顶层加载；Python 维护入口在分派参数之前导入完整服务；连接检查串行等待公司资料及多次身份解析。
5. 图片分块每次重复解码、校验整张原图，快照和详情重复扫描历史，前端事件合并后仍重读快照与详情，适合优先优化。
6. 现有第三方模型仅承担聊天文字及有效人工建议的翻译。其他语言生成仍依赖 Accio，且与采购 AI 共用一个商家级执行槽。下一版需要任务路由和独立资源管理，单纯替换模型地址不足以解决排队延迟。

## 2. 身份校验与授权

### I-01：身份解析异常没有统一使当前核验失效（优先修复）

证据：

- [service.py:1924](../services/reception/src/reception_service/service.py#L1924)：`_ensure_identity` 直接调用 `facade.resolve_identity(self.seller_id)`；只有正常返回且 ID 不同时才 `_pause()`。
- [原生适配器 live.py:183](../services/reception/src/reception_service/integrations/accio_native/vendor/adapters/live.py#L183)：解析身份文件，发现卖家不符时直接抛 `AdapterError`。
- [LiveIntegration:30](../services/reception/src/reception_service/integrations/live.py#L30)：边界将原生异常转换为 `ServiceError`。
- [service.py:1531](../services/reception/src/reception_service/service.py#L1531)：普通任务异常分派没有通用身份失效处理，部分生成错误进入生成重试分支。
- [service.py:1955](../services/reception/src/reception_service/service.py#L1955)：重新连接检查有自己的异常失效处理，和普通任务路径不一致。

触发条件：已核验会话执行任务期间，原生身份校验发现不同卖家、无效身份或无法核验并抛出异常。异常仍会阻止该次调用继续，但服务的旧 `account_verified`、接待开关和 epoch 不由 `_ensure_identity` 统一更新。

本次探针使用真实 `_ensure_identity` 和 LiveIntegration 边界，以不含网络和数据访问的替身替代原生身份源；未构造 ReceptionService，暂停函数使用调用记录替身。结果如下：

| 路径 | 返回错误 | 暂停函数调用次数 | 旧状态 |
| --- | --- | ---: | --- |
| 原生身份解析抛 AdapterError | adapter_error，stage=identity | 0 | account_verified、running、auto_send、WhatsApp enabled 均保持原值，epoch=7 |
| 身份函数正常返回另一卖家 ID | seller_mismatch | 1 | 确认进入暂停分支；此对照不验证暂停函数内部行为 |

探针的 5 条断言通过，记录见 [检查记录](verification/0.4.0-plan-audit.json)。该结果证明局部异常路径未撤权，不代表完整平台发送越权已复现。

修复方向：建立明确的身份失效入口，处理身份异常分类、撤销两个渠道接待及采购授权、取消未提交生成、递增有关代次、发布失效状态；保全在途/unknown。用户正常暂停国际站与身份失效应区分，不能为此改变两个渠道日常独立开关的含义。适配器使用明确错误码和 stage，不能靠异常正文识别账号变化。

### I-03：重复身份解析可测量，但不能直接使用长期 TTL 缓存

一次连接检查先解析身份，再调用公司资料任务，随后调用消息同步；后两项分别再次 `_ensure_identity`。证据：[service.py:1946](../services/reception/src/reception_service/service.py#L1946)、[service.py:345](../services/reception/src/reception_service/service.py#L345)、[service.py:1981](../services/reception/src/reception_service/service.py#L1981)。每次原生解析还涉及 workctl 子进程和临时身份文件。

发送路径服务层及原生提交边界也会多次校验，且授权回调可重新构建完整上下文。优先复用同一短流程内的不可变计算；跨外部等待和实际提交保留新鲜核验。身份凭据失效必须绑定 seller、数据根、运行环境、epoch；不能用“几秒内检查过”直接证明可发送。

## 4. 存储与缓存

### D-01：已有索引和持久性设计，优先改调用方式

[repository.py](../services/reception/src/reception_service/repository.py#L25) 使用 WAL、FULL、事务和 JSON 实体；[storage_guard.py:23](../services/reception/src/reception_service/storage_guard.py#L23) 已有 kind+conversation_id、kind+case_id 表达式索引。`list(kind)` 仍会解析该类全部 JSON，`history=True` 会另写完整修订。

建议先消除重复读取、复用一次事务内投影、合并非关键统计写入。新增排序索引、表或 schema 时必须走显式版本迁移及完整备份，严格 schema 校验不允许随意给旧库加索引。WAL/FULL、原始消息、修订、账本和回执不能成为性能清理对象。

### D-02：快照与详情随历史增长重复计算

- [service.py:375](../services/reception/src/reception_service/service.py#L375) 每次快照读取会话、事项、任务、发件记录等。
- [reception_state.py:7](../services/reception/src/reception_service/reception_state.py#L7) 构建全局状态投影；[reply_pending:51](../services/reception/src/reception_service/reception_state.py#L51) 对每个会话调用 `_messages`，读取和排序完整历史。
- [service.py:512](../services/reception/src/reception_service/service.py#L512) 消息接口先加载所有消息，随后截取最多 200 条；详情默认显示 100 条，但存储层没有因此只读 100 条。
- [service.py:499](../services/reception/src/reception_service/service.py#L499) 详情先读取全部事项再筛选，已有按 conversation_id 的存储过滤可复用。

建议从请求内复用开始，再增加可重建的按版本投影和真正的数据库分页。必须逐项保持相同时间、空时间、游标归属、未读、未决操作和多事项状态语义。

### D-03：原图分块重复解码和哈希

[cached_media.py:79](../services/reception/src/reception_service/cached_media.py#L79) 每次 `_cached_image` 读取 Base64、完整解码并计算 SHA；[original_chunk:111](../services/reception/src/reception_service/cached_media.py#L111) 每块再次执行；[copy_chunk:162](../services/reception/src/reception_service/cached_media.py#L162) 即使已保留转换后的 PNG，也会重新校验整张原图。

按现有 256 KiB 分块推导，6 MiB 原图需要 24 块，加 describe 共发生约 25 次完整原图解码/哈希；这是代码工作量推导，没有计时。建议复用有界、短期、绑定完整来源引用和版本的传输会话：首读完整校验，逐块做轻量归属/版本检查，宿主收齐后核对最终 SHA。必须先保证所有资产写入/替换都有可靠版本失效，再省去块内完整哈希。

### D-04：上下文窗口有界，但读取阶段仍取全历史

[reception_context.py:84](../services/reception/src/reception_service/reception_context.py#L84) 加载全部当前会话消息并排序、逐事项查询来源，然后选择最近 50 条文字及窗口外明确依据。优化应先共用消息读取与证据查询，再做“取窗口 + 按 ID 补依据”。不能直接把存储读取改成最近 50 条，导致旧需求依据或关联图片丢失。

### D-05：前端有合并保护，还存在重复请求

[useWorkbench.ts:195](../apps/desktop/src/renderer/hooks/useWorkbench.ts#L195) 的序号防止旧响应覆盖；[事件处理:285](../apps/desktop/src/renderer/hooks/useWorkbench.ts#L285) 有 70 ms 合并。但合并后仍并行请求完整快照与当前详情，跨窗口突发或手动刷新还会重叠。

建议按变化域和会话归属刷新，同类在途请求合并；执行期间再有变化则在结束后补读一次。未知事件回退全量刷新。保留会话切换、后台断开、健康事件及时性及迟到响应保护。

### D-06：缓存命中统计反而触发持久写入

[translation_service.py:242](../services/reception/src/reception_service/translation_service.py#L242) 在读取命中译文时更新控制库 `translation_usage`。可将此类非业务计数在内存累计后有界批量刷新，和发送意图、accepted 回执、授权等关键写入分开。若统计改为允许异常退出丢失少量尾部计数，须在统计说明中明确；不能扩展到业务账本。

## 6. 仍待量测与验收

- 冷/热启动、维护预检、存储校验、恢复、首次快照和身份联网的分别耗时。
- 合成大历史下的查询次数、JSON 解析量、业务锁占用、图片解码次数与峰值内存。
- 实际商家网络下身份解析、消息读取、模型服务、提交与回执的耗时分布；必须在相应授权范围内另行验收。
- 新旧模型对自然一至三条回复、中文需求、证据、报价限制、多事项及图片语义的表现。
- DeepSeek、阿里云百炼、Anthropic 官方文档本轮抓取均因域名访问校验失败而未取得；本报告没有核实其最新型号、价格、参数或区域可用性。

当前结果足以形成实施优先级，不能据此宣称 0.4.0 已提速、真实模型效果通过或真实平台登录收发已验收。

## 8. 已确定的第三方视觉 API 设计前提

用户已明确接待使用具有视觉能力的第三方 API，并补充允许添加多个 API、接待与翻译分别选择；最新要求将模型配置移到启动台，为所有商家统一配置。0.4.0 采用本机同 Windows 用户共享的多配置列表及两个全局用途绑定，商家工作台不另存模型覆盖：接待选择视觉 API，翻译可选择独立的纯文字 API，也可明确共用同一配置。接待图文仍同轮调用，不在失败时自动回到 Accio 或借用翻译 API。具体接口、图片证据和验收见 [多模态调用设计](0.4.0第三方多模态API调用设计.md)。以上是方案修订，不改变本报告对当前 0.3.21 的事实描述。

多 API 方案同时限定：每个全局用途独立路由修订、每条配置独立能力/凭据修订；全局翻译变更使全部商家的旧翻译失效，但不取消独立接待；全局接待变更使全部商家的旧接待生成失效并撤销相关自动授权，共用 profile 变更影响所有引用用途。配置写入比较修订并原子提交，跨进程通知以外仍在调用/应用边界核对最新版本。身份、数据、启用范围和 grant 保持商家隔离，不因一次全局配置就全部开通。

译文按商家、profile 与语义版本隔离，翻译不外发图片或完整接待上下文。连接池按需创建，同 profile 复用、不同 profile 隔离，单业务进程总并发和内存预算不随配置数增加；同时启动多个商家仍可能增加服务商侧总用量，不能把单进程上限称为全机上限。现有翻译配置仅迁入翻译用途，冲突的旧选择须明确归一。启动台可用合成输入主动检查模型，不构造商家业务服务。此扩展没有执行真实 API 配置或调用。

额外确认了 WhatsApp 图片接入缺口：[宿主 DTO](../apps/desktop/src/main/whatsapp/host.ts#L21) 只传 body 等字段，[业务入库](../services/reception/src/reception_service/whatsapp.py#L198) 只对非空文字的新买家消息置 pending。因此仅替换 provider 不能获得 WhatsApp 图片接待；本版需要媒体元数据、同页面 SDK 读取、私有分块交付、原图缓存和账号/连接代次校验。纯图片新消息要建立真实来源，历史/metadata/媒体完成不额外触发新一轮。

### 10.1 静态内存估算与 SDK 限制

20,000,000 像素 × 4 字节约 76.3 MiB，仅为一份 RGBA。64 MiB 原图的 Base64 约 85.3 MiB；原字节、Base64、JSON 字符串及 HTTP 编码体同时存在时，视字符串表示约需 320–576 MiB，尚不含像素工作区、SQLite、SDK 和进程基线。此估算说明必须限制副本和按阶段预留，不代表运行实测。主方案的 16/32 MiB 可选缓存及 512 MiB Python 重载荷预算均为待校准初始值，不能宣传为进程 RSS 上限。

本轮只读核对本机安装的 whatsapp-web.js **1.34.8**：`src/structures/Message.js:516` 的 downloadMedia 完整 Base64 返回；`:549` 已有 downloadMediaStream，默认块 10 MiB，按 Blob 切片；`src/util/Injected/Utils.js:1129` 的 resolveMediaBlob 仍先通过页面下载/缓存完整 Blob。这些是锁定依赖的本地源码证据，不是线上接口验证。方案优先使用已有流式能力并调小块，补首块前/半途取消句柄释放；明确 SDK/页面内部的完整 Blob 仍需测量，不能把 IPC 分块称为端到端内存硬上限。实际包内接口还需候选验证。

### 10.2 收紧收益承诺与版本范围

- 移除无基线支持的 30%/50%/60% 提速承诺；以语义等价、工作量减少、内存/取消正确性为硬条件，先测基线再确定耗时目标。区分进程重启与 OS 缓存冷启动，模型完整结果与首次输出分开统计。
- 现行 Accio 图像接待已是同任务读取；新版收益应来自移除代理/工作区步骤、减少本地重复准备与排队，而不是假定“原来固定两轮、现在一轮”。
- 不强制双并发、跨请求大缓存、schema v3、额外拆包或全量历史规范化。退役热路径优先删；有效登录配置与历史账本 reader 只有在必要转换验证后才能移除。
- 真实 provider 能力验收增加预先固定的答案/图片顺序/结构化组合判据；使用量缺失记未知，图片和缓存费用按实际口径避免重复计数。图片准备、结构失败或超预算都不能静默改成无图自动回复。

本轮最终交付仍仅为方案、设计和检查记录；未改运行源码、未运行项目测试/性能基准、未访问真实业务数据、未调用模型或平台、未构建、迁移、安装或发布。
