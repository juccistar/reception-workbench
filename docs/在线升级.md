# Windows在线升级

本文介绍安装版的在线升级与发布规则；安装版本以程序窗口为准，公开版本以发行仓库实际 Release 为准。源码在独立私有仓库`juccistar/reception-workbench`维护，安装包和更新继续使用原公开仓库`juccistar/reception-workbench-releases`，见[项目约定](PROJECT.md)。便携版支持离线运行，不能执行在线安装。

安装版采用NSIS按Windows用户安装，并使用独立安装助手；工作区按商家选择，同一安装位置的升级有互斥保护。正式NSIS安装仍需独立验收。

## 1. 使用方式

当前安装版支持公开 GitHub Releases 或静态 HTTPS 更新源；便携版继续支持离线运行。

1. 正常保存并退出旧工作台，运行安装包。安装按当前Windows用户进行，业务数据继续使用原设置中的目录。
2. 0.4.0 普通双击进入启动台，可查看授权指引并复制当前安装位置的 Accio 启动命令，在目标商家的 Accio 授权环境中执行。已登记商家如仍有通过核验的运行窗口，可从启动台切回；新建业务窗口仍需受支持的授权启动。安装目录内的“授权启动接待.cmd”继续保留。
3. 打开“连接与设置 → 关于与更新”。输入公开GitHub仓库地址或静态HTTPS目录并保存；程序显示识别出的源类型。
4. 点击“检查更新”，查看新版本和说明，再选择下载。检查、下载和安装分别触发，普通退出不安装。
5. 下载完成后点击“安装并重启”，在原生确认框继续。程序处理未保存编辑、等待在途结果并完成完整备份后安装。
6. 更新后继续使用原数据目录与商家参数；重新核验Accio身份和读取，自动接待保持暂停，按正常流程恢复。

本项目发行仓库为[juccistar/reception-workbench-releases](https://github.com/juccistar/reception-workbench-releases)，可作为更新源。用户保存过的旧设置优先，包括显式清空；若界面仍显示其他源，请粘贴该仓库地址并保存。

更新源允许清空。地址不接受用户名/密码、查询令牌或片段，不承载客户消息或Accio凭据。GitHub源只支持公开仓库，客户端不需要GitHub Token。

## 2. GitHub 发布

发布人员在`juccistar/reception-workbench-releases`创建对应版本的Release草稿；使用GitHub CLI时必须显式指定`--repo juccistar/reception-workbench-releases`，不依赖当前源码仓库的origin。上传本次构建生成的安装包、blockmap和`latest.yml`，核对版本、签名、大小与哈希后再发布。不得手工改写元数据；业务数据、Accio 配置和发布私钥不属于发行附件。本地构建不自动上传或创建 Release。

## 3. 安装与数据保护

界面通过有限preload桥调用更新宿主，不能提交安装路径、命令、业务源根或重启参数。更新设置存放在固定宿主状态目录的`updates/settings.json`，独立于业务数据库和安装目录。

安装准备先冻结编辑，再检查/保存未保存内容。独立助手取得与现有数据管理相同的Windows命名互斥量，直到安装完成或取消退出，其他协作数据操作不能插入。旧后台正常关闭后，现有离线工具制作并校验完整备份，保留原操作、unknown、回执、图片和草稿，以及商品档案、需求引用和查询状态。旧记录没有商品字段时保持原样，不因升级批量重跑历史 AI 或把空链接当作未查询。

安装助手只处理已下载并验证的安装包。启动前再次核对发布签名绑定的SHA-512，将安装器从挂起状态加入Windows作业对象后运行，等待全部子进程结束、核对目标安装标记，再释放数据管理锁并启动新版。

Accio环境只在进程内继承，不写入升级设置、命令参数或恢复记录。持久化的辅助文件只包含版本、路径、校验值和非敏感参数。更新后不恢复旧自动发送授权。

## 4. 失败处理

- 检查或下载失败：继续使用当前程序，可重新检查或下载。GitHub仓库还没有正式Release或缺少更新附件时，会提示检查公开状态和正式版本。
- 取消确认或继续编辑：保持当前程序，尚未关闭后台或安装。
- 备份失败：取消助手并等待锁释放，再重新打开原工作台；原目录和已有备份保留，自动接待暂停。
- 安装器校验或安装失败：只有确认没有其他同安装位置实例，且旧版本标记、EXE、app.asar、后台EXE以及统一启动脚本和策略文件均完整时，才自动打开旧版；进程查询失败或组件变化时显示恢复提示并保留结果。
- 数据格式升级：沿用启动前兼容预检与完整备份。回退程序不等于回退数据库，不能丢弃较新的发送防重记录。

较旧安装版可能无法自行完成升级；如遇安装准备失败，先完整备份并正常退出所有旧窗口和后台，再按维护人员确认的安装包手动升级。保留业务数据，不以删除数据库解决升级问题。

## 5. 发布签名与下载来源

每份更新元数据由构建机上的稳定Ed25519私钥签名。安装包携带固定公钥，核对应用标识、版本、唯一安装包名称、SHA-512和字节数，再允许下载/安装。

静态HTTPS目录仍要求请求及重定向同源。GitHub模式使用公开仓库provider，仅允许该仓库的Release路径和列明的GitHub附件HTTPS下载域名；不接受HTTP、任意跨站跳转或客户端令牌。员工电脑需要能访问GitHub及其附件下载域名。

私钥保存在构建机的`%LOCALAPPDATA%\AlibabaReceptionWorkbenchReleaseKeys`，不进入Git、安装包、更新源或日志。发布人员应单独备份，未来版本沿用同一密钥，缺失或损坏时不能静默换钥，也不能按构建缓存清理。

Windows Authenticode证书签名与发布签名分别记录。安装包的Windows证书状态应按实际文件核验；Ed25519验证更新来源，不替代Windows对发布者的系统信任。

## 6. 开发端构建

预置本项目GitHub源的候选构建：

```powershell
npm run package:release -- --candidate --output relase/release-next
```

输出目录必须是新目录。下一个版本先同步工程及后台版本，完成回归、候选窗口及安装验证，再使用新目录构建与发布。可将`--update-url`改为实际静态HTTPS目录；不指定时由安装后的使用者填写。

候选包含便携目录、ZIP、NSIS安装包、SHA-256、release-feed及发布清单，不会自动上传或切换本机默认入口。GitHub应在草稿中完成所有附件上传后再发布；静态目录应先上传安装包和blockmap并校验，最后上传latest.yml。

实际公网检查、下载、首次安装及连续版本升级分别留证。合成provider验证和本机HTTPS传输不能替代已发布版本的公网升级验收。
