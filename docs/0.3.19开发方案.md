# 0.3.19开发方案：WhatsApp连接诊断、登录页保留与实际环境验收

日期：2026-11-14。面向开发、维护与验收人员。

状态：0.3.19开发实现、定向回归、源码构建与隔离验收已完成；57项桌面、32项后端定向用例、1项SDK资源用例及类型检查通过。真实Demo窗口6张截图与两组公共扫码页的遮媒体截图已逐张查看，普通冷启动及SDK受控故障后均持续观察二维码超过60秒并覆盖刷新。公开发行仍为0.3.18，本次未打包。实现说明见[版本说明](0.3.19发布说明.md)，实际结果见[验证记录](verification/0.3.19.json)。实际商家连接故障尚未复现，不能视为已修复。

## 1. 本版目标

继续使用左侧独立WhatsApp模块、原始WhatsApp Web、一个Electron WebContentsView和同页面SDK。保留当前商家隔离的持久会话与真实Chromium标准标识。

本版完成三项工作：

1. 将“初始化失败”定位到确切步骤，留下可以核对的脱敏异常记录，并依据记录修复实际原因。
2. 分别管理原始页面和SDK连接。SDK失败时关闭程序自动接待，允许有效的原始登录页继续加载和展示。
3. 加强发行宿主冷启动、二维码持续展示及实际商家启动环境验收，避免仅凭公共扫码夹具通过就认定用户故障解决。

本地旧格式接待数据已按用户授权完成一次性清理，并核验完整备份、有效新版需求及发送记录保全。这项维护已结束，**0.3.19不加入旧数据清理、自动迁移或反复重置事项的代码**。

## 2. 事实与尚未确定的部分

| 项目 | 已确认的范围 |
| --- | --- |
| 实际反馈 | 进入WhatsApp登录页后，二维码尚未正常显示便中止，界面提示“初始化失败，请重新连接” |
| 安装内容 | 已安装0.3.18的应用、SDK归档及后台文件与正式发行输入一致 |
| 错误信息 | 界面对应通用SDK错误，当前没有保存足够的阶段及异常类型信息；不能据此确定具体根因 |
| 当前失败处理 | 宿主初始化异常经固定错误码转换后退役连接，释放SDK/CDP并调用WebContents.stop；这会同时中止尚未完成的页面加载 |
| 隔离对照 | 发行包宿主代码与包内SDK在全新临时会话中冷启动成功，SDK注入完成，原始二维码可见并持续等待15秒 |
| 验收缺口 | 原扫码夹具含CDP预热，并在首次二维码事件后结束；没有覆盖实际商家启动环境，也不足以证明后续页面持续可用 |
| 需求问题 | 已确认的客户案例属于旧格式事项兼容问题；目前没有证明干净数据上的首次需求整理存在同样缺陷 |

不能把旧数据直接定性为恶意或损坏数据，也不能把WhatsApp错误预先归因于缓存、账号限制、网络或安装包缺失。隔离环境通过只作为对照，实际异常须由新诊断与复现确认。

## 3. 保持需求增量规则

本版保持现有接待语义：

- 只有确需建立或更新需求时，AI输出requirement_changes；无变化不重写正式需求。
- 有效ai-v1需求、原始聊天、业务补充、摘要、发送操作和采购关联仍各自保存。
- 不添加“需求为空就强制建单”“每次生成都重新整理需求”或“每轮自动迁移旧事项”的规则。
- 不因为旧事项问题调整正常新客户的建单、事项归属、闲聊保护或发送条件。
- 不依据清理后的事项为空，自动触发历史客户的AI生成或回复。

使用干净合成资料回归首次需求建立、无变化不更新、旧事项引用和闲聊不建单；合成结果只证明程序契约。若干净数据另有可复现缺陷，应单独写明证据与修正范围，再调整对应逻辑。

## 4. 连接阶段与受限诊断

### 4.1 记录当前步骤

连接过程划分为固定阶段：

| 阶段 | 记录的步骤 |
| --- | --- |
| 视图准备 | 创建视图、设置专用会话标识与安全限制 |
| CDP连接 | 调试连接建立、实际浏览器版本读取、取得同一页面 |
| 登录导航 | 主文档响应、允许的最终来源及导航完成 |
| 应用准备 | 受支持页面识别、SDK所需模块可用性 |
| SDK注入 | 认证适配、版本缓存准备、注入与事件绑定的受控步骤 |
| 等待扫码 | 原始二维码是否实际可见、SDK是否已产生二维码事件；两项分别记录 |
| 认证与就绪 | 认证事件、ready及账号与连接代次核验 |

阶段开始、完成和失败均绑定本次连接尝试。记录观测时间及单调计时得到的阶段耗时；正常等待扫码不按总连接时长判失败。

保留0.3.18已有的导航、模块、SDK和认证后ready阶段预算，以及HTTP 429的Retry-After等待。先定位具体失败步骤，不通过无条件扩大所有超时掩盖异常。

### 4.2 异常分类

在关键await边界保留原始异常供内存内分类，再转换为受限记录和界面状态。至少区分CDP/协议失败、资源缺失、页面执行上下文变化、网页模块未就绪、SDK注入失败、阶段超时、页面退出及HTTP/网络/TLS失败。

已有明确错误码继续沿用。未分类异常须保留固定阶段、异常类型和诊断编号，不能全部只剩一个sdk_error。页面普通console或pageerror不能单独作为连接失败依据；只有归属当前连接关键步骤的异常才改变连接状态。

覆盖初始化返回后的本代异步回调、页面重新导航和调试连接退出。旧连接的失败或超时不能改写新连接结果，也不能停止新页面。

### 4.3 本地日志

宿主在当前商家私有诊断目录保存whatsapp-host.jsonl，采用2 MiB×3份轮转，并对重复故障限频。日志失败不得再次中断连接清理。

可记录：时间、连接尝试编号、阶段、耗时、固定错误码、HTTP状态、异常类型、受限文件/函数/行号、应用与Electron/Chromium/SDK版本，以及必要的页面可用性布尔检查。

不记录：聊天正文、联系人、手机号、账号标识、提示词、二维码及其内容、Cookie、Token、Key、完整请求头、带参数的URL、页面HTML、局部变量或原始异常全文。堆栈路径规范为程序内相对位置，不转存原始stderr或浏览器日志。

诊断目录由宿主根据当前业务根和商家归属计算，renderer不能指定路径。诊断不能替代提交账本及回执，也不作为自动重发依据。

## 5. 页面与SDK分别管理

### 5.1 状态含义

保留现有SDK状态；在宿主DTO中增加可选的page_state、phase和diagnostic_id，具体枚举在shared契约中统一。

- 页面状态区分正在加载、原始页面可用、页面错误和已关闭。
- SDK状态继续区分连接、等待扫码、认证、就绪及失败。
- 网页可用不等于账号已核验或自动接待可用。
- 只有SDK ready且账号、连接代次、AI能力及当前授权均有效，才能开启自动接待。

同步核对shared DTO、main、coordinator、preload和WhatsAppPage。沿用专用宿主桥，不增加任意脚本、CDP命令、控制台或文件接口。

### 5.2 SDK失败后的处理

当主文档已确认来自允许的HTTPS来源，且失败属于SDK接入阶段时：

1. 立即撤销WhatsApp自动接待授权，退役本代程序消息消费与提交能力。
2. 取消本代注入任务，释放SDK监听、计时器及CDP连接；保留原发送操作和确切回执。
3. 不因SDK失败调用WebContents.stop或销毁有效原始页面，允许登录页继续完成渲染及二维码展示。
4. 核验部分注入留下的回调不会持续触发旧SDK任务。不能仅去掉stop而保留失控的注入或监听。
5. 页面存在但尚未完成加载时，继续显示加载状态；SDK失败也不将二维码事件当作原始二维码已可见。

页面本身发生HTTP错误、TLS失败、离开允许来源、渲染进程退出或被关闭时，按对应页面故障处理，不宣称原始网页可继续使用。导航限制和权限拒绝在SDK退役后仍由视图生命周期持有。

普通断开和重连保留登录资料。首次排查不自动清空partition、Cookie或登录目录，不复制个人Chrome资料，不建立第二浏览器。失败后由用户明确重连，不循环重新注入；429等待期内仍不能发起新请求。

SDK故障只影响WhatsApp通道；独立后台执行器健康异常仍按0.3.18规则处理两通道授权，不能混淆两类故障。

### 5.3 界面反馈

正常流程保留“正在加载登录页”“请扫码”“正在加载聊天”“已连接”等简短状态。失败时按实际情况显示：

- “网页仍在加载，自动接待初始化失败”。
- “原始页面可用，自动接待未就绪”。
- “登录页请求失败（HTTP状态）”或对应网络、超时提示。

失败详情按需展开，显示阶段、固定原因和诊断编号，不在聊天区增加常驻技术说明。原始页面可用时可由用户手动操作；SDK未就绪时自动接待按钮停用，不声称程序仍在监测该页面的全部消息。

宽窄窗口、侧栏、抽屉及模态遮挡继续使用同一视图，原始页面不得覆盖工作台控制区。切换模块不应冻结页面脚本。

## 6. 依据实际异常修复

先完成诊断和失效处理，再收集实际失败步骤：

1. 在临时空会话上执行无预热的首次连接，并使用受控故障验证诊断是否覆盖每个关键步骤。
2. 在最终发行宿主及SDK归档上复测，核对原始二维码可见、SDK事件和注入任务正常结束。
3. 在明确授权的实际商家启动环境中，由连接诊断记录本次失败阶段；读取受限诊断不扩大为导出登录资料或聊天内容。
4. 针对确切异常作最小修正，并使用相同条件复测。

没有实际异常证据时，不预先升级SDK、切换真实Chrome、增加自动化隐藏插件或修改浏览器指纹。仍使用真实Chromium标识和当前固定SDK版本；依赖变更只有在复现证明必要时单独记录理由与归档回归。

若实际商家故障仍未复现或未通过复测，交付记录应明确“诊断与展示改进完成，实际连接故障未验收”，不能写成“WhatsApp已修复”。

## 7. 保留发送与业务边界

- WhatsApp仍覆盖当前账号全部入站单聊；国际站绑定可选，仅提供只读背景。
- 历史及联系人metadata不触发回复或人工接管。
- 提交前持久冻结账号、连接代次、目标与正文；同会话未决发送保持互斥。
- 确切消息ID及ACK>=1才能受理；unknown只核查原operation，不换键、换通道或按同文重发。
- SDK失败、断线、账号变化及重启撤销对应授权；重新就绪不自动恢复接待。
- 原始页面手动操作与程序自动发送分别处理，不能用原始页面可用推断程序提交能力正常。
- 国际站接待、人工聊天、后台健康保护及需求增量规则继续沿用，不混入本版WhatsApp问题的修复。

## 9. 定向验证与验收条件

| 验收项 | 通过条件 |
| --- | --- |
| 阶段诊断 | 在关键步骤注入故障后，阶段、错误分类及诊断编号一致；日志没有敏感标记或原始异常全文 |
| 首次连接 | 无CDP/SDK预热的临时空会话能够加载；二维码须在实际可见页面中出现，不能只检查qr事件 |
| 扫码等待 | 原始二维码与SDK状态至少持续观察60秒，覆盖一次刷新或等价受控刷新；不在首次qr事件时立即关闭夹具 |
| SDK尾部 | 记录inject完成及其后的本代回调；首次qr之后的异常不会被提前结束的脚本漏掉 |
| SDK故障降级 | 可信页面在SDK故障后继续加载或保持可用，原生安全限制仍有效；自动接待已撤权，旧任务不再控制页面 |
| 页面故障 | HTTP、TLS、不允许的导航和页面退出有确切反馈，不误报为正常扫码页面 |
| 重连与退出 | 连续点击不产生第二连接，旧超时与旧异步结果不污染新连接；普通退出不清登录资料，429仍等待 |
| 发送证据 | 故障发生在提交前后时，原operation、unknown及确切ACK证据保留，未新增提交或恢复授权 |
| 界面 | 正常、页面可用但SDK失败、页面失败三类状态在宽窄窗口和遮挡场景下正确显示，截图逐张查看 |
| 需求回归 | 干净数据首次建立有效需求、无变化不重写、闲聊不建单及原事项关联继续成立；没有新增旧数据清理或强制建单逻辑 |
| 实际环境 | 明确记录实际商家启动环境是否复现、确切失败步骤及复测结果；公共扫码不能替代实号登录与收发验收 |

定向优先覆盖whatsapp-connection、whatsapp-transport、whatsapp-host-lifecycle、whatsapp-coordinator、whatsapp-ledger、whatsapp-page及SDK资源闭包测试；新增必要的诊断保密和日志失败用例。需求仅回归相关既有用例，不以本版为由运行全部后端测试。修改契约后执行类型检查，按影响范围构建与窗口验证；全量测试仍须用户明确指定。

## 10. 实施与交付

1. 补齐阶段与受限诊断，确保异常可以定位且不会泄露内容。
2. 分离页面与SDK退役行为，补齐取消、重连和单视图限制用例。
3. 完善界面状态及冷启动、持续扫码验收驱动。
4. 在可复现环境定位具体异常，完成对应修正并复测；无法复现时如实记录。
5. 更新0.3.19版本说明和验证记录。实施进入版本构建时，每次构建完成立即创建中文commit，保存相关源码、测试及可提交记录。
6. 若进入候选打包，使用新的空输出目录；核对最终宿主代码、SDK归档、完整ZIP及固定更新签名。发行宿主验收须使用包内宿主代码和SDK，不能只重新编译一份源码宿主；若夹具替换了启动入口或业务身份来源，必须明示其范围，不能称为真实商家窗口验收。
7. 本次已按“开始开发”实施源码开发、定向测试及隔离验收，构建完成后立即本地提交。打包发布、安装替换、默认入口晋级、真实账号登录和收发仍分别按明确授权执行，本次不执行，也不再次清理业务数据。
