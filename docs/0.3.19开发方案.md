## 2. 需求处理：该建则建、该补则补、无变化不重写

比较本轮可见的有效原文与已保存requirements、case_catalog。case_catalog是同一客户会话已有采购事项目录，供匹配不同采购；有事项或摘要，不等于正式需求已经完整记录。

| 场景 | 本版处理 |
| --- | --- |
| 新的一笔真实采购 | create新事项，保留其他事项；同商品的另一笔独立订单也可新建 |
| 需求已在对话中提出，但尚未建档 | 有本轮可见依据时建立需求，或补入对应原事项 |
| 旧需求遗漏数量、地址等字段 | update原事项，仅补有依据的字段 |
| 更正数量、交期、规格等条件 | update对应字段，用当前有效条件替换被更正部分，不混成两个同时有效的条件 |
| 规格字段已有尺寸、材质，仅追加或修改颜色 | 更新该字段时保留仍有效的尺寸、材质，不能把整字段缩减成只有颜色 |
| 纠正旧AI归纳错误 | 可依据本轮可见原文修正，不要求客户重新发一条更正消息 |
| 撤回某个条件而没有替代值 | clear_fields附真实撤回依据；普通空值不能用于清空 |
| 已撤回的字段为空 | 不当作遗漏，不因为早期肯定原文还在就补回 |
| 一轮既更正旧事项又新增另一采购 | 分别update/create，按case_ref归属，不混用条件 |
| 无变化、只聊天或重复生成 | 省略requirement_changes，不重写整份需求、不增加正式需求修订 |
| 归属不明确 | 自然澄清或在会话摘要保留未决内容，不猜事项 |

程序继续使用现有create/update/clear_fields主结构、事务、版本及来源校验。AI决定真实需求与事项归属，程序不因表单为空自行建单，也不使用关键词替代业务理解。

整笔采购取消或暂缓与撤回某个字段、停止联系分别理解。本版准确保留原意及历史，不新增整笔采购取消/暂缓的独立状态流程；不能把字段clear称为已完整支持采购取消，也不能据此清空整份需求或反复补回已撤回条件。

## 3. 最近50条窗口与旧需求保护

- 最近50条指普通文字消息，不是50行文本，也不是需求的有效期。
- 已保存requirements和case_catalog独立进入上下文；有明确引用的窗口外本地原文通过historical_evidence补入。
- 原文未出现在最近50条，不构成撤回、清空或重新归纳已有字段的依据。
- 有明确补充、更正或撤回时，仍可更新旧字段，不把旧需求一律锁死。
- 未列入增量的字段保持原值；空值不清空；复合字段保留未变部分。
- 输入超预算时明确失败，不静默丢弃证据后继续修改。

对于“从未建档、原文已超窗、没有引用关联”的历史需求，本轮可能不可见。本版不声称仅凭提示词就能补齐全部历史，不自动扩大每轮窗口或扫描全历史；受控历史整理需要另行确定范围。

## 4. 提示词的具体替换

修改docs/接待提示词审核稿.md，经scripts/sync-reception-prompts.mjs生成静态模块，提示词版本更新为reception-0.3.19。运行时继续只读静态模块。

### 4.1 区分回复目标与需求依据

P02自动接待开头替换为：

> 只处理宿主指定的当前客户，回复针对reply_target及最新有效买家消息；摘要和需求结合本轮提供的会话，需求按变更模块处理。按case_catalog确定采购事项归属，宿主负责权限、来源版本和实际发送，你不能改变授权或宣称已执行。

“真实新采购才建立新事项”调整为“尚未建档的真实采购才建立新事项”，覆盖前文已经提出但尚未记录的采购。

P02-A共用需求模块首句替换为：

> 结合本轮提供的有效对话与requirements、case_catalog，补建尚未记录的需求，或补入对应原事项；已记录且无变化时省略requirement_changes，不复述整份表格、不只为换中文说法而更新，不因本轮未重复提及或原文未入窗口而撤回、清空或重写已有字段。

在原字段与撤回规则内分别补充：

> 补充或更正同一字段时，保留其中仍有效且未改变的条件。

> 已撤回的条件不因补录而恢复。

规则集中在共用模块，不在自动接待和人工建议中重复堆叠。

### 4.2 商品ID严格只做指定删除

原商品段落仅删除“平台商品ID及”，修改后为：

> 原始聊天中的链接只能帮助识别指代，页面标题、属性、价格、库存、交期或Custom Logo字样不能证明客户需求或本店经营能力。空字段和重复看到商品ID都不授予查询权限。

其余原文保留，不增加关于ID如何判断、选择或排除的新句子、提醒、解释和示例。

### 4.3 自然短消息表达

在P01现有“对话与进度”中合并相关表达要求：

> 用自然简短的聊天口吻，先回应客户当前问题，不机械寒暄、复述已知需求或堆叠流程话术。简单内容一条即可，多个独立意思可分条，不为凑条数拆分；价格、适用条件和必要限定放在同一条，不拆成易误解的片段。

客户语言、有效风格资料、事实与承诺边界继续保留；需求在内部完整保存，对客不必把整理结果全部复述。每轮提问上限仍按整轮计算。

## 5. AI输出改为真实消息列表

自动接待、普通人工建议及WhatsApp使用reply_messages数组。每项为body与本条reply_sources，顺序即发送顺序；按需1至3条非空消息，整轮正文合计最多1200字符。条数上限不要求每次凑够两条或三条。

| 任务 | 输出 |
| --- | --- |
| 国际站自动接待 | action、reply_messages、conversation_summary，按需requirement_changes、reply_case_refs |
| 国际站普通人工建议 | reply_messages、conversation_summary，按需requirement_changes、reply_case_refs |
| WhatsApp自动接待 | reply_messages、wa_summary，不反向修改国际站需求 |
| 正文润色 | 原reply、reply_sources，处理冻结正文，不自行分条 |
| 内部需求整理 | 原需求变更与摘要，不生成对客消息 |

国际站action=skip时reply_messages为空，仍可保存有依据的需求补录。一次AI任务只更新一次需求与摘要。

模型直接确定消息边界；程序不按空行、标点或字数硬拆，不额外补寒暄。旧单条持久化记录兼容读取，不改写历史操作或已受理账本。

## 6. 代码与发送链路

### 6.1 输出、校验和草稿

新增reply_messages.py统一消息列表结构、总长、来源和顺序指纹。Live、Demo及两渠道复用结构处理，正文校验按各自渠道执行；国际站逐条及整轮执行原有正文和来源格式校验。某条不合格时整轮不进入发送，不截断后继续发。形式校验不证明事实、承诺或需求理解的语义正确。

AI草稿保存有序reply_messages；body是用于展示、复制和整轮翻译的组合文本，真实发送以冻结列表为准。消息顺序、正文、来源或数量改变都产生新版本。结构校验不能替代真实语义验收。

### 6.2 整轮冻结、逐条操作

新增reply_batches.py管理一轮多条的冻结、进度和取消；国际站reply_batch与WhatsApp的wa_reply_batch分别保存，沿用原SQLite实体体系。

发送前以事务保存完整消息清单、稳定part_id、来源指纹、草稿版本及顺序；当前条目独立创建operation。前一条取得确切accepted证据后，下一条才进入现有队列。

整轮保持同会话互斥，每条提交前复核当前授权、身份、连接代次、原来源、接管/停止状态及业务版本。检查沿用本地业务依据，不恢复发送前历史重读或Ready/Seal前置。

自身已受理消息及相应本地修订归属于本批次，不能使下一条误判过期；客户新消息、人工回复或依据变化则停止尚未提交的尾部。保留现有公平调度，不用阻塞循环或sleep执行整轮。

### 6.3 防重、回执和恢复

- 每条独立平台消息ID及回执；WhatsApp继续要求确切ID且ACK>=1。
- 任一条unknown，后续停止，只核查该条原operation，不换键重发。
- 受理后逐条写入真实聊天历史，全部受理后才结算整轮待回复和补充续答。
- 国际站原生来源逻辑键同步支持同一冻结批次的后续条目，核对消息清单与前序受理证据；旧版accepted/unknown仍阻止另起批次绕过防重。
- 国际站明确未提交的暂时错误按稳定逻辑条目保留三次总尝试与5秒/15秒退避，新job或草稿不能重置；WhatsApp不新增自动重发。
- 重启撤权、保全已受理及unknown，停止未提交尾部，不自动重播或续发旧尾部。
- WhatsApp宿主继续一次sendMessage、一份单条账本，批次由Python管理，原完整备份边界保持。

### 6.4 修正需求补录的闲聊拦截

service.py目前在最新消息被判为闲聊后清空requirement_changes与reply_case_refs。解除对这两项的一律清空，让有依据的补录进入原事务与来源校验；闲聊本身不强制建单，停止联系与发送授权保护继续保留。

## 7. 人工建议、编辑和进度展示

建议仍在输入框上方的待处理框显示，按顺序分块预览，提供采用/弃用，处理后关闭。采用多条建议后可独立编辑、删除某条或合为一条；普通手写保留单条入口，不增加AI或采购前置。

人工编辑保存message_parts及组合body，并校验二者一致。人工单条原50000字符预算保留，多条按整轮50000字符、最多三条校验。分条编辑中的润色只作用于当前选中、冻结的一条，不改其他条目或重新分条。

发送时冻结整轮版本，期间新输入保存为新编辑版本。回执不能清掉新输入或重新打开已处理建议。界面显示“已发送1/2条”“第2条结果待核查”“剩余1条已停止”等简短进度，核查针对原发送条目，不提供重发整轮按钮。

真实聊天按各自平台消息和时间显示。WhatsApp继续展示原始网页，不另造聊天列表。中文翻译保持段落顺序，仅供查看，不改变发送正文或分条边界。

## 9. 已完成的WhatsApp基础继续保留

继续单个WebContentsView与同页面SDK、真实Chromium标识、商家隔离的持久登录会话，不增加第二浏览器。

已实现的固定连接阶段、固定错误分类、商家私有2 MiB×3份脱敏日志、旧回调清理和即时宿主状态继续回归。日志不记录原始异常全文、聊天、账号、二维码或凭据。

SDK失败时退役程序接待并保留可信原始页面；HTTP/TLS、关闭和不可信导航仍按页面错误处理。普通断开保留登录资料，429继续遵守Retry-After。公共扫码冷启动与SDK故障后持续观察超过60秒的检查保留；实际商家故障与实号收发仍未验收。

## 10. 验证与实施顺序

需求验证覆盖：首次建档、旧需求补充/更正、同字段未变条件保留、撤回不恢复、旧AI错误修正、同商品不同订单、同轮多事项、50条窗口滑动、闲聊时补录、无变化和重复执行。

发送验证覆盖：真实条数和顺序、逐条来源、单条校验失败整轮不发、部分成功/unknown、提前ACK与自身回显、中途客户或人工消息、授权变化、原生来源防重、重启及旧单条账本兼容。

页面验证覆盖：分条预览与采用、编辑/删除/合并、当前条目润色、发送期间继续输入、跨会话切换、迟到回执、宽窄窗口与实际截图查看。真实AI语义和真实平台多条收发分别记录，不以合成回归替代。

实施顺序：

1. 修改并生成提示词，完成消息契约和需求补录入口。
2. 完成共用批次与国际站普通/续答的逐条认领和受理。
3. 完成WhatsApp逐条推进、回执与恢复，保留宿主单条账本。
4. 完成人工建议、编辑、单条润色和进度展示。
5. 运行相关定向测试、类型与提示词一致性检查，不运行未经明确要求的全量测试。
6. 源码构建成功后立即本地中文commit，纳入源码、测试、文档及可提交验证记录；随后实际窗口检查并保存结果。

用户已明确要求开发完成后直接打包上传。完成定向回归、构建提交和实际窗口验收后，按草稿上传、附件核验、正式发布及匿名下载核对执行；实际完成状态以验证记录为准。安装替换、默认入口晋级、真实AI及客户发送不在本轮范围。
