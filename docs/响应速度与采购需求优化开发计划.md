# 0.3.10 响应速度与采购需求优化开发计划

日期：2026-11-12。基线：已公开的 0.3.9。本计划对应历史公开版本0.3.10，已完成当时的定向验证、打包及公开附件核对；后续0.3.11需求展示、业务补充跟进和图片边界另见[新版实施方案](需求展示与自动跟进状态开发方案.md)。

读者：项目负责人、接待业务员、开发及验收人员。本计划所列主要改造已进入 0.3.10 源码；实际实现和验证以[本版说明](0.3.10发布说明.md)、[验证记录](verification/0.3.10.json)及源码为准。第2节保留立项时对0.3.9的检查结论，第7节的建议并非全部已实施；不以合成测试或既有耗时推算真实接待速度。

## 1. 本版目标

1. 缩短新消息发现、排队和答案生成后的发送等待；让同步、人工操作及需求查看不被一次慢 AI 查询堵住。
2. 提高需求采集的准确性和可修正性，区分明确要求、询问、备选、否定、冲突及来源变化。
3. 让业务员在客户页、待报价、客户资料三个入口看到一致、直观且有来源的需求。
4. 取消本轮原图读取“最多四张”的固定限制；同时保留资源预算、实际读取证据和来源归属。
5. 统一审查可调限制，普通设置只暴露业务员常用项，高级设置集中管理容量与超时。

继续使用 Accio 完成自动回复与需求采集，同一轮自动任务合并输出，不增加常规的独立需求模型、图片识别报告或发送前模型复核。第三方模型继续只承担现有聊天及有效人工建议的中文翻译。每次生成独立组装上下文，不增加长期客户 AI 会话记忆。

## 2. 源码检查结论

| 已核实的现状 | 对本版的影响 |
| --- | --- |
| 正文同步、自动生成、人工建议及发送共用一个业务 worker；已就绪的自动发送仍追加到公共队列末尾 | 存在可减少的排队开销；单纯调低轮询时间不能解决全部问题 |
| 活动监测先读首屏、再读可选续页，最后统一派发正文同步 | 首屏的新客户可能额外等待一次续页调用 |
| 自动生成未接入按任务取消，主要在结果返回后拒绝过期结果 | 人工接管、暂停或来源变化后，旧 AI 查询仍可能占用执行通道 |
| 最近文字取 20 条，另补必要事实原文和最多 8 条相关旧原文；原始消息与 message_view 同时进入模型输入 | 有减少重复输入的空间；不能通过丢失关键依据换取提速 |
| 图片候选、上下文、调用器和回执校验均存在四张限制，回执还有最多 14 行的固定限制 | 必须联动修改，不能只删除取图处的切片 |
| 需求是九个固定事实字段，规格与定制主要为字符串；三个页面展示规则不完全一致 | 需要统一展示、细化语义，并保留旧数据兼容 |
| 原文更正时只清理当前采购事项的相关事实，旧待报价事项也可能引用被更正的消息 | 来源失效必须覆盖同会话所有受影响事项 |
| 冲突事实可能被后续同值提取重新覆盖为 confirmed | 需要保留候选、冲突状态与明确的解决记录 |
| Assistance.tsx 已有协助处理表单，但没有在当前主界面挂载 | 属于需要先补齐的功能入口；0.3.9 对该界面完成状态的说明不准确，组件测试不能替代主界面入口验收 |

现有 `confirmed` 表示提取值通过买家原文等程序校验，不代表业务员人工复核、商家接受条件或双方已经达成交易。

## 3. 响应速度改造

### 3.1 先补一轮任务的耗时记录

关联活动发现、正文同步、生成、发送及界面更新，记录：

- 摘要发现时间、正文同步排队及读取耗时。
- 合并窗口等待、生成排队、上下文组装、原图准备及每次身份读取耗时。
- Accio 查询开始、完整结果可核实、来源是否仍有效。
- 发送入队、提交开始、确切消息编号确认、accepted 或 unknown。
- 后端结果落库到界面展示对应版本的时间。

分别统计文字、多图、缓存命中、首次取图、空闲和积压场景；成功、失败、取消、stale 和 unknown 分开。显示实际样本数，样本不足时不宣称稳定的分位耗时。诊断只保留阶段、耗时、数量、版本、结果及关联标识，不保存完整聊天、prompt、签名 URL 或凭据。

阶段内用单调时钟；跨进程通过关联标识和事件序号对齐，不能直接相减不同进程的单调时钟。平台消息时间与本地发现时间可能存在时钟差，应单独标注。

### 3.2 调整调度顺序

- 首屏活动落库后立即派发正文同步，摘要续页随后处理。
- 任务边界优先处理有保护条件的人工发送、回执核查及已就绪自动发送，避免答案完成后继续等待其他客户生成。
- 当前活跃客户的新消息优先于旧历史补读、非必要公司资料刷新和预览预取；加入公平调度，旧任务不能永久饿死。
- 每会话、每来源只保留必要的活跃生成；调用前淘汰已被替代的人工建议和过期生成。

调度优先不代表可以绕过尚未完成的来源同步、同会话未决发送或授权校验，也不能把发送任务插入已经进行的原生提交过程。

### 3.3 将 AI 等待移出唯一业务写入通道

采用“业务协调者冻结输入 → 请求执行槽等待 AI → 协调者复核并应用结果”：

- 业务协调者保持唯一状态写入顺序，负责事务、版本、授权、发送互斥和结果应用。
- AI 请求有独立 request_id、诊断、取消事件和结果容器，不能并发共用 facade 的 last_request 等可变字段。
- 初版每商家保持 1 个 Accio AI 执行槽；AI 等待期间允许必要正文同步、本地操作和符合条件的发送继续。
- 图片受控 HTTPS 下载和解码使用独立的有界执行池，建议同时 2 项；原生来源读取保持自身关联和顺序，不把非线程安全的原生适配器直接并发使用。
- Accio AI 并发 2 仅作为高级能力候选，须先验证原生接入是否支持、是否实际并行及请求结果不会串联；未经验证不开放普通设置。

接管、暂停、明确来源失效及同客户新请求可取消旧生成。取消不应被当作临时失败而重新执行旧请求；释放本地执行槽不等于远端立即停止生成或停止计费。prepared/sending/unknown 的发送另按原协议处理，不将 AI 取消扩展成发送撤回或重发。

### 3.4 缩小模型输入中的重复内容

保留完整本地验证上下文，新增专用的模型输入投影，而不是把内部业务对象直接 JSON 序列化后提交。

2026-11-12 的补充检查已用此前合成示例做静态投影：context 从10415字符降到3229字符，约减少69%，保留了全部适用资料正文。该比例仅针对示例JSON，不包含固定提示词、私有图片路径或视觉输入，也不是响应耗时下降比例；投影尚未应用到运行时，证据见[本轮诊断](../artifacts/diagnostics/polish-context-20261112-a/findings.json)。

自动接待保留采购事项和增量采集所需事实；人工建议保留回应当前客户所需的信息；润色以未发送正文、必要对话、最新补充、风格和核实商务条件所需资料为主，不附带完整需求采集任务和无关图片。三者可复用同一完整本地快照，但应有各自的模型字段白名单。

文字窗口与关键依据按本轮确认的规则处理：

- 最近文字窗口由20条改为50条，包含买卖双方文字；图片和卡片按各自关联加入时间线。
- 先检查当前事实、未决冲突、明确引用及续答所需的已知原文来源，是否已被这50条覆盖；覆盖时直接复用窗口中的原文，不再单独提取、复制或追加历史依据区。
- 关键原文确实在窗口外时，只补入缺少的对应原文；不再默认每轮额外添加最多8条按关键词选出的旧消息。
- 覆盖检查使用本地消息编号及来源版本，不增加AI提取或摘要调用；无法取得的依据保持不可用，不伪造补全。
- 普通窗口与补入原文按 message_id 去重并按时间排列，同一条消息在模型输入中只出现一次。

其他投影要求：

- 一份按时间排列的消息时间线携带 message_id、角色、时间、原文及图片编号，避免同时发送两份重复聊天正文。
- 同一客户身份在请求级绑定，减少每条消息重复的身份字段；本地完整对象仍用于归属校验。
- 保留实际适用的资料、当前补充、已有事实及必要历史依据，不静默裁掉限制条件或冲突原文。
- 模型输入与本地验证对象分别版本化，纳入固定提示词和输入指纹；不能为减小 payload 而削弱结果校验。
- 不增加 AI 摘要压缩任务，不创建长期客户记忆。

此前完整合成样本约 14939 字符，仅能说明一次输入规模，不能换算为真实图片 token、费用或生成耗时。

### 3.5 调整检测参数和界面反馈

直接将新消息检测/轮询（probe_seconds）默认值改为2秒，连续消息合并（merge_seconds）默认值改为1秒，不新增“快响应”等预设、模式或独立开关。沿用现有设置项及可调区间；已有明确保存的配置继续保留，新建或缺少配置时使用新默认值。摘要续页（poll_seconds）维持默认30秒。使用埋点观察请求量、限流、重复生成和连续消息的完整性。

合并窗口以最后买家消息时间判断，不能简单理解成同步完成后固定再等一次。不要先缩短 AI 超时来制造更快失败。

界面及时显示排队、准备图片、生成、提交、核查等真实阶段及等待时长；不显示虚假的完成百分比。当前外部入口没有已核实的业务正文流式契约，正式正文与事实仍在完整结果验证后展示。慢请求期间额外发送“收到”只改善首次回应感知，会增加发送和竞态，本版不作为默认提速措施。

### 3.6 优先修复已定位的 Windows 图片路径错误

0.3.9 的四次短正文润色在约2–3秒内失败。检查确认安装宿主及后台与0.3.9候选匹配，三张可用原图的本地解码、哈希、角色和来源版本通过；合成离线复现发现：visual_query.py 用未转义的 Windows 路径在 JSON 字符串中直接查找，合法路径因反斜杠转义而被判为 args，尚未启动原生图片AI进程。外层又因 AdapterError 继承 ValueError，将错误统一改成 photo_input_unavailable，具体原因丢失。

先修结构化图片清单与路径的绑定校验，使用解析后的精确路径、文件哈希和本轮白名单，不能简单删除路径校验。给预检、工作区、进程、原图read及最终回执分别保留固定诊断分类，并加入 Windows 下从业务图片组装到实际 runner 预检的贯通回归。图片runner被替身整体替代的单元测试不能覆盖此问题。

普通文字润色不自动准备整段历史图片。确需图文理解时，按明确的任务和引用选择图片并保留真实读取证据；最新客户业务补充仍按现有语义使用，不新增默认关闭开关。该修复优先于多图放量和性能调参，不能以缩短超时或重新检查AI能力替代。

## 4. 需求采集与修正

### 4.1 保留九个基础字段，增加结构化明细

保留 product、quantity、specifications、customization、destination、delivery、budget、packaging、contact，保证旧事项可读取。

按需要增加有来源的需求明细，表达颜色、尺码、型号、材质要求、Logo、工艺、包装和认证要求等；区分样品量与大货量、备选数量与确定数量、收货地与其他地址用途。优先服务已遇到的业务场景，不把所有明细变成必填问卷。

每个候选或明细包含原文片段及消息编号、来源版本、所属事项、表达性质、中文展示和复核状态。跨消息的“500”与“pcs”分别保留原文证据，再派生数量和单位，不伪造一个从未出现的原文片段。派生合计标为计算结果，不冒充客户原话。

颜色、尺寸等视觉线索可作为当前结果中的图片候选显示，但不能仅凭图片写为买家已确认事实；商家展示图也不能当作客户选定。仍由同一次主业务任务给出，不恢复独立图片观察链。

### 4.2 区分业务含义

- 明确要求、询问可否、备选、否定、未决定分别表达。
- 买家预算、目标交期与商家报价、承诺交期分区展示。
- 商品能力或商业条件来自适用商家资料、明确补充及允许公开的核实结果，不写进买家事实。
- 缺项区分未提及、未决定、拒答、不适用、冲突及来源失效；不因缺项重新开启采购问卷。
- 必填配置用于待报价判断，不成为正常聊天或普通人工发送的前置。

中文 summary/display_value 继续在原 Accio 分析中生成；三个页面统一优先显示中文、保留原文展开。展示值不反向修改事实，不交给第三方翻译采集链。

### 4.3 保留候选、修订与人工复核

- 冲突保存各候选、各自原文及来源，不能只留下新值和一组合并消息编号。
- 明确的客户更正与互相矛盾的说法分开处理；有新证据支持的修订应留版本，不让每次改量都永久卡在冲突。
- 冲突不能仅因模型再次输出同一新值就消失，需要有依据的新修订或业务员明确裁决。
- 业务员可确认当前值、采用候选、驳回误提取、标为待客户确认；记录复核时间和依据。没有真实操作者身份时只记本机人工操作，不虚构复核人。
- 人工填写的内容按来源分类：补录买家需求需要绑定买家原文；业务员给出的报价或特例进入卖方条件，不冒充买家原话。
- 原文更正或失效时，处理同会话所有引用该原文的采购事项，重算缺项和待报价提示；保留已存在的报价工作记录并标记需要复核，不以失效事实继续宣称条件齐全。
- 旧数据升级后的人工复核状态默认为未复核，不能批量标记“业务员已确认”。

### 4.4 增加独立“整理需求”入口

人工接待、自动暂停时也能明确整理当前采购事项：选中原文补录，或发起一次仅生成需求候选的 Accio 请求。候选经业务员应用后保存，不生成或发送对客正文，不替换编辑器，不恢复自动接待。

该入口是用户明确触发的独立操作，不在每轮自动回复后再增加一个整理请求。生成、查看和应用需求候选不隐式接管客户；保存时核对事项、来源和 revision，并使受影响的未提交旧结果失效。

### 4.5 多事项与协助闭环

- 接通现有协助表单，在主页面提供明确入口，支持待处理、明确开始、保存结果和跟进状态。
- 保存协助结果与修改需求事实是两个明确操作，不能任务 resolved 就自动清除事实冲突。
- 区分当前自动处理事项与业务员正在查看的历史事项；出现新事项时提示，不强行切走未保存编辑。
- 支持把候选归入已有事项、明确新建事项及纠正误归属，保留修订。整套自动合并、拆分事项可后续扩展，首版不自动移动已报价或有未决发送保护的事项。

### 4.6 采购事项标题统一为简短品类名

标题只表达产品属于什么品类，使用中文常用品类词，通常2–6个字，上限8个字符；例如帽子、手链、项链、连帽衫、水杯，允许T恤等常见写法。品类已明确时不再加“采购需求”“定制询价”等重复后缀。

| 当前长产品描述示例 | 统一标题 | 另放在详情的内容 |
| --- | --- | --- |
| 男士宽松拉链连帽卫衣，帽内侧定制印花，复古学院字母，全拉链卫衣 | 连帽衫 | 性别、版型、拉链、印花位置、字母及风格要求 |
| 定制Logo棉质棒球帽，黑色，多种尺码 | 帽子 | 材质、颜色、尺码和Logo要求 |
| 不锈钢镀金串珠手链，定制吊牌 | 手链 | 材质、表面处理、款式和定制要求 |
| 字母吊坠项链，指定链长和包装 | 项链 | 吊坠、链长和包装条件 |

- 增加独立的展示品类字段 category_label，不再把 facts.product.value/display_value 或 procurement_key 直接当作事项标题。现有产品原文、中文描述和证据完整保留，不能用短标题覆盖买家事实。
- 品类由同一次Accio需求分析根据原文概括，不增加独立分类AI调用，也不在程序中维护一套只支持几个品类的固定词典。字段需与DTO、持久化、提示词及输出校验同步；无效标题回退展示，不阻断原本有效的回复。
- 标题不包含品牌营销词、性别、颜色、尺码、材质、工艺、数量、价格、地址或处理状态；这些进入对应需求明细或商家条件。不能仅截取长标题前几个字冒充分类。
- 品类不明确时显示“待整理需求”，保留完整产品描述供查看。旧数据有可靠短品类可沿用，其余在下一次正常整理或业务员明确修正时补齐；升级不批量调用AI或改写买家事实。
- 允许业务员修正展示品类，作为展示元数据保存；不隐式接管、不发送，不把改名当成客户变更需求。
- 同客户有多个相同品类事项时，用“手链 · 事项1”“手链 · 事项2”等轻量编号区分，更新时间可作辅助信息。仍以原case_id选择，不因同名合并事项，不把规格重新拼入标题。
- 右侧事项选择、聊天顶部采购副标题、待报价和客户资料中的事项名称共用同一规则；完整产品描述只在详情与原文中展示。

## 5. 业务员界面

### 5.1 事项选择区与标题排版

- “采购事项”作为独立的小标签，处理状态徽标放在同一行另一侧；短品类标题或选择框单独占下一行，不再把标签、长选项和状态挤在一行。
- 仅一个事项时显示静态短标题；多个事项时显示占满可用宽度的选择框及事项数，选项采用短品类与必要编号。保留清楚的选中态、焦点态、键盘选择及无障碍标签。
- 标题字号建议15–16px，与正文拉开层级；选择控件高度与页面其他输入控件统一。容器设置合理的最小宽度和换行，280px窄栏及抽屉中不溢出、不遮挡状态或操作。
- 标题下方用“当前诉求”展示摘要，默认最多两行，可展开全文；不将长摘要塞进选择框，也不在标题重复商品广告描述。
- 产品、规格、定制等明细留在需求卡片；较长的原始商品描述单独标注并可展开，保留来源入口。颜色、尺码、数量及费用条件不能因标题缩短而丢失。

## 6. 取消四张图片限制

### 6.1 产品行为

默认取消每轮固定张数上限，不把四张简单换成八张或十二张。本轮待回复消息段的相关双方新图应完整纳入；明确引用的旧图可回补，用户也可为本次人工任务选择历史图片。

图片候选与普通的50条文字窗口分开：必需图片及其所属消息需要独立纳入时间线，并与已选消息去重。也不将全会话全部历史图片无差别重复读取。

保留 p1/p2/p3 顺序、消息、发送方及来源版本。原图下载缓存可跨轮复用；模型本轮使用视觉内容仍需要本轮实际读取证据。

### 6.2 联动修改范围

- message_photos.py：最近图预取、业务候选、准备流程及四个 queued/running 任务的背压策略。
- photos.py：候选、上下文筛选、已读取列表及视觉表述来源检查。
- business_images.py：输入清单及临时原图准备。
- visual_query.py：多图输入参数、请求长度和资源检查。
- business_image_trace.py：取消图片与单组 read 调用最多四项的判断；回执行数根据本轮清单推导，不能继续固定最多14行。
- 来源数组、任务诊断、DTO、提示词、Demo、界面及测试同步核对；不得再被100条来源等其他容量截断。

保留只允许本轮确切路径、read 参数、当前请求关联、角色、字节哈希、成功结果及受控清理的检查。旧单图显式兼容链仍可保留自身四行协议，不能机械删除所有数字4。

### 6.3 张数与资源预算分开

- 单图仍保留6 MiB、2000万像素、最长边8192和现有静态格式解码限制。
- 并行准备建议为2项，这是执行并发，不是本轮只能看2张。
- 新增明确的整批原图字节及准备时间预算，建议初值64 MiB、60秒，作为高级设置，并在任务中显示实际有效值；模型查询超时另行统计。初值须在实现阶段以常见图片样本和内存占用验证后冻结。
- 超过资源预算、平台实际能力或时限时，显示已读/待处理清单及原因，不默默截断后宣称全部看过。依赖未读图片的问题保留待处理；可以继续给出不依赖未读图的有依据答复。
- 同轮相同内容减少重复文件准备及读取，保留每条消息的角色和来源映射；内容复用不能将商家图变成买家确认。
- 当前外部接口仍是 read_compat。取消本地张数限制不代表平台原生能力没有上限，5张以上真实输入与逐图读取证据仍需授权验收。

## 7. 其他可调限制清单

下表保留立项时的建议，不代表每项均已交付。0.3.10 已接入检测/合并默认值、图片预算与准备并发、翻译并发及前文预算、提问次数、按品类的待报价必填字段和风格优先级；具体范围以源码和本版说明为准。AI 并发2、调整AI超时、历史读取总时限、审计间隔调整、按阶段采集模板及显式人工选择历史图片的界面仍是后续候选，不能作为本版已实现能力。

| 项目 | 当前限制或默认 | 下一版建议 |
| --- | --- | --- |
| 新消息检测 | 默认5秒，可调2–60秒，已有设置 | 默认直接改为2秒，保留原设置项及区间，不新增预设 |
| 摘要续页 | 默认30秒，可调5–3600秒 | 首屏先派发；常规保留30秒，不为提速频繁扫旧会话 |
| 连续消息合并 | 默认3秒，可调0–120秒 | 默认直接改为1秒，沿用原设置项；0秒可选但提示连续消息可能增加重生成 |
| 公共业务执行 | 1个worker，业务队列未设容量 | 状态协调与AI等待分离；有界待执行队列、按来源去重和公平调度，不限制可接待客户总数 |
| Accio AI查询 | CLI180秒、外层190秒 | 先保留；之后按成功耗时分布开放高级总截止时间，两层配置一致 |
| 生成错误重试 | 2/4/8/16/32/60秒退避，未见单来源次数硬上限 | 增加单来源失败预算，建议连续3次后转明确待处理；新消息可继续接待，不新增全局AI次数上限 |
| 正文同步/补全 | 自动最多10页；显式补全最多1000页，每页100条 | 改为页数加总时间预算，前台最新消息优先，继续保留明确的历史覆盖状态 |
| 旧历史/审计 | 每账号60秒安排一个客户，普通审计条件300秒 | 首版保留；高级设置可调，不与新活动抢占同一优先级 |
| 文字上下文 | 最近20条，另补必要证据及最多8条相关旧原文 | 默认最近50条；覆盖关键依据时不另行提取或追加，窗口外仅补缺少的必要原文，同一消息只传一次 |
| 请求长度 | context校验120000字符；视觉最终prompt140000字符 | 统一计算最终业务输入预算，默认先保留容量；字符与token估计分开，不虚称外部模型支持更大输入 |
| 每轮追问/每字段追问 | 一轮最多2项；已问2次的字段被过滤 | 统一为可配置接待参数，建议每轮1–2项、每字段默认2次；不设置无限追问，政策可进一步收紧 |
| 默认待报价必填 | 产品、数量、规格、目的地 | 可按品类/阶段设采集模板；只影响待报价判断，不阻塞正常回复 |
| 图片读取重试 | 最多3次，尝试间至少60秒 | 按错误分类退避；允许明确人工重试发起新下载周期，来源/格式失败不盲重试。此项不能重置发送失败链 |
| 图片格式与解码 | PNG/JPEG/WebP，静态图，预览最长1280且不超过1 MiB | 首版保留；扩大格式支持单列兼容任务，不自动把低清预览替代原图 |
| 对客正文/建议 | 生成及提交多处限制1200字符 | 暂保留对客提交上限，先核实平台契约；内部需求详情可更丰富，不因需求详情增多而放长客服正文 |
| 保存/润色输入 | 草稿可保存100000字符，润色输入最多50000字符 | 明确输入与输出长度差异，超长内容不静默压缩、截断后让用户误以为完整保留 |
| 资料正文 | 单项正文、公开口径、内部备注各最多50000字符 | 保留存储上限，输入仅选择有效适用内容；不因存得下就全部重复注入 |
| 同轮聊天风格 | 适用风格选1份，按范围及稳定编号选取 | 增加用户可理解的优先级和冲突选择，不直接混入多份互相矛盾的风格 |
| 协助/质量提醒/来源 | 单次模型元数据最多5项协助、10项提醒、100来源 | 按主题合并和资源预算处理，界面折叠展开；图片及有效来源容量联动，不静默丢掉超限关键来源 |
| 第三方翻译 | 并发2、批次最多6片且约4000字节预算；上下文最多2条且合计300字节 | 高级设置提供并发1–4及上下文预算，尊重服务端限流；继续独立队列、缓存和用途，不阻塞需求展示 |

提问次数需要特别说明：当前主要过滤 question_keys 元数据，并按 accepted 回执累计，不能保证最终正文不继续提问。下一版设置需同时影响提示词和元数据处理，界面显示“已记录的受理提问次数”；超问仍是可见的语义提醒，不擅自改写正文、不新增发送前模型或硬性发送门槛，也不宣称已经实现正文问句的严格计数。

这些并非全部都要变成普通设置页的开关。普通页沿用检测/合并设置并提供需求展示偏好，不新增响应预设；容量、超时、并发放高级页；协议关联和数据保护继续由程序统一执行。

身份与商家隔离、当前授权、人工接管、确切正文与来源版本、整会话未决发送保护、accepted证据及unknown原操作核查不作为提速开关。单条发送最多三次总尝试及5/15秒退避继续保持，不能套用新的生成或图片重试预算。

业务处理参数按商家保存，变更沿用现有撤权、版本及旧结果失效机制，不自动恢复接待。纯布局和显示偏好与业务设置分开，不使查看需求变成接管或发信。

## 9. 验收

### 速度

- 同一组场景分别测文字、2图、5图、10图及更多图，区分首次加载和缓存命中，保留完整成功率、来源覆盖和质量结果。
- 模拟慢AI时，新消息同步、本地保存及人工操作不被该查询占满整个通道；已就绪发送不继续排在无关生成后面。
- 取消、暂停、新消息到达以及旧结果迟到不会覆盖新需求或发送旧正文。
- 本地空闲条件下，以结果落库后500ms内界面展示对应版本为初始目标；真实最终答复目标根据基线后确定，不预先承诺加速百分比。
- 首次回应、最终有效答复、平台受理和unknown核查分别统计，不通过更快失败或漏读图片提高速度数字。
- 新建/未配置时检测默认2秒、合并默认1秒，现有明确配置保留，界面不新增预设入口。
- 最近50条已包含全部关键原文时，不另行追加历史依据；关键原文在窗口外时只补缺少项，同一消息在模型输入中只出现一次。覆盖检查不调用AI，图片与卡片关联仍完整。

### 图片

- 离线至少覆盖5、8、20张，顺序及同组多read两种回执；验证不会再命中四张和14行残留限制。
- 买卖双方混合、相同原图多消息、旧图明确引用、单图失败、超预算、来源改变、取消及临时文件清理均有用例。
- 声称“本轮全部已读”必须有对应清单的实际成功证据；未读图保持未读，不能换图或复用旧观察凑通过。
- 超过4张的真实Accio能力只在对应授权环境用合成图验收，不以Demo或本地替身证明平台支持。

### 需求与界面

- 样品10件和大货500件、500改800、两个备选、否定/未定、跨消息数量单位、客户预算与商家报价分别正确表达。
- 原文更正影响所有有关事项；冲突不能被无新依据的重提取清掉；人工复核状态不被后续AI结果悄悄覆盖。
- 三个页面值、中文、原文、来源及状态一致；历史事项与当前处理事项明确；需求操作不覆盖聊天输入或隐式发信。
- 长商品标题显示为帽子、手链、项链、连帽衫等简短品类；中英文原描述、颜色、尺码、工艺、数量及商业条件仍完整保留在详情中，不以截断原文代替分类。
- 同品类多事项可明确区分，选择仍绑定各自case_id；旧数据无短标题、品类未知、单事项与多事项、窄栏及抽屉均有展示用例，标题不会挤占状态或横向溢出。
- 实际Electron主页面点击协助入口、开始处理、保存结果和需求裁决；不能只测未挂载的孤立组件。窄屏抽屉、未保存编辑和重开状态也需验收，截图实际查看。

仅运行改动范围的定向测试，不默认运行全量测试。离线使用临时数据与替身；真实读取、AI、客户发送和飞书业务写入分别遵守届时明确授权。
