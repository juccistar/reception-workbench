# 0.4.2 问题核查与修复方案（修订版）

日期：2026-11-17。面向本项目产品评审与开发实施。本版替换先前范围过大的方案，只处理用户指出的问题及直接相关环节。

开发与隔离验证已完成：聊天图选择、图片读取动效、建议提示去重和自动回复进度已实现；WhatsApp 增加识别失败分类及脱敏阶段记录，商品图支持同一结构的字符串/对象包装并区分失败原因。定向回归、类型与源码构建通过，构建后立即提交 1418614；真实 Electron 隔离窗口 4 项检查通过，10 张截图已逐张查看。自动阶段采用合成投影，发送规则另经后台定向回归验证；未打包或替换安装。当前终端缺少 Accio 授权环境，公开商品页读取被网络限制，尚未取得两个目标商品的新返回或真实 WhatsApp 失败阶段，因此不计这两项现场故障已解决。详细状态见 [本轮验证记录](verification/0.4.2-issue-fixes.json)。

## 1. WhatsApp 当前单聊识别

**已确认：** 当前识别路径的多种失败都返回空值，侧栏统一显示“请选择一个单聊”。用户现场具体失败在聊天集合、活动项、ID 还是 SDK 查询，尚未确定。

**修改：** 在现有识别路径补充必要的失败阶段信息，确定原因后修正对应适配；界面区分“未选择单聊”和“暂时无法识别当前客户”。连接恢复仅在确认与本次故障直接相关时调整。

**验收：** 已打开单聊能显示当前客户，切换客户后资料正确，刷新后能够恢复；保留现有身份和来源核验。

涉及入口：`apps/desktop/src/main/whatsapp/chrome-host.ts`、`apps/desktop/src/main/whatsapp/customer-panel.ts`。

## 2. 聊天图片进入模型上下文

**已确认：** 国际站接待选图依赖已有需求图片来源，尚未归入需求的新聊天图可能被排除。业务补充图走独立路径。

**修改：** 调整接待选图，让本轮聊天上下文中的相关图片随文字提交，不再要求图片先成为正式需求依据；正式需求中保存哪些产品图，仍沿用原有归属和证据规则。同时核对选图、原图准备与请求组装是否一致。图片读取失败时提供失败和重试反馈，沿用现有后续处理策略，不新增发送阻断。

**验收：** 覆盖单张、多张、已有需求后新发图片，以及聊天图与补充图同时存在的情况；在两种模型协议的实际请求中核对图片内容，而非依据预览或 token 数量判断。

涉及入口：`services/reception/src/reception_service/requirement_media.py`、`reception_context.py`、`message_photos.py` 及模型请求组装。

## 3. 商品图片读取与替代来源

**已确认：** 截图商品 1601907408579、1601982084503 都失败于 `product_metadata`，错误为 `product_display_invalid_response`，尚未进入图片下载。原始返回结构未取得，具体解析失败原因尚未确定。

**修改：** 先取得这两个商品返回的必要结构信息，查明当前接口无法解析的原因，修正对应处理。替代来源先验证能按确切商品 ID 查询图片的官方只读接口；官方接口确实不可用时，再评估对应商品页的结构化图片。根据归属核验、实际可用性与可靠性比较结果，决定是否替换。

目前没有证据证明某条备用接口更可靠，不提前指定替换，也不新增上传管理功能。

**验收：** 两个目标商品能读取并显示正确图片；无图片、不可访问和读取失败能正确区分；采用替代来源时能确认属于同一商品。

涉及入口：`services/reception/src/reception_service/integrations/product_display.py`、`product_presentation.py`。

## 4. 图片读取和重试反馈

**已确认：** 商品图重试主要依靠文字变化和按钮禁用，缺少明确加载动效；聊天图和原图弹层也以文字提示为主。

**修改：** 在现有图片区域增加加载动效，点击重试后立即显示“正在读取”并禁用重复点击；成功后显示图片，失败后显示简短原因及重试按钮。商品图有真实阶段信息时，区分“读取商品资料”和“下载图片”，不显示虚假进度。相同图片组件的直接使用入口一起检查。

**验收：** 点击立即有反馈，处理中可辨认，成功或失败都有明确结束状态；保持已确认布局。

涉及入口：`apps/desktop/src/renderer/components/ProductMainImage.tsx`、`MessageImages.tsx`、`OriginalImageDialog.tsx`。

## 5. 自动回复进度与建议提醒去重

**已确认：** 生成任务结束后，聊天中的生成提示消失，后续发送批次没有连续接入当前进度。人工建议同时出现在顶部任务条和输入框上方建议卡。

**修改：** 复用现有任务、草稿、发送批次和回执，在同一处连续显示：

**生成回复 → 保存草稿 → 准备发送 → 提交第 n/m 条 → 等待回执 → 发送成功。**

各阶段跟随真实后台状态更新，保持位置与动效连续；失败、停止和结果待确认也在同一处呈现。后台缺少必要阶段信息时，只补对应状态通知，不改变业务执行顺序或发送规则。

人工建议只保留输入框上方的下方提示，移除顶部重复提醒，在原建议卡内增加加载动效和取消反馈。不恢复发送记录或手动核查入口。

**验收：** 生成到发送之间没有状态空档，多条发送计数正确，失败和停止有对应结果；建议生成只出现一处主要状态提示。

涉及入口：`apps/desktop/src/renderer/components/Reception.tsx`、`ReplyActivity.tsx`、`renderer/receptionStatus.ts` 及现有后台阶段通知。
