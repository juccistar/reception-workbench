## 1. 版本目标与范围

交付结构为：**启动台统一管理国际站和WhatsApp账号；多个WhatsApp账号独立运行；真实Google Chrome承载聊天；客户侧栏提供当前客户资料和关联操作；各商家服务按已核验身份提供只读背景。**

| 项目 | 更新后的0.4.1交付内容 |
| --- | --- |

不扩展群聊、广播、群发、采购询价、报价回收或飞书写入；不接管日常Chrome资料目录，不引入固定的OCR后再回复流程。按用户补充，预留“WhatsApp→国际站”受控反写接口和版本化能力开关，0.4.1默认关闭且不执行真实反写，未来按具体写入对象及授权逐项解锁，见第8.2节。

## 2. 界面与日常使用

### 2.1 统一账号首页

首页采用“全部 / 国际站 / WhatsApp”三个分类，筛选同一份账号列表。每张卡片显示名称、渠道、账号尾号、当前连接/窗口状态；状态旁始终提供铅笔编辑按钮，右侧直接执行该账号的主操作。未连接的WhatsApp显示“连接”，已连接或等待扫码显示“打开窗口”；国际站已打开显示“打开窗口”，需要授权时显示“授权”。不再使用单选行加底部统一打开按钮。

国际站主标题默认使用已核验的公司名；可另存本地显示名称，但不得覆盖公司身份来源。缺少公司名时保留账号尾号和简短占位，不用AI猜测。WhatsApp使用用户填写的账号名称。长名称截断并可查看全文，窄窗口仍保留状态、编辑与主操作，不出现横向滚动。

连接状态、自动接待状态、未读与发送回执分别保存和展示。“已连接”不能推导为自动接待开启。连接失败短因如“连接超时”直接占用原状态位置，旁边仍为“连接”；不新增整行错误提示条，不因失败拉高卡片或挤动后续账号。更详细原因进入悬停或账号连接详情。

右上角提供“添加账号”和全局“设置”。添加时选择国际站或WhatsApp；添加WhatsApp只要求账号名称，随后“连接”和按需扫码。页面不常驻“可保存多个环境”“在Chrome聊天”等解释，不显示UUID、连接代次、管道、SDK或数据目录等实现细节。模型配置集中在全局设置；首页仅显示简洁就绪状态和入口。

### 2.2 账号设置与客户侧栏

卡片编辑打开账号设置面板；窄窗口占满可用宽度，底部固定“取消 / 保存”。WhatsApp包含名称、自动接待、允许接待商家及新联系人默认商家；接待关闭时收起相关配置。联系人分配使用独立可搜索列表，不常驻下拉框和完整联系人表单。国际站包含显示名称、公司信息、接待设置与共享模型入口；规则和业务资料仍在对应工作台维护。

备份恢复、连接详情和必要历史接入维护收进“更多设置”。模型缺失或历史来源待核验等事项，在用户开启接待时给出缺项与可操作入口；不得隐藏真正阻断当前动作的原因。未开放的回写能力不显示为日常设置。普通改名、筛选和打开窗口不增加确认；扩大自动接待范围、改变客户商家等有业务影响的动作按实际范围提示。

聊天窗口提供可收起的客户侧栏，随宿主核验的当前单聊切换。显示当前客户信息、接待商家、可选国际站客户关联、摘要/需求摘要及“关联客户”“人工接管 / 恢复接待”等入口。侧栏不替代原网页消息输入或发送。客户关联使用当前已选商家范围的搜索/选择器，不让普通用户手填conversation_id。

当前聊天只作为侧栏显示及操作的明确目标，不凭焦点、联系人显示名或最近入站消息推断业务归属。切换客户时立即清空旧客户展示和未确认选择，迟到结果不得回填；涉及未保存修改时由用户保存或放弃，不能静默改到新客户。可靠识别、扩展安装及宿主隔离边界见第4.1节。

### 2.3 国际站授权：复制完整口令

“添加国际站”“授权”“重新授权”打开统一授权弹窗，提供只读全文与“复制口令”。复制范围是用户确认的完整三段内容，包括换行：

```text
请仅在允许启动此工作台的当前目标商家 Accio Work 授权 PowerShell 会话中执行以下命令。

Start-Process -FilePath '<本机当前安装目录>\ReceptionWorkbench.exe' -ArgumentList '"--connect-from-accio"'

该命令启动本机当前版本后立即返回，请勿等待桌面进程退出。
```

示例只用占位表示安装位置；正式全文继续由[launch-command.ts](../apps/desktop/src/main/launch-command.ts)的buildAccioLaunchInfo生成。显示读取现有launcher.authorization，复制调用现有launcher.copyAuthorization，由宿主写入info.instructions全文；不截取command、不在前端拼接或硬编码用户提供的路径，不删掉前后说明，也不改变PowerShell参数引用。复制成功/失败给出简短反馈，失败时全文仍可选择复制。

口令只是从当前目标商家受支持授权会话启动程序，不保存或延长Accio授权。重复启动只定位已有窗口，不能借复制口令向旧进程注入另一商家的新授权。

授权启动还须兼容Accio当前公开的短路径布局。共享工作区已补齐[connect-live.mjs](../scripts/connect-live.mjs)对`accounts/<当前账号>/r/<单层代次>/p/<workctl|workctl.cmd|workctl.ps1>`的精确识别，映射到同一p目录下既有固定node_modules路径中的真实workctl.exe；原generations布局保留。不读取、解析或执行shim内容，不跨账号，不接受目录链接或未知布局。此修复已纳入候选B，候选A及已安装文件不因此更新。

另一会话的脱敏[验证记录](../artifacts/verification/launch-workctl-20261116/compact-layout-verified.json)报告两文件31项定向测试通过、无失败或跳过，并验证同一公开路径在安装版被拒、修复源码可解析。本会话已核对源码差异与该记录，并在候选B前重新运行当前连接脚本24项定向测试；另一会话早期31项报告单独保留，不叠加计数。真实授权启动、平台读取和AI未由这些回归验收。后续另一会话提供的[临时入口启动观察](../artifacts/verification/launch-workctl-20261116/temporary-launch-observed.json)记录用户自行执行后，商家窗口响应、后台启动，主/后台身份和原数据根一致。此结果仅证明临时每进程映射路径下的实际启动；候选B已包含修复源码，但安装版普通入口未更新，新包正式授权启动、真实模型和客户收发仍未验收。临时入口保留为独立支持材料，不替代正式口令流程，也不进入发行默认入口。候选B已复核连接脚本并纳入发行资源；临时入口成功仍不等同于正式补丁已完成安装验收。

### 2.4 发送结果未知的提示

“发送结果待核查”仅表示已尝试提交，但尚无确切受理或确切未提交证据；不表示每条回复需要人工确认。正常发送没有待办条。实际存在unknown时，在相关卡片原状态区域附简短可点数量如“1条待核查”，进入该账号/客户的发送核查明细；不增加跨卡片提示条。连接状态仍独立显示。

优先由后台沿原operation自动核查；需要用户介入时提供“核查结果”和必要原因，不提供“重发”或以新请求继续发送的入口。客户侧栏可显示该客户的同一待办，两个入口读取同一权威记录。设计稿的异常预览是合成状态，不代表用户账号真的存在未决发送。

### 2.5 默认商家与多账号退出

账号可设置新联系人默认商家，也可留空。单聊首次收到通过账号、来源与入站时间校验的有效实时买家消息时，在同一事务内冻结默认值为该聊天的明确绑定；历史与联系人metadata不触发绑定。改默认值只影响新单聊；保存绑定不等于开启发送，新增商家不自动扩大授权。

多个不同WhatsApp账号分别连接和运行，不设切换模式。连接B、关闭B窗口、断开B或B后台故障，只撤销B资格并排空B的任务，A保持原连接与授权。每个账号的窗口、联系人、绑定、接待开关和未决操作均按账号定位；最小化不暂停，关闭自有聊天页/窗口则暂停该账号并保留未决操作。

启动台窗口关闭时按现有托盘语义隐藏，普通重复启动定位原宿主。托盘按账号提供打开窗口和暂停/断开入口，不能依赖最后选中的账号；“退出并暂停全部接待”先对全部活动账号撤权，再逐账号完成落账、任务收尾和实际进程退出，不因一个账号失败而跳过其他账号清理，也不提前释放失败账号的锁。独立Accio商家进程不强制关闭。

宿主单实例仍按Windows用户约束，浏览器/服务消费者互斥按账号约束。宿主崩溃后重启不恢复自动授权；核对已登记自有进程、profile锁和连接失效状态，不能删除锁或凭PID复用接管旧消费者。

## 3. 架构与服务边界

### 3.1 三类服务

| 组件 | 职责与边界 |
| --- | --- |
| 启动台宿主 | Chrome进程、账号锁、原生确认、绑定界面、受限IPC及服务生命周期 |
| 独立WhatsApp服务 | JSONL子进程，保存账号消息、摘要、绑定、草稿、任务与发送操作，调用全局模型 |
| 商家上下文代理 | 连接已有且已核验的商家服务，导出当前绑定所需的只读资料与权威修订 |

WhatsApp服务不构造Accio商家执行器，不继承或保存Accio令牌。启动台不提前启动全部商家后台，也不让renderer直接打开SQLite、调用CDP或执行任意RPC。

商家代理使用宿主私有、双向核验的本机连接，绑定当前用户、seller_id、实际data_root和服务实例。只暴露导出受限上下文、读取修订、必要的当前商家客户候选及撤销通知，不提供任意SQL、文件路径、shell、采购或国际站发送能力。客户候选是新增受限只读能力，不复用任意RPC；不能把原窗口激活握手扩大成无限制业务代理。

### 3.2 多账号运行时、路由与所有权

现有每workspace的profile、业务库、Python服务和协调器隔离基础继续复用。把WhatsAppAccountManager的单一active、starting、cleanup改为Map<workspace_id, AccountRuntime>，每项分别保存启动/关闭Promise、串行修改队列、ChromeHost、ServiceClient、Coordinator、模型及上下文任务、窗口/当前聊天状态与runtime_instance_id。一个账号启动失败、清理挂起或模型同步较慢，不能占用其他账号的生命周期队列。

列表摘要与单账号详情分开：列表只读路由元数据和已有运行时投影，不为刷新卡片启动所有后台；详情显式指定workspace_id。删除selectWhatsAppAccount作为运行前置，不再使用selected_workspace_id、唯一host/state或current()选择业务目标。上次查看账号仅可保留为界面偏好。

连接、打开、断开、联系人、历史来源核查、名称修改和详情读取均显式传workspace_id。保存绑定、默认商家、接待授权和接管除workspace_id外继续校验expected_account_id、expected_connection_epoch及对应权威修订；核查原操作和读取客户上下文分别绑定workspace_id + operation_id或workspace_id + chat_id。main、preload、DTO及Python分派同时核对。普通网页不能调用这些桥。

事件附workspace_id与runtime_instance_id，异步请求按账号及请求序号合并。断开后以已持久化的账号owner投影原发送和待核查记录，不能因在线account_id为空而让旧unknown消失。全局模型变化对全部受影响运行账号同步/撤权，并保留每账号失败原因。

保留短时账号索引metadata锁；浏览器/服务的长期运行锁改为workspace级，并补跨目录的真实account_key占用保护与永久account_key→workspace/ledger_root归属。不同真实账号可并行，同一真实账号的第二workspace、不同根或恢复副本不能创建第二消费者。account_key只依据可信SDK身份及可验证别名，不能按尾号、名称或未证实的PN/LID关系合并。旧操作的原账号和epoch字节不因身份映射而重写；来源对应不明时冻结相关接待。

启动先持有workspace所有权，真实身份核验和真实账号级占用通过后才允许业务读取及发送。正常退出等待该账号自有Chrome根进程和Python进程真实结束，再释放运行锁；永久账本归属继续保留。unknown保留不等于必须永久占用活进程，重连后仍只能核查原操作。崩溃恢复同时验证进程创建时间/句柄、目录和旧消费者状态，不能因心跳失联就释放所有权。

### 3.3 商家服务离线的明确行为

WhatsApp登录、入站保存、回执核查和人工聊天不依赖商家窗口。使用商家业务背景自动接待时，对应已授权商家服务必须在线且身份、目录和修订可核验；国际站自动发送授权与WhatsApp自动授权独立。

商家窗口最小化或明确隐藏时可继续使用仍在线的服务。真正退出商家服务，按现行退出语义撤权：只暂停该商家绑定联系人的自动生成和发送，其他商家继续；Chrome人工聊天保留。全部商家服务退出时，不使用失效缓存继续自动接待，也不凭旧登记重新创建授权环境。

0.4.1不默认实现关闭后隐形保活商家服务。恢复后重新核验身份与授权，暂停期消息保留为待处理，由用户明确选择是否处理，不自动回放历史或已受理内容。

## 4. 真实 Chrome 接入

使用系统安装的Google Chrome，固定随包Puppeteer和whatsapp-web.js依赖。先以现有`24.38.0`和`1.34.8`组合试验；不兼容时依据试验结果最小升级，并重新核验生产闭包，不直接宣称兼容所有Chrome版本。

Chrome由程序以可见模式启动，SDK通过程序私有pipe控制同一个页面与登录会话；不开放调试TCP端口，不连接用户日常浏览器。保留真实客户端标识，避免SDK旧默认User-Agent覆盖实际Windows/Chrome环境。

每个账号使用独立profile、可见窗口、SDK Client及私有pipe，延续当前宿主对userDataDir的单一管理，不同时加入冲突的LocalAuth目录管理者。首次从旧Electron接入使用新profile重新扫码，旧partition原位保留，不复制Cookie。多个不同账号分别启动和关闭，自有进程归属不能只按chrome.exe名称判断。

发现标准安装路径，必要时通过宿主原生选择器指定Chrome程序；校验规范路径、产品与版本，renderer不能提交任意EXE、启动参数或profile路径。不存在、不兼容、profile占用或SDK初始化失败时，给出具体状态，不自动清空资料或替换浏览器。

每次连接记录实际浏览器版本与SDK归档摘要；版本变化后重做连接兼容检查。超出已验证范围或关键能力失败时暂停自动接待，保留网页人工使用和诊断，不静默下载、降级或关闭Chrome更新。支持范围必须来自本版实测。自动检查包括pipe通联、实际版本、可见页与SDK的同一目标、必要脚本/回调及公共登录页；登录持久化、真实入站、发送回执和手机接管另列实号验收，版本检查通过不能代替这些结果。

Chrome进程和profile保持单写入者，仅关闭程序明确创建的进程；崩溃后先确认旧进程及锁状态，不凭PID存在与否或删除SingletonLock强行接管。

### 4.1 客户侧栏的正式接入路线

首选Chrome官方Side Panel扩展，侧栏作为独立扩展页面承载客户资料；不把商家资料、密钥或业务写入能力直接注入WhatsApp普通DOM。聊天网页维持原有原生聊天职责。独立伴随窗口可作为另行评估的兼容路线，但不能冒称已实现浏览器内侧栏；不以可访问业务RPC的网页注入作为自动回退。

正式接入已改用锁定Puppeteer支持的私有CDP扩展安装：自有Chrome以headless=false、pipe=true、enableExtensions=true启动，宿主通过browser.installExtension安装固定资源目录并使用返回的真实扩展ID。Chrome读取resources/customer-panel中的五个正式文件，打包逐文件核对版本、权限及哈希，扩展仅有sidePanel权限。未使用常规--load-extension、Web Store或日常Chrome的安装状态。真实Chrome 152前置探针003已验证原生侧栏打开、私有扩展binding及普通网页无binding，截图已查看；该前置结果不替代当前客户与关联的正式联调。

侧栏打开需要明确用户操作，入口使用扩展图标或经过验证的用户点击。设计稿示例放在右侧，但原生侧栏左右位置由Chrome用户设置决定，不承诺程序强制固定在右侧。缺少扩展时按需提示启用，现有登录与原网页聊天不因此报错或被替换。

扩展与宿主经自有私有pipe上的CDP Runtime.addBinding建立有限通路，不开放本地HTTP业务端口。只向实际安装ID的panel.html默认执行上下文赋予随机会话能力，核对origin、frame、execution context及runtime；普通WhatsApp网页和日常Chrome中的同ID扩展均不取得业务通路。能力不写入WhatsApp DOM、URL或日志。侧栏开放当前客户展示、受限客户选择、保存关联、接管/恢复；原操作核查继续在启动台按workspace和原operation执行。禁止任意方法、任意路径、shell或数据库访问。

当前聊天从已核对上游wa-js getActiveChat实现的聊天集合读取，要求唯一active单聊且无活动频道，再用锁定SDK的getChatById核验完整ID、单聊类型，并重新读取当前ID。识别不依赖姓名、最近入站或焦点。侧栏轮询不重叠，核对workspace_id、浏览器实例/标签、account_id、connection_epoch、chat_id、view_revision及request_id；读取返回与变更执行前再次比对。切换、重连、关闭、群聊、集合缺失或识别失败时清空旧资料并禁用操作。上游源码证明集合语义不等于实际已登录页面验收；真实账号识别继续单列未验收。

新增仅面向已核验商家的客户候选接口，限字段、限量/分页，只返回当前查询所需的客户名称、稳定会话引用及修订，支持名称和买家标识搜索、最多25条，不读取消息正文；当前仓储没有可信买家公司字段，因此不返回或搜索公司；选取及保存时重新核验商家归属和绑定修订。关联只是建立本地对应关系并读取允许的背景，继续不反写国际站。侧栏只收必要展示数据，不取得模型Key、Accio令牌、完整商家库、内部提示词或无关客户资料。

最小前置验证包括：正式Chrome扩展安装/启用、手动开关及位置行为、隔离profile绑定、有限宿主通路来源拒绝、当前单聊识别，以及两账号快速切换客户与迟到请求隔离。使用隔离目录、合成资料和允许范围内公共页；真实账号识别与收发仍须单独验收。前置未通过时将侧栏列为技术阻塞，不用原型截图或Puppeteer测试扩展加载结果代替正式Chrome验收。

## 5. 账号、绑定与发送契约

### 5.1 账号级存储

新增独立账号服务入口和所有权校验，不把WhatsApp账号伪装成数字seller_id启动原商家服务。可复用SQLite WAL/FULL、JSONL传输、任务调度、模型路由与受限媒体实现，但数据主键和服务权限重新按账号定义。

| 对象 | 关键字段或作用 |
| --- | --- |
| 账号环境 | workspace_id、经SDK核验的account_id、profile位置、登录代次、连接代次 |
| 单聊 | account_id、chat_id、未读、human_owned、reply_pending，各状态独立 |
| 绑定 | account_id、chat_id、seller_id、merchant_record_id、data_root、可选conversation_id、binding_revision |
| 上下文分段 | 绑定生效边界、来源消息版本及该段独立摘要，历史分段保留 |
| 发送操作与分条 | 原operation_id、账号、chat、冻结正文/哈希、商家与绑定修订、状态和确切回执 |
| 历史来源清单 | 原业务根、旧账号/聊天/操作对应、文件摘要、导入版本与完整性结果 |

沿用真实Windows用户目录下现有账号根`ARWData/whatsapp/workspaces/<workspace_id>`，实际账号库继续位于该根的whatsapp-accounts/<workspace_id>内；登录目录继续为`ARWBrowser/wa/<去横杠workspace_id>`。账号索引仅保存路由元数据、显示名称及必要修订，不保存凭据。改名、统一列表和并行运行不重排业务目录；更换根须走完整维护流程。新库、WAL、账本和锁按实际最终路径检查长度，不用不存在的短目录掩盖已有数据。

扫码前用workspace_id管理环境，扫码后核对平台账号身份。相同account_id不能因创建第二个workspace而拥有第二消费者；同Windows用户的账号互斥覆盖不同Accio环境。账号身份改变立即撤权，旧账号的消息和未决操作不转归新账号，不依据显示名称或手机号尾号合并。

### 5.2 单聊归属与上下文隔离

一个单聊只保存一个活动接待商家。关联国际站客户必须属于该商家；联系人的名称、手机号或聊天内容不能被程序猜测成其他商家客户。

原始WhatsApp消息按账号和单聊保存，不复制到多个商家库。商家切换形成新上下文分段，旧商家的摘要、内部备注、供货事实、未提交草稿和承诺不自动进入新商家上下文。Chrome中原始历史保留；新生成默认使用新段及明确归属的依据，必要旧买家需求须明确选择来源，不把其他商家的外发报价变成当前商家的承诺。

商家代理只返回当前绑定所需的规则、风格、允许对客事实和可选客户背景，附seller、根、服务实例及资料/会话/需求/补充修订。用户私图、其他客户、其他商家资料不能扩大读取。获取失败、身份或修订变化使当前生成失效；0.4.1默认只读该背景；未来反写必须经过第8.2节独立接口，不能借读取权限执行写入。

### 5.3 切换绑定必须与发送围栏原子协调

1. 先冻结该单聊新任务和提交，取消旧生成，停止尚未提交的分条；不能仅因本地显示prepared就认定一定未出站，需宿主确切未提交证据。
2. 已有sending或unknown时保留原operation与原商家归属。可保存待切换意向并显示“旧发送核查中”，但不激活新商家的发送资格。
3. 原未决操作受理或确切未提交后，原子提交新绑定并增加binding_revision；旧任务迟到结果不能写入新段，也不能清理新输入。
4. 新绑定默认暂停该联系人的自动接待，用户明确恢复后生效。切换本身不重新处理历史或已受理来源；需要处理暂停期消息时选择确切未回复来源。

所有自动任务冻结账号、连接代次、chat、商家、根、绑定修订、资料版本、消息版本及模型快照。生成结束和实际提交前再次核验。绑定变化只影响相关单聊；账号范围、默认商家或全局接待模型变化按依赖撤权，不影响无关商家或独立翻译用途。

### 5.4 发送与入站语义保留

发送互斥范围为`account_id + chat_id`，覆盖所有绑定和商家。原operation持久冻结在调用SDK之前，accepted仍要求确切平台消息ID和ACK≥1；unknown仅核查原操作，不能换商家、正文、job或新账号库重发。自然分条、总长度和重试预算沿用现行约束，逐条受理后推进。

历史加载、联系人metadata、回执或媒体就绪不制造新入站。原页面或手机人工回复接管当前联系人；程序自己的确切回显不误判为人工。无消息ID的未知提交不能靠同文或时间接近猜测受理。

## 6. 模型、媒体与资源

继续使用0.4.0 C修正后的当前Windows用户共享目录和CurrentUser DPAPI。启动台保存API及接待/翻译用途，账号服务通过宿主私有管道接收所选凭据；Chrome网页、renderer、argv和日志不接收明文Key。权威文件修订核对继续保留，通知不能替代真实依赖检查。

本版不新增WhatsApp专用翻译界面，不把当前未实现的能力列为已可复用；国际站现有聊天翻译和全局翻译选择继续保留。

文字与相关受控原图同轮提交，保留实际编码字节证据、来源角色和版本。继承单图6 MiB、受限下载并发、分块传输、图片准备期限和取消后真实结束再释放资源的机制，不拉取全部历史图，也不把商品展示图自动变为买家图片。

多账号开放前增加同Windows用户唯一的模型额度协调器，全部WhatsApp账号、国际站第三方模型请求及能力检查接入同一有界预算。首期沿用接待1槽、翻译1槽、活跃HTTP合计2、带图1作为用户级上限；各服务现有本地上限继续保留。旧实现的这些值只是进程内限制，不能把未接入协调器的旧进程也宣称计入全局上限；升级时先核对参与版本及旧活动消费者。

协调器使用受限本机通路和当前用户单实例所有权，不开放业务HTTP端口。所有模型入口和检查都走同一租约客户端，按账号/商家公平轮转，设置全局及每所有者固定容量等待队列与同API的共享退避。等待在模型任务中完成，不持有业务仓储锁；消息同步、人工发送、接管和回执核查不排在模型等待后。队列满时保留业务待处理状态并返回明确等待/繁忙结果，不丢入站，不把未取得额度算成模型尝试。

额度由实际HTTP和资源清理完成后归还，不能在提前取消的调用方finally里释放；账号断开只撤销该账号未开始请求，在途任务按真实终态收尾。协调器断线/重启先核对旧租约对应消费者及在途任务，不清零后立刻放行第二批请求。模型与发送的持久尝试预算继续分开，重连、换job或绑定变化不重置预算。

全局用途或端点/Key变化撤销确实依赖它的接待授权；单账号改名、打开窗口或断开不影响其他账号。共享模型不改变原提示词正文、协议、上下文排序和图片来源去重。

多个账号只在用户主动连接时各自启动Chrome，不预热所有已保存账号。独立浏览器进程会增加内存，模型预算不是Chrome或整机RSS上限。基准至少记录单账号和两个账号同时运行、单账号断开/故障及全部退出的进程组快照和响应时间，不能仅用Python或单进程数据宣称整机性能提升。

基准实测记录机器、版本、账号数及阶段：启动到窗口/扫码就绪、SDK初始化、人工与自动任务排队、空闲及文字/图片处理时的进程组内存和CPU、退出后的残留进程。不预先承诺更省内存或固定提速百分比。

## 7. 旧数据、切换与恢复

旧发送账本已有account_id、connection_epoch、chat_id和operation_id，是历史对应依据；不能仅因目录按商家命名就丢掉账号证据。来源范围限定为已登记及用户明确选择的确切目录，不扫描其他账号或磁盘猜测，不宣称已找全未登记来源。

初始化区分“接管已知旧环境”和“本机声明来源内未发现历史的新接待环境”，不能用新建按钮绕过旧记录。保存可核验的本机来源清单，至少包括公共登记、用户明确选择的源、已有账号环境登记、目录/文件可读性、账号操作索引和已知旧进程/锁状态。集合内发现同账号历史则进入接管；来源缺失、不可读或账号对应存疑时阻断关联范围。仅在该集合检查完整、无同账号旧活动或未决操作且无已知旧消费者时，才允许建立新的接待起点，从明确开启后的新消息开始。记录检查范围，不声称排除了未登记目录或其他机器；以后发现旧未决记录时立即冻结相关单聊并核查。

缺少平台消息ID的旧unknown可能长期无法核实。围栏持续保留，解除只依据确切受理或确切未提交证据，不承诺通过迁移或重新扫码一定能恢复该单聊自动发送。

切换流程：

1. 暂停旧通道，保存编辑并正常退出已知旧消费者，检查相关锁和进程所有权；仅新账号锁不足以证明旧版本已停止。
2. 对声明的源集合做完整备份并校验文件清单、有效WAL、旧WhatsApp实体、账本和回执。源变化则停止导入，原目录保留。
3. 在临时目标验证按account_id/chat_id/op映射的导入，保留原操作、正文、受理证据和来源摘要，不按正文合并操作；缺失、冲突或账号不明的来源不得视为空历史。
4. 新环境保留可追溯的旧ledger字节和必要操作快照；导入标记与数据原子落地、重复执行幂等。相关prepared/sending/unknown继续形成单聊围栏，不能通过“确认导入完成”清除。
5. 新Chrome用新profile重新扫码并核验账号。先核查未决操作及来源完整性，再明确开启允许范围；历史加载不触发自动补答。

若已知旧消费者未退出、无法核验来源或账号对应，则关联范围自动发送保持阻断，人工网页仍可使用。不能用用户一次确认、新空库、换根或忽略错误代替确切证据。旧版本不支持新账号锁的限制必须在切换说明中披露，不承诺阻止用户在未知旧目录另开程序。

0.4.1必须实现合成数据的升级与回退演练。真实历史导入、合并或迁移须对具体源、目标和备份范围另获明确授权，方案不触发这些操作。原Electron登录目录不删除、不复制Cookie，不保证免扫码。

账号备份覆盖消息/媒体、分段摘要、绑定及修订、草稿、任务、模型尝试、发送账本、回执和历史来源材料。完整业务备份还需覆盖相关商家根与旧账本集合；只导出账号库时明确不包含哪些商家资料，不能称完整恢复副本。Chrome登录profile与业务备份分开。

恢复到空目标，保全原操作与unknown；恢复后核验账号、商家来源和绑定并保持自动接待暂停。回退程序不等于回退账本，禁止用旧库覆盖新发送历史。恢复边界沿用[数据与运行](DATA_AND_RUNTIME.md)与[迁移说明](MIGRATION.md)。

## 8. 商家发现、模型诊断与反写预留

### 8.1 发现和就绪状态

继承C版从当前Windows用户令牌定位共享目录的修复，覆盖普通启动和Accio重定向环境的对照测试。启动台索引、模型配置与Chrome账号环境使用同一真实用户根；商家业务数据仍使用各自已登记的实际根，不因统一设置而迁移。

商家通过受支持授权启动、身份及数据根核验成功后登记到公共索引。登记失败有明确提示和有界重试；已有隔离目录通过原生选择导入位置提示，不能变成永久授权，也不能反向读取其他进程的令牌或环境。

状态处理至少区分下列情况；首页使用短词和直接动作，来源、修订及详细能力信息收进连接/模型详情，不将整张诊断表常驻在日常界面：

| 状态 | 用户可见含义及动作 |
| --- | --- |
| 当前来源无商家 | 指明检查来源，可选择已有登记目录或从对应Accio会话授权启动 |
| 元数据不可读/格式异常 | 显示登记读取失败，不伪装成没有商家，不输出底层敏感堆栈 |
| 商家已登记但未在线 | 允许选择位置；使用业务资料需重新建立受支持的授权连接 |
| 运行窗口/服务核验失败 | 不激活或代理该服务，重新授权，不恢复旧发送权限 |
| 共享配置不可用 | 显示共享目录解析或读取失败及下一步，不回退隔离空配置 |
| 未选接待API或无凭据 | 跳到全局模型配置，不要求逐商家绑定Key |
| 能力未检查/配置已变化 | 显示具体能力、用途和检查修订；用户确认后执行可能计费的检查 |
| WhatsApp绑定商家不可用 | 只暂停相关联系人；独立Chrome人工聊天仍可用 |

模型配置与商家登记是两个独立条件，不把全部失败合并为“接待模型不可用或已变化”。诊断展示配置来源、用途和修订，不展示明文Key。过期能力检查和迟到结果不能覆盖新配置。

### 8.2 预留WhatsApp内容反写国际站接口

用户要求保留未来可解锁的反写能力。0.4.1定义版本化DTO、能力查询和宿主私有服务接口，状态默认`available=false / enabled=false`；关闭时返回明确的能力未开放结果，不创建写入任务、不写库、不调用平台。内部保留能力查询与契约测试，普通界面不展示未开放的回写入口，不能靠renderer或扩展参数把关闭能力改为可用。

读背景与反写分属独立权限和接口。未来采用“预览计划→核对并确认→提交→独立回执”的流程，不能扩展只读上下文接口为任意写入RPC。来源以用户明确选择的WhatsApp内容为单位，不默认同步全部历史。

| 契约部分 | 预留内容 |
| --- | --- |
| 能力 | 版本、目的地类别、内容类别、是否可用/开启、所需授权及禁用原因 |
| 来源 | account_id、chat_id、确切message_ids/来源版本、上下文分段及原绑定归属、内容哈希 |
| 目标 | 明确商家、实际data_root、国际站客户conversation_id、写入对象及预期目标修订 |
| 内容 | 规范化摘要、需求增量、备注或消息引用等受限载荷；保留WhatsApp渠道与发送方来源，不伪造国际站原始消息 |
| 预览与提交 | 预览编号、载荷哈希、来源/目标快照、原生确认凭据；目标或关联变化后重新预览 |
| 幂等与回执 | 稳定操作键及operation_id，区分本地保存、平台受理和unknown；未知结果只核查原操作 |

“写入本地国际站客户业务记录”和“真实写入国际站平台”是不同目的地，能力分别声明；后续可按摘要、需求、备注等具体对象逐项解锁。真实平台是否支持某种写入须核对受支持的适配器和权限，不能因为预留DTO就声称已有平台API。给客户发送平台消息也不是普通内容同步，须另列发送能力和授权，不能借反写开关自动开启。

反写目标必须与冻结来源的商家归属及明确客户关联相符；切换商家或变更关联不能静默改写既有预览的目的地。不得把其他商家的内部资料、未授权客户信息或模型/平台凭据一并反写。需求回填继续遵守ai-v1、证据及独立requirements_revision，未来需补齐跨渠道证据契约，不能直接将WhatsApp消息ID伪装成国际站证据。

本版仅做接口预留与关闭状态的契约测试，不实现真实同步、自动回填或外部写入，也不因此改变现有业务数据。后续解锁需有对应适配器、逐项能力检查、独立授权和幂等/冲突测试。
