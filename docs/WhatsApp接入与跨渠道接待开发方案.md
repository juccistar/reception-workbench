# WhatsApp接入与单向上下文技术方案

日期：2026-11-13。面向开发及验收人员。

状态：0.3.17已实施并公开发布，已并入[0.3.17主方案](0.3.17开发方案.md)。依赖固定为whatsapp-web.js 1.34.8和Puppeteer 24.38.0，锁定生产运行资源随包校验；原始Electron视图与SDK共用DOM、公共登录页注入到扫码状态已通过。未登录真实账号或执行真实收发，公开交付状态见[验证记录](verification/0.3.17.json)。旧自绘聊天原型已停止采用。

## 1. 最新范围

- 左侧新增独立“WhatsApp”模块，不与国际站客户接待混在同一聊天页。
- 使用WhatsApp Web原始列表、气泡、输入框和登录界面；本程序只加外层连接状态、当前控制对象、国际站对话绑定、背景详情与自动接待开关。
- 完成账号接入和当前账号所有单聊客户的文字自动接待，包括未绑定国际站及后续新联系人；国际站对话绑定是可选增强，有绑定才追加其聊天及补充背景，未绑定也正常接待。
- 数据方向仅国际站→WhatsApp AI上下文。WhatsApp消息、摘要、更正和回执独立保存，不写入国际站消息、摘要、需求、未读/回复状态或采购/登记流程。
- 不在首版实现自绘建议/润色编辑器、WhatsApp正式需求/采购管理、群发、附件自动发送或双向同步。原生页面中的人工操作由用户直接完成。

## 2. 原生页面与SDK的技术门槛

whatsapp-web.js通过Puppeteer访问WhatsApp Web。2026-11-13读取官方main/package.json为1.34.8、Puppeteer 24.38.0；这是读取分支时的事实，实施时须选定正式版本和lockfile，不据此声称Electron兼容性已验收。

官方Client.js当前在browserWSEndpoint/browserURL连接分支中执行puppeteer.connect，随后browser.newPage；因此不能把“支持连接现有浏览器”误写成“原生嵌入页面可直接接管”。

本版推荐：

1. Electron用独立WebContentsView承载真实WhatsApp Web页面，保留原始布局及隔离的商家/账号持久session partition。
2. 增加受控Page适配，让whatsapp-web.js使用同一可见页面。先验证Electron45与选定Puppeteer/SDK的兼容性，必要时使用最小可审查初始化适配，保留上游来源及许可。
3. 登录态由该页面的Electron持久partition统一管理。LocalAuth管理的是另一套浏览器profile，不与partition并发管理同一目录，也不另开一份后台浏览器假装共享账号。
4. WhatsApp远端页面没有业务preload、window.reception或Node权限；SDK控制能力仅在受信宿主。页面会话及权限策略与工作台分开，按原生操作和用户手势处理所需权限，不能为接入而放开全应用权限。优先使用仅作用于该WhatsApp内容的页面适配，不对整个工作台开放通用调试入口。
5. 同页面、导航、预注入脚本及公共扫码页先以隔离Electron实际检查；账号身份、重连及真实收发按另行明确的测试账号范围验收。前者通过不能冒称后者通过，不以双页面/双会话替代。本版原始页与SDK同页面适配已通过，真实收发仍未验收。

项目仍为非官方WhatsApp客户端连接器，官方README不保证账号不会受限；原生网页外观不等于官方授权API。此处不改变已说明的选型边界。

## 3. 身份与绑定

首版每商家一个WhatsApp账号，并保留account_id维度供后续扩展。商家边界仍是当前实际seller_id，WhatsApp登录身份单独保存。

绑定键为商家+WhatsApp账号+确切chat_id，指向同商家的一个明确国际站会话，保存revision、带入范围和确认记录。外部ID作为不透明值保存，PN/LID别名仅采用SDK可验证映射，不从联系人名或手机号相似度推断。

原生页面当前聊天必须可靠映射到chat_id；如果不能可靠识别，外层绑定弹窗明确选择后台核实的联系人，不按页面标题猜绑。绑定信息随可见聊天切换，但后台已冻结的生成/发送目标不随焦点漂移。

账号开启自动接待后覆盖全部单聊，未绑定联系人也使用WhatsApp对话和商家通用资料正常接待；新联系人无需逐个绑定或逐个授权。绑定只增加可选国际站背景，不打开或关闭接待。解绑/改绑递增背景状态版本并取消旧生成/未提交草稿；原本自动接待且仍有有效待回复消息的客户按新背景重新生成，原已接管/暂停的状态继续保留，旧在途及unknown操作仍按原目标核查。

## 4. 单向背景与独立写入

| 数据 | 国际站→WhatsApp上下文 | WhatsApp→国际站 |
| --- | --- | --- |
| 原始聊天 | 只读带入绑定会话的近期消息和必要旧依据 | 不同步 |
| 会话摘要 | 作为背景导航，事实可回查原文 | 不更新国际站摘要 |
| 采购需求/有效供货条件 | 只读参考，不改变国际站case | 不写回需求、选择或修订 |
| 业务补充/已提取附件文字 | 带来源与版本进入该客户上下文 | 不写回国际站补充 |
| WhatsApp消息、独立摘要和回执 | 仅用于该渠道 | 不进入国际站消息或业务状态 |

“带入上下文”不等于把国际站历史逐条发送到WhatsApp。后台优先读取本机已同步版本，国际站有新来源时更新背景版本，下一轮WhatsApp生成再采用；不因背景变化主动补发消息。

新增独立wa_message、wa_summary、wa_draft、wa_operation等对象。WhatsApp入站不直接调用会自动创建国际站case或触发采购/登记的现有ingest/保存流程；通过明确的渠道处理边界保存。

## 5. AI任务

沿用当前商家已授权Accio环境，将AI运行身份与国际站target校验拆开；不伪造数字客户ID。所有单聊以当前WhatsApp对话、独立摘要和商家适用通用资料生成回复；没有国际站买家ID或绑定关系也是正常路径。有有效绑定时再追加对应国际站背景，未绑定不借用其他客户数据。绑定状态（含未绑定）有独立版本，生成及提交时均可核对变化，输入受现有总预算约束。

保留事实、意图、更正、资料用途、内部成本和业务承诺限制。新模式只输出WhatsApp回复、reply_sources及wa_summary，不输出或应用国际站requirement_changes，不创建产品/采购/询价/飞书登记副作用。

例如国际站500个、WhatsApp明确改800个：当前WhatsApp可根据明确关联理解更正并保存在独立摘要，国际站仍保留原500个和原记录。归属不明确时澄清，不用一个渠道的新增消息自动覆盖另一个渠道的正式需求。

图片仅在受控缓存和本轮确切读取证据成立时参与理解；首版先验证文字自动回复。无需独立“背景理解”AI请求。原生UI的附件功能不等于本程序已经解析或自动发送该附件。

## 6. 事件、人工接管与发送

监听账号、入站、fromMe、ACK及更正/撤回等必要事件，按固定SDK版本校验。ready不替代同步水位；断线补读须去重，历史回放和本程序发送回显不再次触发AI。

原生页面和手机端的新人工回复，如果不属于已登记的程序操作，则取消旧生成并接管该WhatsApp客户。原生页面切换、人工接管、暂停及绑定变化均不能把迟到结果路由到另一个聊天。

程序自动发送绑定冻结账号/chat_id、确切正文、来源/绑定版本和当前授权，保留业务operation与实际提交端持久账本。ACK_PENDING不称已送达；有确切消息ID及ACK_SERVER证据才能记为已提交，送达/已读分别记录。缺失回执或崩溃间隙保持unknown，只核查原操作，不按正文相同猜成功。

程序的未决发送锁只约束本程序新增自动发送，不能声称禁止用户在原生UI或手机里自行发送。新的人工消息也不能被用来清掉旧unknown。

WhatsApp与国际站授权分别保存，重启/重连不自动恢复发送。WhatsApp开启后覆盖全部单聊，继续尊重单客户人工接管/暂停；群聊、广播、状态和频道不算单聊，不对全部历史联系人主动补发。两渠道在当前商家AI槽内公平排队，消息接收和本地保存独立于长AI请求。

## 7. 接口及验证重点

宿主负责原生容器、登录态、SDK适配与事件转发；Python负责商家归属、绑定CAS、只读背景快照、任务、授权及业务账本。现有JSON Lines业务传输保留，不新增本地HTTP业务端口。

具体拟新增边界包括：账号状态、当前/明确选择的chat_id、绑定保存/解绑、背景预览、WhatsApp独立接待启停、宿主私有入站和发送回执。DTO、preload、main和Python白名单同步核对；原生页面不直接调用这些业务接口。

验收先证明同一原生页面/会话，再分别验证未绑定存量单聊、新入站联系人和已绑定单聊均能自动回复；增加绑定时背景增强、解绑后回到WhatsApp独立背景的回归。最后验证自动发送与异常恢复，并比较任务前后国际站消息、摘要、case修订和采购/登记记录，证明无反向写入，不能只看UI没有显示WhatsApp消息。

真实连接/收发限定届时明确的自有测试账号及联系人；目前方案和旧HTML原型均不构成生产接入验收。完整实施阶段与商品图/复制/时间修复一起见[0.3.17主方案](0.3.17开发方案.md)。
