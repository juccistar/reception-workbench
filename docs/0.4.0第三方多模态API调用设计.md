# 0.4.0 第三方多模态 API 调用设计

日期：2026-11-15。面向负责 Python 业务、Electron 宿主、模型适配和验收的开发人员。

状态：设计，尚未实现。依据用户已确定的“使用具有视觉能力的第三方 API”编写，属于 [0.4.0 开发方案](0.4.0开发方案.md) 的实施契约补充。具体服务商、端点和模型尚未指定；本文定义项目自己的请求与校验边界，不声称任意服务商均支持某个字段、图片上限或价格。

## 1. 确定的调用方式

启动台统一保存本机同一 Windows 用户下所有商家的多个 API 配置，以及“接待 API”和“翻译 API”两个全局选择；商家窗口不再保存自己的模型覆盖。可以使用不同服务商、同一服务商的不同模型或明确选用同一配置。接待、建议、润色、需求整理、摘要和 WhatsApp 回复使用全局所选接待视觉 API；中文翻译使用全局所选翻译 API，允许纯文字模型。模型配置共享，各商家的身份、数据、用途启用及授权范围独立。

- 接待有相关图片：正文、业务上下文、图片来源清单及实际图片内容同轮提交所选接待 API。
- 接待没有相关图片：仍用所选接待 API 的文字输入，不临时改用翻译 API。
- 中文翻译：仅把待翻译文字及受限翻译上下文提交所选翻译 API，不发送图片、需求或整份接待上下文。
- 一轮正常接待同时返回回复列表、必要的需求增量、多事项归属及摘要；一至三条回复只发起一次正常业务生成。
- 不固定增加先识图/OCR、再转文字、再生成回复的串行调用。模型拒绝、不完整结果和有限重试分别记录，不计为正常业务设计所需的多轮请求。
- Accio 保留商家身份、平台读取、平台提交、回执和真实采购工具职责。接待推理不再依赖 Accio AI 工作区、桌面 query 或本地临时图片路径。

第三方未配置、图片能力未通过或图文请求失败时，显示具体任务状态；不自动切换到 Accio 生成，不丢弃图片改为纯文字自动发送。手写聊天仍走独立人工发送链。

启动及调用诊断遵守主方案第 4.3 节的精简输出契约。provider 初始化、能力状态和图文调用不向启动终端打印请求体、Base64、响应正文或原始 SDK 调试日志；允许的阶段计数与耗时进入受限本地诊断，避免它们被 Accio 收入上下文。

## 2. 模块与职责

| 模块 | 职责 |
| --- | --- |
| 宿主 provider 配置 | 多配置列表及稳定 ID、独立模型/端点/凭据修订；DPAPI 保存，按所选用途受控注入 |
| `model_router.py` | 按启动台全局 reception 或 translation 绑定解析 profile，冻结路由/配置修订；独立校验商家/数据根权限及所需能力 |
| `model_inputs.py` | 冻结文字上下文、时间线、输出 schema、来源版本和输入顺序 |
| `model_media.py` | 解析受控资产引用、核验图片内容与归属、计算原图/实际输入摘要、管理字节预算与缓存 |
| `model_providers/base.py` | 统一文字/图片内容块、能力、截止时间、取消、完成状态与安全错误对象 |
| 实际协议适配器 | 将内容块转换为服务商要求的图文协议，管理连接池，解析停止原因、完整响应和 usage |
| 共用输出校验 | 校验回复、需求、来源和图片证据，复核生成期间的状态变化，发布有效结果 |
| 原生平台/WhatsApp 发送层 | 冻结正文并按原规则提交、保存受理证据、核查 unknown |

以上新增模块均为规划路径。协议相同的多配置复用适配器，协议不同则实现对应适配器。接待使用兼容 Chat Completions 时必须实现真实多模态内容块，翻译仅需文字及其输出契约；使用 Anthropic 时采用官方 Python SDK。只实现实际选用协议，不猜参数或多轮探测兼容性。

接待 `check_ai` 按所选接待 profile 检查文字、结构化和图片能力；翻译检查所选翻译 profile 的文字及翻译结构化能力，不要求视觉。同步修改现有单一 AI 门控，平台连接检查独立。接待文字/结构化通过但视觉失败时，仅允许真正不需图片的任务，不能删图获得准入。启动/保存配置不自动发付费检查，不要求先跑 Accio AI 检查。

### 2.1 配置与用途绑定

遵守主方案第 8.3 节：启动台保存多个稳定 profile_id，以及全局 reception_profile_id、translation_profile_id 和两个用途各自的 route_revision。存储在真实 Windows KnownFolder 的宿主配置，作用域为本机同 Windows 用户，不随商家 registry、业务数据根或启动方式复制。没有商家也能配置；商家工作台只有摘要与跳转，不支持商家级模型覆盖。接待下各子任务共用接待选择，商家本身的独立开关、数据范围、grant 和任务 schema 保留。

切换全局翻译使全部运行商家的旧翻译失效；切换全局接待使全部运行商家的旧接待生成失效并撤销相关自动授权，分别重新开启。仅编辑另一独立 profile 或添加未选配置不使当前请求失效。同一 profile 的端点/模型/凭据变更影响全部实际引用方，单纯改名称不改变执行修订。请求以全局用途路由和所选 profile 修订核验，同时校验独立商家来源；不能用整个配置目录修订取消所有任务。

全局配置写入使用跨进程锁、预期修订比较及完整快照原子替换，避免多个窗口覆盖对方修改。宿主通知/有界刷新加速变更传播，调用、结果应用和未提交自动批次推进边界仍核对最新依赖修订；不能确认最新配置时停止相关外发。已进入不可撤销平台提交的操作沿原回执处理。启动台关闭不影响商家读取已保存配置，不要求常驻配置进程或集中代理模型流量。

旧有效共享翻译连接只承接翻译用途；若多个旧有效选择存在冲突，列为待选择配置，不按第一条或最近商家覆盖。旧商家/数据根的数据外发授权范围不扩展到其他商家或接待用途。删除仍被引用的配置须先解绑或明确替换；配置缺失、停用、能力失败时该用途不可用，不默认借用另一 API。译文缓存按商家、profile 和语义版本隔离，旧译文不算新配置命中；费用/耗时按商家、用途及 profile 分开。未选配置不初始化连接或注入密钥。

启动台主动能力检查使用合成输入和有限生命周期的独立检查进程，不依赖商家业务服务或 Accio 授权；先告知可能产生 API 费用，由用户主动发起。全局能力证据绑定实际配置修订，同一检查去重；各商家进程仍检查本次运行可用性与自身权限。配置或检查成功不自动开启商家接待。

## 3. 一次生成的完整流程

1. 入队只保存任务/来源 ID、版本、范围和期限，不持有完整上下文及图片；核对已验证商家、数据根、接管、许可和 provider 修订，分配本次认领与取消标记。
2. 取得一致的业务来源快照，确定消息、事项/需求、资料、补充、供货方案、渠道代次和所需图片。此时仍是准备阶段，不声明模型已收到图片。
3. 在受控媒体队列准备图片，不持有业务锁或模型 HTTP 槽。媒体就绪只推进原任务，不构成新输入或重置尝试链；若真实消息/附件/授权变化则取消旧任务。
4. 逐张核验归属、格式、像素、大小和 SHA，释放像素工作区；按主方案第 6.3 节预留缓存、编码及请求副本内存，检查服务商真实限制。资源暂缺延后准入，单任务超上限明确失败。
5. 核对原业务快照仍有效后，冻结包含 ready 媒体版本/输入摘要的最终上下文，再组装图文块。发送前复核来源、授权、能力和取消，持久记录 generation_id、attempt_chain、配置修订及允许的输入清单摘要；不持久重复保存 Base64。
6. 通过持续生命周期的 HTTP/SDK 客户端执行一次推理。取消立即使结果失去发布资格并主动取消本地网络任务，不能承诺服务端同时停止；连接/读取/总时限受控，SDK 无隐式重试。
7. 有界接收完整结果，检查 HTTP/协议状态、停止原因、JSON 完整性、schema、来源引用和请求级图片证据。流累计和解压后响应同受上限约束，不保存全部流事件作为第二份正文。
8. 复核当前来源和配置，失效结果仅记受限状态/耗时，不在多个缓存保存整份过时上下文。有效结果才进入同一事务应用，润色不写需求/摘要；失败/取消在执行单元 finally 释放各自资源。
9. 自动任务冻结整轮回复批次，再按原通道逐条发送；模型请求完成不表示平台已经发送或客户已读。

本用途路由或所引用配置改变、人工编辑、新买家消息和账号代次变化可使旧生成失效；独立翻译配置变化不使接待生成失效。迟到的图片下载或模型返回不能恢复旧授权。

## 4. 项目内部请求契约

以下为项目内部规范，不是某家服务商可直接接收的 HTTP JSON。实际编码由协议适配器负责。

| 部分 | 主要字段 | 边界 |
| --- | --- | --- |
| 请求身份 | format、generation_id、task_kind、client_request_id | 本地生成，绑定一次准确调用与原任务尝试链 |
| 用途路由快照 | purpose=reception/translation、route_revision、profile_id | 冻结启动台全局所选 API；商家权限另验，另一用途变化不使本请求失效 |
| provider 快照 | profile_id、config_revision、credential_revision、requested_model、capability_revision | 绑定实际配置及凭据版本，冻结后不能在原请求中途替换 |
| 本地范围 | mode、seller_id、data_root_key、channel、conversation_id 或 WA 目标 | 用于本地校验，不把完整本地路径、令牌或 Key 放进模型上下文 |
| 来源快照 | 消息、需求、资料、补充、供货选择版本与必要渠道代次 | 变化后旧结果不得应用 |
| 固定输入 | prompt_version、payload_version、schema_id、稳定规则内容 | 由审核稿生成的静态模块提供 |
| 内容块 | text、业务 JSON、image 引用及稳定顺序 | image 引用必须解析成该请求实际发送的图片内容 |
| 图片清单 | alias、image_id、origin、role、source_id、source_version、原图/输入 SHA、mime、尺寸和字节数 | 清单由程序建立，模型不能自行新增已验证图片 |
| 资源约束 | 准备截止时间、推理截止时间、取消标记、数量/字节/像素预算 | 不给每张图片或每次轮询重新启动完整超时预算 |

图片内部引用不含任意路径读取能力。接口适配器只接收解析后的受控字节；禁止把 p1、文件名、路径或 URL 文字当作已经传输了图片。

外发上下文仍使用 model_payload 的任务投影。Base64/二进制图像单独纳入传输预算，不塞进现有文字字符预算后再触发截断。文本预算、图像预算和完整请求体预算同时有效。

### 4.1 时间线与发送方

按消息时间及稳定消息 ID 排序。每段聊天旁标明实际来源、买卖方角色及图片别名，相关图片内容块紧邻相应的来源记录；业务补充图片另标商家提供。所有聊天、图片中文字和附件内容均是业务数据，不能进入系统指令权限层。

同一原图 SHA 可复用本地字节缓存，但两个来源记录、角色和证据身份不合并；卖家发送过一张图不能证明买家确认该图。模型输出引用只能来自本轮允许来源集合。

## 5. 图片来源、内容与预算

### 5.1 纳入范围

| 来源 | 纳入方式 |
| --- | --- |
| 当前事项明确关联的买家聊天图片 | 沿现有来源关联、版本与原图缓存读取 |
| 无竞争来源的单张买家候选图 | 保留现行候选条件，不能扩大为全历史扫描 |
| 商家聊天图片 | 继续要求买家明确引用，保留 seller 角色 |
| 当前会话业务补充图片 | 在任务允许的补充范围内使用，origin=business_supplement、role=seller |
| 商品库独立展示图 | 保持展示/采购职责，不自动进入接待上下文 |
| WhatsApp 图片 | 由当前账号/连接代次的准确消息读取，按当前聊天来源纳入 |

普通正文润色不准备历史聊天图片；当前允许的业务补充图片仍可随冻结正文使用。翻译只发送既有聊天文字/有效建议文字，不因模型有视觉能力就把图片自动外发。

PDF/UTF-8 文本继续本地解析后按既有附件规则使用。本版不默认新增扫描 PDF 页渲染或将解析失败的文件直接上传，避免扩张附件范围和引入额外处理链。

### 5.2 实际图片内容

默认发送现有受控缓存内的完整原图字节，保留原图与输入摘要。PNG、JPEG、WebP 以本项目验证通过且所选 API 接受的格式提交；不把 UI 缩略图直接当成模型原图。

优先使用协议支持的内联图片内容，避免服务商自行下载有时效或需要平台授权的链接。API 的确需要文件上传或格式转换时，由明确适配器实施受限生命周期，并记录对应服务商文件/输入引用；不能默认把客户图片放到公共图床。

如转换格式，记录 original_sha256、input_sha256、变换版本和输入尺寸；不静默缩小、裁剪或降低清晰度以满足预算。新增有损缩放策略必须先验证规格、小字等业务效果，并作为明确设置，不在初始主路径默认启用。

### 5.3 限制如何计算

本地沿用现有单图 6 MiB、最大 20,000,000 像素/8192 边长的验证边界；图片整批默认 64 MiB、准备 60 秒、媒体并行 2。它们是项目边界，不是服务商能力保证。

单次有效容量取本地配置、服务商已核实图片数量/尺寸/字节限制、上下文与完整 HTTP 请求预算、当前内存预留的共同约束。媒体网络并行 2 不意味着像素解码并行 2；按主方案第 6.3 节重型像素处理默认串行。20MP 一份 RGBA 约 76.3 MiB，64 MiB 压缩输入的原字节/Base64/JSON/UTF-8 多副本可能约 320–576 MiB，故必须先按实际编码器预留，逐张校验后释放像素，再编码请求。数值是静态估算，64 MiB 准备额度不是服务商容量或进程峰值保证。

缓存只复用同商家/模式/数据根的压缩字节或受限验证/变换结果，不常驻像素数组，不同时无限保留原图、Base64、JSON 和 SDK 请求副本。可选缓存的 LRU、TTL、字节/项数上限、在用固定与取消释放统一使用主方案预算；不另为 model_media 建一套独立不限量池。格式转换也要受工作区/输出大小限制，不能因压缩原图不足 6 MiB 就跳过输入转换后的限制。

不增加固定“每轮只取前四张”的规则。所需图片超出有效容量时，任务返回明确图片/请求预算错误，保留原上下文与图片；不截取前几张继续自动发送，也不自动拆成多轮识图再拼接事实。后续如实现分组归纳，需另有来源一致性和质量验收。

## 6. 图片输入证据与业务校验

### 6.1 证据由程序生成

为每次实际请求生成 `image_input_evidence`，至少包含：

- 本地 generation_id、attempt_chain、请求格式/配置修订、规范输入清单摘要，以及构建/发出/完成/验证各状态。
- 实际编码的各图片 alias、image_id、来源版本、原图 SHA、输入 SHA 和内容块位置。
- provider 返回的请求标识（如有）、停止原因与结果应用状态。
- 本地预期清单与实际编码清单的匹配结果。

规范清单摘要为必需字段。只有适配器能在发送边界对实际编码字节增量计算时才记录 `encoded_body_sha256`；否则明确记不可用，不能把另一遍 `json.dumps` 的摘要称为实际 HTTP 请求摘要。请求编码测试核对真实发送内容块；诊断只留摘要/允许元数据，不为哈希另复制一份完整 Base64 请求体。

只有对应视觉请求完整成功、响应通过协议检查且清单一致后，图片引用才能进入本轮输出校验。构建完成但未发出、请求取消、上传未完成、响应截断/拒绝、未知清单或旧配置返回都不能标为有效图片输入。

这项证据证明请求实际携带哪些图像，不能证明模型逐像素理解或识别绝对正确。模型自己输出 images_seen / 已看过图片不产生证据，也不能给失败的输入补证。

### 6.2 修改现行 read 工具语义

当前 [photos.py](../services/reception/src/reception_service/photos.py#L146) 和 [reception_context.py](../services/reception/src/reception_service/reception_context.py#L57) 仍使用 read_images、ready_for_read、read_compat 及“本轮 read 工具打开”规则。0.4.0 必须同步修改：

- 将传输类型规范为第三方多模态输入，与无图片任务区分。
- 组装阶段区分待提交和已绑定请求，不能准备完成就提前标为模型读过。
- 用请求级输入证据向统一校验器提供实际可引用图像；模型无权回填这部分本地字段。
- 提示词改为“本请求附带的图像”，移除文件路径和调用 read 工具的要求；保留角色、来源、不确定性及禁止把视觉推断当确认的规则。
- 同步自动、人工建议、润色、需求整理、WhatsApp 和合成检查的上下文与 schema，不能只让第三方结果绕过原图片校验。

需求仍为 ai-v1 固定 13 字段。图片可提供可见产品特征的依据；数量、材质、认证、报价、交期等不能仅凭外观无依据推断。旧业务资料与销售口径仍按当前启用和适用范围控制。

### 6.3 输出原子性

自动回复、requirement_changes、多事项引用及摘要来自同一冻结输入。先完成结构与来源校验，再事务应用；同轮失败不部分发布需求后再丢弃回复。润色只处理冻结未发送正文，不更新需求/摘要。

自动回复保持自然一至三条、整轮预算和逐条来源；人工建议严格一条。流式预览必须标注未完成，不能直接采用、保存为有效需求或提前自动发送。

## 7. WhatsApp 媒体入口

现状依据：[宿主消息 DTO](../apps/desktop/src/main/whatsapp/host.ts#L21) 只有 body 等文字字段；[业务入库与触发](../services/reception/src/reception_service/whatsapp.py#L198) 仅在新买家消息 body 非空时设 pending。这是接入视觉 API 之外必须补齐的工作。

1. 消息事件增加媒体类型、准确消息 ID、来源版本和 `pending/ready/failed` 媒体状态；caption 继续保存原文。纯图片新消息也建立待回复来源，不能仍以 body 非空筛选上下文。
2. 原任务处于等待媒体状态，有准备期限及唯一唤醒标记；媒体 ready 推进原任务，failed/超时终止该次生成。消息 ID、原始来源版本、媒体就绪内容摘要进入最终上下文/指纹和允许引用集合；同步调整 `_wa_fingerprint`、attempt_fingerprint、结果引用及 `_wa_current`，不能把媒体完成当新客户输入或让同指纹防重误挡恢复。
3. 宿主通过原始页面关联的同一 SDK 按准确消息取媒体，保留单页面/CDP。只拉当前所需图片，不预下载全历史媒体，不把登录资料交给第三方。
4. 先校验可用媒体类型/大小，未知或超过边界不自动拉取；下载、SDK 分块、宿主交付、Python 入库逐层限定累计字节和期限。采用私有 256 KiB 块、背压和增量 SHA，不经 renderer 推送原始大 Base64。
5. 每个任务绑定 seller、WA account、connection_epoch、chat_id、message_id；下载前、分块中/完成及结果应用前复核，账号切换取消原读取，迟到内容不能借新账号补取或入库。无完整内容及 SHA 不标 ready。
6. 历史导入、联系人 metadata、商家消息和媒体完成仍不新增接待事件；群组/广播排除，后台媒体读取不推导客户已读。
7. WhatsApp 需求和摘要保持独立语义；国际站绑定背景只读，平台私图不因绑定自动共享，WA 结果不反向写国际站或触发采购/飞书。

**锁定 SDK 的实际边界。** 本机 1.34.8 的 `downloadMedia()` 会先把完整 Blob 转为 Base64；已有 `downloadMediaStream({chunkSize})` 可分块取得内容，默认块为 10 MiB，不能直接沿用默认值。优先基于该已有能力做受控适配，不重复实现第二个浏览器；但它仍先调用 `resolveMediaBlob` 取得页面完整 Blob，流式 IPC 并不限制页面自身下载/解码的全部内存。元数据限制、返回后大小校验及应用请求配额都不能被宣称为网页端绝对硬上限。

适配器必须明确拥有 stream、页面句柄和取消标记，在正常结束、首块前拒绝、半途取消、断页及代次变化时全部释放；不能仅假设 `stream.destroy()` 必然覆盖尚未开始迭代的句柄。实施时核对实际打包 SDK 的相同接口并验证页面/宿主内存，仍无受控读取能力时将该媒体记为不可用，禁止回退到无界整图下载。

WA 媒体失败保留原消息及人工处理入口，停止该次需要图片的自动生成，不丢图继续回复，也不把空 caption 当作没有客户消息。SDK 静态能力不等于实号媒体读取/收发验收通过。

## 8. 并发、缓存与失败处理

默认每商家 1 个第三方生成请求；通过质量、配额及内存测量后最多 2 个，其中带图最多 1 个，同会话有状态写回的生成互斥。翻译独立队列、最多 1 个请求，可与不同 API 的接待并行。全部 profile 在同一业务进程内活跃 HTTP 默认合计最多 2 个，每个 profile 上限也为 2；增加配置不增加总并发、缓存或图片额度。限流按 profile/已知配额组分别处理，独立翻译 API 的 429 不暂停接待；共用 profile 或同端点同 credential_ref 时共用限流组。实际容量仍受服务商与资源上限进一步约束，采购保留 Accio 槽。

队列仅保存轻量引用，准备图片不占推理 HTTP 槽；资源暂缺延后准入而不堵住业务消费者。原图/编码/验证缓存遵守主方案的统一额度，固定在用对象不能被 LRU 驱逐。每次请求仍有自己的来源清单和证据，复用字节不代表模型记住了上一轮图片，下次需要时仍提供实际内容。

同一进程的持续事件循环拥有按 profile/凭据修订隔离的客户端与连接池，不跨 asyncio.run 共享 AsyncClient，也不为每个 API 新建独立线程组。只初始化当前绑定或主动检查的配置；同 profile 两用途复用池，停止一种用途不关闭另一种仍引用的池。不同 profile 不共享带授权状态的客户端；不再引用、检查结束或版本替换后关闭相应池，旧池清理也计入总连接预算。

取消立即使结果失效，主动中止本地请求；实际结束才归还认领与缓冲。关闭有截止时间，未退出单元继续登记并禁止写已关闭仓库，不靠无期限 join 或虚构 clean 完成退出。单个 profile 的超时只使相关任务失败；协调线程失活或清理越过声明期限仍触发全局执行器撤权，需同步改造 executor_health。

统一规则由各任务接入 attempt_chain，不能假设现有国际站预算已覆盖 WhatsApp、人工和翻译。自动链绑定真实来源，人工链绑定明确操作，翻译链绑定源文/上下文/目标语言；job/profile/重启/媒体就绪均不自动刷新预算。每链默认最多 2 次 HTTP 尝试，SDK 重试为 0；生成初始总期限 180 秒（含媒体最多 60 秒和退避），翻译 30 秒。排队年龄另限，失效来源不进入 HTTP。新客户输入或明确人工再试才可开新链。

| 情况 | 动作 |
| --- | --- |
| 图像损坏、格式/预算不符 | 发出前失败，不重试或丢图；单任务超容量不能永久标繁忙 |
| Key、模型、视觉协议不符或 401/403 | 相应能力不可用，等待修正，不换厂商试探 |
| 确定尚未发出的暂时网络错误、明确 429/可重试服务端错误 | 原链内最多重试一次；Retry-After/退避须装入剩余期限，服务端错误仍可能计费 |
| 上传后超时/断连，无完整结果 | 记录结果未取得和计费未知，默认不自动重放；协议支持时核查原请求，不由新 job 绕过 |
| 结构化输出无效/截断/拒绝/含工具动作 | 不应用、不自动发“修复 JSON”请求；记录受限错误 |
| 身份、配置或来源变化 | 取消/标 stale，不重试旧来源、不恢复授权 |
| 平台发送 unknown | 与模型结果不确定分开；只核查原 operation，不解除围栏 |

HTTP 响应解压后累计初始上限 1 MiB，流式与非流式相同，另限制 JSON 深度、条数和字段长度。各任务按实际 schema 设置输出 token/推理参数，不能把翻译的 4096 或其他厂商专有参数套用全部生成。应用层流式预览不是本版必需，传输流式也不能提前采用或发送。

不默认预热/保活、并行请求多个模型抢答案或跨服务商/跨用途静默回退。接待切换需选择已配置、能力通过且允许接收相同内容的视觉 profile；翻译只需满足文字及翻译 schema。切换重新核对用途修订和授权，不自动重放旧发送批次。

## 9. 能力检查与定向验收

按所选用途检查对应 profile：接待分别记录文字、JSON、单图、多图及图文结构化组合；翻译只检查文字和翻译结构化输出。能力绑定 profile/model/config_revision，两个用途的 schema 检查分别记录，不能用翻译通过推导接待通过，也不因翻译 profile 无视觉能力标记翻译失败。

接待视觉能力检查在实际调用前固定合成图片、输入、预期答案和通过规则，不在文件名、提示词或 alt 文本泄露图片答案；这些图像探针不用于仅绑定翻译的 API。接待能力探针至少包含：同一文字配两张内容不同的单图、两张图交换顺序后仍按 alias 正确归属，以及图文与实际业务 schema 同时输出。对应用例须全部满足预设答案/归属、请求含真实图块、响应完整、结构合法；失败只标记相关能力失败，超时/未执行标未验证。不能用 HTTP 200、模型名含 vision 或一次文字翻译通过代替视觉证据。

能力探针与业务质量验收分开。业务样例在调用前固定预期需求增量、可引用证据、允许的不确定回答及禁止承诺；样例内出现跨客户引用、伪造买家确认、越权发送或无依据改需求即不通过。自然程度、小字识别和有效结果率单列人工评估，不能只比较更快/更短。小样本通过不证明所有实图均可靠。实际模型检查及样例执行需要明确数据范围与费用预算，本轮未调用。

必须覆盖：

- 启动台在无商家时也能配置，商家切换/不同启动环境使用同一全局选择；旧选择冲突、并发保存修订冲突、配置通知丢失、启动台关闭后读取及过时生成结果保护。
- 全局接待变更撤销全部引用商家的相关自动授权，翻译独立变更只影响翻译；模型配置不自动合并商家权限、内容或缓存，主动检查不启动业务服务。
- 多 API 的添加/重命名/引用删除、不同服务商或协议按用途路由、文字翻译不发图片、不做视觉检查；同配置可共用，缺配置不自动借用。
- 独立翻译切换/429 不影响接待，共用配置修改使两用途失效，无关配置修改不使任务 stale；译文按 profile 隔离，单用途停用不关闭共享池，多配置仍遵守进程总额度。
- 文字、单图、多图，买卖双方图片、业务补充图、窗口外明确依据和图文冲突。
- 原始字节/图片角色/来源版本不匹配、请求缺图、输入清单伪造、输出自称已看图、图像失效后迟到响应。
- 规格小字、EXIF 方向、透明 PNG、WebP 与不可识别细节；无损输入和原图可追溯。
- 6 MiB 边界、批量/最终请求体预算、过多图片、解码像素、取消和并发内存回收。
- WhatsApp 纯图片、带 caption、历史图片、群组排除、下载中切账号/代次、媒体迟到不新增接待。
- 整轮校验前不发送、自动两/三条的确切回执、人工输入不被旧结果覆盖、配置切换保全 unknown。
- 文字通过/视觉失败的按需准入、单请求超时不误伤其他任务、协调线程失活仍撤权、来源未变的新 job 不重置重试预算、已上传无结果不自动重放。
- 媒体等待不占模型槽、首块前和半途取消均释放句柄/字节额度、旧任务未退出不提前复用额度、响应超限及时停止；热身后多图轮换不持续增长内存/线程。
- 纯文字与带图任务分别计时：排队、准备、编码、上传、模型、验证和第一条/整批受理；费用按真实计费维度统计，不重复累加已包含在输入 token 的图片费用。

代码、替身和请求编码测试证明协议与状态行为；实际模型样例证明质量方向，公共扫码证明页面能力。三者分别记录，不互相代替。第三方视觉主路径未完成实际验收时，不能把 0.4.0 图片接待宣称为已验证能力。

## 10. 删除旧生成链的顺序

1. 先统一 provider 契约、图文输入和证据，复用现有业务校验并同步提示词。
2. 接通国际站与 WhatsApp、人工/自动各入口，完成取消、版本及定向回归。
3. 完成所选视觉 API 的实际图文验收后，删除接待专用 Accio query、AI 工作区发现、临时图落地、read_compat 和旧单独观察路径；不留双链隐式回退。
4. 清理仅服务于旧生成链的配置、DTO、提示词和测试；原始图片、旧结果历史、发送/采购原请求及回执保全。
5. Accio 真实采购工具、平台身份/读取/发送的组件按实际引用独立保留。历史 unknown 继续核查原记录，新模型不接续旧批次。

本设计不授权真实模型调用、发布、安装或真实数据迁移；本轮修改范围为方案与检查记录。
