# 需求文档：项目目标与交付标准

本文定义产品目标和验收条件；当前源码版本为 0.3.3，发行及新目录验证正在进行，见[本版说明](../0.3.3发布说明.md)。需求不等于已经实现或验收。

读者：项目负责人、接待业务员、开发与验收人员。

实现方式见[架构文档](02-架构文档.md)。本文是需求基准，不能仅凭需求认定已经实现或验收。

## 1. 项目定位

国际站客户接待工作台是一款Windows桌面软件，通过当前商家已授权的Accio Work环境连接阿里国际站，在业务员处理消息之前完成报价前接待：及时回应客户、理解采购意图、逐步补齐需求、保存依据，并把具备报价条件的采购事项交给业务员。

用户已明确产品定位：

> 我对这个程序的理解是这个样子的，这个程序目前主要的目的实现的是自动接待，但是在客户接待页面保留人输入信息并发送信息的功能，你觉得呢？

因此，自动接待和普通人工聊天共同构成客户接待页。人工发送不应被AI分析、采购条件齐全或资料配置阻塞。程序完成的是报价前准备；具体报价、交期承诺和商务决策仍由业务员负责。

### 1.1 成功应体现在哪里

| 目标 | 可观察的结果 |
| --- | --- |
| 客户得到及时、相关的回应 | 新消息被检测并按需同步；回复回答当前问题，寒暄不会被强制转成采购问卷 |
| 业务员减少重复询问 | 已知需求和出处可查；缺什么有清单；客户修正后保留旧版本并使用新值 |
| 同一客户多次采购不混淆 | 每个采购事项有独立需求、状态和草稿；新需求不覆盖旧待报价事项 |
| 业务员随时介入 | 客户页可直接输入、连续补充和主动跟进；接管后自动处理暂停 |
| 报价前信息可交付 | 待报价事项有需求摘要、未决问题、事实依据及交接状态 |
| 数据和发送结果可追溯 | 原文、修订、操作及回执保留；未知结果按原操作核查，升级恢复不制造重复发送 |

默认5秒检测是调度配置，不是“客户发来后5秒内必定回复”的服务承诺。AI和平台延迟需要实测；当前未设定或验收统一回复时延、识别准确率、RPO/RTO指标。

## 2. 使用对象与范围

每个接待实例服务单个已核验卖家工作区和主要接待业务员。2026-11-10用户确认统一启动方式：在不同Accio Work授权环境执行相同指令，程序先核验当前真实商家，再自动选择或创建该商家的独立工作区和宿主配置。不同商家可使用独立窗口，同一商家不创建第二个并行接待写入者。维护人员负责备份、升级及故障核查；开发验收人员负责实现和证据记录。这里的独立实例不包含统一客户控制台、跨店调度、共享客户库或多人权限体系。

| 范围 | 内容 |
| --- | --- |
| 当前核心范围 | 授权连接、消息检测与历史、自然接待、采购事实与事项、客户照片、人工聊天、待报价队列、本地数据与恢复、运行状态 |
| 正式业务完善范围 | 事实人工复核、完整待报价交接、复杂上下文与回复质量、持续运行和故障恢复验收 |
| 可选集成 | 飞书需求登记/待办；本地业务先完成，外部失败不阻断接待 |
| 当前不纳入 | 自动找货、RFQ、报价核算/自动报价、自动下单、多账号控制台、完整CRM、多人权限体系、云端多机同步 |

不以接待迭代为由恢复已经暂停的模块。后续若扩大范围，先更新本文和对应验收任务。

## 3. 业务流程

1. **进入工作区**：从当前商家已授权的Accio Work环境启动，核验卖家身份和客户归属，加载所选数据目录。启动后默认暂停自动接待。
2. **接收消息**：轻量检测会话活动，仅对变化客户读取正文；原文、消息标识和修订本地保存。历史覆盖不完整时明确显示，不假装已读全量。
3. **构建上下文**：结合最近原文、已保存需求和出处、当前采购事项、人工消息、适用卖家资料及照片观察；保留冲突和不确定性。
4. **理解当前意图**：先判断客户是在问候、咨询、补充/修改需求、发照片、开启新采购，还是结束交流。先回应当前问题，再问必要的缺失条件。
5. **准备回复与需求变更**：生成正文与逐项核验事实分开。商业承诺、正文数字或重复提问等质量问题只提醒，不暂停接待；非法事实不确认，冲突保留依据并自然澄清，需要商家核实的事项创建协助待办。图片观察与客户已确认事实分开。
6. **提交回复**：自动发送要求当前授权范围有效，并重新核验来源/正文版本、接管状态及未决操作；不限AI和自动发送次数但持续统计。人工发送按用户保存的确切正文提交。
7. **确认结果**：平台受理与排队分别显示。取得确切平台消息编号和核查证据后确认；未知结果保护整会话，核查原操作而不重发。
8. **进入待报价**：配置要求的条件齐全后进入“待我报价”。业务员复核和处理交接；新采购独立登记，普通聊天不清空旧事项。

“平台受理”“需求已登记”“已交接”“已报价”是不同事件，不允许用一个成功状态替代。

## 4. 功能需求及验收条件

以下FR编号是需求的稳定索引。

| 编号 | 需求 | 交付条件 |
| --- | --- | --- |
| FR-01 | 授权连接与身份隔离 | 当前卖家和客户归属可核验；演示/真实数据分离；缺授权、身份变化或连接失败有原因；不通过复制令牌授权 |
| FR-02 | 轻量新消息检测 | 自动暂停时仍可收消息；摘要检测不被AI长任务占用；按变化客户取正文，重复读取不产生重复消息；显示检测与同步状态 |
| FR-03 | 历史和未读 | 原始正文、附件关联、平台标识、时间及修订可追溯；历史覆盖状态明确；逐条未读随实际阅读边界推进，并发新消息不误清 |
| FR-04 | 自然接待 | 回答当前问题；问候、致谢、近况可正常交流；纯聊天不新建采购事实或事项，不反复追问；待报价后普通聊天不重开问卷 |
| FR-05 | 采购事实与事项 | 事实有消息出处、版本和事项归属；新增、补充、纠正、冲突可区分；不能把客户预算当卖家报价；新采购保留旧待报价事项 |
| FR-06 | 人工复核 | 业务员可逐项确认、修订、标记待核实并查看依据；修改留痕、影响缺失项和待报价判定，并使旧版本草稿/预演失效；AI提取的confirmed不等于人工已审核 |
| FR-07 | 图片接待 | 在来源可唯一关联时展示安全预览；视觉观察用于辅助回复并可追溯到图片和原消息；图片不可用有明确状态；猜测不能成为已确认采购条件 |
| FR-08 | 普通人工聊天 | 客户页直接输入和发送，无独立人工模式前置；不依赖AI检查、资料或采购齐全；支持连续补充、主动跟进；新输入不被迟到回执或建议覆盖 |
| FR-09 | 接管与恢复 | 首次人工编辑暂停该客户自动处理，其他范围内客户继续；人工消息进入历史与后续上下文；恢复此客户及全局启动均须明确操作，重启不恢复旧授权 |
| FR-10 | 自动范围与使用统计 | 当前授权内不限AI/自动发送次数，持续展示真实调用与发送统计；保留实际授权范围和阻断原因，每次外部调用及发送前重新检查；暂停、设置变更、退出、身份变化撤销尚未提交的权限 |
| FR-11 | 可靠发送与核查 | 保存确切请求及正文版本，按原请求防重；发送中/未知阻断整个会话；取得权威证据才能确认；核查、切事项、恢复备份均不得造成重复提交 |
| FR-12 | 待报价交接 | 条件齐全进入本地待报价队列，展示事实、缺失/冲突、来源与跟进信息；完整交接应支持业务员确认交接、退回补充及记录处理状态，不等于已报价或成交 |
| FR-13 | 可选飞书登记 | 本地保存成功后异步同步；展示失败、重试、未知和对应业务版本；写入需配置及授权；飞书不可用不阻断聊天和需求登记 |
| FR-14 | 可配置数据目录 | 设置页可手输或选择本机绝对路径，显示实际目录、配置来源和备份；配置独立持久，移动程序后仍有效；已选目录缺失不能静默新建空库 |
| FR-15 | 完整备份、迁移与恢复 | 正常停止并保存在途结果后执行；空目标、完整清单及哈希验证；保留原目录；恢复不能丢弃较新的发送历史；失败保留可用原配置且不恢复自动权限 |
| FR-16 | 升级与发行 | 兼容预检、必要的升级前完整备份；拒绝未知/未来结构；明确版本、哈希、使用说明及旧包；最终便携EXE实际验收后才晋级 |
| FR-17 | 状态、异常和可用界面 | 客户状态反映实际范围和阻断；生成动画区分排队/运行/完成且不伪造历史消息；重复后台日志汇总；常见窗口尺寸可使用，减少动画偏好生效 |
| FR-18 | 安装版在线升级 | 支持公开GitHub Releases或静态HTTPS目录，显示版本、说明及下载状态；GitHub只允许仓库Release与固定附件HTTPS域名，静态目录同源，均验证固定发布公钥；同一安装位置存在其他实例或未退出后台时阻止覆盖，启动与安装有共享互斥；明确确认后保存编辑、正常停止、完整备份，再安装并使用原商家/数据根重启；失败给出可恢复结果，不恢复旧自动权限 |
| FR-19 | 统一授权启动与独立商家实例 | 同一条当前程序启动指令先通过本次Accio授权环境核验真实商家AliID，再选择其独立数据与配置目录；旧根只在已有归属证据一致时收编，新商家自动分配新根，缺根/未知归属/身份冲突不静默新建或覆盖；不同商家可并行，同一商家跨数据根也不允许第二个接待写入者；重启重新核验身份，复制指令不固定当前商家或数据根，不保存令牌或恢复自动授权 |
| FR-20 | 人工协助及核实跟进 | 模型请求帮助、待核实承诺和事实冲突形成独立待办，AI继续正常回复；回填使用版本与幂等控制，内部结果不进入对客上下文，明确公开结果可在当前授权内安排实际跟进；保存/排队/生成/平台受理分别显示，不抢回人工接管 |
| FR-21 | 连续生成与故障恢复 | 可确定格式自动整理，缺可用正文或临时超时自动退避重试；新消息合并重规划，旧结果不能覆盖人工编辑；必要时一次简短确认并保留最终答复；单客户故障隔离，发送未知只核查原操作，恢复不扩大权限 |
| FR-22 | 资料与质量记录 | 提供空白产品/样品Logo/交期/运输/售后模板，经营事实由业务员填写；提示词追求准确自然并持续沟通，不加入错误承诺许可；质量问题、修复/重试和后续处理有记录 |

### 4.1 照片的当前产品限制

0.2.13起支持可受控获取的静态PNG/JPEG/WebP，单张原图上限6 MiB。一次生成最多处理最近20条消息中的4张买家照片；超出、无法关联或失败的图片应明确保持未处理。有效观察可复用，识别失败不无限重试。

首次图片识别与文字生成分别记录实际AI调用，不再按次数限额停止。照片可以辅助描述外观和可见文字，材质、实物尺寸、价格、库存、交期仍需客户或适用卖家资料确认；普通识别失败保留未观察状态并继续文字接待。纯图片不能靠模型猜测创建新采购事项。

### 4.2 商业承诺规则

允许一般产品沟通、规格偏好、样品和Logo咨询，以及“将核实后答复”。模型继续以准确为目标，使用适用、已确认、可公开且未过期的卖家资料；数额相同但币种、单位、订单条件不同，不能视为同一依据。0.2.22按用户要求将商业承诺和正文数字缺依据降为质量提醒，合法正文继续接待，不自动转人工或停止发送；提示词不添加允许错误承诺的内容。采购事实入库仍逐项核验，错误或冲突不能冒充已确认条件。

## 5. 非功能要求

| 方向 | 要求与验收方式 |
| --- | --- |
| 本地持久性 | 重启后保留原文、事实、草稿、修订、阅读水位、事项和操作；自动授权不恢复；完整恢复按数据清单验证 |
| 可追溯性 | 能从草稿/操作定位来源及版本，从发送结果定位平台消息和原请求；人工修改保留原记录 |
| 安全边界 | 页面不能直接执行shell、读数据库或读取凭据；令牌不进入正文、命令行参数、文件和常规日志；外部集成按核验身份调用 |
| 并发与退出 | 同一数据根单后台；同会话未决发送互斥；退出先撤权再等待在途结果；数据管理不能强杀后继续迁移 |
| 资源与失败控制 | 保留摘要、正文、历史、图片及上下文大小限制；AI/发送不限次数但统计真实尝试。可恢复生成故障持久退避，不紧循环、不重复确认；暂停/接管/来源变化后重新核验，单客户失败隔离 |
| 可维护性 | 核心回归、实际窗口、包完整性与真实平台结果分别留证；故障记录保留，修复追加新结论 |
| 稳定性与容量 | 后续进行8小时整班观察；1000客户/10万消息仅是容量验证建议目标。最终设备、数据集、时延阈值、备份频率及恢复目标在验收前固化 |

不把本地用户可读的SQLite描述为已加密存储，不把单机文件锁描述为分布式或跨机器一致性方案。

## 6. 核心验收场景

| 场景 | 应达到的结果 | 证据要求 |
| --- | --- | --- |
| 新客户只发问候 | 自然回应，不产生空采购事项，不循环致谢 | 合成回归和窗口；真实接待按授权范围独立记录 |
| 连续两条新消息 | 第二条不因第一条已成功但本地未确认而永久停住；真正未知则阻断并可核查 | 发送保护回归、同版本连续新入站平台证据 |
| 客户纠正数量或地址 | 新事实关联纠正原文，旧值留在修订；旧草稿失效 | 业务回归和复核界面验收 |
| 老客户提出新采购 | 新事项独立，旧待报价和事实保留 | 多事项窗口及状态断言 |
| 客户发图片 | 能预览并基于实际图片辅助回复；失败时不声称已看懂 | 下载/视觉关联回归、真实合成视觉、打包窗口；客户体验可另记用户确认 |
| AI处理中业务员输入 | 当前客户接管，未提交自动发送取消；手写文本保留；已提交外部消息不可假装撤回 | 并发回归和实际窗口 |
| 发送超时或回执丢失 | 保持unknown，核查原操作，不换请求试发 | 异常注入及授权真实回执证据 |
| 备份恢复、迁移或升级 | 数据与回执完整，较新操作不丢失；新根正确、原根保留、自动暂停 | 完整清单/哈希与最终便携窗口 |
| 飞书不可用 | 本地消息、需求和待报价正常，外部失败单独可见 | 隔离故障验证；真实飞书写入另验收 |
| 整班使用 | 无重复发送、无数据丢失、无无限重试；异常可恢复且不擅自恢复授权 | 预定环境下连续运行、资源/故障/人工操作记录 |

## 7. 交付标准

每次交付应提供范围、源码基线、版本及包哈希、适用测试和实际窗口证据、涉及数据变更时的备份恢复证据、剩余限制和操作说明。一次专项测试不能算作完整回归。

## 8. 证据与变更规则

- **代码实现**证明存在功能；**离线测试**证明覆盖的合成场景；**实际窗口**证明界面和流程；**真实平台记录**证明对应外部调用；**用户确认**证明用户反馈；**整班验收**证明限定环境下的持续运行。各层分别记录。
- 新业务规则同步需求及验收条件；实现路线变化同步架构和实施契约。
- 真实验证沿用已明确的授权对象和范围；指定测试客户授权不扩大为其他客户试发。本次文档整理不新增发送或部署动作。
