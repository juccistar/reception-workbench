# 架构文档：技术路线与系统边界

当前源码及最新公开发行均为0.3.14；本版接待规则及会话级补充附件见[发布说明](../0.3.14发布说明.md)、[实施契约](../IMPLEMENTATION_CONTRACT.md)及[验证记录](../verification/0.3.14.json)，原需求和采购基础见[0.3.13开发说明](../0.3.13开发说明.md)。下文早期版本的调度、存储与宿主边界继续适用；旧facts/协助/商品卡的历史描述由以下0.3.13数据契约取代。

0.3.13以Case.requirements的13项AI中文值保存正式需求，conversation_summary独立绑定会话，无Case仍支持聊天；正常生成同轮更新，润色仅处理冻结正文。product_library.py维护产品、供应商、供货方案、需求选择、采购grant和一次性任务，sourcing.py负责确切请求持久化、同入口找货及原任务恢复；所选供货方案版本进入生成/发送指纹。采购共用AI槽但不作为本轮现成回复前置，未验收的定向询价/报价回收明确blocked。旧quality/business_progress/待协助提醒及假定卡片/SKU业务解析退出活动路径，真实图片与发送证据保留；旧数据净化经完整备份后离线白名单清理。源码变化不代表已发布、安装、迁移真实数据或验收真实询价。

读者：后续开发、维护和技术验收人员。业务目标见[需求文档](01-需求文档.md)。

## 1. 技术路线

沿用 **Electron + React + TypeScript桌面端、Python业务服务、SQLite本地存储、Accio Work外部适配**。本工程独立于旧Qt桌面工程；运行时不导入旧工程，不自动迁移旧工程数据库。

| 层次 | 选型与职责 | 选择依据 |
| --- | --- | --- |
| Windows桌面宿主 | Electron主进程 | 窗口、原生确认、文件夹选择、授权环境继承、后台生命周期、数据维护 |
| 界面 | React、TypeScript | 会话、消息、需求侧栏、待报价、设置和状态投影；延续已选A版对话布局与可收起侧栏 |
| 安全桥 | preload + 有限IPC | 页面只访问明确列出的业务/存储方法，不获得Node、shell、数据库或任意文件接口 |
| 本地业务 | Python接待服务 | 持久化、接待状态机、上下文、任务调度、权限与预算、人工/自动发送 |
| 进程通信 | UTF-8 JSON Lines，stdin/stdout | 主进程启动并管理服务，不开本地HTTP业务端口；请求、结果和事件分离 |
| 数据 | SQLite，WAL，synchronous FULL | 本机事务、查询和修订保存；发送操作持久化；当前不引入云数据库或向量库 |
| 外部能力 | Accio Work原生适配及独立聊天翻译HTTP Provider | 需求、回复和图片AI保留Accio；只读聊天翻译使用独立配置的第三方通用模型 |
| 构建与验证 | Vite、esbuild、Vitest、PyInstaller、electron-builder、Playwright | 桌面构建、后台独立打包、回归、便携包及实际窗口验收 |

具体依赖版本以[package.json](../../package.json)、[npm锁文件](../../package-lock.json)、[Python项目](../../services/reception/pyproject.toml)和[Python构建锁](../../services/reception/requirements-build.lock)为准。使用发行包时无需用户自行安装Node或Python；源码开发环境要求见[工程README](../../README.md)。

## 2. 进程与信任边界

| 组件 | 输入/输出 | 必须保持的边界 | 源码入口 |
| --- | --- | --- | --- |
| React renderer | 显示快照、接收事件、提交编辑和明确操作 | 不自行判定平台发送成功；不执行任意命令；业务状态由后台投影 | [renderer](../../apps/desktop/src/renderer) |
| preload | 冻结的有限方法桥 | 不暴露原始IPC对象或通用文件系统；存储管理与业务RPC分开 | [preload/index.ts](../../apps/desktop/src/preload/index.ts) |
| Electron main | 验证IPC来源、原生确认、后台请求、窗口事件 | 检查本窗口及主frame/本地页面；不接受renderer指定任意后台命令或source根 | [main/index.ts](../../apps/desktop/src/main/index.ts) |
| ServiceClient | 启动子进程、请求关联、响应及事件分派 | 子进程异常与业务失败分开；stdout用于协议，不能混入普通日志 | [service-client.ts](../../apps/desktop/src/main/service-client.ts) |
| Python服务 | 业务方法、任务、事件、持久化 | 权限、身份、来源版本和幂等的最终检查在服务及原生提交边界完成 | [__main__.py](../../services/reception/src/reception_service/__main__.py)、[service.py](../../services/reception/src/reception_service/service.py) |
| 原生集成 | 平台读取、AI、预演、发送和核查 | 输入与结果绑定当前请求及核验身份；凭据不经页面传递 | [integrations](../../services/reception/src/reception_service/integrations) |

窗口开启contextIsolation、sandbox、webSecurity，关闭nodeIntegration。`demo`使用合成适配器，`live`使用真实适配器；两者共享业务流程但数据隔离。演示成功不能作为真实平台成功。

统一授权启动先在当前Accio环境进行只读原生商家身份探测，在创建Chromium profile和业务后台之前选择商家工作区。未解析的当前EXE `--connect-from-accio`通过受控Node启动器完成探测/注册，再启动同一EXE并传入一次性的非敏感路由上下文。上下文消费后立即删除；商家、目录及bootstrap约束必须一致，后台连接时仍重新核验真实身份。演示窗口不做真实探测。

每个最终接待进程只继承其来源Accio环境。不同商家使用独立数据与宿主状态；相同商家跨数据目录全局排他，已有窗口不能注入新授权。Native子进程继承占用，父进程异常退出但子进程存活仍拒绝第二owner。更换授权需正常关闭该实例再执行同一指令。启动默认只核验身份/读取，AI检查与自动发送授权有独立动作；重启保留原窗口seller约束并重验，路由上下文不能代替业务授权。真实双Accio并行接待闭环仍待验收。

## 3. 消息读取与任务调度

接待服务包含活动监测线程、业务协调 worker 和每商家一个可取消的 AI 执行槽。业务队列容量为256，按就绪发送、明确人工任务和正文同步等优先级派发，并周期照顾较早任务。AI等待期间可继续同步正文、保存及执行受保护的发送；状态修改仍由服务锁、事务和来源版本约束。真实生成使用独立 facade，读取令牌绑定当前owner、监测代次、数据库及活跃任务。

| 通道 | 当前机制 | 目的及限制 |
| --- | --- | --- |
| 活动摘要 | 新配置默认每2秒轻量检测，首屏落库后立即派发正文同步，再处理续页 | 降低全量读取；间隔可配置，不承诺端到端回复时延 |
| 正文同步 | 变化客户优先，正文排队/读取最多4个，保存正文真实水位 | 摘要活动变化不代表正文已经可读，两个进度分开记录 |
| 历史与巡检 | 重叠分页、有限重试、历史/维护补读全账号每60秒最多一个 | 两次成功空读后等待新活动；打开客户可触发受控读取，普通刷新不补读 |
| 人工处理 | 保存与入队独立；在分页/图片之间优先处理人工任务 | 尚未提供完整的人工等待上限保证，OPS-04需测量并完善 |
| 聊天图片加载 | 受限队列，全局active最多4 | 图片下载/预览不等于AI已识别 |
| 商品展示参考图 | 独立媒体池按数字商品ID读取并安全缓存 | 不占AI槽、不作为回复前置；采购可等待终态后选择图或文字找货，不作为SKU图 |
| 视觉与文字生成 | 主业务请求直接读取受限原图并生成需求和回复 | 不再先生成独立观察报告；Accio内部可能使用视觉服务 |

全局自动暂停仍继续普通聊天同步。0.2.22将可恢复生成故障的retry_at与尝试次数持久化，到期重新调度，不在串行业务worker中sleep等待。每次尝试复核当前epoch、身份、范围、客户接管和来源；新消息取消旧版本并合并规划，单客户失败不撤销其他客户权限。0.3.1对自动发送失败链另设上限：同商家、会话、来源消息和阶段最多三次（首次加两次，协助阶段另区分结果版本），仅明确暂时性且未提交时按5秒、15秒重试；确定性或未分类拒绝停止本条，新job、草稿及重启不重置计数。可能已提交或unknown只核查原operation_id。正常AI和发送总使用量仍不限。

0.3.11 的business_progress由business_progress.py维护，与human_owned、reply_pending、case.state及旧协助发送状态分别投影。正常自动和人工建议请求携带followup_context，模型附带逐问题进度候选，服务校验当前来源后应用，不新增常规分类模型。保存最新补充使旧判断待更新，已有有效问题在当前授权内经严格绑定的supplement续答；相应草稿accepted后才证明已对客答复。稳定问题跨补充版本共享重试链，不同问题可分别跟进，未决发送仍保护整会话。日常不再要求逐项开始处理或回填表单；旧processing_started_at、内部/公开结果及既有跟进回执保留兼容语义。人工建议不启动实际任务，生成或保存不冒充平台受理；临时确认和最终答复仍分阶段防重。

运行记录汇总普通后台任务，同类真实错误聚合次数和最后时间；明确手动操作、生成、发送，以及质量提醒和自动修复/重试保留记录。

相关实现：[message_monitor.py](../../services/reception/src/reception_service/message_monitor.py)、[message_photos.py](../../services/reception/src/reception_service/message_photos.py)。

## 4. 数据模型与事实生命周期

业务数据以`entities(kind,id,data)`保存JSON实体，`revisions`保存需要保留的历史修订。当前Repository schema为v2，原生/Demo Ledger schema为v1；0.2.14未再次提升schema编号。

| 对象 | 保存什么 | 与其他对象的关系 |
| --- | --- | --- |
| conversation | 卖家/买家/CID、同步与阅读水位、接管和状态 | 一个会话可有多个采购事项，未决发送保护按会话执行 |
| message | 平台message_id、方向、正文、时间和消息版本 | 原文是事实来源；人工已受理消息也进入历史；修订不抹去旧证据 |
| case及其事实 | 采购事项、事实值、来源、修订、缺失项和采购状态 | 绑定客户及会话；新采购不覆盖旧待报价事项 |
| draft | AI建议、来源消息版本、事项/资料版本及图片依据 | 来源变化后旧建议不能继续提交；不同于用户手写正文 |
| chat_draft | 会话人工正文及版本 | 独立于采购事项；迟到建议和回执不覆盖新输入 |
| job | 排队、运行和结果、调用关联 | 任务状态不等于平台受理或业务交接完成 |
| operation | 原请求、幂等键、结果及回执关联 | 发送核查围绕原操作，不新建请求试探结果 |
| outbox | 外部登记待办和业务版本 | 本地保存后异步处理，远端失败不撤销本地接待 |
| image_asset / message_image | 原图、预览、哈希及消息关联 | 图像内容存入卖家SQLite，随完整业务备份保存 |
| requirement_media / requirement_media_cache | 事项封面、消息版本绑定的产品来源选择、商品展示图片状态及缓存关联 | 展示revision从本地投影计算，与事项业务revision独立；来源选择不同于封面 |
| requirement_media_mutation / requirement_media_request | 展示修改与加载请求的幂等记录 | 按商家业务库保存；加载完成仍须复核owner、来源版本、服务世代及任务 |
| photo_observation | 历史图片观察及其来源 | 保留历史兼容；0.3.7主业务不再依赖独立观察任务，图片内容不能直接升级成客户确认事实 |
| policy及修订 | 商家正文、类别、范围、确认/启用状态、用途、公开口径、人工备注及有效期 | 人工、内部规则和对客资料分开；内置采用后的副本按商家独立保存及版本校验 |

内置目录提供六份规则和三份模板，默认关闭；商家明确采用后复制本地，关闭保留正文，版本更新须对照后明确选择。旧公开资料保持可用，旧非公开资料仅供人工；内部指导与对客资料分开投影，公开口径与仅人工备注分开，模板占位不作为事实。

`confirmed`等AI提取状态不代表业务员已经复核。历史独立人工复核、冲突候选、结构化明细和来源失效处理继续兼容；需求整理、proposal应用及移项接口仍保留，但客户页、待报价及客户资料不再渲染对应手动表单。协助结果与事实裁决分开，不能借用发送或飞书登记成功充当独立业务交接完成。

0.3.13商品档案按商家、平台及商品ID建键，`requirement_product_binding`保存需求与产品及所选供货方案的关联；不同客户的数量、规格、预算、消息和业务补充分开。数字ID由代码生成 `https://www.alibaba.com/product-detail/_<ID>.html`，AI不查询或填写链接。明确的自定义需求可使用稳定复用的`定制-数字`本地编号，偶然碰撞原子换号，不生成平台链接或读取平台图片。产品与首次采购任务原子建立，unknown只核查原任务；供应商及供货方案已具备管理入口，定向询价与回复回收尚未验收并保持blocked，不自动报价。商品页面资料不能转为已核实经营事实。

自动接待、人工建议和润色共用完整本地上下文与资料选择，再由[model_payload.py](../../services/reception/src/reception_service/model_payload.py)按任务投影实际模型字段。最近50条双方文字已包含关键原文时直接复用，窗口外只补缺少的必要依据，消息按编号去重；图片和卡片独立关联，普通润色不自动读取历史图片。仅明确允许对客使用的核实结果进入回复上下文，内部协助备注不进入。实际模型JSON预算为120,000字符，含提示词与图片清单的完整请求预算为140,000字符；超限明确待处理，不静默截断证据或推断human_owned。来源定位可按需读取全部本地旧原文。

### 4.1 0.3.1界面和只读展示

右侧需求在上、会话补充在下，窄屏合并到抽屉；顶部只有一个固定需求入口，支持事项切换、原文定位和从待报价进入指定事项。发送左侧单一主动生成按钮，最新成功建议在正文上方；补充默认用于自动接待、建议及润色，不写入客户事实或通用政策。生成、查看、补充及翻译不接管；采用无确认完整替换编辑框，采用、手写和人工发送接管。固定发送与unknown期间仍可编辑下一条，不能更改原操作。

保留事实value、evidence_ids及缺项、冲突，客户预算和商家报价来源分开。0.3.4在原Accio分析中直接输出中文summary/display_value，旧记录缺展示值时回退原文，不再请求需求区翻译，也不以字段齐全或逐项确认作为回复前置。聊天文字采用独立第三方通用模型，原文与译文并列，不进入事实、正文或发送队列，不做OCR或术语表。每条默认附最多两条、合计300 UTF-8字节的轻量前文，可在高级设置调整条数、字节和HTTP并发；缓存绑定商家、会话、原文/前文、端点、模型及提示词版本。独立HTTP线程不依赖Accio AI检查，不被原生业务抢占，关闭时先收尾再关库；配置和加密Key经专用宿主桥管理。0.3.6使用Windows用户级DPAPI及真实KnownFolder目录跨商家共享服务地址、模型和Key，避开Electron各userData目录的加密密钥隔离；旧密钥在原数据根验证后一次导入，已有或已清空的共享配置不被旧值覆盖。宿主通过跨进程互斥与共享修订CAS保存，并同步已开窗口；启用绑定各商家实际数据根，改端点或恢复到新根须重新确认，聊天、译文及用量仍分别持久保存。

全局运行状态、客户接管、会话回复义务和采购进度分别投影；未读、reply_pending与需求整理互不等同。连接/后台异常及发送待核查持续提示并可处理，本地保存、平台受理、飞书同步分开。

0.3.7的补充仅保存每客户最新正文，保留revision/CAS/hash；启动时定向压缩补充专用revisions/mutation正文副本，不删除发送账本、回执或普通业务历史。非空正文触发润色并冻结正文和版本，采用才替换并接管。有效manual_suggestion复用独立翻译队列和缓存，stale不能新请求；自动内部草稿不单独翻译，发送后作为卖家消息翻译。

公司名由独立慢任务 `refresh_company_profile` 正常只读 `ai_minisite_get_company_info(dataType=all, language=zh_CN)`，有限读取HTTPS Ali CDN/OSS，缓存仅公司名、seller_id和更新时间；`get_snapshot`不联网。左下显示公司名并支持失败重试，标题保留商家ID。右栏最大宽600、需求比例默认0.55，支持键盘、双击复位和按商家保存。

## 5. AI与客户照片处理

### 5.1 文字分析

当前LiveIntegration通过Accio执行分析任务，严格关联本次请求与完成结果。0.3.13对需求核验归属和来源，非法附属字段不覆盖有效结果；不生成或保存独立语义质量warnings，也不将其升级为硬issues或整会话接管。金额相同仍不能视为同币种、单位或条件的可靠依据。不能猜造事实或把截断JSON/工具载荷当正文；缺可用正文则交由持久化重试恢复。

普通聊天不强制创建采购事项或增加采购追问。含采购内容的问候及图文混合消息继续走需求处理；纯图不能靠视觉猜测新建事项。

### 5.2 图片管线

1. **消息身份来自普通消息接口**：保存message_id及版本。`[image]`占位并不说明平台无法取图。
2. **补充媒体来源**：aimode提供图片入口，通过固定CID、发送者和毫秒时间在两侧唯一匹配；不能替换原消息身份。非唯一或未核实的附件形态保持不可识别。
3. **受控下载与解码**：HTTPS、每跳精确主机及公开地址核验、固定目标IP和TLS；不携带Cookie/Authorization或环境代理凭据。最多3次请求，共享15秒预算。
4. **保存安全图像**：静态PNG/JPEG/WebP，原图≤6 MiB、像素≤20M、最大边≤8192；完整解码并检查MIME。处理方向、RGB重绘去元数据，最长1280的JPEG预览≤1 MiB；原图和预览保存在SQLite。
5. **主业务直接读取**：下载结果缓存，主业务Accio请求仅读取本轮宿主限定的原图，结合文字生成需求及回复；取消独立观察报告任务链。
6. **确认读取并复核**：初始pixel_access=false，只有本轮确切原生记录证实读取才视为看过；来源版本或图片指纹变化使未提交旧结果失效。图片推断不是客户确认的采购事实或商业承诺。

0.3.10的[图片上下文](../卖家图片与上下文.md)不再固定限制四张，默认整批64 MiB、准备60秒、纯下载并行2项，原生来源读取保持串行。引用和本轮读取证据均保留role、消息版本和哈希，商家展示不成为买家确认。授权环境中5张双方混合合成图已取得本轮证据，8/20张仅完成离线回归；实际耗时及边界见本版记录。图片继续使用同任务read_compat，Accio内部可能使用视觉服务，不保证一次物理模型调用；不可用图片不能声称看过。每次请求独立组装本地上下文，不新增长期客户记忆。

0.3.11源码在原图准备前按确切事项筛选产品来源：显式绑定或客户明确引用选择的图片可进入相关请求；单事项、没有竞争产品来源且只有一张直接买家图时可作为同轮候选。多图含义不明时不全部自动读取，商家图须有买家明确选择并保持seller角色。产品字段仍保存文字；图片推断不能作为已确认客户事实。最近50条文字和窗口外必要来源去重保留，普通润色不准备历史图。

本地消息、原图和来源验证对象保留完整；程序派生的商品链接和独立商品展示图不进入接待指定上下文、photo_context、manifest或语义指纹，原始聊天和冻结润色正文中的链接不篡改。客户明确的文字需求、适用资料和最新补充仍可进入模型；客户来源图片须按本轮归属和读取证据处理。展示图加载不改变业务生成指纹；来源选择变化使相关未提交生成失效。商品展示图使用独立媒体池与安全本地缓存，不占AI槽；采购可等待读取终态后使用图或文字找货。图片原始地址不交给renderer。

`product_main_image`与客户需求的`product_images`独立。正式list-information只读接口使用整数productId、queryType=trunk和componentList=[images]，响应的data是JSON字符串，图片组位于basicInfo.images，每项提供imageIndex和originalImageUrl。返回体没有商品ID或主图标记，按确切请求绑定商品，选择最小imageIndex作为展示参考；不得称平台已证主图或SKU图。样本商品1601902417143在售状态未知，见[只读报告](../../artifacts/verification/reception-0.3.13/product-image-component-accio.json)。不再依赖假设的商品卡/SKU字段，全量SKU及真实图搜链尚未验收。

workctl v0.1.65外部接口没有原生图片附件；当前使用P05-B read_compat，在同一业务任务中读取限定原图，p1/p2按买卖双方消息时间顺序关联。公司资料和图片读取记录安全的失败阶段及类别，普通诊断不保存完整签名URL、凭据或原始响应。

实现入口：[media.py](../../services/reception/src/reception_service/integrations/accio_native/media.py)、[image_assets.py](../../services/reception/src/reception_service/image_assets.py)、[visual_query.py](../../services/reception/src/reception_service/integrations/accio_native/visual_query.py)、[photo_vision.py](../../services/reception/src/reception_service/integrations/photo_vision.py)、[photos.py](../../services/reception/src/reception_service/photos.py)。

## 6. 人工、AI建议与自动发送

| 路径 | 前置和来源 | 共同保护 |
| --- | --- | --- |
| 普通人工聊天 | 已核验身份和会话；保存确切正文版本，按client_request_id提交；不要求AI检查、采购完整或商业资料齐全 | 身份/目标、格式、正文版本、幂等、退出撤权及整会话未决操作 |
| 主动生成建议（0.3.1） | 身份及AI能力正常；可无事项、缺项、卖家最后发言、暂停或已接管；会话补充也用于自动接待及润色 | 生成和查看不接管、不改正文；只显示最新成功结果，采用无需确认完整覆盖并接管，随后沿人工正文路径发送 |
| 自动接待 | 当前读取和AI检查、明确范围；不限AI/发送次数但持续统计；当前来源与版本有效，未接管/停止联系 | 每次准备和最终原生提交前复核权限与版本；来源变化、暂停和接管使未提交行为失效，不生成正文质量提醒 |

人工编辑将当前会话置为人工处理；恢复自动接待须明确操作。重启、连接检查、数据恢复和故障恢复均不恢复旧自动权限。已经提交的平台消息不能通过本地暂停撤回。

当前源码的[发送通道简化](../自动发送通道简化.md)保留全部本地业务检查，常规自动回复和续答直接提交，发送前不重读平台历史、生成Ready或执行Seal；提交后以确切消息编号有限读取确认。新常规自动适配器请求使用purpose=reception和原来源防重键，旧快照unknown仍沿原回执核查。

以下规则仅留作旧显式预演/手动确认兼容：原生快照兼容Ready的`from`与旧`senderRole`；双字段冲突、未知/无效角色及显式发送者不符仍拒绝。同ID权威平台消息存在时核对角色和正文。已核实的图片标记可在严格身份、会话、消息编号和角色匹配时投影；已验证当前来源以外的历史消息，仅对代码识别的原生商品卡片描述及对应展示，匹配权威记录、角色和时间后投影，并在封存后重新核验。当前来源和其他正文仍严格核对，不改写封存Ready。失败详情只保留严格消息ID、差异枚举、类型/有界长度和比较布尔，不展示原文或令牌。

发送生命周期可概括为：准备原操作 → 提交 → 根据证据标记accepted、rejected或unknown。准备/发送中/unknown均保护整个会话。只有确切未执行证据才能将中断操作判为未提交；一般中断不能当作安全重试。

- accepted要求平台message_id及提交/核查证据，任务入队成功不是发送成功。
- unknown沿原operation_id、回执关联和平台消息核查；核对方向、双方身份、正文及平台时间。证据不足继续unknown。
- 核查成功更新原操作、草稿和任务，不新增发送；不能通过换事项、换请求键或同文猜测消息编号绕过。
- 原生账本保存防重和尝试历史；chatToken只在内存/stdin中传递，不进入argv、文件或账本。

实现入口：[manual_chat.py](../../services/reception/src/reception_service/manual_chat.py)、[service.py](../../services/reception/src/reception_service/service.py)、[原生集成](../../services/reception/src/reception_service/integrations/accio_native)。

## 7. 本地数据与目录配置

### 7.1 根目录和存储集合

默认registry为`%LOCALAPPDATA%\AlibabaReceptionWorkbenchHost\merchants.json`，state仍为`profiles/<SHA256 seller>/state`。0.2.21新商家默认业务根位于registry同级`ARWData/<registry规范路径SHA256前16位>/<sellerId>`，安全备份位于同级`ARWBackups/<相同namespace>`；建库前核对Windows SQLite日志路径预算。已有根及迁移后的选择继续以profile的`state/storage.json`为准，不静默搬移。实际位置以设置页显示为准。旧全局storage保留，仅唯一匹配seller的正面证据才收编旧根，保留原路径和lastBackup、previousRoot等；未知、多重匹配或缺失拒绝。不保存令牌或自动发送授权。

优先级：本次明确`--data-dir` → 已保存dataRoot → 默认根。明确参数不会自动改变偏好；若恰好等于已保存根，也要求目录存在。配置损坏或根缺失不能静默改用空工作区。

典型真实模式集合：

```text
<业务根>/
  live/control.sqlite3
  live/sellers/<卖家ID的SHA-256>/workspace.sqlite3
  live/adapters-live.sqlite3
  live/workctl-state/chat-analysis/send-receipts/
  .receipt-roots.json
  .reception-workspace.lock
  .reception-clean-shutdown
```

demo使用独立模式目录。原图及预览在卖家业务库中；Chromium profile、浏览器缓存和登录凭据不属于业务备份。完整集合还需按清单处理数据库一致性及相关元数据，不能只复制两份SQLite文件。

只接受安全本机绝对路径；拒绝UNC、卷根、符号链接、目录联接和不合法Windows路径。业务根不能与固定配置或程序目录重叠。

### 7.2 锁与正常关闭

Electron保留profile范围单实例控制；Python WorkspaceLock覆盖整个数据根，包括demo/live，防止同根多个后台。启动准备、配置写入和数据管理另由按固定stateDir生成的Windows命名Mutex串行化。有限PowerShell辅助进程持有该内核锁，stdin关闭或进程死亡时释放，不靠删除遗留wx锁文件恢复。

关闭先处理未保存编辑，再撤销新权限，等待worker、监测和受跟踪原生子进程结束，保存结果并关闭数据库，最后产生正常退出证据。数据管理不提供强杀后继续迁移的分支；普通强制退出不能被当成正常关闭证明。

### 7.3 离线维护及升级

[storage-host.ts](../../apps/desktop/src/main/storage-host.ts)由主进程限定参数和源目录；[storage_maintenance.py](../../services/reception/src/reception_service/storage_maintenance.py)通过包内后台的`--maintenance`入口执行。维护在接待服务实例化之前分派，不调用AI或发送；子进程使用Windows运行必需变量白名单，不继承Accio或其他平台凭据。原始恢复快照`recovery_backup`与完整恢复包`backup`分别处理，不把原始快照写为lastBackup。启动恢复可能晚于页面首次请求，后台首次快照成功后发送本地state.changed通知，页面重新读取并清除断连显示。

| 操作 | 实现原则 |
| --- | --- |
| prepare | 启动前兼容预检；有效clean伴随残留WAL时先保留原始快照、独占checkpoint并核验；旧schema升级另做完整备份；未知/未来结构拒绝 |
| recover-profile | 只恢复严格合格的旧版过长路径首次零字节created档案；备份原始源与登记配置，CAS切换到新短根，保留旧根，不伪写owner；失败现场保留，后续使用新目标 |
| inspect / open | 核验已有根；打开其他根时备份当前根并比较发送历史；选择当前根可以只核验并保存目录偏好 |
| backup | 正常离线后按白名单复制至staging，验证清单、大小、hash及回执来源，完成后发布备份 |
| migrate | 完整备份当前根，核对源未变化，恢复到空目标；成功后才原子更新选择并真正重启 |
| restore | 校验备份、比较当前发送历史、备份当前根，再恢复至空目标；不合并或覆盖原根 |

当前schema脏退出可走已有恢复流程，不伪造clean marker；需要schema升级且缺少正常退出证据时，要求先由旧版本正常关闭。正式新协议离线备份要求数据库已关闭且不存在非空待处理WAL；尚未遵守新协议的旧版本需独立停机核实及legacy导出，不能套用普通按钮虚构证明。

打开/恢复目标的operations与attempt_history必须包含当前完整记录，retry_grants必须一致，避免用旧副本丢掉已发生提交或复活旧重试授权。历史绝对回执引用由`.receipt-roots.json`及receipt_hashes映射到新根本地副本，不访问旧目录寻找结果，也不据此直接伪造accepted。

失败保留原配置与原根，并按可恢复情况重新打开原工作区，自动权限关闭。最近一次迁移前的旧真实启动路径会被新版拒绝；这不能使所有历史副本或已发布旧二进制自动遵守新协议。

目录解析：[data-location.mjs](../../scripts/data-location.mjs)；完整备份：[workspace_backup.py](../../services/reception/src/reception_service/workspace_backup.py)。
