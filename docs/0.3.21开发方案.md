# 0.3.21 开发方案：真人聊天式自动分条与交互简化

日期：2026-11-15。面向工作台使用者、开发维护与验收人员。

状态：用户已明确要求开发、打包发布，正在实施与定向验证。以已发布0.3.20为基线，沿用上一版已完成的自动分条同步等待与防重修复，不重新调查旧失败原因。本文件定义新版生成、发送与交互；实际构建、发布及验收以[验证记录](verification/0.3.21.json)为准。

## 1. 本版目标

自动接待按真人即时聊天的方式组织一轮回复，自然生成一至三条，并按顺序自动发送。人工保持普通单条输入，不参与自动批次的逐条编辑、确认或接续。

| 方面 | 本版要求 |
| --- | --- |
| 生成目标 | 自然交流感、上下文承接及完整有效的信息，不能以“尽量合成一条”为优化目标 |
| 自动发送 | 一轮生成、冻结顺序、逐条受理、自动推进，不让用户手动发第二条或第三条 |
| 人工聊天 | 普通单输入框，保留整段建议、整段润色和一次发送 |
| 进度展示 | 自动批次在聊天区域独立展示，当前草稿与历史发送记录明确分开 |
| 故障处理 | 确切未提交按既有策略处理；未知只核查原操作；停止说明原因 |
| WhatsApp | 自动回复遵循同样的生成目标及有序发送；原网页人工聊天保持原入口，纳入已完成的短登录分区源码修正 |

本版继续使用每轮一至三条、整轮正文合计最多 1200 字符的既有协议预算。条数上限是协议预算，不是每轮应凑满的指标。

## 2. 生成：按真人聊天节奏组织一轮回复

### 2.1 如何决定条数

AI 结合客户的表达、问题、当前关系与对话节奏，决定本轮一至三条。自然地接话、回应、解释或追问，消息可以长短不同，也可以一条含几句话。

不能因为几句话可以塞进一个气泡，就要求合成一条；也不能套成固定的“第一条确认、第二条回答、第三条提问”。整轮需要连贯，不重复开头、重复解释或连续追问已经明确的事项。

真人感来自措辞、承接和自然分条。正常发送沿用无额外固定条间停顿的机制，不用发送等待来替代内容质量。

### 2.2 提示词调整方式

仅替换现有表达规则及自动任务中的分条指引，避免叠加互相冲突的段落。建议采用以下核心表述：

> 按真实业务员即时聊天的口吻和交流节奏组织本轮回复，自然地接话、回应、解释或追问。用一至三条有序消息表达，长短和条数随语境变化；分条服务于自然交流，不以压成一条为目标，不套固定条数、固定顺序或每条一句的模板，不添加凑数的空话，各条之间自然承接。

实施时分别核对：

- P01 共用表达规则：更新自然表达部分，保留其余有效业务与证据规则。
- P02 国际站自动接待及 WhatsApp 自动任务：按上述原则输出 reply_messages。
- P03 普通人工建议：仅生成一份可编辑、可一次发送的单条建议，reply_messages 必须且仅含一个条目。
- 人工润色：只润色整份冻结人工正文，不再设置当前条目下标。

原有语言选择、资料适用范围、事实依据、报价权限、停止联系、提问预算、价格及必要限定的完整表达继续保留。需求、摘要、供应商、图片和来源语义不因自然分条改变。商品 ID 段落继续保持用户已确认的内容，不追加判断提示。

审核稿仍生成运行时静态模块，运行时不读取 docs。必要提示词版本更新和一致性检查随实施完成。

### 2.3 生成结果的约束

一轮只生成一份有序 reply_messages，每条保留各自 body 和 reply_sources。程序校验数量、非空正文、总长和有效来源，不按标点、换行或字数自行重新拆分。

正常接待、final 与业务补充续答都沿用整轮生成和有序发送。需求增量及摘要按整轮处理，不因为三条消息而重复做三轮需求分析。

## 3. 自动发送：同一轮按顺序可靠完成

### 3.1 正常流程

收到并同步客户消息 → 组装有效上下文 → AI 一次生成完整回复列表 → 校验并冻结本轮正文与顺序 → 发送第一条 → 保存确切受理证据 → 复核必要条件并发送下一条 → 全部受理后完成本轮。

发送第二条、第三条不重新生成正文，也不要求人工确认。消息不会并发提交。条间没有额外固定等待，实际耗时由渠道提交、回执、必要同步和调度决定。

每条独立保存 operation、消息 ID 与回执，已受理前缀不重发。国际站沿用其确切提交证据；WhatsApp 沿用确切消息 ID 加 ACK≥1 的受理条件。两条渠道只统一用户理解和进度表达，不混用账本或确认标准。

### 3.2 自动推进与中断

| 发生的变化 | 后续动作 |
| --- | --- |
| 本批次第一条、第二条的确切自身回显及已支持的正常传输修订 | 按既有归属规则复核，必要时等待增量同步，再推进剩余条目 |
| 消息同步尚未完成，其余硬条件有效 | 国际站沿用 waiting_sync，首次等待最多 60 秒，释放执行线程 |
| 允许重试的暂时错误，且有确切未提交证据 | 国际站沿原条目和预算重试，最多三次总尝试，退避 5 秒、15 秒 |
| 当前条目结果未知 | 核查原 operation；不重发，不越过它发送下一条；确认受理后在原批次未停止且依据仍有效时继续 |
| 客户中途发来新消息 | 停止尚未提交的旧尾部，后续按最新消息判断；新上下文包含已经实际发出的前缀，避免重复回答 |
| 人工开始编辑、采用建议或人工发送 | 接管当前客户，停止尚未提交的自动尾部；在途操作仍等待确切结果 |
| 暂停、撤权、账号变化或真实业务依据变化 | 停止未提交尾部，显示具体原因 |
| 重启 | 继续保全回执与 unknown，旧批次不自动续发，旧授权不恢复 |

沿用 0.3.20 已修复的等待和自身回显逻辑，仅进行集成与定向回归；不以本版为由重做发送通道、移除必要业务检查或重复调查旧失败。

每次实际提交前继续核对身份、商家/客户/会话、授权范围、接管、来源、事项、资料、图片、业务补充及供货方案等有效依据。正常流程不恢复 Ready、Seal 或发送前整批历史重读。

## 4. 自动接待的界面

### 4.1 当前进度

国际站把当前自动批次的轻量进度放在聊天区域底部、人工输入框之外。只在生成、发送、等待或本轮刚结束时显示，不成为常驻建议栏。

| 阶段 | 显示示例 |
| --- | --- |
| 生成 | 正在生成自动回复 |
| 第一条提交中 | 正在发送自动回复，已发送 0/3 条 |
| 第一条受理 | 正在发送第 2 条，已发送 1/3 条 |
| 同步等待 | 已发送 1/3 条，正在同步后继续 |
| 确认结果 | 已发送 1/3 条，正在确认第 2 条发送结果 |
| 允许重试 | 已发送 1/3 条，第 2 条将在 5 秒后重试 |
| 全部完成 | 自动回复已发送，共 3 条 |
| 停止 | 已发送 1/3 条，剩余 2 条已停止；显示具体原因 |

发送数量按确切平台受理统计，不能表示客户已读。必要说明可放在详情中，日常界面不展示 operation、hash 等实现字段。

只有已经受理的正文进入已发送聊天气泡；待提交正文不伪装成已发送。使用现有消息 ID 对齐回执投影与平台回显，避免同一条显示两次。

完成提示短暂显示后收起，建议约 3 秒。停止或待核查状态在相关会话中保留，解决或明确关闭后收起；切换会话时严格按会话和批次归属读取。

### 4.2 历史与详情

历史批次移入折叠的发送记录；完成、停止及旧批次不再逐项堆在人工输入框中。

记录至少区分渠道、自动/人工、时间、总数、已受理数、逐条状态及停止原因。详情可查看确切状态，结果未知时提供原操作核查；查看记录不接管客户。

当前进度和历史记录使用同一份后台投影，不由前端根据正文、最后发言人或输入框内容猜测发送结果。

### 4.3 WhatsApp 的展示

WhatsApp 保留原始 WebContentsView。工作台在原网页外侧的现有状态区域展示当前账号自动批次的进度，按联系人区分；不把状态控件塞入原网页聊天 DOM。

当前批次与历史记录分别显示，完成批次不常驻。原网页继续承担人工聊天；人工回复的接管和在途保护沿用既有实现。

## 5. 人工聊天恢复普通单条输入

保留一个普通文本框和发送按钮，支持换行、整段润色及 Ctrl+Enter。人工建议仍在输入框上方的待处理框出现，可替换、重新生成和弃用，处理后关闭。

移除人工分条编号、当前条目选择、逐条删除、合并，以及将自动尾部提取到人工草稿的日常操作。自动回复正文和进度不写入人工输入框，自动回执也不清除人工新输入。

查看聊天、建议或进度不接管；手写或采用建议引起正文编辑时接管。恢复客户自动接待后按最新聊天继续判断，不重播旧的 stopped 批次。

### 5.1 旧数据兼容

- 尚未发送、没有关联发送操作的旧分条人工草稿，以原 body/按原顺序空行组合的正文显示为单条；由正常版本保存转换，不做启动时批量改库。
- 已受理的旧人工草稿不作为待发送正文重新出现；保留其原记录与回执。
- 旧人工批次若在途或结果未知，继续原核查流程和会话发送围栏，不因改成单输入框解除保护。
- 旧人工批次部分成功且已明确停止的，保全原批次及受理前缀。只有确认无未决操作后，才允许转入独立的新人工草稿；原尾部不自动填入或发送，也不把整批旧正文当作新发送。
- 旧自动批次、提取记录及人工 operation 保留，不迁移、不清除。新版移除自动尾部提取的前端入口与常规桥调用，不再依赖人工恢复来完成自动分条。

后端兼容读取历史字段和批次，不通过前端隐藏按钮来替代回执与版本保护。

## 6. WhatsApp 登录路径修正并入本版

并入本会话已经完成的短登录分区源码修正，具体证据见 [路径验证记录](verification/whatsapp-0.3.20-path-2026-11-15.json)。本方案不重新调查该故障。

- 已保存的零代和旧版代次继续使用原分区，不在升级时静默切换登录环境。
- 只有用户通过现有原生确认新建环境时，使用 27 字符短分区名，配置保存为新格式；已存在的目标目录拒绝复用。
- 保留原登录目录，业务库和发送账本位置不变；unknown 不因换登录环境消失。
- 新格式配置提交后，旧 0.3.20 不识别该格式，不支持用旧程序覆盖或静默回退。未执行新确认时旧格式保持不变。
- 已有原目录短分区 SDK 检查通过、扫码保持超过 60 秒且刷新；这不等于新版最终 EXE 或实号收发已经验收。更深的自定义数据目录仍按实际路径验证。

## 8. 验收标准

### 8.1 生成语义

选取合成聊天覆盖接话、报价、解释、澄清、客户抱怨、连续追问、简单确认及业务补充续答。逐例从以下方面评价：

1. 读起来像业务员在即时聊天，各条有自然承接。
2. 没有为了塞进一条而把多个交流动作压成一段，也没有凑数的短句。
3. 不固定每轮两条/三条，不固定确认→回答→追问模板，不限制每条一句。
4. 整轮信息完整、不重复，报价及必要条件不造成歧义，提问数量继续符合原预算。
5. 未编造事实、报价、承诺或内部安排，中文需求及摘要语义保持。

结构测试只能证明一至三条、总长和字段有效；真人感必须看实际模型结果。真实模型调用按当次授权范围执行，未执行时在记录中明确标注未验收，不以替身结果代替。

### 8.2 自动发送定向回归

- 两条、三条均通过真实本地业务链依次推进，最终 2/2 或 3/3，每条各有确切回执，顺序正确，无重复。
- 第一/第二条自身回显、已有同步等待与任务排队交错时，沿上一版修复继续推进，不要求人工接续。
- 明确未提交的允许错误沿原预算重试；unknown 只核查原操作，不重发、不跳条。核查后是否继续取决于批次和当前依据。
- 客户新消息、人工接管、暂停、撤权及业务依据变化正确停止尾部，已受理前缀保留。
- 需求与摘要按整轮处理，第二、第三条不重复生成或重复修改需求。
- 国际站与 WhatsApp 各自验证，不因其中一条渠道通过就认定另一条通过。

### 8.3 交互及旧状态

- 普通单条人工输入、整段建议和润色、Ctrl+Enter、发送期间新输入及切换客户均正常。
- 人工建议仅接受单条结果，不实现旧多项建议的兼容、拼接或转换。
- 人工输入区没有分条编号、合并、当前条目润色及自动尾部提取控件。
- 自动批次生成、发送、同步、核查、重试、完成和停止的文案与后台状态一致，详情能区分当前/历史与自动/人工。
- 回执投影与真实消息 ID 对齐，同一消息不重复显示；旧历史不挂在当前草稿下。
- 旧未发送草稿、旧已受理草稿、旧部分受理批次及 unknown 分别覆盖，不覆盖新输入、不重发受理前缀、不清除原账本。

### 8.4 实际窗口与候选

源码与最终候选 EXE 均实际打开 Electron，检查宽窄窗口下的普通人工输入、自动 1/3→2/3→3/3、同步等待、核查、停止和历史详情。截图逐张查看；投影夹具明确标注，不冒充真实平台自动收发。

WhatsApp 使用最终包内宿主及固定 SDK 检查短分区公共扫码超过 60 秒及刷新，验证原目录和回执保留。公共扫码不替代实号登录收发。

按改动运行相关后端、桌面/宿主、提示词生成一致性和工具定向测试，按需类型检查及构建；没有全量测试指令，不运行全量测试。

## 9. 实施与交付顺序

1. 以 0.3.20 修复为基线，先落实自然交流的提示词及人工建议单正文契约。
2. 完成人工输入简化、当前自动进度与历史记录分离，同时处理旧草稿及未决批次兼容。
3. 并入已完成的 WhatsApp 路径修正，执行自动两条/三条及各中断分支的定向回归。
4. 同步 0.3.21 版本，源码构建后立即本地中文 commit，包含本版源码、测试、文档与可提交的脱敏记录。
5. 完成实际源码窗口检查；候选打包后立即再次本地 commit，再核对最终 EXE、SDK 闭包、固定更新签名及实际窗口。
6. 构建、公开发布、安装与真实商家验收分别记录实际授权与完成情况。本方案本身不作为发布、安装或真实发送的授权。
