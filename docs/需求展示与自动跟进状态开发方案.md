# 0.3.11 需求展示与自动跟进状态开发方案

日期：2026-11-12。基线：已公开的0.3.10。实施版本：0.3.11。

读者：项目负责人、开发及验收人员。本方案已按用户指令完成本版实现、定向回归、最终EXE窗口和公开附件核对，0.3.11已公开；真实平台未覆盖场景及商品卡字段限制以[本版说明](0.3.11发布说明.md)及[验证记录](verification/0.3.11.json)为准，方案条目本身不代替验收证据。用户本轮确认的工作方式和上下文边界优先于此前方案：业务员直接聊天、填写业务补充，不使用逐项协助处理表单；普通展示图片、商品链接和SKU不进入模型，仅产品需求直接引用的来源图片可作为例外。

## 1. 本版目标与范围

1. 右侧采购需求只保留“摘要”和“客户需求”两个内容区，下方业务补充继续保留。
2. 取消聊天区常驻的“待你协助与跟进”和“开始处理/逐项完成”流程，保留有依据的跟进状态。
3. AI结合聊天和最新业务补充判断当前问题是否已有答案、是否仍需回复或等待客户；平台发送状态由实际回执决定。
4. 在客户需求中保存、展示客户图片、询盘商品链接和SKU图片，支持多个采购事项及来源定位。
5. 收紧模型输入：展示资料不自动进入上下文，只允许当前产品需求的来源图片进入相关业务请求。
6. 优先复用原有AI请求，不为每次状态变化、补图完成或资料展示增加独立模型调用，不让商品补齐成为自动回复前置。

继续保持商家隔离、当前授权、人工接管、确切正文与来源绑定、整会话未决发送保护、accepted证据、unknown原操作核查及发送失败链规则。

## 2. 界面整理

### 2.1 右侧两个内容区

顶部标题行保留短品类及必要的多事项选择，不再单独设置一块“采购事项”说明区。单事项使用静态标题；多事项仍以case_id区分，同品类使用轻量编号。

| 内容区 | 显示规则 |
| --- | --- |
| 摘要 | 简短中文，通常1–3句：客户当前诉求、沟通进展及下一步。建议不超过120字，默认两三行，较长旧摘要可展开。 |
| 客户需求 | 显示已采集的产品、数量、规格、定制、目的地、交期、预算、包装等，以及关联图片、商品链接和SKU展示。 |

摘要不显示事项编号、来源版本、内部推理、提示词解释或整段聊天复述。长度要求作为生成和展示规范，不能因摘要偏长使原本有效的回复失败；旧长摘要不批量调用AI重写。

普通需求行以名称和值为主；不逐行重复“未人工复核”。冲突、来源失效、待客户确认等异常在对应字段旁简短提示。点击字段或“原文”可按需查看来源、候选及复核操作，保留人工纠正入口，但日常使用不要求进入这些入口。

移除当前右侧的“本轮变化、商家条件、独立待确认列表、回复依据、本次应用的内部规则、事项与历史”，以及底部飞书版本/登记说明和重复保存提示。记录仍保存在相应业务对象或运行记录中。适用资料及业务校验不会因界面隐藏而失效。

下方业务补充继续按客户保存最新正文，支持原有侧栏比例调整和窄窗抽屉。客户页、待报价及客户资料复用相同需求显示规则。

### 2.2 聊天区

取消常驻协助任务表单和任务数量堆叠。整理需求、候选修正等操作收进需求区的按需操作入口，聊天顶部不再堆叠多个业务面板。

聊天顶部保留一行状态，例如“自动接待已暂停 · 待客户回复”。接待方式和跟进状态分别计算。未读、采购进度和发送回执仍是独立含义，不能互相推导。

生成中、发送中等短时执行进度按真实任务显示；发送失败和结果待核查保持清楚、持续且可操作，不能被普通跟进状态覆盖。

## 3. 跟进状态与自动判断

### 3.1 用户可见状态

| 跟进状态 | 依据 |
| --- | --- |
| 待回复 | 客户仍有需要回应的问题，且已有足够可用信息；或核实信息已具备，但相应回复尚未受理。 |
| 待你补充：具体事项 | 仍有明确需要人工提供的信息，如运费、库存或核价结果。普通需求缺项不自动成为人工待办。 |
| 待客户回复 | 当前相关问题已回应或已向客户提出必要澄清，等待客户反馈；不表示整个采购已经完成。 |
| 暂无待办 | 未发现当前需要继续处理的具体义务。 |
| 状态待更新 | 当前来源已变、尚未分析，或状态判断缺少可验证依据。 |

不设置“你正在处理”状态，不要求点击“开始处理”。除非消息或补充有明确事实，AI不能声称业务员或团队已经开始核实、已经联系工厂或已经完成某项工作。

同一客户可能同时存在等待客户反馈和待核实的不同问题。后台保留各问题状态，主界面显示当前最需要行动的一项及简短原因，按需查看其余内容；不把所有维度压成一个不可解释的完成状态。客户列表与详情使用同一有效问题集合，查看历史事项不改变当前接待事项。

### 3.2 判断和应用

AI在正常业务请求中一起输出需求、简短摘要及有依据的进展判断。每项判断关联具体问题、来源消息及当前业务补充版本；模型输出只作候选，由服务校验后应用。

服务负责核对当前客户、事项、消息和补充版本、引用的原文、权限及发送回执。迟到结果不能覆盖新消息或新补充产生的状态。AI不决定平台是否受理，不授予自动发送权限，也不把AI提取状态改写为人工复核记录。

状态分析部分缺失或无效时，保留可用回复和需求结果，将状态标为待更新或保留尚有效的原判断，不因附属状态解析失败重跑整次回复。

### 3.3 典型过程

客户询问运费，当前没有答案：显示“待你补充：运费”。

业务员在补充中填写“到法国运费20美元”：保存后先标记相关判断待更新；下一次正常AI任务确认信息足够后，该问题转为已有答案、待回复。仅有文字保存不能证明问题已核实完成。

生成了相应回复但尚未发送：仍为待回复。相应回复被平台受理后，结合问题与回复的关联变为待客户回复。若回复只回答了价格，运费问题不能一并关闭。

客户随后提出新的数量或规格：只重开或更新受影响的问题，不让旧的“已处理”判断掩盖新问题。

## 4. 业务补充驱动工作流

业务员继续直接聊天和填写业务补充，不新增逐项处理窗口、公开结果开关或必须完成的核实表单。

- 最新补充默认用于自动接待、人工建议及润色，继续只保留当前正文。
- 价格、运费、交期等作为当前客户的商家说明使用；“暂不降价、先问目标价”等作为接待安排使用。
- 成本、底价或明确标注仅内部使用的内容用于判断，不能直接复制给客户。
- 商家补充不写成客户预算、客户已接受价格、客户已同意寄样或其他买家确认事实。
- 补充更正或清空后，依赖旧补充且未完成的判断失效，按当前来源重算。已实际发送的历史及原发送回执保持原样。

自动接待开启且当前有应回复或应跟进事项时，将稳定保存的补充合并进待执行的正常业务请求；必要的对客跟进复用现有续答机制和当前授权。不逐字触发模型，不额外先跑一次状态分类。

自动接待暂停、客户人工接管或AI不可用时，只保存补充及待更新标记，不自动恢复接待或发信。没有正常AI任务时，不默认另开付费分析；语义状态在下一次正常、已授权的AI任务中更新。恢复自动接待后，尚有效的待回复义务才进入正常调度。

跟进须绑定实际问题和结果，避免同一补充反复触发相同发送。补充版本变化不能绕过整会话prepared/sending/unknown保护，也不能重置既有失败链。

## 5. 需求图片、商品链接和SKU

### 5.1 展示资料与产品来源分开保存

| 类型 | 用途 | 默认模型行为 |
| --- | --- | --- |
| 客户参考图片、展示封面 | 业务员查看、放大及定位原消息 | 不读取，不额外进入模型。 |
| 询盘商品链接及商品主图 | 查看商品来源、必要时后台补齐展示 | 不向AI展开网页、图片或商品详情。 |
| SKU编号、属性目录及SKU图 | 展示客户询盘中选项及候选 | 不额外进入模型。 |
| 产品需求直接引用的图片消息 | 作为该产品的原始来源依据 | 仅相关业务请求可纳入本轮原图读取。 |

“原始值”和“来源依据”继续区分：facts.product.value保留文字兼容，原图保存在图片资产中，新增产品来源关联。不能把图片字节或路径塞进文字产品值，也不能把图片识别出的名称当成客户原话。

产品来源记录至少关联当前商家、客户、事项、图片消息、消息版本、图片哈希及关系依据；原图、缩略图及关联进入现有完整备份范围。

设置封面或加入展示图库不等于设置产品来源。商品主图和SKU图不能仅因显示在需求卡中，被自动提升为允许读取的产品依据；首版产品图例外以可核实的聊天图片消息关联为准。

### 5.2 自动建立产品来源关联

优先利用明确的回复/引用关系，例如客户引用某图片并说“我要这款”；保留被引用图片的实际发送方，商家展示图只有被买家明确选用时才可能成为产品来源，不能将它当买家确认图像属性。

新采购中仅有一张直接发来的图片、没有竞争性产品来源时，可以先建立“产品来源候选”，在同一次主业务请求读取并判断，不增加独立图片分类调用。候选和确认关系须区分，图片推断的材质、尺寸等继续未确认。

多张图片且无法确定产品对应关系时，保留展示候选，正常文字回应或请客户澄清，不默认把全部图片升级为产品来源。明确“这几款”的多图引用可以关联多张，仍按事项归属和资源预算处理，不新增固定张数上限。

业务员可按需纠正关联，但不把人工逐图绑定设为日常必经流程。原消息被更正、图片改变、事项移项或关联撤销时，相关未提交生成及来源判断失效，不能影响其他事项。

### 5.3 后台补齐展示

优先使用已有询盘/商品卡字段和本地图片缓存。商品资料读取接口及SKU字段先核实实际能力，不能把登记模块已有字段名当成完整采集能力。

补充商品名称、主图及SKU展示使用受控后台读取和独立有界下载，不增加图片识别AI任务，不排在正文同步或发送之前。未核实不会抢占回复资源的外部接口暂不作为自动补齐前提；取不到资料时保留原链接及明确状态。

按商家、商品和SKU复用展示缓存。缩略图加载、封面调整及展示资料补齐只更新展示版本，不改变模型上下文指纹，不取消正在生成的回复。

## 6. 模型输入边界

### 6.1 输入内容

| 内容 | 自动接待/回复建议 | 普通润色 |
| --- | --- | --- |
| 最近50条文字及窗口外必要原文 | 保留；已覆盖的依据不重复追加 | 按当前正文所需保留。 |
| 有效需求及未决候选/冲突 | 带含义与来源，不把候选当确认 | 只取保持原意所需内容。 |
| 最新业务补充、适用资料与风格 | 按既有用途保留 | 保留必要条件及风格。 |
| 当前有效问题 | 简短描述、已有答案及还缺什么 | 不附带完整任务列表。 |
| 已关联的产品来源图片 | 本次任务需要时进入，须有本轮读取证据 | 默认不准备、不读取。 |
| 展示图片、商品链接、SKU资料及网页内容 | 不额外注入或读取 | 不注入或读取。 |
| 事项历史、修订列表、已应用规则列表、飞书状态 | 留在本地 | 留在本地。 |

采集字段的文字来源继续保留。客户明确说出的颜色、尺码、数量等属于文字需求，可以进入；不因此带入整套SKU目录。

### 6.2 防止从其他字段间接混入

不能只删image_manifest而仍保留全部原图准备，也不能只删除商品附件数组而让原始商品卡JSON继续作为聊天正文完整进入模型。

模型副本对商品链接URL、商品卡/SKU元数据使用简短类型或本轮引用说明，保留“客户引用了某商品”的对话位置及必要数量关系，不让模型据此访问链接。原始消息在本地完整保存，点击“原文”仍可查看。若原始值或候选中混有这类展示资料，也需按同一边界投影。

排除的普通图片保留必要的“此处有图片、未供本轮查看”说明，不附像素、URL或旧观察报告。产品来源图片必须由服务维护的明确关联及允许清单选出，不能让模型通过自报image_id扩大读取范围。

右侧摘要作为派生展示，不作为独立权威事实反复注入；AI依赖原消息、有效需求、当前问题及最新补充。UI隐藏资料应用信息不意味着移除适用规则本身。

本地仍保留完整验证对象；窗口外必需来源、角色、版本和哈希校验不削弱。当前read_compat、本轮原图读取证据及未读不能声称已读的规则继续保留。

## 7. 旧协助任务与状态兼容

不按旧open条数直接显示“6项待处理”，也不将所有旧任务自动标成已完成。

按客户、事项和业务问题建立稳定关联，同一核实主题的重复描述合并为一个有效问题。后续正常AI分析可提议已解决、仍未解决、已被新需求替代或依据失效，服务依据当前来源应用；历史记录保留。

未分析的旧记录显示状态待更新，不宣称全部完成，也不要求业务员逐项清理。旧processing_started_at只保留历史含义，不再作为新流程的必需操作。

旧任务关联的跟进计划、发送operation和回执继续原协议；撤出可见待办不撤回已经提交的发送，不清unknown，不解除防重锁。

新“业务跟进状态”与旧任务的发送followup_status、采购state、human_owned和未读分开保存/投影，避免复用同名字段造成含义冲突。

## 8. 响应速度要求

- 保留2秒检测、1秒合并、最近50条文字以及已有明确配置，不增加响应预设。
- 常规业务AI一次返回回复、需求、摘要和状态判断，不追加独立状态检查或摘要调用。
- 保存补充使用现有自动保存与防抖，合并同客户连续变化，取消旧来源任务；不逐字调用模型。
- 商品详情、展示图和SKU补齐不进入回复等待链路，后台展示变化不使有效回复过期。
- 仅产品来源图片可能增加必要的视觉耗时；复用下载缓存不等于可跳过本轮模型读取，也不能承诺图文回复与纯文字一样快。
- 每商家仍一个Accio AI槽，不通过未经核实的并发提高吞吐；本版不缩短180/190秒查询时限制造更快失败。

记录补充保存、任务排队、上下文组装、产品图准备、AI、结果应用和发送阶段。对相同纯文字输入比较新旧版本的额外外部读取与调用次数；只有足够实测后才报告耗时改善，不提前承诺百分比。

## 9. 实施顺序与维护入口

| 阶段 | 交付 |
| --- | --- |
| 1 | 跟进状态语义、结构化判断和来源验证；业务补充与状态待更新接线；旧协助去重投影。 |
| 2 | 产品来源关联、展示资料分离与模型投影；先保证普通图片/SKU不被旁路带入，再做后台商品补齐。 |
| 3 | 右栏两个内容区、精简状态栏、移除常驻协助表单；来源和修正入口改为按需打开，三页面保持一致。 |
| 4 | 定向回归、实际Electron窗口及必要授权合成验证；更新提示词审核稿和维护文档。 |
| 5 | 功能验收后按明确交付指令打包、核验和上传，记录实际范围。 |

主要入口：

- service.py、continuity.py、reception_state.py：有效问题、补充跟进、状态投影、旧任务及发送回执兼容。
- procurement.py、context.py：产品来源关联、需求字段、候选、跨事项及来源失效。
- reception_context.py、model_payload.py、message_photos.py、photos.py：消息选择、展示资料隔离、允许图片清单及读取准备。
- integrations/live.py、analysis.py、business_images.py：同任务输出、状态结果与原图证据校验；商品适配接口另经核实。
- Reception.tsx、Assistance.tsx、RequirementActions.tsx、RequirementFacts.tsx、SharedRequirementCard.tsx、useWorkbench.ts及shared DTO/协议：精简展示、自动保存、按需纠正和跨进程契约。
- 接待提示词审核稿及生成脚本：明确来源、状态判断、商家补充用途和图片边界；运行时继续使用生成的静态提示词。
