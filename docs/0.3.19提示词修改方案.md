## 1. 需求输出的判断边界

以本轮提供的有效对话和已保存需求比较：

- 真实需求已经存在于对话，但尚未记录：建立需求；已有对应事项但记录不完整时，补入原事项。
- 需求已经记录且没有新增、遗漏或更正：省略requirement_changes，不重新输出整份需求。
- 有新增或更正：只输出对应事项和字段的增量；真实独立采购沿用现有多事项归属。

客户没有在最新一条消息重述需求，不等于需求不需要建档；已有case或摘要也不等于正式需求已完整保存。补录仍由AI结合原对话判断，程序不因空表单自行建单。

沿用现有一次生成任务与本轮上下文，不新增每轮独立整理任务、历史全量扫描或定时补录。

### 1.1 最近50条与旧需求保留

最近50条是普通文字聊天窗口，不是需求记录的有效期，也不是50行文本。当前程序将已保存requirements和case_catalog独立传入模型，并按其中明确的证据引用补入本地已有的窗口外historical_evidence；输入过大时明确失败，不静默删去旧证据后继续修改。

旧需求原文没有在最近50条出现，不构成否定、撤回、清空或重新归纳旧字段的依据。补录只填尚未记录的真实内容；已有字段有明确补充、更正或撤回时才作对应增量，其余保留。仍允许客户明确修改旧条件，不将所有旧字段锁死。

程序继续按字段合并：未列入变更的字段保持原值；空值不清空；清空使用带真实原文依据的clear_fields。来源、事项归属和版本检查继续执行，但这些形式校验不能代替模型是否正确理解更正的语义验收。

如果旧原文没有本地记录或本轮确实没有相应依据，不以“本轮看不到”推翻已有值；无法确认的内容留待澄清。对于尚未建档、已超出窗口且没有任何引用关联的历史需求，本轮可能完全不可见，不能仅凭提示词宣称可以完整补齐；历史覆盖问题须另外明确处理范围，不自动扩大每轮窗口或扫描全历史。

### 1.2 实施前规则覆盖核对（2026-11-14）

下表保留实施前对reception-0.3.16提示词、requirement_changes.py和自动接待应用入口的核对。实施前18项需求增量与7项提示词用例通过；本轮已升级为reception-0.3.19并修正闲聊入口，实际新增结果另见验证记录。测试使用本地合成结果，不代表真实模型语义已经验收。

| 场景 | 当前覆盖 | 具体处理与边界 |
| --- | --- | --- |
| 首次提出真实采购 | 已覆盖规则及程序应用 | create建立事项，可安全复用无正式需求且无待办占用的空事项；必须有产品及真实买家原文 |
| 给旧需求补一个尚未记录的字段 | 已覆盖规则及程序应用 | update原事项，仅set_fields列出的字段改变，其他字段保留 |
| 补充已有复合字段的一部分条件 | 部分覆盖 | update支持保存，但每个字段的value整体替换；同一specifications内未改变的尺寸、材质须由AI保留，现有用例不足以证明这一点 |
| 更正旧数量、交期等字段 | 已覆盖规则及程序应用 | update原事项的新值及依据，不另建需求，不将新旧冲突条件并列 |
| 纠正此前AI归纳错误 | 已有提示词依据与更新能力 | 引用本轮可见的原始证据修正；不能要求一定有更新的客户消息，也不能仅为换说法重写 |
| 撤回某个条件而没有替代值 | 已覆盖规则及程序应用 | clear_fields携带真实撤回依据；null、空字符串或未提及不执行清空 |
| 同商品的另一笔独立采购 | 已覆盖规则与定向用例 | 明确独立采购可create，不能仅因商品相同合并为原事项 |
| 一轮更正旧事项并新增另一事项 | 已覆盖规则与定向用例 | 同轮分别update与create，reply_case_refs分开归属 |
| 无变化或重复应用结果 | 已覆盖规则与定向用例 | 省略或空数组不改正式需求；同请求幂等，重复建档来源不覆盖较新的条件 |
| 已保存需求原文超过最近50条 | 已有上下文机制，新增语义验收待实施 | 已存需求独立传入，有引用的本地旧原文补入；不能因窗口滑动重写旧字段 |
| 历史需求未建档，但仍有本轮可见原文 | 程序可应用，提示词与自动入口有缺口 | 缺少明确补录指引；最新消息被判闲聊时会清空AI返回的变更，本版拟修正 |
| 已撤回字段为空，旧肯定原文仍可见 | 部分覆盖 | 已有否定/更正原则和撤回证据，但补录须明确区分“未记录”和“已撤回”，不能把后者补回 |
| 尚未建档且原文在窗口外、无引用 | 未完整覆盖 | 模型本轮不可见，不能仅改提示词保证补齐；另行明确历史覆盖范围 |
| 整笔采购取消或暂缓 | 不能用字段撤回视为完整覆盖 | 当前需求变更契约只有create/update及字段clear；记录否定意图和摘要不等于已有独立取消采购动作，也不等同停止联系 |
| 查看或引用已停止的旧事项 | 已有状态保护与定向用例 | 不因事项路由重新开启接待或抢占当前指针 |

保持create/update/clear_fields的现有主结构。重点补齐未建档需求识别、闲聊入口、复合字段条件保留及撤回后不恢复的规则与验收，不把这些语义判断改成关键词建单，也不把结构校验当成模型理解正确的证明。本版不新增整笔采购取消/暂缓的独立状态流程；准确记录原意和历史，不将其等同停止联系，专门生命周期另行定义，不能混入普通字段补录。

## 2. 提示词的具体修改

修改源为docs/接待提示词审核稿.md，再由scripts/sync-reception-prompts.mjs同步运行时静态模块。

### 2.1 区分回复目标与需求整理依据

P02自动接待开头，将“针对最新有效买家消息”只用于回复目标，摘要和需求结合本轮提供的会话。

拟替换为：

> 只处理宿主指定的当前客户，回复针对reply_target及最新有效买家消息；摘要和需求结合本轮提供的会话，需求按变更模块处理。按case_catalog确定采购事项归属，宿主负责权限、来源版本和实际发送，你不能改变授权或宣称已执行。

P02“聊天与采集”中的“真实新采购才建立新事项”改为“尚未建档的真实采购才建立新事项”，使此前已经提出但尚未记录的采购也属于可建档范围。

### 2.2 在共用需求模块中明确补录与不重复的边界

P02-A首句拟替换为：

> 结合本轮提供的有效对话与requirements、case_catalog，补建尚未记录的需求，或补入对应原事项；已记录且无变化时省略requirement_changes，不复述整份表格、不只为换中文说法而更新，不因本轮未重复提及或原文未入窗口而撤回、清空或重写已有字段。

在原set_fields规则中补充：“补充或更正同一字段时，保留其中仍有效且未改变的条件。”在原撤回规则中补充：“已撤回的条件不因补录而恢复。”这两处用于区分复合字段修改和已撤回的空值，不另设建单阈值或关键词判断。

其余归属、增量字段、来源、清空和防重规则保留。自动接待、普通人工建议和内部需求整理共用这一处规则，不分别叠加同义说明。正文润色仍不整理需求。

### 2.3 商品ID段落只删除指定表述

从现有段落中仅删除“平台商品ID及”，删除后全文为：

> 原始聊天中的链接只能帮助识别指代，页面标题、属性、价格、库存、交期或Custom Logo字样不能证明客户需求或本店经营能力。空字段和重复看到商品ID都不授予查询权限。

不补写关于如何判断、选择或排除商品ID的新句子，也不增加提醒、例子或解释。保留该段其余原文。

## 3. 自动接待中的对应拦截点

service.py当前按最新买家消息计算social_reply，随后在应用需求变更前将requirement_changes和reply_case_refs清空。这会使“前文有未建档真实需求，最新一句是感谢”即使获得模型补录结果，仍无法保存。

实施时解除该分支对需求变更和事项引用的一律清空，让模型返回的增量继续经过原有来源、归属、版本、事务和防重校验。闲聊回复、停止联系、授权及发送保护分别沿用现有处理；不增加程序主动创建需求的逻辑。

这项调整依据当前明确要求与可复现合成场景，不依据本机旧数据状态，也不重新清理或迁移数据。

## 4. 定向验证

| 场景 | 预期 |
| --- | --- |
| 前文已有仍有效的真实采购，正式需求未记录，最新消息未重述采购 | 模型可输出补录，程序能够保存 |
| 同一需求已完整保存，最新消息没有新增条件 | 不输出需求增量，不增加需求修订 |
| 已保存需求的原文早于最近50条 | requirements及有明确引用的本地原文仍进入上下文，旧字段不因窗口滑动而被重写 |
| 本轮只有数量的新依据，原规格或交期未再次出现 | 只更新有依据的数量，保留原规格与交期 |
| 旧字段原文确实缺失，本轮也没有更正依据 | 保留原字段，不能用缺失推导撤回或清空 |
| 客户明确更正早于窗口的原条件 | 有依据的更正可以应用，不因旧字段保护而锁死 |
| 已有对应事项，但遗漏前文一个有效条件 | 只补对应字段，保留原事项及其他字段 |
| specifications已有尺寸和材质，客户只补充颜色或只更正颜色 | 同字段的新值保留未改变的尺寸和材质，不整字段缩减为只有颜色 |
| 某字段已有撤回记录而为空，旧肯定消息仍可见 | 不把撤回后的空值当漏记，不恢复旧条件 |
| 原文有明确数量，旧AI归纳错误但客户未发新消息 | 可依据本轮可见原文修正，不要求客户重复更正，也不无故改写其他字段 |
| 相同补录结果重复应用或再次生成 | 沿用现有防重，不重复建档或反复改写 |
| 只有问候或感谢，没有真实采购依据 | 不因表单为空建单 |
| 客户明确撤回或更正旧需求 | 不按旧条件重新补回 |
| 同客户多事项 | 补入对应事项，不混用条件或重复建立已有采购 |
| 正文润色 | 不输出需求变更 |
| 商品ID措辞 | 指定短语已删除，未新增任何ID判断提示 |

定向覆盖既有提示词装配、需求增量和闲聊接待相关文件，执行提示词生成一致性检查；不运行全量测试。合成回归只证明装配、应用和保护逻辑，不能代替真实模型是否正确识别未建档需求的语义验收。

## 5. 自然短消息的提示词修改

### 5.1 共用表达规则

在P01现有“对话与进度”中替换、合并相关表达要求，集中使用以下文字，不在各任务重复增加同义段落：

> 用自然简短的聊天口吻，先回应客户当前问题，不机械寒暄、复述已知需求或堆叠流程话术。简单内容一条即可，多个独立意思可分条，不为凑条数拆分；价格、适用条件和必要限定放在同一条，不拆成易误解的片段。

当前客户语言、有效风格资料、事实依据、承诺边界及每轮提问上限继续按原规则执行。需求补录结果供内部保存，对客回复只表达当前需要交流的内容。

### 5.2 AI直接给出发送边界

P02自动接待、P03普通人工建议、WHATSAPP任务的单个reply改为reply_messages；每项包含body与该条自己的reply_sources。只给一份消息列表，避免模型同时输出整段正文与分条正文而互相矛盾。

拟使用的格式说明：

> reply_messages是按发送顺序排列的消息数组，每项为{"body":"客户语言正文","reply_sources":[本条真实来源编号]}，每项将作为一条独立消息发送。需要回复时输出1至3条非空消息，条数由内容决定，不为凑数量拆分；整轮正文合计最多1200字符。

1至3条是本版单轮协议预算，不要求每次发送两条或三条，也不限制每条必须只有一句话。沿用整轮1200字符预算，不把原预算放大为每条1200字符。

各任务的完整字段：

| 任务 | 输出字段 |
| --- | --- |
| 国际站自动接待 | action、reply_messages、conversation_summary，按需追加requirement_changes、reply_case_refs |
| 国际站普通人工建议 | reply_messages、conversation_summary，按需追加requirement_changes、reply_case_refs |
| WhatsApp自动接待 | reply_messages、wa_summary |
| 正文润色 | 保持reply、reply_sources，不自行切分人工冻结正文 |
| 内部需求整理 | 保持需求变更及摘要，不生成对客消息 |

国际站action=skip时reply_messages为空数组；仍可返回有依据的需求补录。skip表示不发送回复，不表示需求必然已经记录。

P01来源说明、P02动作与格式、P03输出格式和WHATSAPP输出格式同步到新字段。P02-A仍只负责一轮需求增量，不在每条消息内重复需求变更；第2节的商品ID修改仍严格只有指定删除。

### 5.3 输出示例

下例仅说明两条独立消息的结构，不加入固定提示词；m1代表当前客户已提供的真实依据：

```json
{
  "action": "ask",
  "reply_messages": [
    {"body": "Got it, black for the logo.", "reply_sources": ["m1"]},
    {"body": "What’s the delivery postcode?", "reply_sources": ["m1"]}
  ],
  "conversation_summary": "客户更正Logo颜色为黑色，收货邮编尚待确认。"
}
```

程序不按字符数、标点或空行再拆AI正文。模型给一条就是一条，给两条就按两条处理；不自动补寒暄、过渡语或尾句。

## 6. 输出契约、校验与草稿

### 6.1 共用规范化模块

新增reception_service/reply_messages.py，提供消息列表结构校验、展示正文组合和有序消息指纹计算。Live、Demo、自动接待与WhatsApp统一复用，正文润色走原单条分支。

校验内容：数组为允许的条数、正文为非空字符串、总长不超预算、来源为字符串数组、每条正文格式有效。国际站逐条执行现有validate_reply，并对组合正文执行现有整轮校验；各条使用自己的来源，不能用整轮来源并集替代。WhatsApp沿用本渠道的归属与来源检查，不套用国际站Case前置。有任何一条无效则整轮不进入发送，不截断或只取前几条。价格与限定是否表达完整仍须通过提示词及真实语义验收核对，不把结构校验当作语义正确的证明。

新模型结果使用新契约；旧版已保存的单条draft、manual_suggestion和operation按单条兼容读取，不原地改写历史账本，不把新结果缺少数组自动当作旧格式放行。

### 6.2 草稿保存一轮消息

AI草稿增加reply_messages，保留body作为程序派生的展示文本，等于各条body以空行连接。body仅兼容现有展示、复制与整轮中文翻译，真实发送以保存的消息数组为准。

冻结指纹包含有序正文、各条来源、消息数量、草稿版本及原来源指纹。改变顺序、合并、删除或编辑任一条都会形成新的草稿版本；发送开始后的一轮内容不可被编辑器改写。

requirements和conversation_summary在生成完成后按整轮应用一次；不能因为有三条回复就应用三遍需求、生成三次摘要或调用三次AI。

## 7. 一轮多条的持久化与发送

### 7.1 保存整轮，再逐条提交

新增reply_batches.py处理窄范围的批次状态与推进。国际站使用reply_batch实体，WhatsApp使用独立wa_reply_batch实体；原operation与wa_operation继续按渠道独立保存。

父批次保存batch_id、渠道和商家/客户归属、原来源消息、冻结草稿版本、来源指纹、消息列表指纹、next_index及状态。每条保存稳定part_id、从0开始的part_index、正文、来源、尝试operation_id列表、实际message_id、回执及状态。

第一次提交前以事务冻结整轮及所有有序条目；尚未轮到的条目为planned，不提前向平台提交。激活当前条目时创建独立发送operation。只有前一条取得该渠道的确切accepted证据，下一条才进入现有发送队列。

同会话在整个批次活动期间保持互斥，包括两条之间、明确未提交重试等待及回执核查等待，不能被另一轮自动回复或人工发送插入。只有本批次当前合法条目能通过内部继续检查，不能泛化排除其他未决操作。

父批次状态使用prepared、sending、waiting_retry、waiting_receipt、accepted、stopped；“部分已发送”根据已受理条数显示，不用它替代单条真实回执。

### 7.2 每条仍执行现有检查

每条提交前重新核对账号与连接代次、当前授权、人工接管/停止联系、原来源消息、草稿和业务资料版本，以及同会话未决操作。来源与业务检查沿用现有本地依据，平台历史读取仍只在提交后按确切消息ID核查受理，不恢复Ready/Seal前置。客户新消息、商家人工回复或补充/资料变化使旧依据失效时，取消尚未提交的尾部；已经在途的条目只收取原操作结果。

第一条被受理后，程序会写入自己的卖家消息并推进本地修订。必须在同一受理事务中将这些确切自有写入归属于本批次，推进批次预期版本；不能直接沿用第一次的全会话指纹，否则第二条会被自身消息误判过期。也不能排除所有卖家消息：其他人工回复仍须中止旧批次。

现有调度器逐条推进，保留人工发送和回执核查的优先级及公平调度；不在业务线程中用循环和sleep占住整个批次。

### 7.3 部分成功、unknown与重启

- 每条拥有独立平台消息ID与受理证据；国际站沿用确切平台回读，WhatsApp仍要求确切ID且ACK>=1。
- 任一条unknown，停止后续发送，只核查该条原operation，不补发、不猜同文、不换请求键。
- 核查后来确认accepted时，只有原批次、授权和来源仍有效，才考虑下一条；已经取消的尾部不因迟到回执恢复。
- 明确未提交的暂时错误，国际站沿用现有最多三次与5秒/15秒退避，计数改按稳定part_id归属。不同正常条目不是相互的重试；新job、草稿或批次编号不能清零原逻辑条目的失败预算。WhatsApp不因此新增自动重发机制。
- 重启保全已受理和unknown记录，撤销授权并停止未提交尾部，不从第一条重播，也不因重新授权自动续发旧尾部。
- 逐条受理后逐条写入真实聊天历史；整轮全部受理后才清除该轮待回复标识、完成补充续答并结束批次。部分成功不能显示“整轮已发送”。

### 7.4 国际站原生防重键必须同步适配

当前accio_native/chat.py把自动回复逻辑键绑定到商家、会话和source_message_id；续答也按来源与阶段认领。仅创建多个Python operation会使第二条被原生账本拒绝。

普通回复首条继续受原来源逻辑键保护，并在冻结意图中绑定batch_id和有序消息哈希清单。后续条目使用来源、批次及part_index派生的稳定条目键，原生适配器同时核对同来源首条记录属于该冻结批次、清单一致、前序条目均已确切受理。续答的final/supplement按相同原则扩展现有来源/阶段认领。

不能只给每条换一个随机键。旧版同来源accepted或unknown若没有本批次绑定，仍阻止新批次；旧unknown不能通过新消息结构绕过。明确未提交重试仍沿用原逻辑条目身份。

### 7.5 WhatsApp保留单条宿主账本

Python的_task_whatsapp_reply先保存整轮；_schedule_whatsapp、_wa_prepare_send、_wa_transport_result、_wa_ack、_wa_ingest、_wa_cancel及恢复入口按父批次与当前条目推进。原pending只在整轮完成或明确取消时结算，不能第一条ACK就触发另一轮生成。

whatsapp-coordinator.ts只接收当前可提交子操作，继续逐条prepare、submit和reconcile。host.sendFrozen仍是一次sendMessage，SendLedger仍是一个operation一份冻结单条意图；批次关联保存在Python实体中，不把多条结果塞进一个message_id，也不必改变既有JSONL账本格式。

自身消息回显与提前ACK按确切operation/message_id归属本批次条目，不能误判为人工接管。所有未决账本、回执和新实体继续进入既有完整业务备份。

## 8. 页面与人工编辑

### 8.1 AI结果按条预览

沿用现有输入框上方待处理框，将多条建议显示为有顺序的独立预览块，提供“采用”和“弃用”，处理后关闭，不增加常驻建议栏。中文翻译仍对整轮展示正文使用已有翻译入口，保持段落顺序；翻译结果不反向决定分条边界或发送正文。

采用多条建议后，当前编辑区进入分条编辑：各条可独立修改或删除，并提供“合为一条”。普通手写入口仍为单条文本；分条润色只处理当前选中的一条冻结正文，其他条目保持原样，不自动合并或重新分条。

分条润色请求在原草稿版本与正文hash基础上增加可选part_index；后台核对该版本中对应条目的确切正文，context.unsent_reply只传该条。返回建议带input_part_index、整份编辑草稿版本及冻结正文hash；采用时再次核对，期间编辑、删除、合并或切换导致版本不符则结果过期，不按新位置误替换。无part_index的原单条润色保持兼容。

### 8.2 编辑与发送契约

Draft、ManualSuggestion增加可选message_parts或reply_messages投影；save_chat_draft增加可选message_parts字符串数组，并核对body等于这些条目按空行组合。前后端统一同一字段含义：AI来源消息用reply_messages，人工编辑冻结正文用message_parts。

普通人工发送仍不要求AI、采购事项或买家最后发言。发送AI建议采用后的多条草稿也属于人工明确发送：只按冻结版本创建一轮发送批次，后续在新买家消息、人工暂停或原授权意图失效时停止尾部。人工单条正文原有50000字符预算保留，多条编辑按整轮50000字符校验，最多三条。

发送开始后新增输入保存在新的编辑版本中。旧批次的部分或全部回执不得清掉新正文、恢复已处理建议框，或修改用户后来编辑的分条。

部分成功的草稿持续绑定原批次，不能编辑后重新发送已受理的前缀。界面提供“只保留未发送内容”，后台按冻结批次的连续已受理前缀及条目索引核对，再保留当前已保存尾部；已受理前缀包含新编辑时先保留全部正文，提示将新增内容移到未发送条目，不能静默丢弃。在途及部分受理时禁用破坏条目归属的删除/合并。普通人工明确新建相同正文的单条发送仍允许，不引入全局同文禁发。

### 8.3 回执显示

发送区域显示“已发送1/2条”“第2条结果待核查”或“剩余1条已停止”等简短状态；核查按钮只针对未决子操作，不提供重发整轮入口。正常聊天区按真实平台消息显示多个气泡和各自时间，不额外复制父批次的组合正文。

WhatsApp原始聊天区继续由网页展示；工作台只增加批次进度和必要核查信息，不仿造第二套WhatsApp消息列表。

## 10. 新增定向验收

第4节需求回归继续执行，补充以下场景：

1. 一次AI生成两条，平台实际收到两条，正文、顺序和来源与冻结列表一致；单条结果仍只发送一次。
2. 三条建议的总提问次数仍按整轮限制，不按每条重新计算；普通短确认不被强制拆分。
3. 单条校验失败、来源不合格或整轮超长时，没有任何一条提交。
4. 第一条受理后，程序自身历史与修订更新不阻断第二条；插入真实客户/人工消息则停止尾部。
5. 第二条unknown、提前ACK、迟到回显、断线或暂停时，保全第一条回执，停止第三条，不重发第二条。
6. 明确未提交重试按条限次且预算跨job/草稿保留，其他条目不混算为同一条的失败尝试。
7. ordinary/final/supplement以及WhatsApp均通过批次推进；固定收悉ack仍为原单条，不重复收悉。
8. 子操作被认领前后、提交后未保存回执等断点重启，均不重复提交，原unknown仍按旧证据核查。
9. 新结构不能绕过旧版已受理/unknown的来源逻辑键；旧单条草稿、原生账本及完整备份可读取核查。
10. 人工建议分条预览和采用、修改某条、合并、发送期间继续输入、跨会话切换与迟到回执均保全正确版本；分条润色只替换原冻结条目，删除或重排后的迟到结果失效，普通手写与原单条润色保持兼容。
11. 实际Demo窗口逐条查看宽窄窗口截图；真实平台双消息、真实AI表达及实号ACK分别记录是否验收。

定向覆盖提示词装配、requirement_changes、social_reception、native_automatic_chat、continuity、send_retry_policy、manual_chat/manual_receipts与WhatsApp相关文件，新增必要的reply_messages/reply_batches用例。执行类型检查、提示词生成一致性检查及实际Demo窗口检查；不以本版为由运行全量测试。
