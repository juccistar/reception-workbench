# 0.3.20 多条发送逻辑与交互梳理

核对日期：2026-11-15。依据：已发布 0.3.20 的源码基线 3feee61；本次另行修正的 WhatsApp 登录目录路径不改变下述多条发送逻辑。面向工作台使用者及维护者。

本次按源码核对，没有读取截图客户的真实业务库或调用其平台接口，没有执行客户发送。因此可以确认实现规则及可构造的缺陷，不能仅凭截图确定该次第二条停止的具体原因、当前正文是否已经发送，或客户实际收到几条。

目前的问题集中在三处：当前人工草稿与历史发送批次的归属没有在界面说清楚；自动批次与人工批次的尾部处理是两套交互；旧自动尾部转人工后缺少持续来源关联，存在再次提取并重复人工发送的路径。不能将这些问题理解为所有发送保护都失效。

## 1. 先分清四个对象

| 对象 | 保存什么 | 对用户的含义 |
| --- | --- | --- |
| AI 回复草稿 | 模型生成的一至三条正文、来源、生成依据 | 可以成为自动回复，或供人工采用；生成不等于发送 |
| 当前人工草稿 chat_draft | 当前会话编辑中的正文、可选分条、修订号、处理状态 | 底部输入区正在编辑的内容 |
| 发送批次 reply_batch / wa_reply_batch | 冻结正文、条目顺序、正文摘要、条目与批次状态 | 记录一次确切发送计划，不随当前输入框任意改写 |
| 发送 operation 与渠道账本 | 每次提交意图、确切结果、消息 ID、提交证据 | 判断已受理、明确未提交或结果未知，防止重复提交 |

人工编辑器按客户会话保存，不按采购事项分别保存。一个客户可以有多个采购事项、多个历史发送批次，同时只有该会话当前的人工编辑状态。

## 2. 三条发送路径

| 项目 | 国际站自动回复 | 国际站人工回复 | WhatsApp |
| --- | --- | --- | --- |
| 正文来源 | 正常接待、final 或业务补充续答的 AI 结果 | 手写、采用建议、当前条目润色、尾部提取后的人工草稿 | 自动回复由 AI 生成；人工回复在原生 WhatsApp Web 中操作 |
| 分条生成 | AI 自然选择一至三条，程序不按空行自动拆条 | 采用多条建议或取得分条草稿后可以逐条编辑 | 自动回复一至三条；没有国际站人工分条编辑器 |
| 单条情况 | 一条使用原单条路径，多条冻结批次 | 一条使用单条 operation，多条冻结人工批次 | 自动结果即使一条也冻结 WhatsApp 批次 |
| 正常推进 | 前一条确切受理后，复核依据并排下一条 | 前一条确切受理后排下一条 | 消息 ID 与 ACK≥1 满足后准备下一条 |
| 同步等待 | 有 waiting_sync，首次等待最多 60 秒 | 没有同一套自动同步等待策略 | 没有国际站 waiting_sync 策略 |
| 明确失败重试 | 部分明确未提交的暂时错误最多三次，退避 5 秒、15 秒 | 被拒绝或未知即停止尾部，不套用自动重试 | 不套用国际站 5/15 秒自动重试 |
| 结果未知 | 沿原 operation 核查，阻止新发送 | 同左 | 沿宿主原账本及确切消息 ID 核查 |
| 停止后处理 | 符合证据条件时“取出未发送内容”到人工草稿 | 关联人工批次部分成功时“只保留未发送内容” | 没有国际站这两个尾部编辑入口 |

AI 多条输出每条必须有非空 body 和 reply_sources 数组，共一至三条，正文总计最多 1200 字；程序以两个换行拼接展示。结构检查不保证语义自然，也不意味着每轮应固定回复三条。国际站 skip 可以没有回复，不能同时带待发送正文。

## 3. 自动多条的顺序和等待

一次多条结果冻结为一批，每条有确定顺序、原文、来源和正文摘要。国际站自动批次还绑定父草稿修订、买家来源、授权代次、事项与会话版本、业务上下文指纹；同来源已有发送尝试时不能新建批次重置原发送链。

正常顺序为：冻结批次 → 检查第一条 → 持久化提交意图 → 渠道提交 → 保存确切受理证据 → 复核后续依据 → 排下一条。多条不是并发发出，也没有正常条间固定等待五秒或十五秒。实际间隔包含提交耗时、回执确认和排队调度；业务协调线程约每 150 毫秒调度一次，这也不是实际发送间隔的承诺。

国际站每条自动发送继续检查当前账号、授权、范围、接管、当前事项、买家来源、草稿与会话版本、业务资料、补充、图片、供货选择和未决操作。原生通道还在认领前、取通信令牌后、提交前三处检查。人工普通发送不要求已经有需求、AI 检查通过、字段齐全或最后一条来自买家。

只有消息同步尚未完成而硬条件仍成立时，国际站自动批次才进入 waiting_sync。这个状态释放执行线程，通过普通增量同步推进；等待期限从首次进入起最多 60 秒，不因新任务或活动水位变化刷新。同步完成不代表必然续发，还必须重新通过原依据检查。

第一条受理后的自身回显，只有属于本批次确切消息 ID、角色、归属、正文和附件匹配，且受控时间修订没有改变消息顺序时，才允许更新后续依据。真正的新买家消息、不同 ID 的人工消息或其他业务依据变化不会借同步一并吸收。

提交前预检发现同步未完成，可以尚未创建 operation，不占尝试；operation 已经创建后遇到明确未提交的同步门控，仍计入原条目的尝试数。三次上限不因等待、换任务或重启重新计算。

## 4. 人工编辑区实际能做什么

- 手写普通正文。换行或空行不会自动拆条。
- 采用多条 AI 建议后进入分条编辑；也可以从可恢复批次取得分条草稿。
- 逐条修改正文，点击某条输入框将其选为当前润色对象。
- 删除条目，或把当前全部条目以两个换行合并成单条。
- 对当前选中条目润色；采用润色结果只替换该条，仍要核对原文、下标和草稿版本。
- 发送当前草稿；发送前保存并核对会话、正文和修订号。

当前没有“新增一条”“在光标处拆分”按钮，也没有直接上传聊天发送附件的入口。删除后即使只剩一条，编辑器仍可能保留“第 1 条／合为一条”的分条形态；它不代表后台必然按多条发送。

业务补充面板的多选、粘贴和拖入附件用于补充上下文，不是给客户发送附件。该面板最多五个附件，单个 6 MiB、合计 20 MiB，并限制格式。

| 操作 | 关键条件与实际结果 |
| --- | --- |
| 生成／重新生成建议 | 生成结果供选择，不直接替换正在编辑的正文，不直接发送 |
| 替换建议 | 多条结果进入分条草稿，单条结果进入普通正文；锁定批次的结构不能通过普通建议随意替换 |
| 弃用建议 | 记录结果已处理并关闭待处理框，不发送 |
| 润色当前条目 | 选中条目必须有字，保存并核对版本；接受结果只替换该条，不自动发送 |
| 删除／合并 | 改变当前人工草稿结构；关联未决或部分受理批次会限制结构操作 |
| 发送 | 要求连接、后台健康、接管确认、有效非空正文及没有阻塞的未决发送；先保存，再核对当前会话、正文和版本 |
| 重试原发送 | 沿原请求编号及冻结参数查询／完成原请求，不以新请求绕过未知状态 |
| 只保留未发送内容 | 处理关联人工批次的连续受理前缀；核对原文及未决状态后保存尾部 |
| 取出未发送内容 | 处理可恢复的停止自动批次；当前人工输入必须为空且没有未保存修改、保存中或未决发送 |
| 核查发送结果 | 按原 operation 查回执，不重发 |
| 恢复此客户自动接待 | 改变当前客户的接待归属，原来已经 stopped 的批次不会因此重新续发 |

编辑正文会尝试接管当前客户，并约 800 毫秒自动保存。查看或生成建议不接管；采用建议引起正文修改时会接管。弃用只记录该建议已处理，不发送；同一结果处理后不会重复弹出。全局“自动接待中”和当前客户“人工接管”可以同时存在，分别表示全局和单客户状态。

## 5. 人工发送期间、部分成功和切换客户

发送时冻结当时版本。发送期间仍可输入新内容；只有回执对应的冻结版本与当前编辑版本、正文都相同时，前端才清空输入。因而回执回来而输入区仍有文字，并不自动表示该文字需要再次发送。后台持久草稿也可能保留正文并将状态改为 accepted，而前端显示为空。

切换客户、离开接待页前会尝试保存；保存失败或仍有未保存内容时阻止切换。详情读取和异步结果按请求序号、会话及编辑版本核对，避免迟到结果覆盖别的客户或新输入。

人工批次前面已受理、后面停止时，不直接把整份原草稿重新发送。关联批次会锁住直接新发，提供“只保留未发送内容”：必须没有待核查操作，已受理部分为连续前缀，前缀正文仍与原文一致，剩余内容恰为原尾部，才能移除受理前缀并保存尾部。若已编辑受理前缀，可能需要先还原原文才能执行这一步；界面没有足够解释这个要求。

人工发送通信未确认时，前端保留原请求编号及冻结参数，“重试原发送”继续使用该请求，并非创建新发送来绕过未决状态。unknown 的核查按钮也是读取原结果，不是重发。

## 6. 停止、失败、未知分别意味着什么

| 状态 | 含义 | 后续行为 |
| --- | --- | --- |
| planned / prepared | 条目尚待执行，或已准备提交意图 | 仍要检查授权及来源；接管、暂停等可以取消未提交尾部 |
| sending | 正在提交或处理提交结果 | 不能把它当作肯定没发 |
| accepted | 渠道满足确切受理条件 | 推进下一条；不等于客户已读，WhatsApp 的 ACK 条件也不等于所有平台相同送达含义 |
| rejected 且 submission_started=false | 有明确未提交证据 | 自动发送仅在允许的暂时错误上限次重试；其他情况停止 |
| unknown / waiting_receipt | 尚不能确认确切提交结果 | 只核查原 operation，阻止新增发送，不能提取为“肯定未发” |
| waiting_retry | 自动批次正在等待原条目的允许重试 | 5 秒／15 秒退避，最多三次总尝试 |
| waiting_sync | 国际站自动批次等待同步完成 | 首次起最多 60 秒，再复核原依据 |
| stopped | 原批次不再推进后续条目 | 已受理的仍保留，未决的仍须核查；可恢复性另行计算 |

出现接管、撤权、买家来源或其他依据变化，会停止未提交尾部。停止不能撤回已经受理的前缀。存在在途或未知条目时会保留回执围栏；重启也不自动续发旧批次、恢复旧授权或清除 unknown。

WhatsApp 新买家消息、人工回复、接管、撤权及账号或连接变化都有相应停止检查。它的发送领取先把 operation 持久化为未知，再交宿主提交；没有确切消息 ID 和 ACK≥1 时，不因为传输函数返回了“失败”就推断肯定未发。

## 7. 截图里为什么会出现一条编辑正文与“已发送 1/2 条”

截图中的元素来自不同对象：

| 元素 | 真正来源 |
| --- | --- |
| “第 1 条 · 当前润色” | 当前人工草稿的条目下标，以及当前选中的润色对象 |
| 当前正文 | 当前人工草稿，与旧批次冻结正文分别保存 |
| “合为一条” | 对当前编辑数组做合并，不负责历史批次 |
| “已发送 1/2 条” | 某个历史或活动批次中 accepted 的数量及总条数 |
| “后续发送已停止” | 上述批次的 stopped 状态 |
| “取出未发送内容” | 上述批次通过自动尾部恢复条件时提供的另一个动作 |
| “发送” | 当前人工草稿的发送入口；按钮是否可用还取决于 canSend |

当前界面逐项展示该会话返回的批次，包括已完成和已停止的历史批次，没有把它们限定为当前编辑器的批次；进度 DTO 也没有提供足够的来源、时间和逐条正文信息。界面因此容易让人把“旧批次第一条”与“当前编辑器第 1 条”理解成同一条。

“取出未发送内容”要求当前输入为空、未修改、不在保存中、没有未决发送。因此截图中当前有正文时该按钮变灰符合现有规则；但界面没有直接说明禁用原因。

仅凭截图不能认定点击发送会重发旧批次第一条。正常关联人工批次有受理前缀保护；当前人工草稿如果来自另一个批次或已重新编辑，则会按自己的版本和状态处理。需要具体批次及 operation 记录，才能解释截图这一次停止的原因。

## 8. 已确认的缺陷和交互问题

**旧自动尾部可以重复提取并再次人工发送。**

可以从代码构造的链路为：自动批次停止且尾部确切未提交 → 点击“取出未发送内容”保存人工草稿 → 人工发送成功 → 当前输入清空且没有未决操作 → 原自动批次仍满足原来的恢复条件 → 新 mutation ID 可以再次取出同一尾部 → 再次点击发送可造成重复内容。

根因是提取只创建草稿和请求级幂等记录，没有把旧自动批次、原条目与后续人工草稿及发送 operation 建立持续关联。后来的人工 operation 归属新发送，不会消费旧自动批次的恢复资格。它不会自动重发，但交互允许用户重复完成上述操作。

**分条输入的 Ctrl+Enter 提示与实现不一致。**普通单条文本框绑定了快捷键，分条文本框没有对应处理，操作栏却始终显示同一提示。

**历史批次与当前编辑器混排。**进度缺少自动／人工来源、时间、当前／历史归属和逐条状态，无法直接判断当前正文与哪次发送对应。这是截图困惑的重要来源。

**两种尾部动作名字和前置条件不同。**自动批次用“取出未发送内容”，关联人工批次用“只保留未发送内容”；一个要求当前草稿为空，一个要求仍能证明原受理前缀及尾部。界面没有解释差异。

**润色对象和按钮文案可能不一致。**是否显示“润色当前回复”按整体正文判断，但实际只取选中条目；选中空白条目、其他条目有字时，会在点击后才提示先填写。

**附件处理中再次粘贴或拖入会被跳过。**业务补充面板先拦截默认行为，随后因正在处理附件而返回，没有给这一次操作显示排队或拒绝原因。这与聊天消息附件发送是不同问题。

## 9. 建议统一的交互

1. 把当前人工编辑与历史发送记录分开。当前编辑区只显示当前草稿的发送状态；历史批次明确标注自动／人工、时间、已受理／未提交／待核查条目。
2. 自动批次逐条展示“第几条已受理、下一条等待什么、为何停止”。提供原 operation 的核查动作；不要让“停止”看起来等于全部没发。
3. 将转人工处理统一为有来源关联的草稿。保留原批次和条目 ID，后续人工受理消费对应尾部资格；未发送放弃和结果未知分别处理，不能只做按钮隐藏或永久禁止重新取回。
4. 人工多条提供明确的新增、拆分、删除、合并入口，并统一 Ctrl+Enter。已受理条目只读显示，避免允许修改后又因原文不匹配阻塞取尾部。
5. 按钮直接说明原因，例如“当前草稿有内容，请先处理后再取出旧尾部”；明确“润色第 N 条”和“发送剩余 N 条”。

以上是交互调整建议，本次没有据此改动多条发送业务规则、冻结正文、防重或重试次数。
