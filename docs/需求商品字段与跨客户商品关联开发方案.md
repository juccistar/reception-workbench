# 0.3.12 需求商品字段与跨客户商品关联开发方案

方案日期：2026-11-12；实施更新：2026-11-13。基线：已公开的0.3.11。状态：0.3.12运行时代码、界面及提示词已实现；实际打包、公开交付及验证结果以[本版记录](verification/0.3.12.json)为准。首次查询采用正式只读 get-product；当前真实返回没有URL，保留no_link。

读者：项目负责人、开发及验收人员。本文件替代此前《商品来源绑定与供应商复用开发方案》中的0.3.12范围；本版不包含采购、供应商绑定或报价执行。

## 1. 本版范围

本版只完成：

1. 在现有采购需求中正式保存商品ID、产品链接和可用产品图片。
2. 调整现有接待提示词，使AI在同一次需求输出中主动返回产品链接等字段；商品首次可执行受控只读查询，查询状态和结果按商品ID持久保存，后续复用，不能因链接为空而反复查询。不新增独立AI解析或采购任务。
3. 将同一商家下不同客户针对同一商品ID的询盘，关联到同一个商品档案，为以后报价引用商品资料打基础。
4. 产品链接可以进入上下文，但国际站商品页面内容不能直接作为已核实经营事实。
5. 清理需求区及建议栏中的手工表单、内部说明和规则清单。

本版不做：Accio采购工具箱接入、找货、供应商询价、供应商管理/绑定、采购路由、成本核算、报价规则引擎、自动报价发送；也不新增飞书或第三方大模型业务链路。不再把“已有货源/待找货”作为本版界面状态。

## 2. 需求字段

保留现有九项业务字段：产品、数量与单位、关键规格、定制要求、收货地、交期、客户预算、包装与认证、联系方式。短品类和摘要继续独立。

新增商品来源信息，以结构化product_ref保存，不把ID或链接混入产品描述文本：

| 字段 | 本版行为 |
| --- | --- |
| product_id | 从现有询盘/消息依据中取得的平台商品ID，按字符串保存；没有可靠ID时留空。 |
| product_url | 接待AI在本次需求输出中主动返回，可使用现有输入、缓存或首次受控查询的结果；无法取得或不适用时可为空。空值不代表从未查询，不能触发重复查询。 |
| product_images | 关联当前已有、可确认来源的图片资产或消息引用；有则显示，没有则为空。 |
| original_title | 原始商品标题，作为商品识别参考，不当成客户提出的全部规格要求。 |
| sku | 现有来源能取得时可保留，没有则为空；不新增SKU采集、识图推断或补全流程。 |

服务另保存来源平台、来源消息和版本、关联询盘编号，以及内部商品档案编号。这些是后台关联与追溯信息，不增加日常表单。

需求、客户资料和待报价页读取同一份字段。进入待报价及重启后，商品ID、链接和图片关联仍存在，不让业务员重新录入。

## 3. 接待AI在原有任务中一并输出

本版不新增一个“解析商品链接”的AI任务。使用现有接待请求，让AI在输出回复、摘要和需求时同时返回product_ref；首次允许通过受控只读工具取得商品资料，后续按持久查询记录复用，不能由AI看到空链接就自行重复查询。优先由程序控制首查并将结果交给原有主AI任务，不额外增加一轮链接解析模型；具体工具入口能否返回真实链接需先核实。

提示词须明确：

- 主动填写product_id、product_url和可关联的product_images；没有信息时返回空值，不能省略整个约定结构。
- 商品ID、询盘ID和商品标题来自实际消息。用户收到的“This is a inquiry card. Inquiry id is ...; Product id is ...; Product Name is ...; The note of the buyer's inquiry is ...”属于本次实际输入，不能要求它先变成自设JSON卡片。
- product_url使用当前输入、已保存商品信息或本轮首次受控查询中可确定的链接。上下文必须同时告知查询状态、已有结果、缺失原因和是否允许首查；已查过但没有链接时不得重查，不为凑字段编URL。
- 商品标题说明页面如何描述商品，买家留言说明客户实际要求或问题；标题里的Custom Logo不能直接变成客户定制要求。
- 图像字段只能引用服务提供且属于当前商品/需求的图片，不能由模型发明图片URL或跨客户取图。

正常接待和需求生成不增加模型调用次数。专门的正文润色继续保持原意，不因商品字段变化新增需求写入副作用。

服务负责轻量的类型、归属、URL格式、ID与来源一致性校验，以及保存和关联。附属商品字段无效时保留合法回复，相关字段留空或保留尚有效旧值，不为了填字段重跑整轮AI。

现有上下文投影需要同步调整：当前消息中的商品来源链接、实际询盘描述，以及已保存的product_ref不再被旧的通用URL/商品卡过滤规则整体删除；不能只修改提示词却让模型看不到原信息。不为此展开网页全文或整套SKU目录。

## 3.1 首次查询、空结果及不适用分别记录

查询键使用“当前商家+来源平台+商品ID”，不使用客户ID、询盘ID、AI任务编号或链接是否为空作为是否重查的判断。同商品跨客户复用一次查询结果，不同商家仍隔离。首查只针对本轮确有需要关联的商品，不因上下文历史中出现旧询盘卡就逐个查询历史商品。

| 查询状态 | 含义及后续行为 |
| --- | --- |
| not_queried | 尚无查询记录；满足当前首查授权及明确商品ID时可认领一次查询。 |
| querying | 原查询正在执行；后来的任务或客户复用/等待原任务，不另开查询。 |
| completed | 已取得实际结果；使用缓存，链接可能存在也可能缺失。 |
| no_link | 已查询但未取得链接，或当前接口不提供链接；保存原因，不自动重查。 |
| failed | 查询明确失败；保存原错误，本版不因下一轮AI、空字段或重启自动重试。 |
| unknown | 查询中断且是否完成不明确；保留原任务，不能当成未查询重新执行。 |

程序在外部调用前原子保存querying和原任务编号，避免并发的两个客户对同商品各查一次；取得结果后保存实际工具结果及时间。只有确切工具执行/返回记录能推进查询状态，不能仅凭AI说“看过商品”写为完成。

商品查询结果与“该商品是否符合当前客户需求”分开：

- 商品档案保存客观取得的商品ID、链接、参考标题、来源及查询结果，即使当前客户不适用也不能丢弃查询记录。
- 当前客户的关联另外记录未判断、符合、不符合或待澄清及依据；不符合时可不采用到当前需求，但保存已查看的商品身份和不采用原因。
- 例如A客户询盘指向P，但实际需要另一款，保留P已查记录和A的不适用判断；B客户确实咨询P时可以复用P的资料，不能把A的不适用判断变成所有客户都不能使用P。
- 暂未判断是否符合不触发反复读同一商品，后续结合新留言或业务补充和已有结果判断。

切换客户、重复询盘、新AI任务、补充修改、需求链接为空及程序重启均不重置查询记录。只有出现新的商品ID，或用户明确执行重新查询，才产生新的查询机会；重新查询保留原记录。消息直接提供了新链接时，可按来源校验更新字段，无须再查一次商品。

工具调用权限必须由实际执行边界控制，不能只依赖提示词“只查一次”。优先使用程序可控制的正式只读商品入口；若希望在Accio同一次任务内由AI调用，则必须先验证宿主能限制确切商品ID、工具和次数。现有纯生成入口不能仅改提示词就放开任意工具。若工具不提供链接，应保存no_link，不能自动轮换工具或搜索方式反复尝试。

本版验收的一次指持久关联的一次受控查询任务；Accio内部是否物理重试应以可核实执行记录说明，不凭提示词宣称只有一次底层调用。首次查询可能有工具耗时，已有结果的后续接待不重复支付该查询耗时；不承诺首次查询与纯文字同速。

## 4. 同商品ID关联的是不同客户的询盘

用户要求的场景是：客户A和客户B分别询问同一商品ID，系统知道两份询盘指向同一款商品，以便以后报价使用。

采用两层数据：

- 每个客户自己的需求记录：保留其数量、规格、定制、收货地、预算、聊天和业务补充。
- 当前商家的商品档案：保存平台商品ID、可用链接、参考标题和适宜复用的商品基础资料。

两份需求引用同一个内部商品档案，但不合并两位客户的需求。例如A询问100件、B询问500件，两人的数量、收货地、价格沟通和后续报价均独立。

匹配键默认使用“当前商家+来源平台+商品ID”：

1. 首个客户提供某商品ID时，建立或关联本地商品档案。
2. 其他客户询盘出现相同ID时，自动关联已有档案。
3. 重新打开工作台后，关联仍保留。
4. 不同商品ID、仅同名/同品类/相似图片，不自动合并。
5. 没有可靠ID时保留未关联，不强行认定同款。
6. 不同商家数据继续隔离。

本版不扩展跨ID同款识别、供应商匹配或共享价格。商品公共资料可复用，客户留言、业务补充、预算及客户私发定制图不能因商品ID相同自动混入另一个客户的上下文。

## 5. 链接进入上下文的可信度

产品链接和商品ID用于定位商品、关联询盘，并为以后报价提供商品引用。它们不证明商品页面描述真实。

固定提示词应明确：国际站商品页面可能批量上货，页面标题、详情、规格、材质、标价、库存、交期、认证和可定制能力只作页面参考，未经独立核实不能直接成为已确认条件或对客承诺。

- 商品链接及ID：证明当前消息指向哪个平台商品。
- 页面标题和详情：提供识别参考，不能证明实际供货能力。
- 买家实际留言：可以说明客户要求，不能证明本店能满足。
- 当前业务补充及适用的已核实资料：按各自范围支持商家条件，不能由页面内容冒充。

同商品档案命中也不意味着沿用另一个客户的报价或承诺。本版不进行报价计算。聊天第三方翻译仍不加载业务补充和商品档案。

## 6. 图片及SKU边界

产品图片只关联现有可用来源和安全本地资产，不把取图作为需求保存或待报价的前置。现有受控预览可继续使用，不增加“必须取齐商品主图/SKU图”的目标。

没有图片或SKU时正常保存需求并继续聊天。设置封面、预览准备好不表示模型已读；相关产品来源图片继续遵守当前任务的来源、角色及确切读取证据要求。普通润色不自动读取历史图片。

图片缓存或缩略图加载完成不改变商品身份，也不取消仍有效的文字生成。

## 7. 界面清理

客户页右侧仅保留摘要、客户需求，下方业务补充。客户需求中的产品内容可显示商品ID、链接、可用图片，不新增商品/供应商管理面板，也不要求操作同ID关联表单。

从客户页、待报价及客户资料的日常需求展示中移除：

- “整理与复核需求”整块表单。
- 展示品类手动保存、逐字段确认/待确认/驳回/编辑。
- 新建事项、候选应用和纠正归属等折叠表单。
- 内部规则、应用版本及其他已明确不要的堆叠说明。

这次移除渲染入口，不是再次折叠隐藏；原始历史记录保留。字段提取confirmed仍不冒充业务员人工复核。

建议预览只保留客户可读正文、中文译文、采用操作及必要的简短过期/失败提示。内部协助段落、质量分析长文和“本次应用的资料与规则”名单进入运行记录，规则及检查继续执行。发送失败、unknown和原操作核查入口仍保持可用。

## 8. 数据、性能及兼容

沿现有本地Repository增加商品档案与需求引用，优先兼容现有实体存储，不为本版迁移数据根或重写消息历史。

旧记录没有新字段时显示为空，后续正常已授权AI任务可补齐；不批量重跑历史AI、不补发旧回复，也不新增大规模历史消息解析任务。已有媒体和来源记录继续保留，不把猜测结果批量提升为商品关联。商品查询状态、空结果、失败及中断记录持久保存并纳入备份，重启不恢复成未查询，也不能因需求未采用查询结果而删除查询历史。

保持默认2秒检测、1秒合并、50条文字及窗口外必要来源；新增字段与关联不恢复暂停的接待权限。客户正文、任务及发送回执保持独立，整会话prepared/sending/unknown保护和原操作核查不变。新增档案和引用纳入完整备份。

## 9. 实施顺序

1. 修改共享DTO、AI输出契约及提示词，接通product_ref的输出、校验和保存。
2. 调整上下文过滤，保留相关链接和询盘描述，同时加入页面不作核实依据的明确规则。
3. 建立当前商家的商品档案、首次受控查询及持久去重、同ID跨客户关联和重开持久化；查询结果与各客户适用性分开，不合并客户需求。
4. 在客户页、客户资料和待报价页展示一致的新字段，清理需求及建议栏。
5. 按改动范围定向回归、类型检查、构建和实际Electron窗口验收，交付按后续明确指令执行。

主要入口：shared/api.ts及必要的preload/main/Python契约；integrations/analysis.py和生成元数据处理；service.py、procurement.py及商品档案关联模块；reception_context.py/model_payload.py；提示词审核稿和静态提示词生成；SharedRequirementCard、RequirementFacts、RequirementActions、Reception及待报价/资料页面。

## 10. 验收标准

1. 同一次正常AI任务明确输出商品ID、product_url及图片关联结构，不新增独立解析调用。
2. 你提供的实际询盘文本能在需求结果中保留正确商品ID；没有URL或SKU时不编造、不阻断正常回复。
3. 商品字段进入待报价、切换客户和重开后仍存在。
4. 两个不同客户咨询同商品ID时关联同一商品档案，各自数量、规格、业务补充和消息不被合并或串用。
5. 不同ID、不同平台或不同商家不会因同名/相似图片错误关联。
6. 产品链接和实际询盘描述进入相关上下文；页面标价、属性等没有被当成已核实事实。
7. 客户页不再出现手动需求复核表单，建议栏不显示内部协助长文及规则版本列表。
8. 未保存正文、过期建议、窄窗、发送失败和unknown核查保持正常。
9. 同商品查询过后，链接仍为空、换客户、补充变化、新AI任务或重启都不自动重查；并发首次请求只有一个实际查询任务。
10. 已查无链接、查询失败/中断和客户不适用分别留证；A客户不适用不会阻止B客户复用同商品客观资料，且不触发第二次查询。
11. 新商品ID或明确重新查询才产生新的查询机会；只看到上下文中的历史询盘不查询无关商品。
12. 仅运行改动范围定向测试，截图实际查看；只有用户明确要求才执行全量测试。

该方案只定义本版需要实现的需求字段、跨客户商品关联和界面清理，不以字段预留宣称采购或报价能力已经完成。
