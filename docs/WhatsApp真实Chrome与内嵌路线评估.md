# WhatsApp真实Chrome与当前内嵌路线评估

日期：2026-11-14。面向项目负责人、开发与验收人员。

状态：源码与本机安装环境的静态评估，未启动真实Chrome测试，未登录账号、收发消息或修改程序。评估后用户已选择0.3.18继续当前内嵌路线；本文保留为比较记录，Chrome试验与迁移步骤不纳入本版实施。当前交付范围以[0.3.18开发方案](0.3.18快速开发方案.md)为准，环境核对参考[浏览器兼容候选方案](WhatsApp浏览器环境与自动化兼容候选方案.md)。

## 1. 结论

当前路线更适合工作台内的一体化原始界面和0.3.18快速修复；真实Chrome路线更贴近whatsapp-web.js的标准浏览器启动流程，预计可减少自定义适配维护，但会引入独立窗口、浏览器版本和生命周期管理。

两条路线均通过非官方SDK操作WhatsApp Web。没有账号风险对照数据，不能认定真实Chrome就更不容易封号，也不能把原始界面或真实Chrome等同于官方授权接入。

建议0.3.18先修复已证实的请求头、执行线程和界面问题；若接受独立Chrome窗口，再单独验证真实Chrome适配器，保留现有业务契约和数据。

## 2. 现有实现与版本事实

当前路线：Electron的WebContentsView承载WhatsApp原始页面，Puppeteer通过自定义ViewTransport访问同一内容，WhatsAppHost手动执行SDK初始化的部分步骤。视图登录态由Electron persist partition管理，未使用LocalAuth。

真实Chrome候选：由程序启动独立、可见的Chrome，whatsapp-web.js通过Puppeteer标准接口使用其页面；登录态使用专用Chrome profile，可评估SDK LocalAuth，避免与另一套userDataDir管理重复。

本机只读核对：

| 项目 | 当前事实 |
| --- | --- |
| 当前应用 | 0.3.17 |
| Electron | 45.2.3，实际Chromium 156.0.8078.80 |
| 标准路径发现的Chrome | 用户级安装，152.0.7977.65 |
| Puppeteer | 项目锁定24.38.0；本地revisions元数据所列Chrome为146.0.7680.31 |
| whatsapp-web.js | 1.34.8 |

因此，切换本机Chrome不等于升级浏览器内核。不同浏览器/Puppeteer组合需要测试，不能仅凭“Chrome已安装”判断兼容。

## 3. 主要差异

| 维度 | 当前Electron内嵌 | 真实Chrome独立运行 |
| --- | --- | --- |
| 聊天界面 | 工作台中直接显示原始WhatsApp Web | 独立Chrome窗口显示同一原始网页，工作台模块负责控制与定位窗口 |
| 导航体验 | 切模块隐藏视图，后台继续 | 点击模块打开/定位专用窗口，需定义最小化和关闭行为 |
| 浏览器运行环境 | Electron自带Chromium及Electron API环境 | Chrome提供浏览器环境，但仍由自动化和SDK控制 |
| SDK初始化 | 自定义CDP传输，并维护初始化适配 | 更多沿用SDK标准launch/initialize流程，仍需明确启动、标识及认证配置 |
| 登录持久化 | Electron partition | 专用Chrome profile；可采用LocalAuth，但不能同时另配冲突目录 |
| 浏览器升级 | 随工作台/Electron版本更新，便于控制 | 系统Chrome可能独立升级；随包浏览器可控但需要单独更新分发 |
| 资源占用 | 复用Electron浏览器与GPU基础进程 | 工作台之外增加Chrome进程组，通常会增加资源占用；未做本机压测 |
| 打包安装 | 已有Electron及SDK归档，无额外Chrome二进制 | 使用系统Chrome时包体变化较小；随包提供Chrome会增加分发体积 |
| 故障边界 | WhatsApp视图单独渲染，但与工作台共享部分浏览器基础设施 | 浏览器进程组更独立，同时要处理用户关闭窗口、崩溃和遗留进程 |
| 兼容维护 | Electron、CDP适配、SDK及网站四方变化 | 主要维护Chrome、Puppeteer、SDK及网站组合，自定义适配预计减少 |
| 账号限制风险 | 非官方接入，无零风险保证 | 同样非官方，无证据证明仅换浏览器就降低账号限制风险 |

将独立Chrome窗口强行嵌入Electron不是现有WebContentsView的直接替换，需处理窗口句柄、焦点、DPI、尺寸、遮挡及退出顺序，不建议作为快速版本实施目标。

## 4. 可复用与需要调整的代码

### 可保留的核心

- Python WhatsApp独立消息、摘要、绑定、草稿和operation数据。
- 全部入站单聊范围、可选国际站只读背景、AI队列和人工接管语义。
- 宿主冻结发送意图的持久账本、确切消息编号及ACK核查。
- 协调层的账号/连接代次、未决发送保护、重启撤权和unknown原操作核查。

### Chrome路线需要调整

- 新建Chrome传输宿主，替换当前视图创建与ViewTransport。
- 将setVisible/bounds一类嵌入控制改为专用窗口的显示、定位及生命周期管理。
- 管理Chrome可执行文件、版本兼容、独立profile占用和进程所有权。
- 定义Chrome关闭、工作台退出、SDK失联及异常终止时的撤权、落账和恢复。
- 继续核对程序回显、手机/原生人工接管及未决操作，不因浏览器更换简化业务检查。

## 5. 两个容易忽略的维护点

1. 当前ViewTransport向Puppeteer提供的是虚拟Browser/Target，其中Browser.getVersion返回固定Chrome/140，而实际页面运行于Chromium 156。这是内部CDP版本信息差异，不等于发给WhatsApp的HTTP User-Agent；后续应校正，真实Chrome标准CDP可以减少这类自定义维护。
2. 当前SDK默认User-Agent仍是固定的Mac/Chrome 101字符串。当前宿主明确关闭了该默认覆盖；真实Chrome路线也必须保留真实客户端标识，不能简单采用SDK全部默认配置并声称它反映实际Windows/Chrome环境。

## 6. 推荐的Chrome试验方式

程序启动专用、可见Chrome；优先通过程序私有连接控制，避免开放全应用调试端口或连接用户日常浏览器。专用profile不与个人资料或其他商家共用，同一profile保持一个写入者。

使用本机Chrome便于开展初步兼容试验，但正式交付需要选择并验证稳定的Chrome/Puppeteer组合。若选择随包浏览器，须增加来源、版本、完整性、分发体积及安全更新维护。

进程退出前先撤权、等待/保留在途结果并落账，再关闭程序拥有的浏览器。用户提前关闭Chrome时，新发送停止；提交结果不明的操作保持unknown。不能因发现Chrome未响应就启动第二个会话重发。

## 7. 切换与验收

切换前暂停旧通道并正常关闭；新Chrome使用新profile重新扫码，不直接复制Cookie。保留同商家业务记录和宿主提交账本，不重建或清空未决operation。

账号身份核对后，先核查原未决操作，再由用户明确开启接待。同一账号不同时运行两套自动接待。Chrome切换不会修复Python执行循环的保活问题，0.3.18后台修复仍需完成。

最小验证顺序：

1. 专用浏览器可启动、版本可识别、普通网页与WhatsApp公共登录页正常。
2. SDK与可见页面共用同一登录会话，重开保留资料，不出现第二页面假共享。
3. 在明确授权的自有账号/联系人范围验证收发、手机人工接管、重连撤权和确切回执。
4. 人工关闭Chrome、浏览器异常及工作台退出时，无第二消费者、无重复提交，unknown可沿原记录核查。
5. 测量首次启动、常驻内存与CPU，再给出资源结论。

本评估没有以上真实Chrome试验结果，不将预计维护收益写成已验证稳定性或账号安全优势。
