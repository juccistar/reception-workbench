# 本地消息与运行结构

面向维护人员，描述当前源码 0.3.3 的数据和运行规则。发行及新目录验证正在进行，见[本版说明](0.3.3发布说明.md)。业务数据的位置以当前商家 profile 和设置页为准；本次整理不复制或迁移业务数据。

## 数据目录

按已核验商家选择独立profile：默认registry为`%LOCALAPPDATA%\AlibabaReceptionWorkbenchHost\merchants.json`，state保存在`profiles/<SHA256 seller>/state`。0.2.21新商家的默认业务根改为registry同级`ARWData/<registry规范路径SHA256前16位>/<sellerId>`，避免两次嵌套seller哈希形成过长SQLite日志路径；旧版已登记根、自定义目录与迁移后的根继续以profile的`state/storage.json`为准，不自动搬移。实际位置以设置页显示为准，支持自定义本机目录、完整迁移、备份和恢复。安全备份使用registry同级`ARWBackups/<相同namespace>`；无商家registry的演示环境按state路径生成独立namespace。

旧全局 `%LOCALAPPDATA%\AlibabaReceptionWorkbenchHost\storage.json` 保留作为旧版配置；仅有唯一匹配当前seller的正面证据时才收编旧根，保留原路径及lastBackup、previousRoot等记录。身份未知、多重匹配或已保存根缺失时拒绝，不静默创建空库。正常管理操作使用Windows命名互斥量，重启不恢复自动权限。

新live首次建立空账本与空回执目录，未发送也可备份重开；已有账本丢失时底层Ledger.get拒绝重建，不能把无主或缺失历史当作空。

业务目录内：

- `demo/workspace.sqlite3`：虚构客户、消息与演示草稿。
- `demo/control.sqlite3`：演示设置。
- `demo/integrations-demo.sqlite3`：存在时保存演示适配器的幂等、操作与重试记录，完整备份不能遗漏。
- `.reception-workspace.lock`、`.reception-clean-shutdown`：0.2.12起使用的独占锁与正常退出证据；不是Accio授权。0.2.11及更早版本不遵守此协议。
- `.receipt-roots.json`：备份生成并随恢复保留的回执来源目录元数据，用于验证历史绝对回执引用；不是凭据，不自动修复或确认未知发送。
- `live/control.sqlite3`：当前真实模式的本地设置；不保存 Accio 凭据。
- `live/sellers/<商家ID哈希>/workspace.sqlite3`：核验身份后才打开的卖家业务库。
- `live/adapters-live.sqlite3`：当前原生适配器操作账本。
- `live/workctl-state`：应用私有的原生CLI状态；其中发送回执参与结果核查，不是可随意删除的缓存。
- `host/live/default/layout.json`：真实模式的导航、列表和需求侧栏尺寸。同一数据根的真实模式共享单实例锁，改变预期商家编号不会再打开第二个真实写入窗口。
- `host/demo/<预期商家或default>/layout.json`：演示布局。

原生适配器另有持久化操作账本，用于发送与飞书未知结果防重。业务库、控制库、原生操作账本、核查所需回执及SQLite的有效WAL必须作为一个恢复集合处理。正常退出后完整复制数据根的既有说明仍适用；不要在运行中只复制单个sqlite文件。`backup-ai-verification.py`只备份两库用于验收，不含原生账本，不能作为完整灾难恢复副本。普通备份或诊断不采集Accio账号凭据，恢复授权沿用宿主重新授权流程。离线工具只收录明确白名单。不能先运行新程序改旧库再补备份；旧版导出须独立核实应用、后台及原生任务已停止。

## SQLite 记录

旧0.2.11业务schema版本为1；0.2.12先预检后事务升级到2，原生/演示账本的已知旧结构升级到1。新增阅读信息使用JSON实体，表结构不变。未知格式和未来版本拒绝；不能用旧发行版直接打开新语义工作区。使用WAL和FULL同步。`entities(kind,id,data)` 逐条保存业务对象，`revisions` 保存历史版本；不是把所有聊天拼成一个文件。消息、需求、草稿、任务、确认、操作、政策、登记和 outbox 使用不同 kind，标识与约束由业务层负责。账号库保存卖家绑定，不接受不同卖家复用。

消息每条记录包含消息编号、卖家、买家、会话、角色、原文、平台时间和附件元信息。数据库为会话和事项建立索引，读取一个客户时先在 SQLite 按归属筛选，再解码消息；不需要把其他客户所有聊天加载到 Python 后再过滤。

需求事实包含原文来源 ID、状态与版本；草稿保存其消息、需求和资料依据版本。草稿不会出现在原始聊天中。平台已确认受理的消息进入真实历史；合成受理只进入隔离的演示历史。0.2.10核查恢复使用确切平台消息编号和实际时间，不用核查时刻改写旧回复顺序。

## 一轮接待

消息监测独立于AI/发送worker，默认每5秒读取轻量摘要。按客户活动变化读取正文，活动进度与正文水位分别保存；新活动优先，正文排队/在读最多4个。确认空历史等待新活动，历史及维护补读共享全账号每60秒一个额度。

同步先持久化消息，更新会话修订和历史覆盖。构造上下文时取最近20条、当前需求、相关旧原文及适用的已确认公开资料；保留上下文大小预算，超限明确显示待处理原因，不把静默截断当作完整依据，也不据此冒称业务员已接管。

AI生成自然正文和有出处的事实。0.2.22将商业承诺和正文数字依据问题保留为质量提醒，不转人工停接待；逐项核验采购事实，非法字段不确认，冲突保留双方依据。需要核实或模型请求人工帮助时创建协助任务，不设置human_owned。停止联系、身份及当前正文/来源版本仍检查。草稿和任务先落本地；飞书通过outbox后续处理，本地接待不依赖飞书可用。

支持selected、all、incoming范围；0.2.22不限AI及自动发送次数，持续保存调用与发送统计。budget中的limit/remaining/ai_remaining为null并标记unlimited；旧数字scope参数仅兼容，不再据此拒绝任务。授权起点、范围和暂停语义仍由服务端检查；暂停不清零统计，配置变更撤权，重启不恢复权限。缺少可靠平台时间仍不能猜造发送依据。已有积压不是重新伪造的新入站，应按明确处理路径执行。

待我报价按采购事项列队。同一客户的新实质采购消息可继续分析并建立新事项，旧待报价事项仍保留；无需回复的致谢不制造循环。合成AI检测使用独立构造的会话与消息，不读取真实客户、知识或草稿。

保存草稿采用期望版本和操作幂等编号。保存期间新增输入保留，下一次以新服务端版本保存。迟到AI作为建议展示；采用建议也是一次新编辑，保存成功后才显示已保存。

自动发送绑定客户、正文、草稿版本和当前来源，提交前重新检查权限与版本；语义质量提醒单独保存。整会话prepared/sending/unknown阻止新发送；核查读取原操作证据，不重新提交。重启不会将未知结果变成可以重发的失败。

0.2.22的协助任务、核实结果、跟进状态及生成重试时间使用同一业务库的JSON实体保存，随完整备份与修订保留。协助回填使用expected_revision和client_mutation_id防止覆盖及重复入队；仅明确result_public的结果进入对客上下文。保存结果不等于已回复，实际跟进仍按当前授权执行；内部结果不能自动对客发送。生成重试到期由后台调度，不在串行worker中sleep，重启只保留任务记录、不恢复自动授权。

## 0.3.1建议、翻译与重试

会话补充和最新成功的主动建议按当前卖家及会话隔离；补充CAS保存，只用于主动建议，不写客户事实或自动接待上下文。主动生成可在暂停、人工接管、卖家最后发言或无事项时运行，身份和AI能力仍须正常。生成不改正文或接管，采用不经确认完整覆盖会话编辑框并接管；固定发送快照与继续编辑的正文独立。

事实value与evidence_ids保留来源，display_value仅供展示；旧事项按当前来源hash按需缓存译文，缺失则回退原值。聊天译文按卖家、会话、消息、原文版本、目标语言及提示词版本隔离，只读、不进入事实或发送队列、不接管；失败保留原文并可重试。真实模式翻译须AI检查通过；辅助翻译调用为主业务让位并在关闭时收尾，真实Native能力仍需独立验证。

自动发送总使用量不限；每个商家、会话、来源消息、阶段的失败链最多三次自动尝试（首次加两次，协助阶段还区分结果版本）。仅明确暂时性且未提交时等待5秒、15秒重试；确定性或未分类拒绝停止本条，新job、草稿或重启不重置计数。可能已提交及unknown只核查原操作。相关操作和任务证据随业务库与原生账本保全，不能通过删账本或恢复旧备份重置。

## 普通人工聊天

0.2.0起，客户页始终保留独立人工输入与发送，不要求开启单独人工模式，不依赖AI检查、采购条件、商业资料出处或“最后一条必须是买家”。历史兼容API中的 `manual_only` 不应重新成为普通人工聊天的页面前置条件。

人工正文按会话保存，使用 `client_request_id` 防重，提交确切正文版本。首次人工编辑只暂停本会话自动处理，其他客户不受影响；恢复该客户自动接待需要明确操作。人工发送保留身份/客户归属、平台正文格式、版本、退出撤权、请求幂等和整会话unknown保护，不套自动回复的资料或采购检查，不消耗自动额度。已发送人工消息进入实际历史及后续AI上下文。详情见 [人工接待使用](人工接待使用.md)。

## 进程通信与关闭

Electron负责窗口、受限IPC、文件选择及系统确认。renderer没有Node、SQLite、任意shell或令牌访问接口。Python作为一个自有子进程，通过UTF-8 JSON-lines读写业务请求和事件，不开放本地HTTP端口。

外部业务操作由单一worker串行执行，消息监测独立运行，本地查询、保存和暂停独立处理。暂停请求不被尚未返回的开启请求去重；确认中的旧开启请求也会被后来的暂停作废。

正常退出先保护未保存编辑，然后撤销新发送权限并等候外部调用结果落库。强制退出后的未决操作保留unknown，后续核查原操作。后台意外退出会禁发并保留窗口中的编辑；当前尚无完整的同窗口后台重启与编辑恢复流程，不能把“正文暂时留在窗口”描述为跨重启恢复已经验收。

## 验证与发行

真实AI、发送和飞书分别按明确授权验证，不以演示或历史回执推断当前线上状态。发行及新目录验证正在进行，见[本版说明](0.3.3发布说明.md)。原始 Ready 的 14 字符正文具体内容未知，真实 Accio 两轮发送尚未执行。
