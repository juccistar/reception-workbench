# 本地消息与运行结构

面向维护人员，描述0.3.14的本地需求、摘要、采购及媒体存储；交付验证和附件限制见[发布说明](0.3.14发布说明.md)及[记录](verification/0.3.14.json)。业务根以当前商家profile和设置页为准，源码修改不迁移真实数据；合成回归不代表真实平台、供应商发送或长期运行验收。

0.3.9 的内置目录是随程序打包的只读 JSON 资源，不在启动时写入商家库。明确采用后仍使用现有 policy 实体保存正文、用途、启用状态和来源版本，随完整业务备份保全，按商家隔离。内部备注不进入模型；旧非公开资料保持仅人工查看。协助开始时间、应用资料版本及固定读取诊断使用现有实体保存，不改变 Repository schema v2 或 Ledger v1。

0.3.14以supplement_attachment实体保存会话级商家补充附件及原件、提取文字、哈希和受限缩略图，随完整业务库备份；正文仍只保留最新版本。新增/移除更新补充版本，附件不进入共享产品或跨客户资料，原件与预览不进入模型JSON；模型文字取实际提取内容，图片通过同任务读取并验证证据。删除指从当前补充中移除，不伪称已物理清除所有历史运行证据。格式、页数及字数限制见[本版说明](0.3.14发布说明.md)。

## 数据目录

按已核验商家选择独立profile：默认registry为`%LOCALAPPDATA%\AlibabaReceptionWorkbenchHost\merchants.json`，state保存在`profiles/<SHA256 seller>/state`。0.2.21新商家的默认业务根改为registry同级`ARWData/<registry规范路径SHA256前16位>/<sellerId>`，避免两次嵌套seller哈希形成过长SQLite日志路径；旧版已登记根、自定义目录与迁移后的根继续以profile的`state/storage.json`为准，不自动搬移。实际位置以设置页显示为准，支持自定义本机目录、完整迁移、备份和恢复。安全备份使用registry同级`ARWBackups/<相同namespace>`；无商家registry的演示环境按state路径生成独立namespace。

旧全局 `%LOCALAPPDATA%\AlibabaReceptionWorkbenchHost\storage.json` 保留作为旧版配置；仅有唯一匹配当前seller的正面证据时才收编旧根，保留原路径及lastBackup、previousRoot等记录。身份未知、多重匹配或已保存根缺失时拒绝，不静默创建空库。正常管理操作使用Windows命名互斥量，重启不恢复自动权限。

新live首次建立空账本与空回执目录，未发送也可备份重开；已有账本丢失时底层Ledger.get拒绝重建，不能把无主或缺失历史当作空。

业务目录内：

- `demo/workspace.sqlite3`：虚构客户、消息与演示草稿。
- `demo/control.sqlite3`：演示设置。
- `demo/integrations-demo.sqlite3`：存在时保存演示适配器的幂等、操作与重试记录，完整备份不能遗漏。
- `.reception-workspace.lock`、`.reception-clean-shutdown`：0.2.12起使用的独占锁与正常退出证据；不是Accio授权。0.2.11及更早版本不遵守此协议。
- `.receipt-roots.json`：备份生成并随恢复保留的回执来源目录元数据，用于验证历史绝对回执引用；不是凭据，不自动修复或确认未知发送。
- `live/control.sqlite3`：当前真实模式的本地设置；不保存 Accio 凭据。
- `live/sellers/<商家ID哈希>/workspace.sqlite3`：核验身份后才打开的卖家业务库。
- `live/adapters-live.sqlite3`：当前原生适配器操作账本。
- `live/workctl-state`：应用私有的原生CLI状态；其中发送回执参与结果核查，不是可随意删除的缓存。
- `host/live/default/layout.json`：真实模式的导航、列表和需求侧栏尺寸。同一数据根的真实模式共享单实例锁，改变预期商家编号不会再打开第二个真实写入窗口。
- `host/demo/<预期商家或default>/layout.json`：演示布局。

原生适配器另有持久化操作账本，用于发送与飞书未知结果防重。业务库、控制库、原生操作账本、核查所需回执及SQLite的有效WAL必须作为一个恢复集合处理。正常退出后完整复制数据根的既有说明仍适用；不要在运行中只复制单个sqlite文件。`backup-ai-verification.py`只备份两库用于验收，不含原生账本，不能作为完整灾难恢复副本。普通备份或诊断不采集Accio账号凭据，恢复授权沿用宿主重新授权流程。离线工具只收录明确白名单。不能先运行新程序改旧库再补备份；旧版导出须独立核实应用、后台及原生任务已停止。

## SQLite 记录

旧0.2.11业务schema版本为1；0.2.12先预检后事务升级到2，原生/演示账本的已知旧结构升级到1。新增阅读信息使用JSON实体，表结构不变。未知格式和未来版本拒绝；不能用旧发行版直接打开新语义工作区。使用WAL和FULL同步。`entities(kind,id,data)` 逐条保存业务对象，`revisions` 保存历史版本；不是把所有聊天拼成一个文件。消息、需求、草稿、任务、确认、操作、政策、登记和 outbox 使用不同 kind，标识与约束由业务层负责。账号库保存卖家绑定，不接受不同卖家复用。

消息每条记录包含消息编号、卖家、买家、会话、角色、原文、平台时间和附件元信息。数据库为会话和事项建立索引，读取一个客户时先在 SQLite 按归属筛选，再解码消息；不需要把其他客户所有聊天加载到 Python 后再过滤。

需求以Case.requirements及ai-v1格式保存13项需求、原文来源及版本：业务正文由AI整理，数字ID的product_url由程序派生，无display_value或字段提醒状态；conversation_summary按商家和conversation_id独立保存，不依赖case。草稿保存消息、需求、资料及所选供货方案依据版本，不出现在原始聊天中。只有平台受理消息进入真实历史，合成受理仅在隔离Demo；核查使用确切消息编号和原平台时间，不用核查时刻改写聊天顺序。

0.3.11需求媒体使用卖家业务库的JSON实体：`requirement_media`保存事项封面和按消息版本绑定的产品来源选择，`requirement_media_cache`保存商品/SKU展示图状态与图片资产关联，`requirement_media_mutation`和`requirement_media_request`保存幂等记录；已有`message_image`复用聊天图片关联，`image_asset`保存原图和安全预览。消息原文及附件保持原样，产品事实的`value`仍为文字。展示revision是本地投影的52位摘要整数，并非事项业务revision或递增计数；封面和展示缓存变化不改变业务生成指纹，来源选择变化则使相关未提交生成失效。

0.3.13停用假定商品卡、历史链接及SKU字段业务解析；真实消息/图片协议、受控下载和缓存保留。需求图片是AI选择的get_requirement_media确切media_id，仅当前本地安全预览可展示。独立product_main_image用于商品展示和采购找货，后台通过独立媒体池读取并安全本地缓存，不占AI槽；采购可等待图片终态后使用图或文字找货。它不进入接待photo_context、manifest或语义指纹，不替代客户product_images。正式list-information读取使用productId整数、queryType=trunk、componentList=[images]；data为JSON字符串，图片来自basicInfo.images的imageIndex和originalImageUrl。响应无商品ID及主图标记，按确切请求绑定并选最小imageIndex作展示参考，不能称平台已证主图或SKU图；样本1601902417143在售状态未知，见[只读报告](../artifacts/verification/reception-0.3.13/product-image-component-accio.json)。跨商家不复用业务缓存，迟到结果复核owner、来源版本、服务世代及任务。界面不传任意URL或路径，快照不联网；全量SKU来源和图搜尚未验收。媒体及原图随业务库和有效WAL完整备份。

产品及采购使用library_product、supplier、supplier_offer、requirement_product_binding、procurement_task、library_mutation。产品键为商家+平台+AI产品ID，首次任务与产品原子建立，稍后调度；队列满不丢合法AI需求。产品复用公共资料，不共享客户数量、预算、地址、聊天、补充和私图；供货方案修订历史保留，当前需求选择独立于产品默认。选择、offer与product版本进入上下文指纹。

采购真实调用前将确定会话名、agent、完整请求及UTF-8 SHA256持久在任务私有execution中，UI只收到受限任务投影。该记录不含客户完整聊天、地址、联系方式或凭据；原请求用于唯一会话恢复。失败/unknown、新客户或重启不重新搜索，只核查原请求；采购grant只在内存，重启false。数字商品ID的链接由程序生成 `https://www.alibaba.com/product-detail/_<ID>.html`，不由模型查询或填写；`定制-数字`是稳定复用的本地编号，偶然碰撞原子换号，不生成平台链接或读取平台图片。链接及商品展示图不进入接待指定上下文或语义指纹，原聊天和冻结润色正文中的链接保持原样。供应商候选链接不能回填原商品；页面参考价不是供应商确认报价。询价与报价回收尚未验收，任务明确blocked。

## 一轮接待

消息监测独立于AI/发送worker，新建配置默认每2秒读取轻量摘要，已有明确配置保留。按客户活动变化读取正文，活动进度与正文水位分别保存；新活动优先，正文排队/在读最多4个。确认空历史等待新活动，历史及维护补读共享全账号每60秒一个额度。

同步先持久化消息，更新会话修订和历史覆盖。构造上下文时取最近50条文字、当前需求、相关旧原文及适用资料；窗口外必要依据按消息去重。程序派生的商品链接和独立商品展示图不进入接待指定上下文或语义指纹；原始聊天和冻结润色正文中的链接不改写。原始商品卡JSON、整套SKU和商品展示图不旁路进入模型，仅当前事项允许的聊天产品来源图可进入相关读图请求。保留上下文大小预算，超限明确显示待处理原因，不把静默截断当作完整依据，也不据此冒称业务员已接管。

AI同轮生成自然回复、中文需求及独立会话摘要；缺依据的字段留空。旧quality/待核实/协助提醒不再生成、投影或搬入运行记录，需核实内容自然写入摘要。业务判断不等于人工核实，也不升级为自动接管。身份、授权、当前正文及来源版本仍检查；草稿和任务先落本地，飞书经outbox后续处理。润色只改冻结回复，不写需求或摘要。

支持selected、all、incoming范围；0.2.22不限AI及自动发送次数，持续保存调用与发送统计。budget中的limit/remaining/ai_remaining为null并标记unlimited；旧数字scope参数仅兼容，不再据此拒绝任务。授权起点、范围和暂停语义仍由服务端检查；暂停不清零统计，配置变更撤权，重启不恢复权限。缺少可靠平台时间仍不能猜造发送依据。已有积压不是重新伪造的新入站，应按明确处理路径执行。

待我报价按采购事项列队。同一客户的新实质采购消息可继续分析并建立新事项，旧待报价事项仍保留；无需回复的致谢不制造循环。合成AI检测使用独立构造的会话与消息，不读取真实客户、知识或草稿。

保存草稿采用期望版本和操作幂等编号。保存期间新增输入保留，下一次以新服务端版本保存。迟到AI作为建议展示；采用建议也是一次新编辑，保存成功后才显示已保存。

自动发送绑定客户、正文、草稿及当前来源，提交前检查权限与版本，不保存独立语义质量提醒。现行[发送通道简化](自动发送通道简化.md)移除正常自动发送的Ready/Seal及发送前历史重读，常规业务检查全部保留。新适配器请求以purpose=reception区分直接提交，沿用原来源防重键；提交前落unknown提交记录，返回消息编号即保存，随后有限读取确认。整会话prepared/sending/unknown阻止新发送；旧快照操作继续核查原回执，不重新提交。重启不会将未知结果变成可以重发的失败。

旧提醒专用business_progress、assistance_task及其mutation、requirement_proposal在离线完整备份验证后白名单清理，包含对应revisions；同时移除指定case/draft/job字段及独立商品标题。原始消息、图片、job/draft、operation/outbox、intent、原生账本和回执不删；continuity_plan、supplement_followup中的稳定问题/来源ID、结果版本及原操作关联全部保留，用于业务补充续答和三次退避防重。新任务不依赖旧提醒实体。生成重试由到期调度，不在业务worker中sleep，重启不恢复授权。

maintenance prepare仅在正常关闭且数据库checkpoint可核验时处理内容清理：先制作并验证完整工作区备份，再重新独占并逐文件核对源hash，清理后checkpoint及完整性检查；占用、备份失败或源变化时拒绝修改。已无目标字段时不重复清理或备份，历史备份保持原样；不在ReceptionService._recover中无备份强删。

## 0.3.1建议、翻译与重试

会话补充和最新成功的主动建议按当前卖家及会话隔离；补充CAS保存，默认用于自动接待、主动建议及润色，不写客户事实或通用政策。每客户只保留最新正文，覆盖或清空移除旧值，保留revision/CAS/hash；启动时定向压缩补充专用revisions/mutation正文副本，不删除发送账本、回执和普通业务历史。修改使依赖旧版本的未提交结果失效。主动生成可在暂停、人工接管、卖家最后发言或无事项时运行，身份和AI能力仍须正常。生成不改正文或接管，采用不经确认完整覆盖会话编辑框并接管；固定发送快照与继续编辑的正文独立。

正式需求以AI中文value及evidence_ids保存，原文另存为证据；不写display_value，不把旧值或译文无条件转为ai-v1需求，也不单独翻译需求。聊天第三方译文使用卖家库内translation_v2等JSON实体持久保存，按商家、会话、原文/前文hash、端点、模型和提示词隔离，重启可读，无Key也能读已有缓存。控制库独立meta项保留本商家的启用、enabled_data_root绑定、服务镜像和用量。0.3.6起，服务地址、模型和Key的权威配置经Windows CurrentUser DPAPI整段加密，保存到真实KnownFolder LocalApplicationData下的AlibabaReceptionWorkbenchShared/translation/live固定引用文件，不受Accio改写LOCALAPPDATA影响，不进入业务备份。旧商家state/translation-credentials密钥仅在原数据根校验通过时导入一次；已有或已清空的共享配置不会被旧配置覆盖。恢复/迁移到新根后须重新确认本商家启用，Demo使用独立demo共享目录。HTTP队列不依赖Accio AI检查、不抢占原生任务，关闭前收尾，不写事实或发送队列。本版不自动按保留期清理，显式清聊天缓存不删除消息、需求和发送证据。

自动发送总使用量不限；每个商家、会话、来源消息、阶段的失败链最多三次自动尝试（首次加两次，协助阶段还区分结果版本）。仅明确暂时性且未提交时等待5秒、15秒重试；确定性或未分类拒绝停止本条，新job、草稿或重启不重置计数。可能已提交及unknown只核查原操作。相关操作和任务证据随业务库与原生账本保全，不能通过删账本或恢复旧备份重置。

## 普通人工聊天

0.2.0起，客户页始终保留独立人工输入与发送，不要求开启单独人工模式，不依赖AI检查、采购条件、商业资料出处或“最后一条必须是买家”。历史兼容API中的 `manual_only` 不应重新成为普通人工聊天的页面前置条件。

人工正文按会话保存，使用 `client_request_id` 防重，提交确切正文版本。首次人工编辑只暂停本会话自动处理，其他客户不受影响；恢复该客户自动接待需要明确操作。人工发送保留身份/客户归属、平台正文格式、版本、退出撤权、请求幂等和整会话unknown保护，不套自动回复的资料或采购检查，不消耗自动额度。已发送人工消息进入实际历史及后续AI上下文。详情见 [人工接待使用](人工接待使用.md)。

公司资料缓存仅保存公司名、seller_id和更新时间；`refresh_company_profile`是独立慢任务，快照读取不联网。右栏宽度和需求比例按商家保存。

## 进程通信与关闭

Electron负责窗口、受限IPC、文件选择及系统确认。renderer没有Node、SQLite、任意shell或令牌访问接口。Python作为一个自有子进程，通过UTF-8 JSON-lines读写业务请求和事件，不开放本地HTTP端口。

外部业务操作由单一worker串行执行，消息监测独立运行，本地查询、保存和暂停独立处理。暂停请求不被尚未返回的开启请求去重；确认中的旧开启请求也会被后来的暂停作废。

正常退出先保护未保存编辑，然后撤销新发送权限并等候外部调用结果落库。强制退出后的未决操作保留unknown，后续核查原操作。后台意外退出会禁发并保留窗口中的编辑；当前尚无完整的同窗口后台重启与编辑恢复流程，不能把“正文暂时留在窗口”描述为跨重启恢复已经验收。
